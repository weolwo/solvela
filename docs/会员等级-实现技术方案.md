# 会员等级 —— 实现技术方案

> 选型已定稿，这份是照着写代码的那一份。
> 模型是**考核周期制（B）**：升级即时、降级期末按成长值纯映射、保级期成长值翻倍。

---

## 1. 定稿的规则

| 项 | 决定 |
|---|---|
| 升降模型 | 考核周期制。周期内累计成长值，**升级即时、降级期末** |
| 考核周期 | **入会日起 12 个月**（每人自己的会员年度日）—— 避免年底全平台同时结算 |
| 降级 | **按成长值纯映射**：`等级 = f(周期内成长值)`。不做「只降一级」这类修饰 |
| 保级缓冲 | 有。缓冲期内**等级不变**，UI 显式标「保级中，还剩 N 天」 |
| 缓冲期加速 | **2 倍，不设上限**。只作用于成长值，<b>不影响积分</b> |
| 加速所得归属 | **只计入上一周期**（用于保级判定）。保住了，新周期仍从 0 开始 |
| 成长值来源 | 今天只接一个：**积分入账**。退回**不算**（见 §4.2） |
| 权益 | 第一版靠「任务人群 / 脚本按等级」实现，不建权益中心（见 §7） |

### 1.1 🔴 「不设上限 + 只归上一周期」是一对，不能只取一半

不设上限是给用户的：一笔大额消费就能从 V1 冲回 V4，够得着才有人去够。

只归上一周期是堵套利的：否则用户会**故意让自己掉到边缘**吃双倍，
再带着翻倍的成长值进新周期。拆开任何一半，另一半都会变成漏洞。

### 1.2 🔴 缓冲期是纯映射唯一的例外，必须在 UI 上说出来

缓冲期内成长值已经掉到 V1、等级还挂在 V3 —— 这一刻 `等级 = f(成长值)` 不成立。

这是**刻意的例外**，代价是必须让用户看见：等级页要显示「保级中，还差 X 成长值，剩 N 天」。
不显示的话，用户看到的就是一个说不清的等级 —— 而"规则透明"正是选纯映射的理由。

## 2. 成长值为什么是独立概念，不是积分

| | 积分（`SCORE`） | 成长值 |
|---|---|---|
| 可花费 | 是 | **否** |
| 财务性质 | 负债 | 不是 |
| 花掉之后 | 余额减少 | **不减少**（定级看周期内累计获得） |
| 归属域 | 资产域（ledger） | **会员域（member）** |

**今天它 1:1 来自积分入账**，看起来像是多此一举。但它必须是独立的一个数，
因为**保级期 2 倍**那一刻它们就分家了 —— 用户赚了 100 积分、成长值涨 200。

> 如果当初选了「等级 = 积分收入」（支付宝式），保级加速**根本做不了**：
> 那样必须真的多发 100 积分，而积分是负债。
> 这是「成长值」这层抽象第一次、也是必然会用上的地方。

### 2.1 一个累加器，多来源

```
今天：  ledger 积分入账 ──▶ 成长值 +N        （一个生产者）
将来：  ledger 积分入账 ──┐
        绑手机 / 实名    ──┼──▶ 成长值 +N     （加生产者，累加器不变）
        开通付费会员      ──┘
```

🔴 **今天不建成长值规则表。** 一个来源不需要规则表 —— 系数写在配置里即可。
建了就是两套配置要对齐，而那正是「成长值让业务复杂很多」的主要成本。

流水表记 `source` / `biz_type`，把「多来源」的位置留出来 —— 那两列的成本是零。

## 3. 🔴 会员域读不到钱包，所以走事件

```
solvela-member(14) ... solvela-ledger(18)
       ▲                      ▲
       └─ 成长值与等级在这儿    └─ 积分流水在这儿
```

`<modules>` 顺序决定：**member 物理上读不到 ledger**（写反了 Maven 报循环依赖）。

> ⚠️ 反过来 **ledger 是依赖 member 的**（它的 pom 里有），所以「在钱包入账时直接调
> `memberGrowthService.add(...)`」是编译得过的。**不要这么做**：
> 那会让资产域知道「等级」这个概念存在。资产域该说的只有「积分入账了，来源是 X」。
>
> 而且第二个生产者（绑手机、实名）住在 member 自己域里 —— 走事件两边形状一致。

复用 2026-09-17 那套打点管道，**零新建**：

```
ledger 积分入账 ──▶ BizActionEvent("SCORE_EARNED", memberId, bizRefId, amount, {bizType})
                        └──▶ member 的 GrowthEventListener → 成长值入账 → 判级
```

## 4. 接入点

### 4.1 只有一个发布处

`MemberWalletService` 里写 `INCOME` 流水的有两处：

| 方法 | 谁在调 | 语义 |
|---|---|---|
| `executeWalletCharge(proposal, ...)` | `WalletChargeHandler` | 发奖入账 |
| `executeWalletRefund(memberId, ...)` | `AssetGrantApiService.grantWallet` | **商城/发放入账** |
| 同上 | `AssetDebitApiService.refund` | **真正的退回** |

🔴 **收在一个 `ScoreIncomeActionPublisher` 里**，两个 INCOME 落点各调一次，
不要在每个落点各写一遍 —— 那是 `ORDER_PAID` 漏掉纯积分单的同一个形状
（见 `MallOrderActionPublisher` 的类注释）。

### 4.2 🔴 「退回不算」只能按 `bizType` 判，不能按方法判

这是本方案里最容易写错的一条。

`executeWalletRefund` 的名字叫「退回」，但它**实际是通用入账** ——
它自己的 javadoc 写着「复用 executeWalletRefund（通用退还/入账）……两者的动作是同一个」。
商城发积分走的就是它。

所以：

```
按方法跳过 executeWalletRefund  →  连商城发的积分也不算成长值  ❌
按 bizType 白名单判             →  对                        ✅
```

库里现有的取值（2026-09-18 实测）：

| asset_type | 流向 | biz_type | 行数 | 算成长值 |
|---|---|---|---|---|
| SCORE | 收入 | `PROPOSAL_REWARD` | 4413 | ✅ |
| BALANCE | 收入 | `PROPOSAL_REWARD` | 2 | ❌ 只算 SCORE |
| SCORE | 支出 | `MALL_EXCHANGE` | 2 | —— 支出不看 |

退回会以 `MALL_EXCHANGE` 之类的 bizType 走收入流向，白名单里没有它就不算。

### 4.3 🔴 白名单在 **member 侧**，不在 ledger 侧

ledger **广播全部** SCORE 入账，member 决定哪些算。

这样资产域完全不知道「成长值」「等级」的存在 —— 加一种算数的来源是改会员域的配置，
不用动资产域一行。

## 5. 表设计（6 表模型，2026-09-20 定稿）

```sql
t_member_grade            等级配置
  grade_code / grade_name / threshold / icon_file_id / status

t_grade_privilege         等级权益【纯展示，不驱动逻辑】，见 §7
  grade_code / privilege_code / privilege_name / description
  icon_file_id / action_url / sort / status
  UNIQUE (grade_code, privilege_code)

t_member_growth           会员成长账户主表 —— 只管【当前周期】
  member_id(PK)
  current_grade / grade_since
  period_start / period_end
  current_period_value        -- 本周期累计【冗余，见 §5.2】
  total_value                 -- 终身累计，只展示
  protect_grade / protect_until

t_member_period_summary   期末结算快照 —— 历史周期的唯一凭证，见 §5.3
  member_id / period_no / period_start / period_end
  final_growth_value / grade_before / settled_grade / settle_result
  next_grade / next_threshold / protect_grade / settled_at
  UNIQUE (member_id, period_no)

t_member_growth_log       成长值流水
  member_id / delta / base_value / multiplier / after_period_value
  source / biz_type / biz_id / period_tag / remark
  UNIQUE (source, biz_id)     -- 🔴 见 §5.1

t_member_grade_log        等级变更留痕
  member_id / old_grade / new_grade / change_type / period_value / reason / operator
```

### 5.0 命名：会员域统一用 grade，不用 level

`old_grade / new_grade` 比 `from_level / to_level` 一眼就懂，而 5 表模型本来
就要动表结构，一起改比将来分两次便宜。就这两条理由。

🔴 **不是因为 `level` 是保留字** —— MySQL 8.4 的
`INFORMATION_SCHEMA.KEYWORDS` 里 `LEVEL` 的 `RESERVED = 0`，它不是保留字
（`RANK` 才是；Oracle 里 `LEVEL` 是 `CONNECT BY` 的伪列，那个直觉是从那儿来的）。

⚠️ **范围只限会员域**。仓库里还有 7 处 `*_level`（`prize_level` / `attest_level` /
`stage_level` / `review_level` / `position_level` …），它们表达的是「奖品档位」
「设备可信等级」这些**别的概念**，不在范围内，也不该被顺手改掉。

### 5.1 🔴 `UNIQUE (source, biz_id)` 不能省

打点是**至少一次**的（对账 job 会重推）。没有这个唯一键，同一笔积分入账
会被加两次成长值。形状照抄 `t_task_record_flow.uk_t_tsk_flw_evt`。

**⚠️ 也正因为它，这张表不能按时间分区。** 实测：

```
ALTER TABLE t_member_growth_log PARTITION BY RANGE (TO_DAYS(create_time)) …
→ A PRIMARY KEY must include all columns in the table's partitioning function
```

主键改成 `(id, create_time)` 好办（`t_member_login_log` 就是这么干的），
但 MySQL 要求**每个唯一键**都包含分区列 —— `(source, biz_id)` 变成
`(source, biz_id, create_time)` 之后，同一笔在不同时刻重推**就不再撞键了**，
幂等保证静默蒸发。那正是 `c8478052 发券防重：补上那个从来没生效过的唯一键` 的形状。

**所以这张表走归档，不走分区**：冷数据按月搬到 `t_member_growth_log_archive`，
活表保持唯一键完整。

### 5.2 🔴 `current_period_value` 是冗余，所以必须有对账（✅ 2026-09-21 已落地）

它能从流水求和算出来，但判级是热路径，每次扫流水不现实。

**冗余就要对账**：`memberGrowthReconcile`（每半小时 :50）比对它与
`SUM(log.delta WHERE period_tag=本期)`，对不上打 ERROR 并带样本。
冗余而不对账，迟早出现「明细和总数对不上」，而那时已经没人知道哪个是对的。

**🔴 默认只报不改。** 谁对是确定的（流水 append-only 且带幂等唯一键
`(source, biz_id)`，主表是 `SET x = x + ?` 累出来的派生值），但自动修会让
引起漂移的那个 bug **每半小时被悄悄抹平一次，没有人会知道它存在**。
`autoFix=true` 是一次显式的人为动作，不是常开项 ——
与 `prizeDispatchReconcile` 对「已受理无终态」的处理是同一条。

**🔴 校正必须带并发判据**：`WHERE current_period_value = 读到的值`。
从读到写之间用户完全可能又入账了一笔 —— 不带这个条件会把那笔覆盖掉，
**对账任务自己制造出一笔差异，而且是往少了写，用户凭空掉成长值**。比不对账更糟。

**🔴 游标按「扫到的最大 member_id」推，不按异常行推。** 一批全对也得往前走，
否则扫描原地打转，后面的人永远轮不到。

**⚠️ 默认只扫 24 小时内有变动的人。** 没动过的人不可能新产生漂移，全量扫在
会员量大了之后是纯浪费；代价是**历史遗留的漂移它看不见**。首次上线、
或这个 job 停过之后，手工跑一次 `lookbackHours=0`。

**顺带查孤儿流水**（有流水、没有主表行）。它比「值对不上」严重得多 ——
意味着有人绕过 `MemberGrowthService.accrue` 直接写流水，对账连比都没法比。

⚠️ 对账的**锚点**是 §5.3 那张快照表 —— 见下。

### 5.3 🔴 为什么要 `t_member_period_summary`

它补的**不是**「历史查不到」（流水有 `period_tag`，求和能算出来），是两个更具体的洞：

| 洞 | 后果 |
|---|---|
| **等级没变的周期，全库一行记录都没有** | `MemberGradeChangeService.change()` 在 `old == new` 且非 KEEP 时直接返回。「平级过完一个周期」的人在留痕表里是空的 —— 而「我上周期攒了多少、差多少」正是客诉最常问的那句 |
| **对账没有锚点** | §5.2 要比对的 `current_period_value` **一直在动**。有了快照，对账变成「比对一个封存的数」，那才是能写出来的对账 |

⚠️ `period_no` 必须与 `t_member_growth_log.period_tag` **字节一致**（都是
`period_start` 的 `yyyyMMdd`）。对账靠它 JOIN 两张表；一边 `yyyyMM`、一边
`yyyyMMdd` 的话，对账会**安静地什么都对不上**。

⚠️ `next_threshold` 存的是**当时的快照**。运营改过门槛之后，拿今天的配置回算
会算出另一个答案 —— 而客诉问的是「我**当时**差多少」。

### 5.4 🔴 没有乐观锁，也不要加 Redis 缓冲

`t_member_growth` 上原本有一列 `version`，**从未生效**，已删。成长值累加走的是：

```sql
UPDATE t_member_growth SET current_period_value = current_period_value + ?
 WHERE member_id = ?
```

一条原子自增。没有版本判断、没有读-改-写、没有重试循环，
全工程也没有任何代码读写过 `version`。留着只会让下一个人以为这里有乐观锁保护，
然后基于那个错误前提去设计并发方案。

**所以不存在「大促并发导致乐观锁大量重试」这个问题**，也就不需要在前面加一层
Redis 缓冲。真加了会引入两个真问题：

- 破坏 §5.2 那条不变量（流水求和 == 总数），对账任务不知道该信哪个；
- Redis 丢一次数据 = 成长值凭空消失，而且**没有任何流水能证明它存在过**。

### 5.5 期末结算：分批 job，不是 MQ

「千人千面」周期下每天都有人到期，所以**绝不能**一个大事务
`SELECT * FROM t_member_growth WHERE period_end < NOW()` 然后循环更新。

但这个仓库已经有标准件了 —— `MallOrderExpireJob`：分页捞（`BATCH_SIZE=100`）、
单条独立事务、`MAX_BATCH_ROUND` 上限、整批全失败就退出防活锁。照抄即可。

⚠️ 现在 4500 会员，按入会日均摊每天到期十几个。上 MQ 换来的是 at-least-once ——
而结算本来就必须幂等（`uk(member_id, period_no)` 就够），等于为了一个已经解决的
问题引入一整套投递语义。**等到期量真的压不住再换 MQ，那时 job 的分批逻辑原样搬过去就是消费者。**


## 6. 判级

```java
// 纯函数，没有副作用，好测
int gradeOf(long periodValue, List<MemberGrade> grades)
```

- **升级即时**：成长值入账后当场算一次，跨几级升几级
- **降级**：只在期末结算 job 里发生，**不在入账时发生**
  （入账只会让成长值变大，不可能触发降级 —— 除非风控扣回，那走人工调整那条路）
- **缓冲期**：`protect_until` 未到期时，等级取 `protect_grade`，不取 `f(currentPeriodValue)`

### 6.1 等级的「不知道」态

沿用 `isNewMember` 那套三态：查不到会员时返回 **`null` 而不是 V0**。

配了等级人群的任务拿到 `null` 会**丢弃事件并写明原因**，而不是判成「人群不匹配」。
一个查不到的会员本来就是异常，伪装成 V0 会让异常变成一句看起来很正常的业务结论。

### 6.2 🔴 入账那条路**只升不降**（阶段 2 落地）

`MemberGrowthService.evaluateUpgrade` 里 `target <= current` 就直接返回。
「算出来比当前低」是真会出现的，有三种正当来源：

| 来源 | 为什么会低 |
|---|---|
| 运营调高了门槛 | 成长值没变，档位变了 |
| 人工调级 | 把人提到了他还没攒够的等级 |
| 保级缓冲期 | 等级取 `protect_grade`，本来就高于 `f(成长值)` |

三种情况下「什么都不做」都是对的。**反过来才是事故**：照算出来的值改，
运营调高一次门槛就会在下一次入账时把所有存量用户**静默降级** ——
没有人点过「降级」，也不会有任何报错。降级只属于期末结算那一条路。

### 6.3 判级读的是库里的值，不是快照加 delta

`current_period_value` 是 `addValue` 原子自增上去的，正因为并发下「快照 + delta」是错的才有它。
判级时再用那个错值，等于把刚防住的丢更新请回来 —— 两笔并发入账各自以为只加到 100，
实际已经 200，于是**该升的级没升**，且不报错。所以 `evaluateUpgrade` 重新点查一次。

**并发撞车时本次跳过，不重试**：后到的那条因为「等级已经不是我读到的那个」而更新 0 行，
这一次少升一级。不加重试是因为它**会自愈** —— 判级不以「这次跨没跨门槛」为条件，
下一笔成长值进来时照样重算。为此在热路径上加 `FOR UPDATE` 会让同一个会员的所有入账排队，
换来的只是「升级早一笔」。

### 6.4 等级变更只有一个写入口

`MemberGradeChangeService.change(...)` —— 条件更新 + 写留痕 + 带成长值快照，三件事绑在一起。

等级会从四个地方变（入账升级、期末降级、缓冲期保级、人工调整），散在四处的结果是可以预见的：
**总有一处会忘记留痕**。而忘记留痕不会报错、不影响任何功能，只会在半年后某个用户
问「我为什么掉级了」的时候，变成一句「查不到」。

- 条件是 `WHERE member_id = ? AND level = ?(from)`，影响 0 行就当作「已被并发改过」，跳过；
- 传播级别是 `REQUIRED`：用 `REQUIRES_NEW` 会出现「成长值回滚了但等级留下来」；
- 留痕里的 `periodValue` 是**调用方传进来的快照**，不是这里查的 ——
  这里查到的是变更**之后**的值，而客诉要问的恰恰是「变更那一刻他有多少」。

### 6.5 人工调级：它**不改成长值**

所以调完之后等级和 `f(成长值)` 会对不上。这不是 bug，是这个功能的定义 ——
人工调级是一次**补偿**（活动出了问题、客诉安抚），不是「送他这些成长值」。

- **往上调**：期末结算按他真实的成长值重判，也就是说人工升级默认**只在本周期有效**；
- **往下调**：入账只升不降，他会停在这里，直到自己攒够再升上去。

想让它永久生效得配套调成长值 —— 那是另一个功能（要有额度和审批），这一版不做。
管理端的弹窗上把这三条原样写出来了，否则运营会把它当「发权益」用。

⚠️ 权限点 `memberGrade:adjust` 与 `memberGrade:config` **分开**：
「能改等级规则」和「能改某一个人的等级」是两种完全不同的授权，
后者是能被拿来给自己人送权益的那一种。

### 6.6 等级人群怎么表达（阶段 3 落地）

`t_task_config.target_audience` 存 **`GRADE_GTE_2`** 这种带值的取值，**不加列**。

等级是配置（运营随时加一档），穷举成枚举值不可能；把门槛编进取值里，加一档就是多一个
可选项，存量行零回填。判据是**数字比较**——等级 2 被停用之后 `GRADE_GTE_2` 仍然表示
「等级不低于 2」，停用一档不该顺带让一批任务静默失效。

🔴 **写坏的等级人群要丢弃，不能沿用「取值非法按不过滤处理」**。
那条放行规则对未知取值是对的（多半是历史遗留，为它卡住用户不划算），但
`GRADE_GTE_` 开头意味着运营**明确是在配等级专享**，只是数字写错了——
这时放行的后果是普通会员领走白金专享奖，方向正好反了。

**等级在哪一步取**：`TaskEventService.handle` 里，且只在「这条事件命中了等级人群的任务」时取一次。

| 放在哪 | 代价 |
|---|---|
| `normalize()` 无条件取 | 每一次埋点都多一次点查，而绝大多数任务不看等级 |
| `checkAudience()` 里现取 | 一个任务配置一次：`DAILY_SIGN` 扇出到五个任务就是五次 |
| **`handle()` 按需取** ✅ | 一条事件最多一次，不看等级的活动零代价 |

取不到就留 `null`，配了等级人群的那个任务丢弃并写明原因，**其它任务照常推进** ——
影响面收敛在真正依赖它的那几个任务上。

### 6.7 🔴 「专享」必须在 C 端也是真的

人群过滤只作用在**事件推进**上。不额外处理的话，等级不够的人照样看得见这条任务、
点进去做完动作、进度纹丝不动，而页面上没有任何解释（丢弃原因只写在
`t_task_record_flow` 里，那是给运营看的）。

所以 `TaskCenterProviderImpl` 把**不达标的等级任务从列表里隐去**，与它原有的
「没开始和已结束的任务不展示」是同一条理由：显示出来只会让他点一个做不了的东西。

⚠️ 只能对等级人群这么做。`NEW_MEMBER` / `OLD_MEMBER` 的判据（`isNewMember`）由**上报方**
给，展示这条路上没有那个信息，猜一个出来会和运行态的判定对不上——那比不过滤更糟。

💡 更强的做法是**显示成「银卡可参与」的锁定态**：看得见够不着才有升级的理由，
那才是这套机制要的抓手。但它要 C 端加一种任务卡片形态，与等级页一起做更合适，见阶段 4。

### 6.8 期末结算的状态机（阶段 4 落地）

```
周期到点，不在缓冲期
  ├─ 攒够了   → KEEP / UPGRADE，写快照、清零、推进周期
  └─ 没攒够   → PROTECT_START：给缓冲期，等级先留着，成长值 ×2
                🔴 此时【不】写快照、【不】清零、【不】推进周期

缓冲期满
  ├─ 补够了   → PROTECT_KEPT，等级保住，写快照结清
  └─ 还是不够 → PROTECT_FAILED，按成长值降级，写快照结清
```

**🔴 不达标为什么先给缓冲期而不是直接降**：直接降的话，用户是在「已经掉了」
之后才知道；给缓冲期 + 双倍成长值，他是在「还够得着」的时候知道的。
后者才可能把人拉回来 —— 而这正是做等级体系要换的东西。

**🔴 PROTECT_START 不写快照**：这个周期还没有结局。写了的话缓冲期满还要再写一行，
而 `uk(member_id, period_no)` 只允许一行；真写成两行就得给 `period_no` 加后缀，
那等于承认「一个周期两个结局」。

**留痕与快照各管一件事**，不要互相灌水：

| | 写什么 | 平级的周期 |
|---|---|---|
| `t_member_grade_log` | 等级<b>为什么变了</b> | 不写 |
| `t_member_period_summary` | 每个周期的<b>结局</b> | 写 |

唯一的例外是 `PROTECT_KEPT`：等级没变也要写留痕，因为「你在缓冲期内补够了，
白金保住了」是用户该看见的好消息 —— 不留痕的话他只知道自己没掉，
不知道系统给过他一次机会，那段紧张感就白费了。

**降级按纯映射**，不做「只降一级」：钻石一年只攒了 900 就直接回 0 级。
规则是纯的，客服只有一句话要解释 —— 不用讲「你本来该掉四级但我们只降一级」。

### 6.9 C 端等级页：`current` 与 `reached` 必须分开

缓冲期内用户<b>在</b>白金（`current`），但成长值<b>够不着</b>白金（`reached=false`）。
把两者合成一个高亮，「你正在保的是什么」这句话就说不出来了。

同理，页面上有<b>两个「还差多少」</b>，而且在缓冲期里指向相反的方向：

- `gapToNext` —— 离<b>上面</b>那一档还差多少（按成长值算）
- `protectGap` —— 离<b>保住脚下这一档</b>还差多少

混成一个字段的话，缓冲期的页面会写出「差 900 升银卡」，
而他真正需要知道的是「差 19900 保住白金」。

⚠️ 进度条的起点取<b>已达成的最高一档</b>，不是 `gradeCode` 那一档的门槛 ——
后者在缓冲期会算出负数区间，进度条直接满格，而旁边同时写着「还差 900」。
（2026-09-20 真跑出来过一次，靠看页面才发现，接口数据全都是对的。）

## 7. 权益：第一版不建权益中心

🔴 **没有权益的等级是空转的** —— 用户没有任何理由去保级，而"保级"正是这套机制
要换来的活跃与粘性。

但这个平台的第一版权益**不需要新域**：

| 权益 | 靠什么 | 什么时候有 |
|---|---|---|
| 高等级能做**专享任务** | 任务人群加「等级 ≥ N」 | **阶段 3 自带** |
| 高等级能参与**专享活动/奖池** | 脚本里 `member_grade()` | **阶段 3 自带** |
| 抽奖额度 / 中奖率差异 | 优惠配置差异化 | 后面 |
| 等级价、专享商品 | 商城价格模型 | 后面 |
| 生日礼、月度券 | 权益中心（新域） | 后面 |

所以 **阶段 3 不是「让等级被用起来」，它就是第一版权益**。

### 7.1 权益是一张独立的表，但它**仍然不驱动逻辑**（2026-09-20）

原先是 `t_member_grade.benefits varchar(500)`，现在拆成 `t_grade_privilege` 一行一条。

**为什么拆**：图标要 `file_id`、跳转要 url、排序要独立字段，以后还要多语言 ——
这些塞进一个 varchar 就是历史包袱本身，而那时再拆，得一边拆一边解析
已经写进去的自由文本。现在拆是最便宜的时刻（库里只有种子数据）。

**🔴 拆表不等于建了权益中心**。真正的权益靠上面那张表里的三样东西实现，一样都没变：

- 高等级专享任务 → `t_task_config.target_audience = GRADE_GTE_N`
- 专享活动 / 奖池 → 脚本里 `member_gradeAtLeast(n)`
- 等级价 / 专享商品 → 商城价格模型（还没做）

`t_grade_privilege` 回答的是**另一个问题**：用户在等级页看见自己在保什么。
没有它，用户没有任何理由去保级 —— 而保级正是这套机制要换的活跃与粘性。

⚠️ **谁都不要给它加「生效引擎」**。那一天来临时，应该是新立一个权益域，
而不是让这张展示表长出执行语义 —— 展示与执行混在一张表里之后，
改一句文案就有可能改掉一条业务规则。

## 9. 明确不做

| 不做 | 理由 |
|---|---|
| 成长值规则表 | 今天只有一个来源，系数写配置即可。见 §2.1 |
| 加速倍率分阶段（1.5x / 2x / 3x） | 目的是活跃和粘性，不是做一个可调参数的玩具 |
| 成长值可花费 | 那它就是第二种积分了 |
| 等级写成 Java 枚举 | 运营加一档要发版，而加一档是最常见的运营动作 |
| 把等级列加到 `t_member` | 等级是派生状态，跟着成长值走。放 `t_member_growth` 一次主键点查就拿到 |
| 付费会员（PLUS/88VIP） | 另一个体系，且要先有支付 |
