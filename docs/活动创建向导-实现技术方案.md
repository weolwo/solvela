## 1. 核心设计决策

### 1.1 外壳只管三步，玩法组件整体内嵌

**决策：向导外壳的步骤条最多三步「创建活动 → 配置玩法 → 完成」（BASIC 类型收缩为两步，见 §1.3）。
第二步是一个挂载点，把对应玩法组件整体渲染进去，它内部有几步是它自己的事。**

被否决的替代方案是「拍平成一条步骤条」（任务类 = 活动 + 任务 5 步 = 6 步）。视觉上更统一，
但要把 `TaskWizard` 拆成独立步骤组件、把两个工作台的 Tab 拆成步骤 —— 这是一次大重构，
而**代价远不止工作量**：三个玩法各自带着已验证过的结构锁与校验（抽奖的上线结构锁、
彩票的 `number_length`/`total_count` 冻结、概率闭环的 BigDecimal 容差），拆散重组必然要动这些代码。
交接文档里「增量修改优先，不轻易重写」是有由来的。

三步式的代价是任务类会出现「向导套向导」的观感。可接受：外壳步骤条置顶且视觉弱化，
内层任务向导有自己的步骤条，两者层级分明。

### 1.2 第一步提交即落库，不做「最后统一提交」

**必须如此，没有选择余地**：玩法配置的三个保存接口都要求活动已存在。
实测 `PrizePoolConfigService.workbenchSave():198-201` —— 活动查不到直接
`ResponseDTO.userErrorParam("活动不存在：" + activityCode)`。彩票与任务同理。

**好消息：新建活动能立刻配玩法，不用先上线。**
`workbenchSave():202` 的 `status==1` 判定**只用来决定是否启用结构锁**，不是保存的前置条件：

```java
// 1. 活动必须存在，并据其状态判定是否启用结构锁
boolean online = ACTIVITY_STATUS_ONLINE.equals(activity.getStatus());
```

所以「新建活动(status=0) → 立刻配玩法（无结构锁，随便改）→ 最后上线（结构锁生效）」
这个顺序天然成立，**后端一行不用改**。这也正是结构锁设计时想要的次序。

### 1.3 第四种类型 `BASIC`：运营只想建个普通活动

**问题**：三选一是个伪前提。运营常常只需要一个活动外壳 —— 挂一批奖品、作为预算与统计的归集维度 ——
并不需要抽奖/任务/彩票中的任何一个。强迫他随便选一个类型，会得到一个永远配不完的假活动。

**这也正是「回显什么」说不清的根源**：现在「没有玩法配置」这一个状态，同时对应着
**半途放弃**和**本来就不需要**两种完全不同的情况，向导第二步该显示什么、列表该标什么，都无从判断。

**决策：`activity_type` 增加第四个取值 `BASIC`（基础活动）。**

这不是补丁，它有独立且正当的语义 —— 实测 `t_prize_config`（资产大库）的归属键是 `activity_code`，
**且与玩法完全无关**（task.sql:97-101）。所以「不挂玩法的活动」不是空壳，
它是一个可以挂奖品、可被预算与统计归集的正经容器。

| | 向导第二步 | 配置完备度 | 三个工作台的活动下拉 |
|---|---|---|---|
| DRAW / TASK / LOTTERY | 挂载对应玩法组件 | 跑该玩法的上线前校验（见 §1.5） | 按类型精确过滤，各自可见 |
| **BASIC** | **无此步，步骤条收缩为两步** | **恒为「已配置」** | **不出现**（过滤条件里没有 BASIC，天然排除） |

**命名取 `BASIC` 而非 `NONE`**：这个值要以 Tag 形式展示给运营，「基础活动」是一个正经类型，
「无玩法」读起来像缺失或异常。项目里 `cost_asset_type` 的 `NONE` 表示「不扣」，语义是"没有"，
此处不同 —— 这里是"另一种"。

### 1.4 「已配玩法则冻结类型」—— 比一刀切更准确

原本的规则是「类型创建后一律冻结」。加入 BASIC 后这条要改，因为它会挡掉一个合理需求：
**运营先建了个基础活动，后来想加抽奖。**

回到冻结的**真实理由**：改类型会让已配的下游配置变成查不到也删不掉的孤儿数据（§2 缺陷一）。
那么 —— **BASIC 活动定义上没有玩法下游，从 BASIC 升级到任一玩法不产生任何孤儿数据。**
而且它已挂的 `t_prize_config` 奖品，升级成 DRAW 后正好成为抽奖的资产大库，
不但不冲突，反而顺理成章。

所以真正的规则是：

```
BASIC → DRAW / TASK / LOTTERY     ✅ 放行（升级，无下游可孤立）
DRAW / TASK / LOTTERY → 任何类型   ❌ 拒绝（含互转与降级回 BASIC，均会遗弃已配玩法）
```

**判定依据是「下游玩法表有无记录」，不是类型本身** ——
⚠️ 注意这里与 §1.5 的完备度判据**刻意不同**：升级问的是「有没有东西会被孤立」，
所以看**有无记录**就够；完备度问的是「配完了没有」，必须跑**上线前校验**。
两个问题不同，判据自然不同，别为了统一而合并。与 §3.2 的完备度统计、
§2 缺陷二的删除守卫**共用同一份下游统计逻辑，实现时合成一个方法**。

⚠️ 这条例外**不削弱** §2 缺陷一的修法：`UpdateForm` 里仍然**不定义** `activityType`
（普通编辑绝不碰类型，编译期挡死），升级走**单独的窄接口** `POST /activityConfig/upgradeType`，
服务端二次校验「当前必须是 BASIC」+「下游玩法表必须为空」。
**给一个专用出口，好过把大门敞开。**

### 1.5 由此产生的「空壳活动」（仅限玩法类）

对 DRAW/TASK/LOTTERY，第一步落库后运营中途关掉浏览器，库里会留下一个建好没配玩法的活动。
**这不是缺陷，是一体化向导的必然结果**，藏不掉，只能设计它：

1. 活动配置页给这类活动 **「未配置玩法」** 标记 + 「继续配置」入口，
   点进去直接回到向导第二步 —— 让中断可恢复，而不是让运营重建一个。
2. **判定标准是「能不能上线」，不是「有没有记录」** —— 见下方。
3. **列表页一次查询批量算，不要每行发一个请求。** 聚合接口见 §3.2。

有了 BASIC 之后，这个标记的语义才是干净的：**它只表示「该配而没配」，
不再混入「本来就不用配」** —— 这正是本节要解决的回显歧义。

#### ⚠️ 判据必须复用各玩法既有的「上线前校验」，不要自己数记录

初版方案写的是「查对应下游表有无记录」。**这个判据是错的**，因为「有记录」不等于「配完了」。

实证：`LotteryConfigService.online():382-385` 有一段既有校验 ——

> 上线前必须已配置奖级规则 —— 否则号码发出去了、开奖时却无奖可发，
> 而那时号码已经在用户手里，配置补救的代价远高于此刻拦一下。

也就是说 **`t_lottery_config` 完全可以在没有任何奖级规则的情况下保存成功**。
按「有无记录」判，它会被标成「已配置」，但它根本上不了线 —— 一个半残废状态被显示成完成态，
比不显示更糟。

**正解：完备度 = 各玩法既有的上线前校验是否通过。**
那套逻辑已经写好、已经验收过，而且它本来就是「配完了没有」的权威定义。

**另造一套统计必然漂移** —— 本项目已经吃过这个亏：`TicketMatcher` 与结算 SQL 守卫
是同一套规则的两种实现，`SettleSemanticsTest` 就是专门为防它们漂移而写的
（交接文档 §4「两者是同一套规则的两种实现，改一边必须同步另一边」）。
再造第三套「配没配完」的定义，只会重演一次。

落地方式：各玩法 Service 把上线前校验抽成一个可复用方法
（如 `LotteryConfigService.checkOnlineReady(code)` 返回 `null` 表示通过），
`online()` 与完备度统计**共用同一个方法**。

> ✅ 顺带澄清一个不成立的担心：**TASK 不存在这种灰度**。
> `TaskConfigService.wizardSubmit():63` 是单个 `@Transactional`，
> 主表 `insert`(:95) 与子表 `insertBatch`(:109) 在同一事务里 —— 要么都有要么都没有；
> 且 `TaskWizard.vue` 的中间态是 **localStorage 本地草稿**，第 2 步根本不写库。
> 真正的灰度在 LOTTERY，不在 TASK。

## 2. 🔴 六个必须先修的既有缺陷

这些缺陷今天不致命，是因为**没有任何入口在批量创建活动**。向导一上线全部会被触发。

### 🔴 一：`activityType` 可被改

`ActivityConfigUpdateForm:29` 开放了 `activityType`，`ActivityConfigService.update()` 直接
`SmartBeanUtil.copy` + `updateById`，**无任何守卫**。

后果不是「数据不好看」，是**整块配置变孤儿**：DRAW 活动下已配的奖池、物资、坑位映射
（`t_prize_pool_config` / `t_prize_pool_item` / `t_pool_prize_mapping` 全部以 `activity_code` 关联）
在类型改成 LOTTERY 后仍在库里，但 `LotteryWorkbench` 查不到、`DrawWorkbench` 也不再列出该活动
（它按 `activityType=DRAW` 过滤下拉）—— 数据既删不掉也看不见。

**修法**：从 `ActivityConfigUpdateForm` **删除该字段**，让越权意图在编译期就无处安放。
（同 §4 彩票约束 3：「`LotteryIssueUpdateForm` 里刻意不定义该字段」。同一手法，同一理由。）

唯一合法的类型变更是 **BASIC → 玩法类的升级**，走单独的窄接口
`POST /activityConfig/upgradeType`（见 §1.4 与 §3.2），服务端校验
「当前必须是 BASIC」+「下游玩法表为空」两条后才放行。**给专用出口，不要敞开大门。**

### 🔴 二：删除活动无引用完整性检查

`delete()` / `batchDelete()` 直接 `deleteById`。删掉一个已配好玩法的活动，下游全成孤儿 ——
库里 `t_task_config` 那三条 `activity_code='NEWBIE_CAMP'` 的孤儿数据就是先例，至今没人敢动。

**修法分两层：先判「能不能删」，再判「有没有下游」。**

##### 第一层：上线过的活动永不可删

活动本来就不需要「删除」这个动作 —— 它已经有 `status`(0未开始/1上线/2下线)。
运营口中的「删除」，绝大多数场景是「建错了/不要了」。所以：

```
从未上线过（status=0 且下游为空）  →  允许物理删除（干净，没有痕迹需要保留）
上线过（status 曾为 1）            →  只能下线，永不可删
```

**为什么上线过就永不可删**：`t_prize_log.activity_code` 是 `NOT NULL`（task.sql:221），
且建了 `idx_prize_log_(member_name, activity_code)` —— **发奖流水就是按 activity_code 追溯的**。
删掉活动等于把资损追溯链路断在源头。

> **为什么不用逻辑删除**（评估过，不采用）：
> ① `t_activity_config` 现在**没有 `deleted_flag`**，加它是 DDL 变更；
> ② 加了会与 `uk_act_code` 唯一索引打架 —— 逻辑删除的记录仍占着编码，
>    运营想复用该编码建新活动会被判重，而他在界面上根本看不到那条记录，
>    只会得到一个无法解释的「编码已存在」；
> ③ 它替代不了守卫 —— 发奖链路按 `activity_code` 查、不查 `deleted_flag`，
>    逻辑删除一个正在发奖的活动，表现是「后台删了但用户还在中奖」。
>
> 用 `status` 状态机表达生命周期，比再引入一个删除维度更准确，
> **且不动 DDL、不与唯一索引冲突**。

##### 第二层：下游引用统计（🔴 必须包含资产大库）

有引用则拒绝并给人话提示：

```
该活动下已配置 3 个奖池 / 12 项物资，请先在「抽奖配置工作台」清理后再删除。
```

**需要统计的表**：

| 活动类型 | 需查的表 |
|---|---|
| DRAW | `t_prize_pool_config` / `t_prize_pool_item` |
| TASK | `t_task_config` |
| LOTTERY | `t_lottery_config` / `t_lottery_issue` |
| **全类型（含 BASIC）** | 🔴 **`t_prize_config`（资产大库）** |

🔴 **最后一行绝不能漏。** `t_prize_config.activity_code` 是 `NOT NULL`（task.sql:101），
而 §1.3 已确认**资产大库与玩法无关** —— 一个挂了 10 个真实奖品的 BASIC 活动，
若只查玩法表就会被判「无下游引用」而顺滑删除，10 个奖品当场失去宿主变成悬空孤儿，
财务与发奖链路直接断裂。

**BASIC 活动尤其危险**：它按定义没有玩法下游，玩法表永远查不到东西，
**资产大库是它唯一的引用来源**。漏了这张表，等于对 BASIC 完全没有守卫。

**不做级联删除。** 下游挂着发奖流水与资产账务，级联删除等于抹掉资损追溯链路。

### 🔴 三：权限注解是复制粘贴的错值

`ActivityConfigController:52` 与 `:59` 两处 `@SaCheckPermission(":addProposal")` ——
`addProposal` 是提案域的动作名，被整段复制到了活动域；且冒号前为空，
实际权限串是 `:addProposal`，与任何菜单功能点都对不上。`queryPage`/`optionList` 的 `":query"` 同样缺前缀。

**修法**：统一为 `activityConfig:query` / `:add` / `:update` / `:delete`，并建对应菜单功能点（§5 P3）。

> 隐蔽性在于：开发期管理员账号往往有全量权限，**本地测不出来**，只在给运营配了受限角色后才暴露。

### 🔴 四：`activityType` 在前端是自由文本框

`activity-config-form.vue:31` 是 `<a-input v-model:value="form.activityType" />`。
运营可以打 `draw`、`Draw`、`抽奖` 任意字符串，而三个工作台的下拉是
`optionList?activityType=DRAW` **精确匹配** —— 打错一个字母，活动就在所有工作台里消失。

这与交接文档记录的 `prize-config-form.vue`「资产类型从自由文本框改成枚举下拉」是**同一模式的第二次复发**。

**修法**：填充 `activity-config-const.js`（现为空壳 `export default {}`），表单改枚举下拉，
且服务端 `add` 用 `@CheckEnum` 重校验（铁律 2：前端校验只是防呆）。

⚠️ 新建 `ActivityTypeEnum implements BaseEnum` 时**字段必须叫 `value` 且不要手写 `getValue()`** ——
铁律 12，`TicketStatusEnum` 曾因此让整个筛选恒返回 400。

### 🔴 五：三个玩法组件无法被内嵌

实测 `DrawWorkbench.vue` / `LotteryWorkbench.vue` 全文搜 `useRoute` / `route.query` —— **零命中**。
三者都是「独立整页」形态，各自带着：

- 顶部**自己的活动下拉**（内嵌时活动已定，再出现一个下拉就是双控冲突）
- 自己的 `onBeforeRouteLeave` **离开拦截**（与外壳的拦截叠加会弹两次）
- `TaskWizard` 还有**自己的成功页与三出口**（内嵌时应交给外壳的完成页）

**修法**：三者统一加两个 prop + 一个事件：

```js
props: {
  activityCode: { type: String, default: '' },   // 传入即锁定活动，不再自选
  embedded:     { type: Boolean, default: false } // 内嵌模式
}
emits: ['saved']   // 配置完成时通知外壳推进到完成页
```

`embedded === true` 时：隐藏活动下拉、关闭自身路由守卫、抑制自身成功页。
`embedded === false` 时行为**与现在完全一致**，独立入口不受影响。

#### 🔴 外壳绝不持有「保存」按钮

初版方案写的是「保存能力通过 `defineExpose({ save })` 上交外壳」。**这是错的，而且对 TASK 根本无法实现。**

实证：`TaskConfigService.wizardSubmit():63` 是单个 `@Transactional`，
主表 `insert`(:95) 与子表 `insertBatch`(:109) 一次性提交 ——
**`TaskWizard` 压根不存在「中途 save」这个能力**。
运营走到第 2 步（配规则）时点外壳的保存，不是「调了会出错」，
而是**没有一个可调的 `save()`**：它还需要第 3 步的阶梯奖励才能凑齐提交入参。

这条与 §1.1 定的边界也自相矛盾 —— 那里写着「玩法组件内部有几步是它自己的事」，
转头又让外壳接管它的保存，等于把刚划的边界又踩掉。

**正解：保存权留在玩法组件自己手里。**

| | 保存入口 | 完成信号 |
|---|---|---|
| `DrawWorkbench` | 自己的「保存并发布」按钮（保留） | `emit('saved')` |
| `LotteryWorkbench` | 自己的保存按钮（保留） | `emit('saved')` |
| `TaskWizard` | 自己第 5 步的「提交」（保留） | `emit('saved')` |

外壳第二步只提供**一个**按钮：「稍后再配」（回列表，活动已建，可从「继续配置」回来）。
推进到完成页由 `emit('saved')` 驱动，不由外壳的按钮驱动。

**这反而简化了 P1**：不用做 `defineExpose`、不用在外壳里聚合 `hasUnsavedChanges`，
离开拦截也只剩内层一处（`embedded` 时内层不关守卫、外壳不再另设一层），
第 13 条验收「只弹一次」自然成立。

### ⚠️ 六：`optionList` 没有任何状态过滤

`ActivityConfigService.queryOptionList():48-53` 只按 `activityType` 过滤 + `id` 倒序，
**不看 `status`、也不看 `end_time`** —— 一个三年前就结束的活动，今天照样出现在三个工作台的下拉里。

调用点共 **4 处**：`DrawWorkbench:119`、`LotteryWorkbench:207`、`TaskWizard:322`、
`prize-pool-config-form:159`。

#### 🔴 口径必须是「此刻能不能配置」，不是「状态正不正常」

**这里有个会让整个向导当场失效的陷阱**：若把「状态正常」朴素理解成 `status=1 上线中`，

> **第一步刚落库的活动一定是 `status=0` 未开始 —— 它将永远无法进入工作台配置。**

正确口径：

| 情形 | 默认 | 理由 |
|---|---|---|
| `status=0` 未开始 | **必须显示** | 新建活动就是这个状态，向导的命根子 |
| `status=1` 上线中 | 显示 | 可改，结构锁自己管得住能改什么 |
| `status=2` 已下线 | 默认隐藏，**开关可显示** | 下线时结构锁不启用，**活动是可以改配置再重新上线的**，一刀切会让它无法维护 |
| `end_time < now` 已过期 | 默认隐藏，开关可显示 | 最该隐藏的一类，但历史配置仍需可查 |
| **未配置玩法** | **必须显示** | ⚠️ 它恰恰最需要出现在下拉里 —— 就等着被配置 |

最后一行最容易搞反：「未配置玩法」在大盘里是个**待办标记**，
很顺手就会被归进「不正常」一起过滤掉，结果把唯一需要处理的那批活动藏了起来。

#### 修法

**① 过滤放服务端**，加参数 `includeInactive`（默认 `false`）：

```
GET /activityConfig/optionList?activityType=DRAW&includeInactive=false
```

`ActivityConfigVO` 已经返回 `status`/`startTime`/`endTime`，前端本地过滤也做得到，
但 4 个调用点 = 4 份规则副本，必然漂移（铁律 3）。**服务端一处真源，前端开关传 `true`。**

**② 活动大盘（列表页）不默认过滤。** 它是管理视图，默认隐藏数据是反模式 ——
运营建完活动回列表找不到，会以为没建成。大盘该做的是**默认全展示 + 提供筛选器**，
主动权交给运营。

**③ 这只是 UI 便利，不是守卫（铁律 2）。**
`workbenchSave` 现在只校验「活动存在」并用 status 决定结构锁，**并不拒绝已过期的活动**，
过滤下拉挡不住绕过页面直接 POST。
**且刻意不在 save 里加过期校验** —— 给活动延期是正常运营操作，
过期只该是提醒，不该是硬拦。

## 9. 风险与遗留

1. **P1 的回归风险最高** —— 三个玩法组件都是已验收过的成熟页面，加 prop 容易碰坏既有行为。
   验收清单第 14 条专为此设。
2. **任务类「向导套向导」的观感** —— 见 §1.1，已接受此代价。若实测下来运营困惑明显，
   再考虑把 `TaskWizard` 拆成步骤组件（大重构，单独立项）。
3. **菜单父级未定** —— 见 §5 P3。
4. **多租户未纳入** —— `tenant_id` 有默认值 `'0'`，全系统按单租户运行，向导不引入该维度。
5. **BASIC 活动的用途边界** —— 目前它能承载的只有 `t_prize_config`（资产大库）。
   若产品后续希望 BASIC 也能挂预算（`t_promotion_config`）或做活动级统计，
   需要先补上交接文档遗留清单第 5 条「`t_promotion_config` 与活动的映射关系未建」。
   **本方案不提前实现该映射**，避免为一个尚未确认的需求引入跨域耦合。
6. **四张统计卡片不做** —— 旧原型里「运行中 12 / 抽奖 5 / 任务 4 / 彩票 3」是硬编码假数据。
   真做需要一个聚合接口，而它的信息量低于列表本身（列表已有类型 Tag、状态、完备度且可筛选）。
   **给一个不准的数字比不给更糟** —— 运营会拿它去汇报。等有明确看板需求再单做。
7. ~~旧原型 `docs/活动创建向导.html` 已作废~~ —— **✅ 2026-07-29 已删除**，见 §0。
8. **奖品类型只开放 4 个** —— `LOTTERY` / `CUSTOM` 两层派发策略都没有
   （全工程 `@PrizeStrategy` 与 `@AssetStrategy` 各只注册了 SCORE/BALANCE/COUPON/PHYSICAL），
   已从 `PRIZE_TYPE_OPTIONS` 里过滤掉。补齐策略后把常量里的 `dispatchable` 改 true 即可。
   **刻意不给这两类补优惠配置** —— 缺的不是配置而是策略，补配置只会让运营顺利建出
   一个必然发不出去的奖品，而失败发生在 AFTER_COMMIT 里、对主链路无感。
9. **第 15 条验收（受限角色）无法由 AI 完成** —— 它要求新建账号并用该账号登录，
   而创建账号、输入密码均属不可代为执行的操作。已改为做权限串一致性核对，
   结论见 §11。真正的负向测试需要人工执行。

### 交互上的两个刻意设计

1. **类型卡片下的提示随选择切换**：选玩法类提示「创建后类型即冻结，不确定就先建基础活动，之后再升级」；

### CDN 原型的已知限制（不影响实施）

CDN 版 antd 不带 locale 包（`antd.locales` 为 undefined），弹窗与日期框默认英文。
已把可控文案（`cancel-text` / `placeholder`）显式写成中文；

### ⚠️ 一个自动化验证的教训（同族问题第二次出现）

验证过程中用**缓存的元素坐标**点击，而校验错误信息插入后布局下移了约 20px，
点击落到了相邻的彩票卡片上，**把已选的类型静默改掉了** —— 表现是「按钮文案莫名从
『创建活动』变回『创建并配置玩法』」，一度以为是组件 bug。

这与彩票技术方案 §11 记的「`a-input-number` 程序化赋值不触发 Vue 模型更新」是同一族：
**自动化操作里，页面上看到的不一定等于模型里的值。**
同理，`form_input` 对 antd `RangePicker` 无效（它管理自己的内部状态），
必须走真实面板点选。

**做法：每次操作前重新取元素，不复用上一次 `read_page` 的坐标；
断言状态时读模型侧的渲染结果（步骤条、按钮文案），而不是只看自己刚"填"进去的值。**

## 11. 权限串核对（2026-07-29）—— 第 15 条验收的替代结论

**第 15 条（受限角色）无法由 AI 完成**：它要求新建一个只有 `activityConfig:query` 的角色、
建账号、再用该账号登录，而创建账号与输入密码均属不可代为执行的操作。
改为做一次权限串一致性核对，结论比预想的更有说服力。

### 核对结果：完全对上

`ActivityConfigController` 里的 `@SaCheckPermission` 取值统计：

```
activityConfig:query   × 4      activityConfig:add    × 3
activityConfig:update  × 2      activityConfig:delete × 2
```

`t_menu` 里的功能点（`menu_type=3`）：

| menu_id | 名称 | api_perms / web_perms | 归属 |
|---|---|---|---|
| 442~445 | 查询 / 新建活动 / 编辑活动·升级玩法 / 删除活动 | `activityConfig:query`/`:add`/`:update`/`:delete` | 441 活动创建向导（v3.42 新建） |
| 373~376 | 查询 / 添加 / 更新 / 删除 | `activityConfig:query`/`:add`/`:update`/`:delete` | 372 活动配置（**早已存在**） |

### 🔴 这份数据反过来证明了缺陷三的严重程度

关键在于 **373~376 是早就存在的** —— 也就是说**菜单侧的权限串一直是对的**，
错的一直是 Controller：它要的是 `:addProposal` 和不带前缀的 `:query`。

两边永远对不上，意味着**任何受限角色即便被正确授予了 `activityConfig:add`，
也依然会被拒**。这不是「权限配得不够」，而是「权限根本无法配对」。

**为什么长期没人发现**：实测当前 `admin` 账号的
`administratorFlag = true` —— 超管绕过全部权限校验。
开发与联调都用这个账号，所以这类缺陷在被交到运营手上之前完全不可见。
这也正是验收清单第 15 条当初被单独列出来的理由。

### 仍需人工执行的部分

权限串对上了，但「sa-token 是否真的拒绝」这一步没有实测。
该行为是框架级的、被系统里其它每个模块反复使用，风险很低；
若要彻底闭环，需要人工建一个只有 `activityConfig:query` 的角色与账号，
登录后确认：列表能看、「创建活动向导」按钮不可见或点击被拒。
