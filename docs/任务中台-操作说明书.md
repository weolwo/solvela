## 1. 一页纸讲清这个模块

### 1.1 它做什么

**用户做了某件事 → 任务进度涨 → 达标 → 自动发奖。**

「某件事」由上游系统上报，叫**事件**；「涨多少、涨到多少算达标」由运营配置；
发奖复用已有的派奖链路（风控 → 预算 → 资产到账），任务模块自己不发钱。

### 1.2 数据流

```
上游业务系统
    │  POST /taskEvent/report   {事件编码, 会员名, 业务单号, 金额...}
    ▼
【事件校验】事件是否已注册？是否要求带业务单号？        ← t_task_event 事件注册表
    │
    ▼  (异步，独立线程池，绝不阻塞上游)
【找订阅】哪些任务在监听这个事件？                     ← t_task_config 任务配置
    │
    ▼  每个任务各自一个事务
【幂等】这个事件对这个任务处理过没有？                  ← t_task_record_flow 事件流水
    │
    ▼
【推进进度】按任务类型累加                            ← t_task_record 任务记录
    │
    ▼
【发奖】跨过了哪些档位就发哪些                        ← t_task_prize_mapping 奖励档位
    │
    ▼
复用既有派奖链路 → 审批 → 风控预算 → 钱包/券/实物到账
```

### 1.3 五张表在管什么

| 表 | 中文 | 谁维护 | 一句话 |
|---|---|---|---|
| `t_task_event` | 事件注册表 | 开发 + 运营 | 系统认识哪些事件、上游必须传什么 |
| `t_task_template` | 任务模板 | 开发 | 一类玩法长什么样（表单字段） |
| `t_task_config` | 任务配置 | **运营** | 一个具体的任务（目标几次、发什么奖） |
| `t_task_prize_mapping` | 奖励档位 | **运营** | 达到第几档发哪个奖 |
| `t_task_record` | 任务记录 | 系统 | 某个用户在某个任务上的进度 |
| `t_task_record_flow` | 事件流水 | 系统 | 收到过哪些事件、生效没有、没生效为什么 |

## 2. 四种任务类型怎么选

**这是配任务时第一个也是最容易配错的决定。** 类型定了「进度怎么涨」，选错了后面全错。

| 类型 | 进度怎么涨 | 典型玩法 | 必填参数 |
|---|---|---|---|
| `SIMPLE` 单次节点型 | 一次性，0 → 1 | 完善资料、首次下单 | 无（目标恒为 1） |
| `COUNT` 计次型 | 每次事件 **+1** | 累计签到 7 天、下单 3 次 | `targetCount` |
| `AMOUNT` 计额型 | 每次事件 **+金额** | 累计消费满 500 | `targetAmount`（可选 `minAmount`） |
| `STREAK` 连续型 | **断了清零重来** | 连续签到 7 天 | `targetCount`（可选 `tolerance`） |

### 🔴 `COUNT` 和 `STREAK` 别搞混

- 「**累计**签到 7 天」= `COUNT`：断几天没关系，攒够 7 次就行。
- 「**连续**签到 7 天」= `STREAK`：断一天就从头再来。

选错的后果是用户体感完全不同，而系统不会报任何错。

`STREAK` 的 `tolerance`（允许断签次数）：
- `0`（默认）= 断一天就清零
- `1` = 允许断一天，隔天补上仍算连续

> ⚠️ 断档后是**从 1 重新开始**，不是从 0——断档当天这一次仍然算数。

### 参数键名是固定的，不能随便起

`targetCount` / `targetAmount` / `minAmount` / `tolerance` 这几个名字是**契约**。
模板里把参数键起成别的名字（比如 `targetDays2`），系统读不到目标值，
表现是「**进度一直涨，但永远不完成**」，而且**一条报错都没有**。

保存模板时系统会拦这个错，报错会直接告诉你该用哪个键名，照抄即可。
（存量模板用的 `targetDays` 仍然兼容，但**新建模板一律用 `targetCount`**。）

## 3. 运营：配一个任务的完整流程

### 步骤 0：确认事件已注册

**任务中心 → 任务事件注册**

先确认你要用的触发事件在列表里、且是「启用」状态。没有的话找开发注册
（注册本身只是加一行数据，但**必须同时有上游埋点**，否则事件永远不会来）。

看两列：

- **幂等要求**：显示「必须带单号」的事件，上游对接时必须传业务单号。配任务时不用管，但要知道。
- **计量来源**：`AMOUNT` 类任务要用的金额从哪个字段取。显示「计次（不取金额）」的事件配不了 `AMOUNT` 任务。

### 步骤 1：走任务配置向导

**任务中心 → 任务配置向导**（推荐）

五步：

1. **基本信息**：选活动、填任务名、**选触发事件**、选任务分组
2. **达标规则**：按所选模板动态出表单，填目标值等参数
3. **奖励配置**：配档位（见下）
4. **展示信息**：任务描述、图标、跳转地址
5. **确认提交**

> 选中「必须带单号」的事件时，第 1 步会出现橙色提示。
> 那是给你转告对接开发的，不影响你继续配。

### 步骤 2：配奖励档位

**单档任务**：配 1 条，达标条件 = 任务目标值。

**阶梯任务**：配多条，`stage_level` 从 1 递增，达标条件递增。例：

| 档位 | 达标条件 | 奖品 |
|---|---|---|
| 1 | 3 次 | 10 积分 |
| 2 | 5 次 | 20 元券 |

用户跑到 5 次时，**两档的奖都会发**（第 1 档在到 3 次时就发过了）。

🔴 **最高档的达标条件必须等于任务目标值**。比如目标 `targetCount=5`，
最高档就配 5。配成 6 的话任务永远不会标成「已完成」；配成 4 的话第 5 次事件不再推进。

### 步骤 3：确认奖品可发

奖品必须满足：

- 属于**同一个活动**（`t_prize_config.activity_code` 与任务的活动一致），否则发奖时报「奖品配置不存在」
- 状态是**启用**
- 挂的**优惠配置（预算池）类型与奖品类型一致**，且预算没耗尽

> 预算耗尽的表现是：任务正常达标、发奖记录也有，但状态停在「失败」，
> 原因写「预算或发放数量已耗尽」。这不是任务模块的问题，去风控管理里加预算。

### 步骤 4：任务状态

任务配置落库后状态是 **1-待生效**。

> ⚠️ **不需要手动改成「生效中」**。运行态的判据是「状态不是 3-已下线」+ **当前在起止时间内**。
> 「活动有没有开始」是按时间实时算的，不是靠后台开关。
> 要停一个任务，把状态改成 **3-已下线**。

## 4. 上游开发：埋点对接

### 4.1 接口

```
POST /taskEvent/report
Authorization: Bearer {token}
Content-Type: application/json
```

```json
{
  "eventCode":   "ORDER_PAID",
  "memberName":  "user_10086",
  "eventBizId":  "ORDER20260801123456",
  "amount":      199.00,
  "eventTime":   "2026-08-01 10:30:00",
  "payload":     { "orderId": "ORDER20260801123456", "payAmount": 199.00 }
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `eventCode` | ✅ | 必须是注册表里**已启用**的编码，否则当场返回失败 |
| `memberName` | ✅ | 会员标识 |
| `eventBizId` | **看事件** | 幂等键。注册表里标「必须带单号」的事件不传会被拒 |
| `amount` | ❌ | 计量值。不传时按注册表的「计量来源」去 `payload` 里取 |
| `eventTime` | ❌ | **事件实际发生时间**。不传取服务器时间 |
| `isNewMember` | **看任务** | 是否新会员。任何一个订阅该事件的任务配了非「全部会员」人群时**必须传**，否则那个任务会丢弃事件 |
| `payload` | ❌ | 事件原文，会存进流水供排查 |

### 4.2 🔴 `eventBizId` 是最重要的一个字段

它是防重复的唯一依据：**同一个 `eventBizId` 对同一个任务只会生效一次**。

- **有天然单号的事件（订单支付等）必须传订单号。** 不传的话服务端只能按「事件发生的自然日」兜底，
  那意味着**一天只算一笔订单**——用户下 5 单只涨 1 次进度。
  所以这类事件在注册表里标了「必须带单号」，不传直接返回失败。
- **没有天然单号的事件（签到、分享）不用传**，服务端按自然日兜底正好符合「一天一次」的语义。

### 4.3 `eventTime` 什么时候必须传

**消息可能延迟到达时必须传真实发生时间。** 周期归属按这个时间算：
用户 23:59 签到、消息 00:01 才到，不传的话会算到第二天，
用户当天的连续签到就断了。

### 4.4 返回与重试

| 返回 | 含义 | 上游该怎么办 |
|---|---|---|
| `ok: true` | 已受理（异步处理） | 不用管 |
| `未注册或已停用的事件编码：X` | 编码写错或事件被停用 | 查编码；**不要重试** |
| `事件 X 必须携带 eventBizId` | 缺幂等键 | 补上单号再发 |
| `任务事件处理繁忙，请稍后重试` | 队列打满被拒 | **应重试**，这条事件确实没被处理 |

> 接口返回 `ok:true` 只代表**已受理**，不代表进度一定涨了
> ——事件可能因为不满足任务条件被丢弃，那是正常的。要确认结果查事件流水（§5）。

### 4.5 幂等是安全的

同一个事件重复上报任意多次，进度只会涨一次。上游不需要自己去重，
网络重试、消息重投都可以放心。

## 5. 排查手册（客服 / 运营自查）

> **入口只有一个：任务中心 → 任务记录 → 找到那条记录 → 点「事件流水」。**
>
> 抽屉里按时间列出这条记录收到过的**全部事件**：
> 绿色 = 已推进（显示 `+增量 → 推进后进度`），红色 = **已丢弃并写明原因**。
> 九成问题看一眼就有答案，不用翻日志。

### 5.1 症状 → 原因对照表

#### 「用户做了动作，但进度一点没涨」

| 先看 | 结论 |
|---|---|
| 事件流水里**有这条事件**吗？ | 有 → 看丢弃原因（下表）；没有 → 继续往下 |
| 任务记录**存在**吗？ | 不存在 → 事件根本没匹配到这个任务，见下 |

事件没匹配到任务，可能是：

1. **上游没上报** —— 最常见。找开发确认埋点调没调、返回什么。
2. **事件编码对不上** —— 任务配的触发事件和上游报的编码不是同一个。
3. **任务不在有效期内** —— 当前时间不在任务的起止时间内。
4. **任务已下线** —— 状态是 3。
5. **事件被拒** —— 上游收到的是失败返回（未注册 / 缺单号），事件压根没进来。
6. **人群不符** —— 任务限定了新/老会员而该用户不符（这种情况流水里会有丢弃记录，见下）。

#### 「流水里有事件，但显示已丢弃」

丢弃原因是系统直接写的人话，对照处理。
（流水里还有一个 `discard_code` 分类码，那是给数据大屏聚类用的，排查时看人话原因即可。）

| 丢弃原因 | 含义 | 怎么办 |
|---|---|---|
| `单笔金额 X 未达门槛 Y，本次不计入累计` | 配了单笔门槛 `minAmount` | 符合预期。要改就调低门槛 |
| `事件未携带有效金额（amount=0）` | 计额型任务没收到金额 | 找开发：要么传 `amount`，要么把注册表的「计量来源」配成 payload 里的金额字段 |
| `当日已计入连续进度（20260801），不重复累加` | 连续型任务当天已签 | 符合预期 |
| `任务记录已不在进行中（status=2）` | 任务**已经完成并发过奖了** | 符合预期。用户已经拿到奖了，去发奖记录确认 |
| `任务记录已不可推进（并发达标或已过期）` | 同上，并发情况下的等价表现 | 符合预期 |
| `任务类型未配置或非法：rule_config.taskType=X` | **配置坏了** | 找开发。这个任务谁也跑不了 |
| `没有支持 X 的进度策略实现` | **配置坏了** | 同上 |
| `该任务仅限新会员参与` / `该任务仅限老会员参与` | 任务配了目标人群，这个用户不符合 | 符合预期 |
| `任务限定了目标人群（X），但上游未告知会员属性 isNewMember，无法判定` | **上游没传会员属性** | 找埋点开发补传 `isNewMember`；或者把任务的目标人群改回「全部会员」 |
| `本周期参与次数已达上限（N 次），下个周期才能继续` | 配了每日/每周可完成 N 轮，已用满 | 符合预期。要放宽就调大「周期内可完成轮数」 |
| `并发冲突重试耗尽` | 极端并发 | 罕见。重投这条事件即可 |
| `任务事件线程池队列已满，事件被拒` | 系统过载 | 上游应重投；频繁出现要扩容 |

#### 「进度涨到目标了，但任务不显示完成、也没发奖」

按顺序查：

1. **最高档的达标条件是不是配得比任务目标值高？** 例：目标 5 次，最高档配了 6 次 → 永远不完成。
2. **参数键名对不对？** 目标值读不到时，进度会一直涨但判不了达标。
   查任务配置的 `rule_config`，看有没有 `targetCount` / `targetAmount`。
   （新建模板已经拦了这个错，老模板可能有。）
3. **有没有配奖励档位？** 一条都没配的话，进度到了也没有奖可发。

#### 「任务完成了，但用户说没收到奖」

任务模块的活到「发出发奖事件」为止，往下是公共派奖链路。**去发奖记录查**：

| 发奖记录状态 | 含义 | 怎么办 |
|---|---|---|
| 没有记录 | 奖压根没发出去 | 看任务记录状态是不是「已发奖」；再查奖品是否属于同一活动、是否启用 |
| `审批状态 = 待审批` | 奖品配了人工审批 | 去发奖记录里审批通过 |
| `状态 = 失败`，原因「预算或发放数量已耗尽」 | 预算池空了 | 风控管理里加预算，然后重新发放 |
| `状态 = 失败`，原因「资产配置异常」 | 奖品没挂优惠配置，或类型不一致 | 改奖品配置 |
| `状态 = 成功` | 已到账 | 去会员钱包 / 优惠券里核对 |

> 两套审批是**并存**的，可能要批两次：
> 奖品级审批（运营视角，在发奖记录里）+ 提案级审批（财务视角，在提案表里）。

#### 「阶梯任务只发了第一档的奖」

先确认第二档的达标条件用户**真的到了**（看任务记录的当前进度）。
到了却没发，把发奖记录里的**外部单号**发给开发——正常应该是
`任务记录ID:档位` 这样两条不同的单号（如 `1024:1` 和 `1024:2`）。

### 5.2 排查用的 SQL

```sql
-- 某用户在某任务上的进度
SELECT r.id, r.member_name, c.task_name, r.current_metric, r.status,
       r.period_key, r.complete_time, r.progress_data
FROM t_task_record r JOIN t_task_config c ON c.id = r.task_config_id
WHERE r.member_name = 'user_10086';

-- 这条记录收到过的所有事件（等价于界面的「事件流水」）
SELECT event_code, event_biz_id, flow_type, delta_metric, after_metric,
       discard_reason, create_time
FROM t_task_record_flow WHERE record_id = 1024 ORDER BY id;

-- 发奖去向（幂等键形如 记录ID:档位）
SELECT prize_code, prize_name, external_biz_no, approve_status, status, fail_reason
FROM t_prize_log WHERE external_biz_no LIKE '1024:%';

-- 某任务的配置全貌（含档位）
SELECT c.task_name, c.trigger_event, c.limit_type, c.status, c.rule_config,
       m.stage_level, m.stage_condition, m.prize_code
FROM t_task_config c LEFT JOIN t_task_prize_mapping m ON m.task_config_id = c.id
WHERE c.id = 20 ORDER BY m.stage_level;
```

## 6. 状态字典

### 任务配置 `t_task_config.status`

| 值 | 含义 | 运行态行为 |
|---|---|---|
| 1 | 待生效 | **会正常触发**（在有效期内） |
| 2 | 生效中 | 会正常触发 |
| 3 | 已下线 | **不再触发** |

> 1 和 2 在运行态没有区别。要停用请用 3。

### 任务记录 `t_task_record.status`

| 值 | 含义 |
|---|---|
| 0 | 进行中（**含"低档已发奖、最高档还没到"**） |
| 1 | 已完成（最高档达标） |
| 2 | 已发奖（此后不再接受事件） |
| 3 | 已过期（⚠️ 当前没有过期扫描，这个值不会出现） |

### 事件流水 `t_task_record_flow.flow_type`

| 值 | 含义 |
|---|---|
| 1 | 已推进 |
| 2 | 已丢弃（`discard_reason` 写明原因） |

## 7. 权限

| 功能点 | 给谁 |
|---|---|
| `taskConfig:query` / `:add` / `:update` / `:delete` | 运营 |
| `taskConfig:wizard:submit` | 运营（**向导提交是单独的功能点**，不给的话向导保存会被拒） |
| `taskRecord:query` | 运营 / 客服（**事件流水查询也用这个**） |
| `taskTemplate:query` / `:save` | 开发 |
| `taskEventDef:query` / `:add` / `:update` / `:delete` | 开发 |
| `taskEvent:report` | **上游系统专用角色**，不要给运营 |

> 🔴 **改完权限必须登出重登才生效**。
> 这是基座缺陷：加权限后菜单立刻出来，但点功能仍报"没有权限"，界面上没有任何线索。

## 8. 当前能力边界（明确不支持的）

配之前先看这一节，避免配了不生效还以为是 bug。

| 想做的事 | 现状 |
|---|---|
| **限定人群**（只给新会员 / 老会员） | ✅ 已支持，**但依赖上游传 `isNewMember`**，见 §8.1 |
| **限制参与次数**（`limit_count`） | ✅ 已支持（周期内可完成 N 轮），见 §8.2 |
| **写脚本处理复杂规则**（`rule_script`） | ❌ **不执行**。三层设计里的第三层兜底通道尚未接上，目前只能表达四种类型 + 参数能表达的规则 |
| **任务自动过期** | ❌ 没有过期扫描任务，记录不会自动变成「已过期」；到期后靠任务配置的时间窗停止接收事件 |
| **高频事件的性能优化** | ⚠️ 注册表有「高频」标记但只是标记，路由优化未实现 |
| **事件走消息队列** | ⚠️ 当前是 HTTP 直连 + 进程内异步线程池，未接 MQ |

### 8.1 限定人群怎么用

**配置**：向导「受众与时间」步骤选「新会员」或「老会员」。

🔴 **选了非「全部会员」之后，必须和埋点开发确认上游会传 `isNewMember`。**
营销域里没有会员档案（只有钱包、流水、券，都以会员名为键，没有注册时间），
所以「新/老」只能由会员域告诉我们。

**上游没传的后果**：该任务收到的事件会被**丢弃**，丢弃原因写
「任务限定了目标人群（NEW_MEMBER），但上游未告知会员属性 isNewMember，无法判定，本次不计入」。

> 之所以丢弃而不是放行：放行等于「配了人群但对所有人生效」，
> 运营看不出任何异常，直到有人问「为什么老会员也领到新人礼」才发现，那时奖已经发出去了。

目标人群是「全部会员」的任务不受影响，上游不用传这个字段。

### 8.2 参与次数怎么用

`limit_count` = **一个周期内最多完成几轮任务、领几次奖**。完成一轮后自动开下一轮，用满为止。

只在「每日重复 / 每周重复」下生效，界面上也只在这两种频次下才出现：

| 频次 | limit_count |
|---|---|
| 终身一次 | 不适用（就是一轮） |
| 每日重复 / 每周重复 | ✅ 生效，周期内最多 N 轮 |
| 无限制 | 不适用——「无限制」指轮次不限，若让次数生效会变成「无限制 + 限 1 次 = 终身一次」，自相矛盾 |

例：「每日重复 + 2 轮 + 目标 1 次」= 一天可以完成 2 次、领 2 次奖，第 3 次上报会被丢弃，
原因写「本周期参与次数已达上限（2 次），下个周期才能继续」。

> 排查时会看到同一个用户在同一天有多条任务记录，周期标识分别是 `20260801` 和 `20260801#2`
> ——**第 1 轮不带后缀是刻意的**，这样不用轮次的任务与改造前完全一样。

## 9. 给开发：新增一个玩法怎么改

按改动落在哪一层判断工作量：

| 需求 | 落点 | 要改代码吗 |
|---|---|---|
| 累计签到 7 天送积分 | 任务配置参数 | ❌ 运营自己配 |
| 连续签到 7 天送积分 | 任务配置参数 | ❌ 运营自己配 |
| 累计消费满 500 | 任务配置参数 | ❌ 运营自己配 |
| **新增一种事件**（如"分享商品"） | 事件注册表加一行 + 上游埋点 | ❌ 前后端都不用改 |
| 新增一种**表单长相** | 任务模板加一条 `ui_schema` | ❌ 前端零改动 |
| 新增一种**进度累积方式** | 加一个策略实现类 | ✅ 要改 Java |

> ⚠️ 如果有人提出「加一个 `task_type` 来支持新玩法」，那基本是设计跑偏的信号——
> 绝大多数新玩法应该落在参数层，而不是新增类型。四种类型能覆盖绝大多数场景。
