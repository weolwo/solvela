# 文件模块 架构设计文档

> 目标：重写 SmartAdmin 自带的文件上传模块，做成一套**元数据驱动、端到端流式、CMS-ready** 的运营素材库。
> 前置阅读：`docs/SonicExcel-架构设计文档.md`（错误模型与分档节奏沿用那一套）
> 撰写 2026-08-09 · **实施完成 2026-08-10（六档 + 收尾，见 §10）** · 状态：**已落地**
>
> 实施过程中订正了三处设计错误，见 §10.1；尚未完成的五项见 §10.2。
>
> 本文所有「现状」结论均来自实际读码，不是从 README 或注释推断。凡标注 🔴 的是**动手前必须先修**的既有缺陷。

---

## 0. 一句话结论

**现有模块不是"不好用"，是三个概念糊在了一起**：存储层认识 HTTP 类型（`MultipartFile`、`ResponseDTO`），
业务权限编码在文件路径里（`private/` 前缀），文件名有三个互相矛盾的真相源。

重写的核心不是加功能，是**把「字节 / 引用 / 呈现」三个身份拆开**，让每一层只知道自己该知道的。
拆开之后，本文列出的 11 个既有缺陷有 8 个是自动消失的，不需要单独修。

### 已确认的产品决策

| # | 决策 | 结论 |
|---|---|---|
| 1 | 模块定位 | **运营活动素材库**，不是通用网盘、不是文档管理 |
| 2 | 分类级权限隔离 | **不做**。素材绝大多数是公开的 |
| 3 | 私有文件免登录外发链接 | **不做**。私有文件走后端下载接口（走登录态） |
| 4 | 客户端直传 / 分片 | **推到 v2**。10MB 以内代理上传足够 |
| 5 | 单文件上限 | **10MB**（⇒ 不支持视频素材） |
| 6 | 批量上传形态 | **N 次单传**，不做「一请求多文件」 |
| 7 | 文件标签 | 要，**直接放 `t_file.tags` 字段**，不单独开表 |
| 8 | 分类表字段 | **精简版**：code / name / tag / sort + 审计 |
| 9 | 活动配置推 CDN | **以后再说**，但本版设计必须为它留好 URL 稳定性 |
| 10 | 可视化搭建器（L3） | **不做**。有 amis / formily 等成熟方案 |

## 1. 定位与 Non-Goals

### 1.1 定位

运营人员上传活动素材（banner、主视觉、分享图、规则配图），在后台按分类和标签检索复用，
最终挂 CDN 供 C 端消费。上传者是**内部运营**，不是终端用户。

### 1.2 Non-Goals（明确不做，避免范围蔓延）

- ❌ **通用内容管理（CMS）**。专题页/落地页/表单设计器这一层不做，理由见 §1.3
- ❌ **文件版本管理**。换图 = 传新文件 + 改引用，不是覆盖旧文件（§7.6）
- ❌ **在线预览/编辑**（Office 预览、图片编辑器）
- ❌ **视频/大文件**。10MB 上限是硬约束，视频只能走 v2 的直传
- ❌ **分类级权限、部门隔离**
- ❌ **回收站**。软删 + 定时物理清理，不做 UI

### 1.3 为什么不做 CMS（L3）

把「内容能力」拆成三层之后，投入产出比一目了然：

| 层 | 是什么 | 后端工作量 | 前端工作量 | 成熟替代 |
|---|---|---|---|---|
| **L1 素材库** | 文件存储/分类/检索/复用 | 2~3 周 | 1 周 | 有但都太重 |
| **L2 内容模型** | 结构化内容的定义与发布 | 2~3 周 | 2 周 | Strapi / Directus |
| **L3 可视化搭建** | 拖拽编辑器 + 渲染 SDK | 1 周 | **3~6 人月** | amis / formily / form-create |

L3 的工作量 80% 以上在前端，而且通用搭建器**管不了业务规则**——没有任何一个 CMS 能校验
"抽奖概率之和必须为 1""库存不能超发""彩票期号不能重叠"。本项目的护城河在抽奖/彩票引擎，不在拖拽。

**L2 我们其实已经在做了**，只是领域化的：活动创建向导（`docs/活动创建向导-实现技术方案.md`）
就是"运营在后台配置、前端按配置渲染"。领域化配置比通用内容模型更值钱，因为它能校验、能和业务逻辑联动。

**L1 是所有路径的交集**——做 CMS 需要它，不做 CMS 也需要它。所以本版只做 L1，做对，然后停在边界上。

## 2. 现状盘点：11 个缺陷

全部来自读码，标注了文件行号。**打 🔴 的是会造成数据错误或安全问题的，其余是设计债。**

| # | 缺陷 | 位置 | 重写后 |
|---|---|---|---|
| 1 | 🔴 **同一接口两个实现，`fileName` 语义相反**：local 返回生成名，cloud 返回原名 | `FileStorageLocalServiceImpl:102` vs `FileStorageCloudServiceImpl:131` | §4.2 三字段拆分，自动消失 |
| 2 | 🔴 **Windows 下 fileKey 多一个反斜杠**：先算 `filePath` 后补 `File.separator` | `FileStorageLocalServiceImpl:75,81,96` | §5.2 `StorageKey` 构造校验 |
| 3 | 🔴 **本地模式的"私有文件"根本不私有**：拼一个永久可访问的静态 URL | `FileStorageLocalServiceImpl:122` | §7.4 私有走后端下载接口 |
| 4 | 🔴 **Content-Disposition 不合规且可被截断**：`URLEncoder.encode` 不转义逗号分号 | `SmartResponseUtil:56` | §7.5 RFC 6266 双写法 |
| 5 | 🔴 **扩展名取自用户文件名**，Tika 嗅探结果没用于命名 | `FileStorageLocalServiceImpl:91` | §7.1 从 MIME 反推 |
| 6 | 🔴 **业务表逗号拼接附件**，并发追加必丢 | `NoticeEntity:65` | §4.3 `t_file_relation` |
| 7 | 🔴 **无 `storage_kind`**：local 切 cloud 后历史文件全部失效 | `t_file` DDL | §4.2 |
| 8 | ACL 判定口径不一致：上传 `contains(PUBLIC)` / 取 URL `startsWith(PRIVATE)` | `FileStorageCloudServiceImpl:232,157` | §7.4 visibility 进 DB |
| 9 | `getFileList` 的 N+1：批量查完再逐个查 Redis + DB + 算签名 | `FileService:124` | §5.4 真批量 |
| 10 | 手写 MIME 表，`docx`/`pptx` 映射错误，兜底返回 `""`；项目里另有一套 `MediaTypeFactory` | `IFileStorageService:61` | §7.1 统一 |

## 3. 整体架构

### 3.1 三个身份

| 身份 | 关心什么 | 归属 | 绝不该知道 |
|---|---|---|---|
| **字节** | 存在哪、怎么读写 | 存储层 | 谁传的、叫什么、是否公开 |
| **引用** | 谁传的、谁在用、能不能删 | 业务层 | HTTP、对象存储 SDK |
| **呈现** | 下载名、内联还是附件、缓存 | HTTP 层 | 文件存在哪 |

### 3.2 分层

```
┌──────────────────────────────────────────────────────┐
│ FileController          HTTP 边界                     │
│   · Content-Disposition（RFC 6266）· Range · ETag     │
│   · 唯一认识 ResponseDTO 的地方                        │
├──────────────────────────────────────────────────────┤
│ FileService             业务语义                       │
│   · 校验三道关 · 落库记账 · TEMP/CONFIRMED 生命周期     │
│   · 决定发公开 URL 还是后端下载链接                     │
│   · 只认识 MultipartFile，不认识对象存储 SDK            │
├──────────────────────────────────────────────────────┤
│ ObjectStorage           纯基础设施                     │
│   put / open / exists / delete / deleteAll            │
│   · 只认 StorageKey + 字节流                           │
│   ├─ LocalFileStorage                                 │
│   ├─ S3ObjectStorage        implements PresignCapable │
│   └─ InMemoryObjectStorage  （测试用，见 §11）          │
└──────────────────────────────────────────────────────┘
```

**分层是否正确的验收标准**：`InMemoryObjectStorage` 能不能用一个 `Map<StorageKey, byte[]>`
加二十行代码写出来。写不出来说明接口漏了抽象。现有的 `IFileStorageService` 写不出来——
因为它的入参是 `MultipartFile`，你得先造一个假的 HTTP 请求。

## 4. 数据模型

五张表。DDL 全部按 MySQL 8 + utf8mb4 编写。

### 4.1 `t_file_category` 文件分类

```sql
CREATE TABLE `t_file_category` (
  `category_id`   bigint      NOT NULL AUTO_INCREMENT,
  `category_code` varchar(50) NOT NULL COMMENT '稳定标识，代码引用它而非ID',
  `category_name` varchar(50) NOT NULL COMMENT '显示名称，可随时改',
  `category_tag`  varchar(32)          DEFAULT NULL COMMENT '标签，选择器里分组用',
  `sort`          int         NOT NULL DEFAULT 0 COMMENT '排序，小的在前',
  `create_by`     varchar(32)          DEFAULT NULL COMMENT '创建人',
  `create_time`   datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_by`     varchar(32)          DEFAULT NULL COMMENT '更新人',
  `update_time`   datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`category_id`),
  UNIQUE KEY `uk_code` (`category_code`)
) COMMENT='文件分类';
```

**`category_code` 是本表最重要的字段。** 代码必须引用 code（`"NOTICE"`），**绝不能引用自增 ID** ——
ID 由各环境数据库各自生成，dev 上「公告」是 2、prod 上可能是 7，而代码是同一份。
这是"枚举变表"最经典的翻车点。

**排序两条纪律**：

- 查询必须 `ORDER BY sort ASC, category_id ASC`。**第二排序键不能省** ——
  只按 `sort` 排，相同值时 MySQL 返回顺序不保证，表现是"每次刷新文件夹顺序都在变"，极难排查。
- **`sort` 不加唯一索引**。拖拽的中间态必然有重复值，加了就永远存不进去。

拖拽保存：分类量级只有几十个，**一个事务里发一条 `CASE WHEN` 批量 UPDATE 即可**，
不需要稀疏整数或 LexoRank，那是几百上千个分类才需要的方案。

**内置分类保护不加列，在代码里做**：

```java
// 代码按 code 引用这几个分类，运营删了会造成历史文件成孤儿 + 代码抛异常
private static final Set<String> SYSTEM_CODES = Set.of("COMMON", "NOTICE", "HELP_DOC", "FEEDBACK");
```

删除接口校验、后台按钮置灰。零列开销，而且真相源只有一个 —— 比在 DB 里存一个可能被手工 UPDATE 掉的
`system_flag` 更可靠。

### 4.2 `t_file` 文件

```sql
CREATE TABLE `t_file` (
  `file_id`       bigint       NOT NULL AUTO_INCREMENT,
  `category_id`   bigint       NOT NULL COMMENT '分类',
  `storage_key`   varchar(200) NOT NULL COMMENT '存储键，系统生成，不可变',
  `storage_kind`  varchar(16)  NOT NULL COMMENT '存储介质：LOCAL / S3',
  `original_name` varchar(200) NOT NULL COMMENT '用户上传时的原始文件名',
  `extension`     varchar(16)  NOT NULL COMMENT '扩展名，从嗅探MIME反推',
  `content_type`  varchar(100) NOT NULL COMMENT '嗅探出的真实MIME',
  `file_size`     bigint       NOT NULL COMMENT '字节数',
  `content_hash`  char(64)              DEFAULT NULL COMMENT 'SHA-256，去重预留',
  `image_width`   int                   DEFAULT NULL COMMENT '图片宽，非图片为NULL',
  `image_height`  int                   DEFAULT NULL COMMENT '图片高',
  `visibility`    tinyint      NOT NULL DEFAULT 1 COMMENT '1公开 2私有',
  `status`        tinyint      NOT NULL DEFAULT 1 COMMENT '1临时 2已确认',
  `tags`          varchar(500)          DEFAULT NULL COMMENT '标签，前后各带逗号：,双十一,banner,',
  `deleted_flag`  tinyint      NOT NULL DEFAULT 0,
  `create_by`     varchar(32)           DEFAULT NULL,
  `create_time`   datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_by`     varchar(32)           DEFAULT NULL,
  `update_time`   datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`file_id`),
  UNIQUE KEY `uk_storage_key` (`storage_key`),
  KEY `idx_category_time` (`category_id`, `create_time` DESC),
  KEY `idx_status_time` (`status`, `create_time`),
  KEY `idx_hash` (`content_hash`)
) COMMENT='文件';
```

#### 文件名的三个身份（缺陷 #1 的根治）

**不允许存在任何一个叫 `fileName` 的字段** —— 名字本身没告诉你它是哪个。

| 概念 | 谁定 | 存哪 | 何时用 |
|---|---|---|---|
| `storageKey` | 系统生成，不可变 | DB + 对象存储 | 唯一寻址，程序内部 |
| `originalName` | 用户上传时带的 | DB | 列表展示、下载还原 |
| `downloadName` | 业务可覆写 | 不存，调用时传 | 「2026年度合同.pdf」 |

**铁律：`originalName` 只在两个地方出现** —— 入库写一次、下载时拼 Content-Disposition 读一次。
中间所有环节都不碰它。这样"编码该在哪一层做"这个问题就消失了，因为只有一个地方需要编码。

#### `storage_kind`（缺陷 #7）

系统从 local 切到 cloud 之后，历史文件还躺在本地磁盘、新文件在 S3。
没有这个字段，代码只能按当前全局配置去读 —— **切换存储模式那一刻，所有历史文件立即失效**。

#### `tags` 存储格式

**前后各带一个逗号**：`,双十一,大促,banner,`，查询用 `LIKE '%,618,%'`。

不这么存，搜「618」会命中「6180」，搜「11」会命中「双11」和「1111」。
这种错不报警，只是搜出一堆不相干的东西，运营会当成"搜索不准"忍下来。

代价明确：`LIKE '%...%'` 用不上索引，每次搜索全表扫。几万行几十毫秒，可接受；
真到百万级再换 MySQL 8 的 JSON 多值索引（`CAST(tags AS CHAR(32) ARRAY)`），那时也不用加表。

#### 顺带修掉的类型缺陷

原 DDL `file_size int(0)` 是有符号 INT（上限 2.1GB），而实体是 `Long`。现在限 10MB 撞不到，
但类型不匹配没有任何理由保留 —— 改 `bigint`。

### 4.3 `t_file_relation` 文件业务引用

```sql
CREATE TABLE `t_file_relation` (
  `relation_id` bigint      NOT NULL AUTO_INCREMENT,
  `file_id`     bigint      NOT NULL,
  `biz_type`    varchar(50) NOT NULL COMMENT '业务类型：NOTICE / ACTIVITY_DISPLAY / ...',
  `biz_id`      bigint      NOT NULL,
  `sort`        int         NOT NULL DEFAULT 0 COMMENT '附件顺序',
  `create_time` datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`relation_id`),
  UNIQUE KEY `uk_biz_file` (`biz_type`,`biz_id`,`file_id`),
  KEY `idx_file` (`file_id`)
) COMMENT='文件业务关联';
```

这张表解决三件事，每一件现在都做不到：

1. **并发追加安全**（缺陷 #6）。逗号拼接是「读改写」，并发必丢且丢得很安静。
2. **附件有顺序**。轮播图必需。
3. **`idx_file` 支持反查"这个文件被谁引用着"** —— 这是**安全删除的前提**。
   逗号字符串永远做不到，所以现在这套系统实际上不敢删任何文件。

**为什么这张表可以用通用 `biz_type`，而展示信息表不行**：
"文件被某个业务对象引用"这件事在所有业务里是**同构的**；而展示属性是**异构的**
（活动要规则、商品要参数、公告要落款）。

> **同构的关系可以通用，异构的属性不要通用。**

### 4.4 `t_file_tag`

**不建此表。** 标签直接放 `t_file.tags`，理由见 §4.2。

标签管理能力靠查询即可获得：
- 标签列表与计数：应用层拆分聚合（几万行内可接受）
- 合并标签：`UPDATE t_file SET tags = REPLACE(tags, ',双11,', ',双十一,') WHERE tags LIKE '%,双11,%'`

需要给标签排序、分组、配权限时再升级为字典表 + 关联表，届时数据可平移。

### 4.5 `t_activity_display` 活动 C 端展示

`t_activity_config` 的 **1:1 垂直分表**。

```sql
CREATE TABLE `t_activity_display` (
  `id`             bigint      NOT NULL AUTO_INCREMENT,
  `tenant_id`      varchar(16) NOT NULL DEFAULT '0' COMMENT '冗余租户，让数据权限拦截统一',
  `activity_id`    bigint      NOT NULL COMMENT '关联 t_activity_config.id',

  -- ↓ 所有玩法共有、稳定、程序要读的 → 独立列
  `main_image_id`  bigint                DEFAULT NULL COMMENT '主视觉 file_id',
  `bg_image_id`    bigint                DEFAULT NULL COMMENT '背景图 file_id',
  `share_image_id` bigint                DEFAULT NULL COMMENT '分享图 file_id',
  `share_title`    varchar(64)           DEFAULT NULL COMMENT '分享标题',
  `share_desc`     varchar(128)          DEFAULT NULL COMMENT '分享描述',
  `sub_title`      varchar(128)          DEFAULT NULL COMMENT '副标题',
  `theme_color`    varchar(16)           DEFAULT NULL COMMENT '主题色 #RRGGBB',
  `rule_content`   mediumtext            COMMENT '活动规则，富文本HTML',

  -- ↓ 玩法特有、只透传不解析的 → JSON
  `extra_config`   json                  DEFAULT NULL COMMENT '按 activity_type 各自定义',

  `create_by`      varchar(32)           DEFAULT NULL COMMENT '创建人',
  `create_time`    datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_by`      varchar(32)           DEFAULT NULL COMMENT '更新人',
  `update_time`    datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_activity` (`activity_id`)
) COMMENT='活动C端展示配置';
```

**为什么垂直分表而不是往主表加列**：`t_activity_config` 是热表 ——
C 端每次进活动都要查状态和起止时间。而 `rule_content` 是富文本，几 KB 到几十 KB。
InnoDB 一个数据页 16KB，行越宽单页装的行越少，同样查询要读更多页；
而 MyBatis-Plus 默认 `SELECT *` 会把每次状态查询都拖上几十 KB 的规则文本。

**列 vs JSON 的划分标准只有一条**：

> 程序逻辑要读的、要检索的 → 独立列；纯透传给前端渲染的 → JSON。

**`extra_config` 的纪律**：后端**只存不解析**。一旦开始 `JSON_EXTRACT` 取值做业务判断，
它就退化成一堆没有约束的隐式契约，将来谁都不敢动。真需要后端读的，升格成独立列。

#### 三条必须遵守的约束

**① 图片存 `file_id`，绝不存 URL。**

存 URL 的代价：换 CDN 域名要洗全表、local 切 cloud 要洗全表、想要缩略图拼不出来。

那"将来推 CDN 的 JSON 里必须是绝对 URL"怎么办？——**编辑态存 fileId，发布态渲染成绝对 URL 快照。**
这正是编辑态/发布态分离的意义，而且白送一个好处：**已发布的活动页不受后续素材变更影响**。

**② 🔴 富文本里的图片必须建立引用关系。**

运营在富文本编辑器里插图，编辑器直接写入 `<img src="http://cdn/xxx.png">`。两个后果：

1. URL 硬编码进 HTML，换域名全废
2. **这些图片不在 `t_file_relation` 里，孤儿清理任务会把它们当垃圾删掉**

第 2 条是真正致命的：表现为活动上线三个月后规则说明里的图突然全变叉，
而且查不出是谁删的 —— 因为是定时任务按规则删的。

**落地方式**（不改编辑器，成本低）：保存 `rule_content` 时解析 HTML，提取所有 `img src`，
反查 `file_id`，写入 `t_file_relation`。

**③ 禁止 base64 内联图片。**

富文本编辑器粘贴图片默认转 base64。一张图几百 KB 塞进 `mediumtext`，几十个活动就把表撑爆，
将来推 CDN 的 JSON 也会大到离谱。编辑器配置里关掉，**后端保存时再校验一次**
（检测 `data:image/`）—— 前端配置会被人改回来，后端那道才是真的。

#### 现在不加版本/草稿字段

看似"顺手加个 `version` / `publish_status` 留着"很划算，实则是错的：将来的发布快照与本表
**内容形态不同** —— 本表存 fileId（引用），快照存渲染后的绝对 URL（值）。
所以版本化应该是独立的 `t_activity_display_version` 存渲染后 JSON，而不是本表的历史副本。

现在加那两个字段的结果是它们永远等于默认值，将来做版本时还要洗一遍。**留白比留错字段好。**

### 4.6 审计字段口径

项目里存在两套惯例：

```
activity.sql（营销中台，较新）  → create_by / update_by  varchar(32)
smart_admin_v3.sql（老模块）   → creator_id + creator_name + creator_user_type
                                deleted_flag（25 张表在用）
```

**新表统一用 `create_by` / `update_by varchar(32)`**，跟营销中台那套走。
`t_file` 保留 `deleted_flag`（与老模块邻居一致）。

🔴 **一个现在改成本为零的问题**：全项目**没有一处调用 `setCreateBy` / `setUpdateBy`**，
这两个字段至今全是 NULL，也就是说"存什么"从未定义过。因为没有存量数据，现在定是零成本的；
跑半年后再定就是一次数据清洗，还要处理"一半是名字一半是ID"。

**本设计定义为：存用户名。** 后台系统的操作人几乎不改名，直接可读的价值大于可 join 的价值 ——
运维排查、审计翻记录时一眼就知道是谁干的，不用再关联一次用户表。

**具体存哪个名字**：`t_employee` 同时有 `login_name`（登录账号，如 `zhuoda`）和
`actual_name`（员工名称，如「卓大」）两个字段，必须点明是哪一个。

> **存 `actual_name`，即 `RequestUser.getUserName()` 的返回值。**

依据是 `RequestEmployee.getUserName()` 直接 `return actualName`，项目里
`DataTracerService`、`FeedbackService`、`t_file.creator_name` 走的都是这个口径，跟着它走不会分裂。
宽度也对得上：`actual_name` 是 `varchar(30)`，`create_by varchar(32)` 装得下。

**已知取舍**：重名员工（两个「张伟」）在记录里无法区分。本模块的审计诉求是"大致知道谁传的"，
不是合规级追溯，这个精度够用。真需要精确追溯时，走 `t_data_tracer` 那条线，不靠这两个字段。

## 5. API 契约

### 5.1 `ObjectStorage` —— 纯基础设施

```java
public interface ObjectStorage {

    /** 写入。length 必须准确，S3 需要它算 Content-Length */
    void put(StorageKey key, InputStream in, long length, ObjectMeta meta);

    /** 读取。调用方负责关闭 */
    InputStream open(StorageKey key);

    boolean exists(StorageKey key);

    void delete(StorageKey key);

    /** S3 的 DeleteObjects 一次最多 1000 个，比 N 次 HTTP 快一个量级 */
    default void deleteAll(Collection<StorageKey> keys) {
        keys.forEach(this::delete);
    }

    StorageKind kind();
}
```

**刻意不提供 `putAll`。** HTTP PUT 本来就是一个对象一个请求，S3 没有批量 PUT，
做一个 `putAll` 只是把循环挪个位置，还顺手把"部分失败"的处理埋进了基础设施层。
DELETE 有真正的批量 API，所以它值得。

**能力用独立接口表达，不塞进大接口**：

```java
public interface PresignCapable {
    URI presignedGet(StorageKey key, Duration ttl, String responseContentDisposition);
}
```

只有 `S3ObjectStorage` 实现它。调用方 `if (storage instanceof PresignCapable p)` 显式分支 ——
比运行时才发现"本地模式下私有文件谁都能下"要好得多（缺陷 #3 就是这么来的）。

### 5.2 `StorageKey` —— 构造即校验

```java
public record StorageKey(String value) {
    public StorageKey {
        // 拒绝：空、前导斜杠、`..`、反斜杠、控制字符、连续斜杠、超长
        // 非法状态在这里就无法被表示，而不是散落在 download/delete 各处各防一遍
    }
}
```

这一条的收益比看上去大：**路径穿越、Windows 反斜杠（缺陷 #2）、中文未编码 ——
三类 bug 全部在构造函数里死掉。**

### 5.3 `FileService` —— 业务语义

```java
public interface FileService {
    FileRecord upload(MultipartFile file, String categoryCode, RequestUser user);
    BatchUploadResult uploadBatch(List<MultipartFile> files, String categoryCode, RequestUser user);

    void confirm(Collection<Long> fileIds, String bizType, Long bizId);   // TEMP → CONFIRMED + 建引用
    void releaseRelation(String bizType, Long bizId);

    FileDownload openForDownload(Long fileId);       // 返回流，不是 byte[]
    Map<Long, URI> batchUrl(Collection<Long> fileIds, ImageVariant variant);
    PageResult<FileRecord> query(FileQuery query);   // 分类 / 标签 / 上传人 / 时间 / 文件名
}
```

### 5.4 批量：形态与错误模型

**上传批量 = N 次单传，前端控并发（建议 3~5）。** 不做「一请求多文件」，五条理由：

1. **失败隔离天然成立**。第 7 个炸了，前 6 个稳稳落地，只重试第 7 个。
2. **进度条天然成立**。一个大 multipart 请求只能给整体进度。
3. **重试天然成立**。
4. **不长时间霸占 Tomcat 线程**。
5. **不用为最坏情况放大 `max-request-size`** —— 那个口子对所有接口都开着。

对象存储没有事务，所谓"批量原子性"也是假的（要靠补偿删除，而补偿本身会失败）。
**`TEMP` 状态让这个问题自动消失**：失败就不 confirm，到期自动回收，比补偿事务优雅一万倍。

`uploadBatch` 保留在接口里只是为了服务端也能一次收多个（如果前端就那么调），
其错误模型与 SonicExcel 的导入完全同构：

```java
public record BatchUploadResult(
        List<FileRecord> succeeded,
        List<UploadFailure> failed        // index, originalName, reason
) {}
```

两条纪律，从 SonicExcel 那轮直接沿用：

- **返回 200 + 混合结果，不要返回 500**。批量里的失败是正常业务结果，不是异常。
- **失败项必须能被精确定位**（第几个、原名、原因）。"传了 10 个成功 7 个"不说是哪 3 个等于没说。

**`batchUrl` 必须是真批量**（修缺陷 #9）：一次查库 + 一次 Redis mget + 批量签名。
现有实现对 100 个私有文件冷缓存是 1 次批量查 + 100 次 Redis + 100 次单条 DB + 100 次 HMAC。

## 6. 错误模型

**存储层不认识 `ResponseDTO`** —— 它是 HTTP 响应结构，存储层返回它就意味着这层只能被 Controller 调。

```java
public sealed interface StorageFailure {
    record NotFound(StorageKey key)        implements StorageFailure {}
    record QuotaExceeded(long limitBytes)  implements StorageFailure {}
    record Unreachable(String endpoint)    implements StorageFailure {}
    record Corrupted(String reason)        implements StorageFailure {}
}
```

做成 sealed 是为了让业务层的 `switch` 被编译器检查完整性 —— 与 `SonicErrorPolicy`、`RowConstructor` 同一个模式。
业务层 catch 后翻译成 `ResponseDTO`，**翻译只在 Controller 层发生一次**。

## 7. 关键实现要点

### 7.1 storageKey 生成规则

```
{categoryCode}/{yyyyMM}/{dd}/{id}.{ext}
banner/202608/09/1954823001234567.png
```

四条硬规则：

1. **key 里不含任何用户输入**，一个字符都不行
2. **扩展名从嗅探出的 MIME 反推，不从用户文件名取**（修缺陷 #5）。
   用户传 `evil.html` 而内容是 PNG → 存成 `.png`。**这一条直接掐死存储型 XSS**，比事后拦截可靠
3. **id 时间有序**。**不要 UUIDv4** —— 随机分布会打散对象存储的前缀分片，且不可排序，排查问题时没法按时间扫。

   > ⚠️ **本条已于实施时订正**：初稿写的是"直接用现有的 `SnowflakeIdGenerator`"，**那是错的** ——
   > 它在 `common-api` 模块，而 `common-api` 反过来依赖 `sa-base`（common-api/pom.xml:28），
   > sa-base 引它会成循环依赖。
   >
   > 实际实现见 `StorageKeyGenerator`：**9 位定宽 base36 毫秒时间戳 + 7 位 base36 随机**，
   > 不需要任何协调。定宽是关键 —— 变长 base36 在位数进位时会破坏"字典序 == 时间序"，
   > 9 位可用到公元 5138 年。随机部分 36^7 ≈ 7.8e10，同毫秒碰撞概率可忽略。
4. **日期分片是给运维的**：能让"清理 2024 年之前的孤儿"变成一次前缀列举，而不是全桶扫描

**MIME 判定统一走 Spring 的 `MediaTypeFactory`**（项目里 `SmartResponseUtil` 已在用），
删掉 `IFileStorageService.getContentType` 那张手写表（缺陷 #10），兜底 `application/octet-stream` 而不是 `""`。

### 7.2 校验三道关，顺序不能错

```
① 大小    ← 在读任何字节之前（Content-Length + 容器限制双保险）
② 真实类型 ← Tika 嗅探文件头，不信扩展名、不信 Content-Type
③ 扩展名  ← 从 ①② 的结果反推
```

顺序有讲究：类型嗅探要读字节，所以必须先卡大小，否则嗅探本身成了攻击面。

现有 `SecurityFileService` 的 Tika 白名单方向是对的，但有两个问题要一并修：
一是它挂在 `isFileDetectFlag()` 开关后面（应改为**始终开启**），
二是嗅探完之后存储用的扩展名还是从用户文件名取的 —— 等于白嗅了。

### 7.3 端到端流式

- 上传：`getInputStream()` 直接喂给存储层，不落中间 `byte[]`
- 下载：返回 `InputStream` / `StreamingResponseBody`，**不返回 `byte[]`**（修缺陷 #11）
- 下载支持 `Range` 请求 —— 大图和 PDF 的分段加载依赖它，事后加要改签名

显式配置 `spring.servlet.multipart.file-size-threshold`，别依赖默认值被人"优化"掉。

### 7.4 权限：visibility 进 DB，不进路径

`Visibility` 是**元数据**，存 `t_file.visibility`，不编码进 key（修缺陷 #8）。

| visibility | URL 形态 |
|---|---|
| PUBLIC | CDN / 静态 URL，永久有效，`Cache-Control: max-age=31536000, immutable` |
| PRIVATE | **后端下载接口** `/file/download/{fileId}`，走完整登录态鉴权 |

私有文件**不做免登录外发链接**（决策 #3），因此 `LocalFileStorage` 不需要实现签名 URL，
local 与 cloud 行为完全一致 —— 缺陷 #3 从根上消失。

分类可配 `default_visibility` 的能力本版**不做**（表已精简掉该字段），
新上传的 visibility 由业务代码按 categoryCode 决定。

### 7.5 Content-Disposition：RFC 6266 双写法

```
Content-Disposition: attachment; filename="download.png"; filename*=UTF-8''%E5%B9%B4%E4%BC%9A.png
```

修缺陷 #4。现有 `URLEncoder.encode` 是 `application/x-www-form-urlencoded` 编码而非 RFC 3986
percent-encoding：空格变 `+`（代码里手工 replace 了），`*'()!~` 处理对不上，
**逗号和分号不转义 → 文件名里带分号就能截断这个 header**。

**云端上传时不要把 disposition 写进对象元数据**（现在 `FileStorageCloudServiceImpl:116` 是写死的）。
一旦烧进去就固定了，想让图片/PDF 在线预览（`inline`）得重新上传或 copyObject。
正确做法是在预签名时用 `response-content-disposition` 查询参数按次覆盖 —— 同一对象，
下载给 attachment、预览给 inline，零成本。

### 7.6 🔴 永不覆盖

**换图 = 传新文件（新 key）+ 改业务引用。绝不覆盖同一个 key。**

公开素材挂 CDN，覆盖同 key 意味着每次换图都要刷 CDN —— 刷新有延迟、有配额、有时刷不干净，
最终表现为"我明明换了图，有的用户看到新的有的看到旧的"，排查一整天。

白送两个好处：CDN 可设 `immutable`；换错了能一键改回上一个 fileId。

**这条同时是「活动配置推 CDN」的前置条件**：JSON 里的图片 URL 一旦推上 CDN 就再也改不动了，
所以 key 必须不可变。本版虽然不做发布链路，但这条约束现在就要立。

### 7.7 生命周期：TEMP / CONFIRMED

```
上传成功 → status = TEMP
业务提交表单 → confirm(fileIds, bizType, bizId) → status = CONFIRMED + 写 t_file_relation
定时任务 → 删除 status = TEMP 且 create_time < now - 7d
```

**为什么必须有**：用户在表单里选了文件（已上传）然后关掉页面没提交 ——
这个文件永远没人引用，也永远不会被删。跑几年后存储里一半是垃圾，而且**你无法区分哪些是垃圾**。

**窗口定 7 天而不是 24 小时**：运营周三传素材、周五配活动、下周一发布是常态。
24 小时会把还没用上的素材清掉，这种事故很难解释。做成配置项。

**这个约定必须第一天就定好** —— 事后补等于把所有存量文件当成 CONFIRMED，垃圾永远清不掉。

物理删除必须先查 `t_file_relation` 确认无人引用（`idx_file` 就是为此存在的）。

### 7.8 图片处理

运营素材场景的刚需，不是可选项：素材库列表 50 张原图 × 3MB = 150MB 流量，页面直接卡死。

| 能力 | 优先级 | 本版 |
|---|---|---|
| 缩略图 | 高 | ✅ |
| 尺寸校验（banner 必须 1920×640） | 高 | ✅ 应用层，按 categoryCode 配 |
| WebP 转换 | 低 | ❌ v2 |

接口要能接变体参数，形状现在定死，事后加会改遍所有调用点：

```java
URI url(FileRecord file, ImageVariant variant);   // ORIGINAL / THUMBNAIL / 自定义宽高
```

云端走 OSS 的 URL 实时处理参数；本地实现忽略该参数（或用 Thumbnailator 生成后缓存）。

**一个实现细节**：读图片尺寸**不要用 `ImageIO.read()`** —— 那会把整张图解码进堆，
一张 6000×4000 的 JPEG 解码后约 96MB。用 `ImageReader.getWidth(0)`，只读文件头几十字节。

## 8. 配置项

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB        # 决策 #5
      max-request-size: 12MB     # 必须 > max-file-size
      file-size-threshold: 0     # 显式写出，全部落临时盘

file:
  storage:
    mode: local                  # local / cloud
    temp-file-retention: 7d      # TEMP 状态保留期（§7.7）
    max-batch-count: 20          # 单次批量文件数上限
```

🔴 **现状是反的**：`max-file-size: 20MB` 比 `max-request-size: 10MB` 大，
传 15MB 文件会过了前者倒在后者上。必须一起改。

`max-request-size` 不能等于 `max-file-size` —— multipart 的 boundary、其他表单字段、header
都算在请求体里，设成相等会出现"9.9MB 的文件传不上去"的玄学。留 2MB 余量。

**这里能看出「批量 = N 次单传」这个决策的直接收益**：单请求永远只有一个文件，
所以 request-size 只需略大于 file-size。若做了「一请求多文件」，这里要开到 100MB+，
而这个口子对**所有接口**都是敞开的。

**10MB 的推论**：不支持视频素材。活动短视频随便 30~50MB，将来要传只能走 v2 的客户端直传，
不能靠调大这个值 —— 调大等于给所有接口开 DoS 口子。

## 9. 迁移方案

### 9.1 分类：枚举 → 表，ID 对齐让风险接近零

```sql
-- ① 内置分类的 ID 直接对齐现有 folder_type 的值
INSERT INTO t_file_category (category_id, category_code, category_name, sort) VALUES
  (1,'COMMON','通用',10),(2,'NOTICE','公告',20),
  (3,'HELP_DOC','帮助中心',30),(4,'FEEDBACK','意见反馈',40);

-- ② 平移，值天然相等
ALTER TABLE t_file ADD COLUMN category_id bigint NULL;
UPDATE t_file SET category_id = folder_type;

-- ③ 保留 folder_type 一个版本双写，观察一轮再删
```

新旧编号是同一个数，任何漏改的地方结果都一样。

### 9.2 存量文件

```sql
ALTER TABLE t_file
  CHANGE `file_key`  `storage_key`   varchar(200) NOT NULL,
  CHANGE `file_name` `original_name` varchar(200) NOT NULL,
  MODIFY  `file_size` bigint NOT NULL,
  ADD COLUMN `storage_kind` varchar(16) NOT NULL DEFAULT 'LOCAL',
  ADD COLUMN `status`       tinyint     NOT NULL DEFAULT 2,   -- 存量一律 CONFIRMED
  ADD COLUMN `visibility`   tinyint     NOT NULL DEFAULT 1,
  ADD COLUMN `deleted_flag` tinyint     NOT NULL DEFAULT 0,
  ADD COLUMN `content_type` varchar(100) NOT NULL DEFAULT 'application/octet-stream',
  ADD COLUMN `extension`    varchar(16)  NOT NULL DEFAULT '',
  ADD COLUMN `content_hash` char(64)     DEFAULT NULL,
  ADD COLUMN `image_width`  int          DEFAULT NULL,
  ADD COLUMN `image_height` int          DEFAULT NULL,
  ADD COLUMN `tags`         varchar(500) DEFAULT NULL;

UPDATE t_file SET storage_kind = '<当前环境的实际存储>';   -- ⚠️ 按环境填，别一刀切
UPDATE t_file SET extension = SUBSTRING_INDEX(storage_key, '.', -1);
UPDATE t_file SET visibility = 2 WHERE storage_key LIKE 'private/%';
```

**存量 `status` 一律置 CONFIRMED**，否则定时任务会把历史文件全删了。

### 9.3 业务表的逗号附件

存量 `NoticeEntity.attachment` 等字段拆进 `t_file_relation`。
**双写一个版本**：新代码写关联表、旧字段同时保留，观察一轮再摘。

3. **展示配置接口原按 `activityId` 寻址** —— 前端拿不到 id（`wizardCreate` 只返回 code）。
   改为 `activityCode` 寻址，code→id 的换算在 Service 里做。
