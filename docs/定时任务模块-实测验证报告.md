# 定时任务模块 实测验证报告

> 配套设计文档：`docs/定时任务模块-重构技术方案.md`（v4 终稿）
> 验证日期：2026-08-12 · 环境：dev（MySQL + Redis，单机双实例）
> 结论：**8 个缺陷全部由实跑发现，编译期一个都发现不了。**

---

## 0. 一句话结论

**编译通过 ≠ 能跑。**

三档实现全部完成时的状态是：后端 `BUILD SUCCESS`、前端 `vite build` 通过、
方案经过四轮评审。就在这个「全绿」的状态下，第一次真环境启动就暴露出
**3 个缺陷，其中一个让整条链路 100% 失效**。七轮实测下来共 8 个。

更要紧的是它们的**形状**：8 个里有 3 个属于「整条链路失效」，
而它们无一例外都以**自洽的假象**存在 —— 界面正常、日志正常、没有异常，
只是事情不再发生。其中一个甚至会主动告诉你「上一次执行尚未结束」，
指向一个根本不存在的上一次。

| 类型 | 数量 | 代表 |
|---|---|---|
| 🔴 整条链路失效 | 3 | 手动/重试永远阻塞、重试记录卡死 RUNNING、多节点自举重复插入 |
| 🔴 语义错误 | 2 | 提前 5 秒执行（jitter 被抵消）、MISFIRE 列表页看不见 |
| 功能价值归零 | 2 | 实时日志被 DEBUG 淹没、对不打日志的执行器无用 |
| 观测盲点 | 1 | BLOCKED 记录不记判定节点 |

## 1. 缺陷清单

### 缺陷 1 🔴 手动 / 重试路径永远被判阻塞

**现象**　`_jobZombieScan` 只跑 6~11ms，手动触发却返回
「上一次执行尚未结束，按阻塞策略丢弃本次」（`status=5 BLOCKED`）。

**根因**　`handlePendingLog` 的执行顺序：

```
② preemptPendingLog → 把这条记录自己置成 status=1 (RUNNING)
③ isBlocked → countRunning 数该任务的 RUNNING 记录 → 数到了自己
```

**手动触发与失败重试两条路径 100% 跑不起来**，而界面提示指向一个不存在的上一次。
定时路径没有这个问题（`dispatch` 里是先判阻塞、再插 RUNNING 日志）。

**修法**　`countRunning` 增加 `excludeLogId` 参数。选择排除自身而不是调整顺序，
是因为自我排除在任何调用顺序下都成立，不依赖调用方的时序假设。

---

### 缺陷 2 🔴 预读窗口导致提前执行

**现象**　`schedule_delay_ms = -5000`，负的调度延迟。

| logId | 原定触发 | 实际开始 | 延迟 |
|---|---|---|---|
| 7959 | 08:00:**06** | 08:00:**01** | **-5000ms** |
| 7958 | 08:00:**05** | 08:00:**00** | **-5000ms** |

**根因**　扫描条件是 `next_trigger_time <= dbNow + 5s`（预读窗口，本意是避免边界抖动）。

三个连锁后果：

1. **任务真的提前 5 秒执行** —— 对 `ONE_TIME` 就是「活动提前 5 秒开」，
   正是 jitter 注释里明确说不能干的事；
2. **`schedule_delay_ms` 变成负数**，「延迟持续增长 = 该扩容」这个信号直接失效；
3. 🔴 **把 jitter 的打散效果整个抵消** —— 上表里 `triggerTime` 是 `:05` / `:06`，
   说明 jitter 正确地把两个任务错开了，可预读又把它们一起拽回 `:00` / `:01` 执行。
   **打散做了，等于没做。**

**修法**　删掉预读窗口，连 `scanPreloadSeconds` 配置项一起删 ——
**留一个不起作用的旋钮比没有更糟**，会让人以为调它有用。
扫描间隔本就是 1 秒，不预读的最大迟到也就 1 秒，远比提前执行安全。

**修复后**：延迟归正为 0ms / 1000ms，且两个任务真正错开到 `:05` / `:07` 执行。

---

### 缺陷 3　实时日志被框架 DEBUG 噪音淹没

**现象**　一次 6 毫秒的任务采集到 16 行，级别分布 **15 DEBUG : 1 INFO** ——
94% 是 MyBatis 的 SQL 日志，执行器自己那句话只占 1 行。

**为什么是缺陷**　缓冲区只保留最后 2000 行（`LTRIM`），
一个跑上万次查询的批处理会把执行器真正想说的话**整个挤出去**。
而设计注释里写的理由是「排查时最有价值的通常是最后那几行」——
这个前提被 DEBUG 噪音直接推翻：最后 2000 行全是 SQL，点开「查看实时日志」
比不看更浪费时间，因为你会先花十分钟翻完它。

**修法**　Appender 增加级别阈值，默认 `INFO`，可配 `smart.job.log-collect-level`。
**修复后**：16 行 → 1 行，100% 有效信息。

---

### 缺陷 4　MISFIRE 在列表页看不见

**现象**　一个昨晚被 SKIP 掉的任务，在列表页显示「最后一次：**无**」。

**为什么是缺陷**　MISFIRE / BLOCKED 走 `saveLogOnly`，刻意不回写
`last_execute_log_id`（当时的理由是「最后一次执行」不该包含被丢弃的）。
但站在运营视角，「无」等于「从没跑过」，而真相是「昨晚跳过了」——
要点开日志抽屉逐个任务翻才能发现。

**这把「让漏跑可见」只做了一半**，而那正是整个重构最核心的可观测性收益。

**修法**　回写 `last_execute_log_id`（最后一条**记录**），
但仍不回写 `last_execute_time`（最后一次**真正执行**）—— 两列语义刻意分开。

---

### 缺陷 5　实时日志对不打日志的执行器毫无价值

**现象**　加了 INFO 阈值后，一次执行只采到 1 行，而且是框架打的「执行完毕」。

**为什么是缺陷**　内置任务都只「返回摘要」不打进度日志，
而**摘要只在跑完之后才有，救不了「正卡着」的场景** ——
恰恰是任务卡住时最需要看日志。

**修法**　写进 `SmartJob` 接口约定：**长任务必须在循环里打 INFO 级进度日志**。
「已处理 N/M 条」这种一行日志，是任务卡住时唯一的线索。

---

### 缺陷 6 🔴🔴 重试记录插不进去 → 整条记录永久卡在 RUNNING

**现象**　`_devFailJob` 抛异常后，记录停在 `status=1 RUNNING`，
耗时 0ms、无错误详情，20 秒后仍如此。

**根因**（由实时日志功能自己给出，全程没看服务器日志）：

```
08:17:16.674 INFO  第 0 次尝试 bizDate=2026-08-12
08:17:16.684 ERROR 执行失败：IllegalStateException 故意失败
08:17:16.821 ERROR 执行记录落库失败：Field 'execute_start_time' doesn't have a default value
```

`execute_start_time` / `ip` / `process_id` / `program_path` 四列 `NOT NULL` 无默认值，
而一条**还没开始执行**的 PENDING 记录本就没有这些值。

🔴 **致命的是连带效应**：置 FAIL 与插 PENDING 在**同一个事务**里
（那是为防「重试静默丢失」刻意设计的），插入失败让整个事务回滚，
**连那条本该把状态改成 FAIL 的 UPDATE 也一起没了** ——
记录停在 RUNNING，而 RUNNING 又让阻塞判断永久误判为「上一次还在跑」，
**这个任务从此再也不会被执行**。

> **为防静默丢失而加的安全机制，自己成了放大器。**

**修法**　`v3.59.0` 让这四列可空。**没有用占位值糊过去** ——
手动触发路径原本就是靠 `ip='-'`、`execute_start_time=now` 硬填的，
那是在数据里写谎话（列表页会给一条根本没跑的记录显示「开始时间」），
而且第三条创建 PENDING 记录的路径迟早再撞一次同样的墙。
正解是让模型说实话：**没开始执行，这几列就是 NULL**。

---

### 缺陷 7　内置任务自举是跨节点的 check-then-act

**现象**　（纯推演发现，未真跑出来）

**根因**　`ensure()` 先 `selectByHandlerName` 判断不存在、再 insert，
而 `handler_name` 上**没有**唯一约束（刻意的：同一执行器允许挂 N 个任务）。
两个 WORKER 同时启动 → 三个系统任务**各被插两份**，同一份工作被两条配置各跑一遍。

🔴 **单节点下这个竞态永远不会显形** —— 它只在扩容到第二个节点的那一刻爆发，
而那通常是线上高峰期。

**修法**　系统任务改用**由 handler 名派生的确定性编码**，
让已有的 `uk_job_code` 变成天然幂等键（谁先插谁赢，输的吃 `DuplicateKeyException` 并跳过）。
不引新锁。

> **这一条揭示了一类模式**：凡是「先查不存在、再插入」的自举 / 初始化代码，
> 在多节点下都是错的，而单节点测试对它完全免疫。**同类代码值得全项目扫一遍。**

---

### 缺陷 8　BLOCKED 记录不记判定节点

**现象**　跨节点阻塞测出来了，但那条 BLOCKED 记录的 `process_id` 为空 ——
**无法区分「跨节点阻塞」与「同节点阻塞」**。

**为什么要区分**　排障时这个差别很关键：跨节点说明 DB 兜底那层在工作，
同节点则可能是 Redis 快判没生效。

**修法**　日志表链路的 BLOCKED 分支补 `fillNodeInfo`。

⚠️ **本条修复未经实测**：验证它需要重新加一个 sleep 型执行器再走一轮
「加代码 → 重启 → 测 → 删 → 重启」，为一个诊断字段不划算。
改动是 1 行、只影响诊断字段、不改变任何行为，但**账要记明白**。

## 2. 已验证通过的机制

### 2.1 注册与装配

| 机制 | 证据 |
|---|---|
| handler 名注册对代理免疫 | `handlerClassName` 是真实类名，未被 CGLIB 污染 |
| 启动双向对账 | 4 个 handler 全部注册，无漏报 |
| 🔴 **角色拆分** | WORKER 节点上 `/support/job/handler/list` 返回 `NoResourceFoundException` —— **管理接口物理上不存在** |
| 自举入库 | 3 个系统任务自动创建，编码符合铁律 8（`OKHKUQ5G6K` 等） |
| 预设展开 | FAST→LIGHT、SLOW→NORMAL，档位与车道兼容性校验生效 |
| 参数 schema | `@JobParam` 声明经注册表透出到下拉表单 |

角色拆分这条最有分量：**它是整个重构的起点**（设计文档 §1.1 ——
原来管理接口与执行被 `enabled` 焊死，「业务节点不跑任务但仍能管理任务」物理上做不到）。
现在这条路是通的，独立部署可行。

### 2.2 调度内核

| 机制 | 证据 |
|---|---|
| 车道路由 | 线程名 `smart-job-fast-3` / `smart-job-slow-1` |
| 抢占推进 | `next_trigger_time` 逐轮前进，停机后不卡在过去 |
| jitter 确定性打散 | 两任务稳定错开到 `:05` / `:06` |
| 调度延迟指标 | 修复后 0ms / 1000ms（1 个扫描周期内） |
| 🔴 **跨节点抢占分配** | 同批 3 个任务：`pid=1804` 抢 2 个、`pid=30944` 抢 1 个 |
| 🔴 **零重复执行** | 全库 54 条记录，`(job_id, trigger_time, retry_seq, trigger_source)` 全部唯一 |

### 2.3 失败与恢复

| 机制 | 证据 |
|---|---|
| 失败重试链 | `retrySeq` 0→1→2，`retry_of_log_id` 链完整，间隔精确 5s，第 3 次后停止 |
| 三条硬约束 | 三条记录的 `trigger_time` / `biz_date` / `trigger_source` 完全一致（原样继承）；**「没有第 4 条」同时反证了 FAIL 记录的 `fire_time` 确实留了 NULL** —— 否则扫描线程会每秒把它们重新捞起 |
| 僵尸回收 | 缺陷 6 留下的 RUNNING 记录被置为 `INTERRUPTED`，**并沿用同一套重试状态机**产出 `retrySeq=1/2` —— 证明「一个状态机能表达的事不要写第二个」没有在 `retry_seq` 推进上打架 |
| 连续失败计数 | 6 次失败后 `continuous_fail_count = 6`，健康自检连续三轮报出告警 |
| 列表页最后一次 | 指向重试链**末端**（`retrySeq=2`）而非首次失败 |

### 2.4 阻塞与超时

| 机制 | 证据 |
|---|---|
| 阻塞判定（DB 兜底层） | 跑 30s 的任务占住车道（`SUCCESS`，30273ms），6 秒后第 2 次触发被判 `BLOCKED` |
| 🔴 **超时中断** | 阈值 5s、sleep 30s → `status=4 TIMEOUT`，耗时 **5004ms**（误差 4 毫秒） |
| 超时与失败分开 | 落成 `TIMEOUT` 而非 `FAIL` —— 两者处置方式完全不同：超时该调参数或拆批次，失败才要查 bug |

⚠️ **一个必须写清楚的细节**：这次中断实际是 `TimeUnit.sleep()` 抛
`InterruptedException` 生效的，而不是走 `ctx.checkCancelled()`
（后者兜的是「两片之间」被取消的情况）。两条路都通向 TIMEOUT，
但**纯 CPU 死循环、既不 sleep 也不查中断标记的执行器，依然砍不掉** ——
不能因为「测出来能砍掉」就以为万事大吉。

### 2.5 运营侧

一键重跑（沿用原 `param_snapshot` 与 `bizDate`）、终止对非执行中记录的人话拒绝、
实时日志采集与级别过滤、任务删除、`traceId` 贯通。

## 3. 两次意外收获

### 3.1 一次非人为构造的真实 misfire

验证过程中服务意外停了约 9 小时（08:55 → 18:06）。重启后系统**自己**发现并记录了漏跑：

```
_jobHealthCheck  status=6  错过调度窗口，按 SKIP 策略跳过。原定触发 2026-08-12T09:00:06
_jobZombieScan   status=6  错过调度窗口，按 SKIP 策略跳过。原定触发 2026-08-12T09:00:05
_jobLogClean     status=2  （次日 03:00 才到点，停机期间本就不该跑 → 无误报）
```

四件事同时成立：**漏跑留痕**、**时间轮正确推进**（`next_trigger_time` 推到
18:10:05/06 而非卡在过去）、**jitter 依然错开**、**没有误报**。

**这比任何人为构造的用例都有说服力。** 放在重构前，这 9 小时里漏掉的每一次调度
都会**无痕消失** —— 运营永远不会知道昨晚那次统计没跑。

### 3.2 实时日志功能自证了价值

缺陷 6 的根因是**它自己给出的**，全程没有翻服务器日志。三行、全是信号、零噪音 ——
缺陷 3 那个级别阈值的价值在这里直接兑现（修复前这里会是几十行 MyBatis SQL 夹着关键的三行）。

同时它证明了缺陷 5 那条约定不是空话：`_devFailJob` 是唯一打进度日志的执行器，
**没有它那句 `第 N 次尝试`，根本看不出是哪一次重试失败的**。

## 4. 仍未验证的部分

| 项 | 为什么没验 |
|---|---|
| `FIRE_ONCE` 补跑策略 | 与 misfire 同源但走另一分支，需再造一次停机 |
| 背压跳过 | 需把慢车道压满 |
| 告警抑制窗口 | 需连续观察 1 小时以上 |
| 缺陷 8 的修复 | 需重新加 sleep 型执行器走一轮，为一个诊断字段不划算 |
| `uk_job_trigger` 兜底本身 | **实测中它一次都没被触发** —— 乐观锁抢占从未漏过。这是好事，但也意味着**兜底机制自己没被考验过**；要验它得人为制造时钟跳变或网络分区，成本不划算 |

## 5. 由用户修正的一处设计错误

设计文档 §4.2 与实现里原本用 `ObjectProvider<SmartJob>` 注入执行器，
但在 `@Bean` 方法里**立刻**调了 `orderedStream().toList()` ——
**延迟了注入、没延迟解析，等于没用**，与 `SmartJobZombieScanHandler`
（它自己就是 `SmartJob`，构造又依赖注册表）形成循环依赖。

正解是把 `ObjectProvider` 原样传进注册表，解析推迟到 `afterSingletonsInstantiated()` 里 ——
那时所有单例已创建完毕，**对账看到的仍是完整集合**
（不像 `@Lazy` 那样会让对账在 handler 没注册全时就跑，而那种残缺是不会报错的）。
