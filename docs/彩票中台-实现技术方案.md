### 0.1 in-DOM 模板的正解是 x-template，不是逐个属性改 kebab（2026-07-27 实测）

铁律 6 记的是「camelCase 属性要写成 kebab」。修这份原型时发现**这条规则只覆盖了一半，剩下一半根本没有 kebab 解法**：

| 写法 | 浏览器小写后 | 能否 kebab 绕过 | 后果 |
|---|---|---|---|
| `:customRow` / `:rowClassName` / `valueFormat` / `:maxLength` | `customrow`… | ✅ 能。Vue 会把 `custom-row` camelize 回 `customRow` 去匹配 prop | 行点击、时间回填、长度限制失效 |
| `v-model:activeKey` | `v-model:activekey` | ✅ 能（`v-model:active-key`） | Tab 默认值失效——`activeTab` 明明是 `'issues'`，页面却停在第一个 Tab |
| **`#bodyCell`** | `#bodycell` | ❌ **不能**。**Vue 不会 camelize 插槽名**，antd 查的是 `slots.bodyCell`，永远匹配不上 | **表格所有自定义列渲染成空白** |

最后一行是这次真正的收获：**插槽名没有 kebab 退路**。而它的表现最欺骗人——期号列因为 `dataIndex` 恰好是真实字段，会走默认渲染显示出来，看着「表格是好的」，其余四列（时间/进度/开奖号码/操作）全是空白，**且不报任何错**。

**正解：把整个模板挪进 `<script type="text/x-template">`。** script 标签的内容浏览器按纯文本存储、不做 HTML 解析，驼峰原样保留，一次性堵死整类问题，不用逐个属性打地鼠：

```html
<div id="app" v-cloak class="min-h-screen p-4"></div>
<script type="text/x-template" id="app-template">
  ... 原样的模板，驼峰照写 ...
</script>
<script>
  const App = { template: '#app-template', setup() { /* ... */ } };
</script>
```

**实测验证**（浏览器实跑，非推断）：自定义列全部渲染、Tab 正确停在「生命周期与开奖大盘」、点击行选中并联动右侧操作台、`clickable-row` 类生效、`maxlength=5`、日期 `value-format` 往返正确、console 零错误。

> 这条只针对 CDN 直写 HTML 的原型。**SFC（.vue）编译期处理模板，完全不受影响**，Vue 组件里 `#bodyCell` 照常写。

### 0.2 顺带修掉的一个线上 bug：`TicketStatusEnum.getValue()` 恒返回 null（2026-07-27）

P0 收敛枚举时发现的，与彩票新功能无关，但**现在就在影响已上线的接口**。

`LotteryRecordQueryForm.winStatus` 挂了 `@CheckEnum(TicketStatusEnum.class)`，而校验器 `EnumValidator` 是这样建合法值白名单的：

```java
enumValList = Stream.of(enumClass.getEnumConstants()).map(BaseEnum::getValue).collect(toList());
```

`TicketStatusEnum` 的字段叫 `code` 而不是 `value`，于是 Lombok 的 `@Getter` 生成不出 `getValue()`；作者补了一个手写实现，但**直接 `return null`**。结果白名单是 `[null, null, null]`，`isValid` 里 `enumValList.contains(0)` 恒为 false ——
**按中奖状态筛选购彩记录，任何取值都会被判参数非法返回 400，只有不填才能过。**

修法：字段改名 `code` → `value`，用 `@Getter @AllArgsConstructor` 让 Lombok 生成 `getValue()`，删掉那个手写的 null 实现，以及另外两个只是原样调回父接口默认实现的 `equalsValue` / `equals` override（纯噪音）。对齐 `sa-base` 里 `GenderEnum` 的写法。
`IssueStatusEnum` 有同样的字段命名问题（且没实现 `BaseEnum`），虽然当前零引用，一并对齐，避免将来被 `@CheckEnum` 引用时重蹈覆辙。

**实测**（jshell 跑编译产物）：白名单从 `[null, null, null]` 变成 `[0, 1, 2]`，0/2 放行、9 拒绝。

**可复用的教训**：`BaseEnum` 这类「靠 getter 名字取值」的接口，一旦实现类字段命名不合、又用手写实现糊过编译，**编译器和 IDE 都不会报警**，故障只在运行期以「校验莫名不过」的形式出现。新增 `implements BaseEnum` 的枚举时，字段必须叫 `value`，不要手写 `getValue()`。

## 1. 核心：FPE 发号

### 1.1 为什么是 FPE 而不是号池

号池方案（预生成 10 万条塞表）已被 `lottery.sql` 否掉，理由成立：写放大、扩容困难、且「未售号码」本身是无价值数据。
FPE（Format-Preserving Encryption）把「第 N 个领号的人」这个**连续游标**加密成一个**看起来随机、但保证不重复**的号码：

```
sequence_no (0,1,2,3...)  --FPE(key=f(lotteryCode,issueNo))-->  ticket_number (85210, 03471, ...)
   ↑ 0-indexed，直接就是 FPE 的输入；Redis 游标是 1-indexed，换算见 §1.4.1
```

关键性质，逐条对应表设计：

- **双射** ⇒ 游标不重复 ⇒ 号码天然不重复。`uk_issue_ticket` 从「主要防线」降级为「兜底断言」。
- **不可预测** ⇒ 用户拿到 `85210` 也推不出下一个号，杜绝提前占号。
- **可逆** ⇒ 给定号码能反解出游标。客服验真、对账自证清白全靠它（这正是 `sequence_no` 列存在的意义：它不是「为了存」，是「为了能校验存的对不对」）。
- **无需号池** ⇒ `total_count` 直接物理限死预算，Redis 游标撞到上限即售罄。

### 1.2 算法选型：带 cycle-walking 的平衡 Feistel

```
N = 10 ^ numberLength                   // 号码空间，固定十进制，如 10^5 = 100000
a = ceil(sqrt(N))                       // 平衡拆分，域为 a×a ⊇ N

encrypt(x):
  L = x / a ; R = x % a
  repeat 6 rounds:  L, R = R, (L + F(round, R)) mod a
  y = L * a + R
  while y >= N: y = encrypt_once(y)     // cycle-walking，落在 [N, a²) 就再加密一次
  return y

F(round, R) = HMAC_SHA256(key, round || R) 的前 8 字节 mod a
key         = HMAC_SHA256(masterSecret, lotteryCode + "|" + issueNo)
```

三点说明：

1. **为什么平衡 + cycle-walking 而不是不平衡 Feistel**：平衡 Feistel 在 `Z_a × Z_a` 上无论 F 是什么函数都**恒为置换**（这是 Feistel 结构的代数性质，不依赖 F 的密码学强度）。不平衡版本要在两个不同模数间交替，边界条件容易写错，而写错的后果是**号码重复**——最不能出错的地方，选最难写错的写法。

   固定十进制后 cycle-walking 的开销可以精确算出来，全长度区间都是白菜价：

   | 号码长度 | N | a=⌈√N⌉ | a² | 期望加密次数 a²/N |
   |---|---|---|---|---|
   | ~~3~~ | ~~1,000~~ | ~~32~~ | ~~1,024~~ | ~~1.024~~（已被 §1.3 的下限排除） |
   | 4 | 10,000 | 100 | 10,000 | **1.000**（完全平方，零 walking） |
   | 5 | 100,000 | 317 | 100,489 | 1.005 |
   | 6 | 1,000,000 | 1,000 | 1,000,000 | **1.000** |
   | 7 | 10,000,000 | 3,163 | 10,004,569 | 1.0005 |
   | 9 | 10^9 | 31,623 | ~1.00001×10^9 | 1.00001 |

   偶数长度天然是完全平方数，一次 walking 都不会发生；奇数长度在下限收紧后最差也只有 0.5%。
   ⚠️ **不要图省事把 a 取成 `10^⌈L/2⌉`**（比如 L=5 取 a=1000）：那样域是 10^6，期望迭代次数会变成 **10 倍**。必须是 `ceil(sqrt(N))`。
2. **6 轮**：Luby-Rackoff 定理下 3 轮即 PRP、4 轮即强 PRP；小域下攻击面更大，取 6 留余量。纯内存 HMAC，单次耗时在微秒级。
3. **密钥不落库**（呼应 DDL 注释「0 密钥明文」「0 混淆盐值冗余」）：`masterSecret` 放 `sa-base.yaml`（四环境各一份），`issueNo` 天然充当 tweak/nonce——这就是原型里期号输入框标着「Nonce / 唯一盐值」的原因，也是表里不需要盐值列的原因。

   ⚠️ **两条由此产生的硬约束，必须写进代码注释和运营文案**：
   - `masterSecret` 一旦有期号发过号就**不可轮换**（轮换后旧期号的 `security_sign` 校验和号码反解全部失效）。
   - `issue_no` 创建后**不可修改**（它是 tweak，改了等于换密钥）。UpdateForm 里不放这个字段，前端编辑态禁用。

### 1.3 号码空间固定为十进制 ★

**决策：只发数字号码，字符集不是可配项。** 字母对彩票没有意义，而且有实打实的坏处：

- 用户要口播、手输、比对号码。`A7K9Z` 比 `85210` 难念难记，客服场景尤其痛苦。
- **`0/O`、`1/I`、`2/Z`、`5/S`、`8/B` 在多数字体下形近**。真开了字母，第一批客诉就是「我明明中了、你们说我号码不对」——而按 §1.1 的设计号码是可反解的，这类争议本来应该零成本自证清白，加了字母反而人为制造一类无法自证的纠纷。
- 号码空间也不缺：5 位数字就是 10 万个号，7 位是 1000 万，够用。

由此带来的简化，比"少写一个枚举"要实在得多：

- **不需要 `LotteryCharsetResolver`**，`engine/` 少一个类。base 恒为 10。
- **不需要碰 `DynamicNumbersGenerator`**。原本要为了「区间表达式 vs 字面字符列表」两套语义纠缠半天（§0 第 3 条），现在数字→字符串就是一句 `String.format("%0" + length + "d", n)`，连进制转换都不用写。
- 校验退化成一条：`10^numberLength >= total_count`，不满足拒绝保存。
- §1.2 的 cycle-walking 开销可精确列表（见上），偶数长度甚至为零。

**`number_charset` 列怎么处理**：保留列不动（不做 DDL 变更），当作预留扩展点，但

- 服务端保存时硬校验 `'0-9'`，其他值一律拒绝；
- **前端删掉字符集下拉**（原型 §102-108 那个 select 去掉），号码长度输入框旁边直接标注「纯数字」；
- 实体上给该字段写明「当前固定 `0-9`，为未来扩展预留，改动会破坏已发号码的 FPE 域」。

留列不留 UI，是为了避免「界面上摆着一个可选项，选了却报错」这种最伤运营信任的交互。

### 1.3.1 号码长度下限 = 4（号码空间不小于 1 万）★

**决策：`number_length ∈ [4, 9]`**，即号码空间 `N = 10^numberLength >= 10,000`。原型里号码长度输入框的 `:min="3"` 要改成 `4`。

这条约束一次性解掉了三个问题：

1. **小域下 FPE 的分布质量**。Feistel 的「不重复」是代数性质，域再小也成立；但「看起来随机」在小域下会打折扣（域越小，6 轮置换与理想随机置换的统计距离越明显）。1 万起步是个务实的安全线。
2. **cycle-walking 的最坏开销从 2.4% 降到 0.5%**（3 位那一行被排除，见上表）。
3. **号码可猜性**。3 位号码只有 1000 个，攻击者穷举一遍就能枚举全部有效号码；而这个系统的号码本身可反解、能自证真伪，号码空间太小会让「反解验真」这个能力失去意义——真中奖号码被穷举出来，验真也就挡不住冒领了。

落点（每一处都要写，否则运营从别的入口绕过去）：

- **后端**：`LotteryConfigAddForm` / `UpdateForm` 上挂 `@Min(4) @Max(9)`；聚合保存的 Service 里再校验一次 `10^numberLength >= totalCount`。
- **前端**：`<a-input-number :min="4" :max="9">`，提示文案「纯数字，4-9 位」。
- **常量同源**：`LotteryConst.MIN_NUMBER_LENGTH = 4` / `MAX_NUMBER_LENGTH = 9`，前端 `lottery-const.js` 同名导出（铁律 3）。

⚠️ **别把这条和 `total_count` 搞混**：`total_count` 本身仍可以很小（比如空间 1 万只发 500 张）。空间大而发行少反而是好事——号码在空间里稀疏分布，更难被猜中。下限约束的是**空间**，不是**发行量**。

### 1.4 领号运行态：游标绝不回滚

对比抽奖模块的双层扣减，彩票这里有一个**方向相反**的关键差异，必须显式说明：

> 抽奖的库存预扣失败要 `rollback` 回滚 Redis；**彩票的发号游标永远不能回滚**。
> 回滚游标 = 两个用户拿到同一个 `sequence_no` = 同一个号码 = `uk_issue_ticket` 冲突。
> **浪费一个号（留个空洞）是可接受的，发重号是不可接受的。**

链路：

```
幂等防重(requestId SETNX)
  → 防刷限流(RRateLimiter 单用户单彩票 2次/秒)
  → 期号校验(status=0 且 now 落在售卖窗口内)
  → Redis INCR 游标  ── 超过 total_count 即售罄，且【不回滚】
  → FPE 算号 + 计算 security_sign
  → DB 插入 t_lottery_record（uk_issue_ticket 兜底）
  → DB 条件更新 sold_count（WHERE sold_count < total_count）
```

链路里**没有资产扣减、没有单人限购校验**，这是刻意的：本模块是纯号码派发引擎，那两件事由上游业务负责（§8.1）。保留的幂等与限流防的是网络重试和恶意刷接口，与业务限购不是一回事。

- **游标 vs sold_count**：游标是「消耗掉的槽位数」，`sold_count` 是「真正发出去的张数」，恒有 `游标 >= sold_count`。**硬上限判定认游标**，`sold_count` 只用于展示和对账。这样即使中间失败留了空洞，也绝不会超发。
- **冷启动恢复**：Redis 游标 key 丢失时（重启/驱逐），用 Redisson 分布式锁保护，按 DB 现状 `SET NX` 回填，精确公式见 §1.4.1。
  这里踩过的坑要反过来用：交接文档第 3 轮压测的教训是「只重置 DB 等于没重置」；在彩票场景里失效模式更危险——**Redis 游标偏低会导致重号**。所以回源必须 `SET NX`（绝不覆盖）+ 取 `MAX` 而非 `COUNT`（有空洞时 COUNT 会偏低）。
- **DuplicateKeyException 兜底**：真撞上唯一索引，说明游标状态异常，当场重试下一个游标，最多 3 次，超出则告警并返回「系统繁忙」。不静默吞（交接文档里 `catch(DuplicateKeyException)` 空转的教训）。
- `security_sign` = `HMAC_SHA256(masterSecret, lotteryCode|issueNo|sequenceNo|ticketNumber|memberName)` 取前 32 位十六进制。列是 `varchar(32) NOT NULL` 且无默认值——**每次插入必须赋值**，否则 MySQL 严格模式直接拒绝（这是「NOT NULL 无默认值」模式的第 6 次候选，提前堵上）。

### 1.4.1 游标基准：Redis 1-indexed，`sequence_no` 0-indexed，只在一处换算 ★

**原方案在这里是错的**，记录下来避免重犯。原文写的是「`sequence_no` 从 0 开始」+ 冷启动 `SET NX COALESCE(MAX(sequence_no),0)+1`，两者对不上：

| 场景 | 原方案行为 | 问题 |
|---|---|---|
| 全新期号（key 不存在） | `INCR` 返回 **1**，直接当 `sequence_no` | 游标 0 永远用不到，白扔一个号 |
| 冷启动回填（`MAX=5`） | key 置为 6，下次 `INCR` 返回 **7** | 游标 6 被跳过，又一个空洞 |
| 卖到最后一张（`total_count = N = 10^L`） | `INCR` 返回 **N**，当 `sequence_no` 喂给 FPE | **越界**：FPE 定义域是 `[0, N)`，`N` 不在里面 |

前两条只是浪费号码，第三条是**真正的 bug**——在「发行量拉满」这个边界上会直接算错或抛异常，而且只在卖光最后一张时触发，测试极难覆盖。

**定案：**

- **Redis 游标天然 1-indexed**（`INCR` 对空 key 返回 1，顺着它来，不跟它拧着写）
- **`sequence_no` 存 0-indexed**，且**它就是 FPE 的输入，不再做任何加减**
- **换算只有一处**：`sequenceNo = cursor - 1`

```java
long cursor = redis.incr(LotteryCacheKey.sequence(lotteryCode, issueNo));
if (cursor > totalCount) { return 售罄; }        // 游标 1-indexed，上限判 >
long sequenceNo = cursor - 1;                    // 唯一的换算点
String ticketNumber = fpeCipher.encrypt(sequenceNo);  // 直接入 [0, N)，无需再调整
```

冷启动回填 SQL 相应改为：

```sql
-- key 置为「已消耗的游标数」，下一次 INCR 恰好接上；无记录时置 0，首次 INCR 得 1 → sequenceNo 0
SELECT COALESCE(MAX(sequence_no) + 1, 0)
  FROM t_lottery_record WHERE lottery_code = ? AND issue_no = ?
```

**为什么不采用「`sequence_no` 也从 1 开始」的写法**（这个提议本身能跑通，但换了个位置放风险）：那样 Redis 与 DB 的值确实完全对齐、冷启动写 `SET NX MAX(sequence_no)` 很干净，但 `sequence_no ∈ [1, total_count]`，喂给 FPE 前**必须再减 1**——于是 ±1 从 Redis 边界搬到了**加密边界**。这两个边界的容错完全不对等：

- Redis 边界算错 ⇒ 跳一个号，损失一个号码，可观测、可接受；
- 加密边界算错 ⇒ 越界或号码错位，**动摇的是「号码不重复」这个整个系统的立身之本**。

所以把换算固定在容错高的那一侧。配套加一条断言（`LotterySequenceService` 内 + 单测各一份）：**`0 <= sequenceNo < totalCount <= 10^numberLength` 恒成立**，任一条不满足直接抛异常而不是继续算号。

## 2. 开奖核销

### 2.1 奖级互斥：高奖级优先，一张票只中一次

规则表 `uk_lottery_level(lottery_code, prize_level)` 保证一个奖级一条规则。匹配语义：

- `EXACT`：全号相等
- `TAIL`：末 `match_length` 位相等
- `HEAD`：首 `match_length` 位相等

一张中了一等奖（全号）的票，必然也满足二等奖（尾 3 位）——所以**必须按 `prize_level` 升序逐级认领，且只认领 `win_status=0` 的票**。这是集合式 SQL 天然能表达的：

```sql
-- 按 prize_level ASC 逐条规则执行；win_status=0 的守卫天然实现「高奖级优先」
UPDATE t_lottery_record
   SET win_status = 2, prize_level = ?, prize_code = ?
 WHERE lottery_code = ? AND issue_no = ? AND win_status = 0
   AND RIGHT(ticket_number, ?) = ?          -- TAIL；HEAD 用 LEFT，EXACT 用 ticket_number = ?
 LIMIT ?;                                    -- 分批

-- 全部规则跑完后，剩下的一律未中奖，奖级统一落 99（不是 NULL）
UPDATE t_lottery_record SET win_status = 1, prize_level = 99
 WHERE lottery_code = ? AND issue_no = ? AND win_status = 0 LIMIT ?;
```

- **不要把 10 万条记录捞进 Java 循环判定**。上面的写法在 DB 内完成，`idx_status(issue_no, win_status)` 能把扫描面收敛到「尚未判定」的那部分，且每跑一条规则集合就变小。
- `prize_code` 在此刻**快照写入**记录（见 §0 第 5 条）。规则表后续被改不影响已开奖的期。

### 2.1.1 未中奖的奖级 = 99

C 端「我的号码」要按奖级排序展示（一等奖排最前、未中奖沉底）。若未中奖是 `NULL`，MySQL 的 `ORDER BY prize_level ASC` 会把 NULL 排到**最前面**，正好排反，于是前端不得不写 `ORDER BY prize_level IS NULL, prize_level` 这种绕弯的表达式，或者在 JS 里二次排序。直接落 99 让排序退化成一个朴素的 `ORDER BY prize_level ASC, id DESC`。

- DDL 把默认值也改成 99（见 §4），这样**刚领到、还没开奖**的号码天生就沉底，不用等核销来纠正排序。
- 99 是魔法值，按铁律 3 收敛为具名常量：后端 `LotteryConst.PRIZE_LEVEL_NONE`，前端 `constants/business/lottery/lottery-const.js` 同源导出。规则表的 `uk_lottery_level` 不会挡住它——99 只写在 record 上，不会成为一条真实奖级。
- 配套约束：奖级规则里禁止配置 `prize_level = 99`（服务端保存时校验），否则「未中奖」和「99 等奖」在 C 端无法区分。

### 2.2 `status=1 部分开奖` 的真正用途：可恢复的核销检查点

DDL 给期号留了 `1-部分开奖` 这个中间态。已确认**一期只开一次奖，这个状态值目前纯属预留**——那就把它用作**核销事务的断点续跑标记**，一个预留位刚好补上一个真实需要的语义，两不冲突：

```
0 待开奖  --[条件更新: WHERE status=0，抢到才继续]-->  1 核销中(winning_number 已定案)
   ↓ 分批执行 §2.1 的 UPDATE（每批独立事务）
2 已开奖  --[全部批次完成，写 settle_time]-->
```

- **并发闸门**：`UPDATE ... SET status=1, winning_number=? WHERE id=? AND status=0`，`rows=0` 直接退出。两个运营同时点开奖，第二个人什么也不会发生（对齐提案域审批的做法）。
- **幂等可恢复**：中途宕机后重跑，`winning_number` 已定案不会变，而 §2.1 的 `win_status=0` 守卫使得重复执行天然幂等，接着跑完即可。
- **不搞长事务**：10 万行一个事务会把 undo log 和锁撑爆。分批（建议 2000 行/批）+ 每批独立事务。
- `settle_time` **没有** `ON UPDATE CURRENT_TIMESTAMP` 兜底 ⇒ 按铁律 9 必须在 SQL 里显式写（同 `approve_time` / `first_review_time`）。

### 2.3 摇号必须在服务端

原型的 `generateRandomWinningNum()` 在浏览器里用 `Math.random()` 生成。**这条不能照搬**：开奖号码是资损敏感的，前端生成意味着运营（或抓包的人）可以自选号码。改为 `GET /lotteryIssue/randomNumber?issueId=`，服务端用 `SecureRandom` 生成，前端只负责展示与二次确认。手工录入的路径保留（运营可能要对齐外部彩票源），但服务端必须重校验：长度等于 `number_length`、且全部为数字字符（铁律 2）。

## 3. 派奖：接入既有公共链路

中奖记录 → `UserPrizeEvent` → `GlobalEventDispatcher` → `PrizeDispatchHandler` → 提案域 → 账务域。这条链路抽奖模块已压测跑通，彩票直接复用，**不新造轮子**。

- `sourceBizId` = `t_lottery_record.id`（`UserPrizeEvent` 的 javadoc 原文就是「来源单号（LotteryRecord的ID）」，契约本就为彩票预留）。配合 `t_prize_log.uk_external_biz` 做跨域幂等。
- `prizeType` / `prizeValue` / `prizeName` 查 `PrizeConfigService.getByActivityCodeAndPrizeCode(activityCode, prizeCode)`——**不要用 `getByPrizeCode()`**，交接文档明确它用了 `.one()`，跨活动复用编码时会抛 `TooManyResultsException`。
- **不在核销事务里逐条 publish**。一期可能有几千个中奖者，`GlobalEventDispatcher.dispatch` 现在挂着 `@Async`，一次性灌进有界线程池会打满队列。改为独立的分页派发任务：扫 `win_status=2 AND dispatch_status=0`，每批 200 条，批内 publish、批后置 `dispatch_status=1`。每批一个事务（`@TransactionalEventListener(AFTER_COMMIT)` 要求 publish 发生在事务内）。
- 新增 `dispatch_status` 列而不是靠「重复 publish + 唯一索引拦截」来幂等：后者每次重扫都要触发一次异常路径，而交接文档已经证明**基于异常的静默去重会掩盖真问题**。

## 4. DDL 增量（v3.40.0.sql）

> 版本号说明：`v3.38.0.sql`（时间戳时钟源）此前已被占用，`v3.39.0.sql` 是 P0 清掉号码池菜单的脚本，
> 所以彩票的 DDL 增量落在 **v3.40**。写脚本前先 `ls sql-update-log/` 确认，别再撞号。

```sql
-- 1. 期号：计划开奖时间 与 实际开奖时间分离（原型区分，表里只有一列）
ALTER TABLE `t_lottery_issue`
    ADD COLUMN `plan_draw_time` datetime DEFAULT NULL COMMENT '计划开奖时间' AFTER `sale_end_time`;

-- 2. 记录：中奖时快照奖品编码 + 派发状态 + 未中奖奖级默认 99（C端排序）
ALTER TABLE `t_lottery_record`
    ADD COLUMN `prize_code`      varchar(64) DEFAULT NULL COMMENT '中奖奖品编码（核销时快照，防规则变更后漂移）' AFTER `prize_level`,
    ADD COLUMN `dispatch_status` tinyint NOT NULL DEFAULT 0 COMMENT '派发状态：0-待派发/无需派发, 1-已投递, 2-投递失败' AFTER `prize_code`,
    ADD KEY `idx_dispatch` (`issue_no`, `dispatch_status`);

-- 未中奖/未开奖统一为 99，让 C 端 ORDER BY prize_level ASC 直接可用（NULL 会排到最前，正好排反）
UPDATE `t_lottery_record` SET `prize_level` = 99 WHERE `prize_level` IS NULL;
ALTER TABLE `t_lottery_record`
    MODIFY COLUMN `prize_level` int NOT NULL DEFAULT 99 COMMENT '奖励等级：1..N 为中奖奖级，99-未中奖/未开奖';
```

**`total_count` 不做期号快照**（原方案曾建议加这一列，已撤销）：发行量挂在配置表上是唯一真源，运营要「每期数量不同」的正确做法是**建不同的彩票编码**——一个彩票编码就代表一种确定的发行规格。

这个选择之所以安全，是因为 §5.3 的结构锁已经把 `total_count` 在「任一期号发过号之后」永久冻结了。也就是说「改配置追溯篡改历史期进度」这个风险**在冻结生效的那一刻就不存在了**，再加一列快照属于对同一个风险防两次，反而制造了两个可改的地方。

**`MODIFY prize_level` 的执行顺序**：`NOT NULL` 之前必须先把存量 NULL 刷成 99，否则 MySQL 严格模式会直接拒绝这条 ALTER。开发库当前该表为空，但脚本要能在有数据的环境重放，UPDATE 那句不能省。

**迁移脚本**（单独一份，参照 `任务模块-编码规范迁移与造数.sql`）：
- `lottery_code` 由 `L_5DIGIT_001` 迁到 10 位随机码，**必须级联** `t_lottery_issue` / `t_lottery_prize_rule` / `t_lottery_record` 三张表的 `lottery_code`。
- 建一条 `activity_type='LOTTERY'` 的活动（开发库当前 `t_activity_config` 只有 1 条 DRAW 活动，彩票工作台的活动下拉现在是空的）。

**建表自查**（铁律 9 / 「NOT NULL 无默认值」第 5 次复发的预防动作），写实体前先跑：

```sql

 WHERE table_schema='smart_admin_v3' AND table_name LIKE 't_lottery%'
   AND is_nullable='NO' AND column_default IS NULL AND extra NOT LIKE '%auto_increment%';
```

已知会命中的：`t_lottery_record.security_sign` / `sequence_no` / `ticket_number`、`t_lottery_config.total_count`、`t_lottery_issue.sale_start_time` / `sale_end_time`、`t_lottery_prize_rule` 的四个匹配列。**每一个都必须在代码里显式赋值。**

### 5.3 结构锁（对齐抽奖工作台）

判定条件：**该彩票任一期号的 `sold_count > 0`**，或 `t_lottery_config.status = 1`。命中后服务端拒绝：

两者都冻结，但**冻结的理由完全不同，别混为一谈**：

- **`number_length` —— 密码学约束**。FPE 的定义域 `N = 10^number_length` 完全由它决定。改了它，域就变了：历史号码无法用新域反解验证，新发的号码也可能与历史号码重复。**这是全表最硬的不可变约束。**
- **`total_count` —— 业务约束**。它只是发售上限，**对 FPE 的域和可逆性没有任何影响**（域只看 `number_length`）。冻结它是为了防止运营预算与发售契约被追溯篡改——已经对外承诺「本期限量 10 万张」，卖到一半改成 20 万是业务事故，不是算法事故。
  这也正是「`total_count` 挂配置表」这个决策成立的前提（§4）：冻结之后，配置层就是唯一且不可追溯篡改的真源。

（`number_charset` 不在此列，只是因为它压根不可配，恒为 `0-9`，见 §1.3。）
  - 运营要「每期发行量不同」，正确路径是**新建一个彩票编码**，而不是改这里。这条要写进前端的禁用态提示文案，否则运营会以为是 bug。
- 删除已有奖级、改已有奖级的 `match_rule` / `match_length`（`prize_code` 是否允许改属产品决策，倾向**同样冻结**，因为已开奖的期已快照，改了只影响未开奖的期，语义会分裂）。

前端的 `isOnline` 按抽奖工作台的结论处理：**只读 Tag，不给可拨的 switch**（原型里那个 switch 会和服务端结构锁打架）。

## 6. 前端设计

一个工作台页面 `views/business/lottery/lottery-workbench/`，两个 Tab 完全对应原型：

```
LotteryWorkbench.vue          外壳：彩票下拉 / 只读上线 Tag / 顶部「提交全局配置」/ 离开拦截
├── components/EngineConfigPanel.vue   Tab1 引擎配置 + FPE 推演台 + 奖级规则 + 资产池拖拽
└── components/IssueConsole.vue        Tab2 期号列表 + 行内编辑 + 右侧开奖操作台
```

要点：

1. **FPE 推演台必须调服务端**。原型里 `(seq * 2654435761) % 10^len` 是个占位假算法，前端**不可能也不应该**知道密钥。改为：

   ```
   POST /lotteryConfig/fpe/preview
   { lotteryCode, issueNo, numberLength, sequenceNo }   →  { ticketNumber }
   ```

   **`lotteryCode` 必传**：密钥是 `HMAC(masterSecret, lotteryCode + "|" + issueNo)`（§1.2），缺了它服务端根本算不出正确的 key，推演结果会和线上真实发出的号码对不上——一个「看起来能用、实际全错」的预览比没有预览更糟。`totalCount` **不进请求体**：它不是密码学输入，只用于前端把游标输入框的 `:max` 限住。

   **⚠️ 原型没交代的一个问题：预览时用哪个 `issueNo`？** 推演台在 Tab1（配置态），此时一期都还没建，而号码恰恰是随期号变化的。定案：用一个固定的演示期号常量 `__PREVIEW__` 参与派生，并在推演台上明写「演示号码，实际号码随期号变化」。
   - 为什么不挑一个真实期号：那会让运营误以为「我看到的就是这一期要发的号」，而任何一次期号变更都会让这个印象落空。
   - 为什么不省掉 issueNo：那等于让预览走一条与线上不同的密钥派生路径，就违背了下面这条「同一段代码」的初衷。
   - `__PREVIEW__` 不符合期号格式、也不会入库，不存在与真实期号撞车的可能。

   顺带的好处：运营在保存前就能看到「改了号码长度后号码长什么样」，而这个预览与线上算号是**同一段代码**（同一个 `FpeCipher`、同一套密钥派生），所见即所得。
2. **删掉字符集下拉**（原型 §102-108）。号码恒为纯数字（§1.3），只保留号码长度输入框，`:min` 从原型的 3 改成 **4**（§1.3.1），提示文案「纯数字，4-9 位」。
3. **camelCase 陷阱不适用于 SFC**（铁律 6），所以 `:customRow` / `valueFormat` 在 .vue 里可以直接用。但**原型 HTML 本身要顺手修完**（§0 第 2 条），否则下次谁拿它演示还是会踩。
4. 资产池来自 `GET /prizeConfig/optionList?activityCode=`（抽奖工作台已有这个接口）。拖拽绑定与「指派」按钮两条路径都保留——拖拽好看，按钮才是键盘/触屏用户的救命稻草。
5. 奖级规则的「按等级整理」「新增奖级置顶」等交互直接照搬原型，但 `prize_level` 的**连续性由服务端重排**（前端只是 UI 防呆，铁律 2）。
6. 单一状态源（铁律 4）：整个 Tab1 收在一个 `reactive` 对象里，Tab2 的期号列表是独立的服务端分页，不进这个对象。
7. 保存契约：
   ```
   { lotteryCode, lotteryName, numberLength, totalCount, activityCode,
     prizeRuleList: [{ prizeLevel, matchRule, matchLength, prizeCode }] }
   ```
   回显 VO 与之同构，额外多 `activityName / status / online / issueCount / soldTotal` 和只读的 `prizeName / prizeType / prizeValue`。
   `numberCharset` **不进契约**：前端既不提交也不展示，服务端保存时固定写 `0-9`（§1.3）。

## 7. 已知缺陷模式的防线（本项目最容易复发的三类）

| 模式 | 在彩票模块的落点 |
|---|---|
| **枚举键 map 用字符串查**（已复发 3 次） | `TicketMatcher` 若做成 `Map<MatchRuleEnum, Matcher>` 策略表，取值前必须 `resolveMatchRule(String)` 显式转枚举。倾向直接用 `switch` 模式匹配，从根上没有 map 可查 |

另加两条彩票特有的：

- **游标回滚 = 重号**（§1.4）。任何在发号路径上写 `DECR` 的改动都要按资损处理。
- **游标基准的 ±1**（§1.4.1）。Redis `INCR` 是 1-indexed、FPE 定义域是 `[0, N)`，两者差一。换算固定在 Redis 边界那一侧，并用断言 `0 <= sequenceNo < totalCount` 兜住——**这个错只在卖光最后一张时才暴露**，常规测试覆盖不到。
- **密钥/期号不可变**（§1.2）。给 `masterSecret` 的 yaml 配置项和 `issue_no` 字段都加显式注释。

## 8. 已定稿的边界决策（2026-07-27）

### 8.1 定位：这是号码派发引擎，不是售卖系统 ★

**本模块只负责「给我一个号 / 这个号中了什么」，不碰资产。** `cost_asset_type` / `cost_value` 这类消耗由**上游业务算完再调进来**，单用户限购几张同样由上游业务把关。

这条定位是后面几个决策的总纲，直接决定：

- 表结构**不加**任何消耗字段，也**不加** `user_max_count`。原型里的「售卖」措辞是业务视角的叫法，模型层面就是派发。
- `TicketIssueService.obtain()` **不注入** `MemberWalletService`，链路里没有扣减、自然也没有退还。对比抽奖的 `DrawExecuteService` 要处理 CREDIT 扣减 + NoStock 退还，彩票这条链路短得多，这是好事。
- 领号接口的入参里没有「支付凭证」之类的东西；调用方是可信的上游服务，鉴权在网关层解决。
- **但幂等和限流仍然要做**（§1.4 保留 `requestId` SETNX 与 RRateLimiter）：那是防网络重试和防刷，与业务限购是两回事——上游限购挡的是「你只能买 3 张」，这里挡的是「同一个请求别给两个号」。

  ⚠️ 边界提醒：既然限购在上游，**本模块必须假定同一个 memberName 可以合法地领任意多张号**。所以任何「一人一号」的隐含假设都不能写进代码（比如给 `(issue_no, member_name)` 加唯一索引），`idx_member` 保持普通索引。

### 8.2 一期只开一次奖

`status=1 部分开奖` 目前纯属预留值，本方案将其复用为核销断点续跑标记（§2.2）。若将来真要做分批开奖，这个语义需要重新分配，别在上面叠加第二重含义。

### 8.3 未中奖奖级 = 99

确认采用，动机是 C 端排序（详见 §2.1.1）。DDL 默认值一并改成 99。

### 8.4 `total_count` 挂配置表

不做期号快照。要每期发行量不同，就建不同的彩票编码（详见 §4 与 §5.3）。

### 8.5 `numberpool` 已停用，保留 Service 作算法学习材料

`DynamicNumbersGenerator` 里「洗牌法 vs 哈希去重法」的容量路由判断值得留着读，所以代码不删，只断掉运行时入口。

**✅ 已完成（2026-07-27，重启验证无报错）**：

- 删除 `LotteryNumberPoolController`、`LotteryNumberPoolMapper.xml`、前端 api/const/list 三件套；
- 摘掉 `LotteryNumberPoolDao` 的 `@Mapper`、`LotteryNumberPoolService` 与 `LotteryNumberPoolManager` 的 `@Service`、entity 的 `@TableName`。

整包现在**完全不进 Spring 容器**，只剩能编译、能阅读的纯代码——正是「留作学习材料」想要的状态。保留的 `@RequiredArgsConstructor` / `@Data` 是 Lombok 编译期注解，与容器无关，不用动。

> **为什么必须连 `@Service` 一起摘**（记下来，这个坑很隐蔽）：
> `AdminApplication` 的扫描配置是 `@MapperScan(value = COMPONENT_SCAN, annotationClass = Mapper.class)` —— **只注册带 `@Mapper` 的接口**。所以 `@Mapper` 一摘，Dao 就不再是 Bean；而 `LotteryNumberPoolService`（构造器注入 Dao）和 `LotteryNumberPoolManager`（`extends ServiceImpl<LotteryNumberPoolDao, …>`）只要还挂着 `@Service`，启动期就会抛 `NoSuchBeanDefinitionException`。
> **`mvn compile` 在这个中间状态下是通过的（实测 exit=0）**，编译期完全看不出来，只在启动时炸——又一例「静默到运行期才暴露」。
> 另外 `Mapper.xml` 已删而 `queryPage` 还留在 Dao 接口上也不再有问题：没被 MapperScan 扫到，就不会触发 "Invalid bound statement" 的绑定检查。

**剩余两条隔离动作（P0 收尾）**：

1. **加包级说明**：`numberpool` 下建 `package-info.java`，写明「号池方案已被 FPE 方案取代，`t_lottery_number_pool` 表已移除，本包不进 Spring 容器，仅作算法参考，不要在新链路中引用」。这比留在提交历史里更容易被下一个人看到——尤其现在类上连注解都没有了，光看代码很难判断它是死是活。
2. **菜单里清掉 `lottery-number-pool` 入口**：前端页面文件已删，`t_menu` 里若还有对应记录要一并清，否则运营点开就是白屏。

原方案里那条「charset 语义冲突要对向标注」**不再需要**：新引擎固定十进制、根本不碰 charset 参数（§1.3），两者不会再有交集。

| 项 | 做法 | 结果 |

| FPE 推演 | 页面显示值 vs 用同一 masterSecret + `__PREVIEW__` 在 jshell 里独立计算 | 游标1 → `56032` **逐位相等**；游标4 → `05229`，**前导零补位正确** |

### 服务端校验（11 项，全部拦住且文案是人话）

发售量超空间、号码长度 < 4、编码格式非法、活动不存在、活动类型非 LOTTERY、奖级重复、奖级=99、匹配长度超号码长度、同奖品绑多奖级、匹配规则非法、奖品跨活动引用。

**并且 11 次失败后玩法数仍为 0** —— 校验全部发生在落库前，事务边界成立。

### 结构锁（4 项）

- 已上线：改号码长度 ✗、改发售上限 ✗、**只改名称与奖级 ✓**
- 已发号（sold_count=500）：改号码长度 ✗，文案说明了密码学原因

**锁的粒度是关键**：如果连名称和奖级都锁死，运营改个错别字都得先下线，这种"安全"会逼人绕过流程。两种锁定原因的文案也刻意分开——上线是流程管控（可下线解除），已发号是不可逆（永久冻结）。

### 1:N 与跨活动隔离（5 项）

同活动下两个玩法（5位/10万 与 7位/1000万）并存、规则互不干扰、**EXACT 的 matchLength 按各自号码长度分别归一为 5 和 7**；玩法下拉按活动正确过滤；`activityCode` 与 `lotteryCode` 不自洽被拒；编码跨活动占用被拒。

### 过程中的两个自我修正

1. **第一次测「参数自洽」和「编码跨活动占用」用错了活动**：拿抽奖活动 `12278CBYW7` 去测，被更早的「活动类型不是 LOTTERY」拦住，根本没走到要测的分支——测试通过了，但测的不是想测的东西。造了第二个 LOTTERY 活动后重测才真正覆盖。
   **教训：断言"被拒绝"时必须看拒绝原因，只看 `ok=false` 会把假阳性当成通过。**
2. **`a-input-number` 程序化赋值不触发 Vue 模型更新**：DOM 显示 999999 而模型仍是 100000（提示行按旧值算）。这只影响自动化操作，但它意味着**页面上看到的数字不一定等于将要提交的数字**——所以往返验证一律以接口实际收到的 payload 为准。
