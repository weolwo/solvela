# 奖池抽奖模块原型 · 变更说明

> 对应原型文件：`docs/奖池抽奖模块原型交互设计.html`
> 用途：转正式 Vue 组件（`src/views/business/draw/`）时的对照清单，记录每处改动的**原因**与**落地要点**，避免重写时把坑再踩一遍。

---

## 一、保留的核心设计（转组件时务必延续）

| 设计 | 价值 | 落地提醒 |
|---|---|---|
| **兜底自动配平** | 运营不用做减法凑 100%，把一个奖项设为「兜底」，它自动吃掉剩余概率 | 全局只能有一个兜底项；配平在 `watch(poolMappings, deep)` 里算 |
| **上线后防篡改锁** | 活动上线后只能加库存、不能减/删奖项，防止运营误操作影响进行中的活动 | 由 `isOnline` 驱动：库存 `input-number` 的 `min` 动态取原值、删除/移除按钮 `disabled` |
| **沙盘模拟器** | 上线前用蒙特卡洛验证「概率+库存」配得对不对，给运营一个自证出口 | 纯 `Math.random()`，无需后端；转组件时可保留前端模拟，或改调后端接口跑更大样本 |

## 二、P0 — 致命 bug（必修）

### 浮点概率用 `=== 100` 严格比较

- **现象**：`:disabled="totalProbability !== 100"`。奖项 3 个时不触发，**10 个转盘坑位时约 9.21% 概率**出现 `0.1+0.2+... = 99.99999999999999`，界面显示「✅ 验证通过 100.0000%」但保存按钮却是灰的，运营无从下手。
- **隐蔽性**：开发自测只用默认 3 条数据（恰好精确），根本发现不了，上线配真实转盘才炸。
- **修法**：抽出统一状态，全部走容差比较。

```js
const PROBABILITY_EPSILON = 0.0001;
const probabilityStatus = computed(() => {
  const diff = totalProbability.value - 100;
  if (diff > PROBABILITY_EPSILON) return 'over';   // 超载
  if (diff < -PROBABILITY_EPSILON) return 'under'; // 不足
  return 'ok';                                     // 通过
});
```

- **影响面**：保存按钮 `disabled`、进度条 `status`、文案分支、模拟前置校验 —— **5 处**全部改用 `probabilityStatus`，不再出现裸的 `=== 100 / > 100 / < 100`。
- **转组件铁律**：**任何"概率/金额/比例求和后判等"都不能用 `===`，一律容差比较。**

## 四、P2 — 库存超发预警（本轮重点）

### 背景：库存与概率脱钩 = 超发事故根源

iPhone 库存 5 个、概率 0.05%，活动预估百万次抽奖 → 理论要发 500 个，实际只有 5 个。原型原本对此**零提示**。

### 落地方案（轻量，不动配置页数据结构）

概率表 `poolMappings` 与物资库 `prizeItems` 通过 **`key` 关联**，模拟结果按 key 回查库存：

```js
// 计数器用 key（不用 name，避免同名奖项串数据）
let stockItem  = prizeItems.value.find(p => p.key === item.key);
let unlimited  = !stockItem || stockItem.totalStock === -1;   // -1 = 不限量
let remainStock = unlimited ? Infinity : (stockItem.totalStock - stockItem.usedStock);
let overflow   = !unlimited && cnt > remainStock;
let shortage   = overflow ? cnt - remainStock : 0;            // 超发缺口
```

### 展示

- 结果区**顶部**整体预警条：有超发 → 红色 error「有 N 个奖项会超发」；否则绿色 success「库存充足」。
- **每行**：超发奖项挂「库存超发」红标签、进度条变红、附「预计发出 X / 剩余库存 Y，缺口 Z 个」；不限量的显示「不限量，无超发风险」。

### 实测（同一套概率，放大样本才暴露）

| 奖项 | 模拟 1千次 | 模拟 10万次 |
|---|---|---|
| iPhone（剩 3） | 发 0 🟢 | 发 56 🔴 缺口 53 |
| 100 积分（剩 5500） | 发 115 🟢 | 发 10991 🔴 缺口 5491 |

**关键**：1千次全绿、10万次两项超发 —— 说明「概率合规 + 库存已填」不等于安全，必须放大样本验证。这正是本功能的价值。

## 五、尚未做（转组件或下一轮原型再评估）

- **配置页实时超发校验**：填「预估抽奖量」，每行直接算「预计发出/库存」并标红（本轮只在模拟器里做了，是二选一的轻量版）。
- **多奖池**：原型左侧写死单个「免费普惠池」，真实场景应有 免费/付费/新人 等多池。
- **保存前 diff 确认**：改概率是高危操作，正式版建议弹「X% → Y%」对照再提交。
- **操作审计**：谁在何时调整了概率/库存。
- **概率的人话换算**：`0.05%` → 「约每 2000 次中 1 次」，填的当下就有直觉（降心智负担）。

## 六、验证方式说明

因 `file://` 在预览沙箱加载受限，本轮 P0 与 P2 的核心逻辑是用 **Node 复现原型真实计算**来验证的（浮点边界、超发判定均通过），非肉眼看渲染。**DOM 绑定层（a-alert 显隐、标签颜色）建议本地双击打开 HTML 实际点一次模拟器确认。**
