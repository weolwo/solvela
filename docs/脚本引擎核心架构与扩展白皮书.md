## 0. 三十秒建立上帝视角

这套东西的定位一句话：**让 Java 写"能力"，让脚本写"怎么组合这些能力"。**
Java 侧提供一堆被白名单暴露的原子函数（发积分、查等级、扣库存），运营/活动侧用 QLExpress
把它们串成具体玩法。脚本引擎是这两者之间的**受控通道**。

它有两条完全独立的链路，**分不清这两条就永远看不懂这个包**：

```
【启动期链路】——— 只跑一次，把 Java 能力挂上引擎 ———————————————————————

  Spring 容器就绪
        │
        ▼
  EngineFunctionScanner.afterSingletonsInstantiated()      ★ 唯一的绑定入口
        │
        ├─① 捞出所有 ScriptFunctionHandler 类型的 Bean
        │      └─ 读 bean.domain() 拿业务域（抽象方法，忘写编译不过）
        │
        ├─② 扫每个 @ScriptFunction 方法 → buildMeta()
        │      ├─ 函数名 = domain.qualify(短名)，如 getLevel → member_getLevel
        │      ├─ 首参若为 EngineContext → injectContext = true，该参数不算脚本入参
        │      └─ 非 public / 自己写了域前缀 → 直接抛异常，应用起不来
        │
        ├─③ registry.register(meta)   同名 → 抛异常（不静默覆盖）
        │
        └─④ 全部扫完后，才逐个 evaluator.registerFunction(meta)
                └─ 包成 QLExpressFunctionAdapter 挂进 Express4Runner


【运行期链路】——— 每次执行都跑 ——————————————————————————————————————

  业务代码
        │  ScriptEngine.evaluate(ExecutableScript, EngineContext)
        ▼
  EngineExecutionMonitorAspect          ★ 切在接口上，不是实现类上（§1.4）
        │  计时 / 慢日志 / 异常分流
        ▼
  DefaultScriptEngine                   门面，只认 ScriptEvaluator SPI
        │
        ▼
  QLExpressEvaluator.evaluate()         ★ 防腐层，唯一认识 qlexpress 类型的地方
        │
        ├─ variables = new HashMap<>(ctx.getScriptVariables())  ← 只有这条通道脚本可见
        ├─ QLOptions: timeout / precise / polluteUserContext(false)
        │             / cache(source == TRUSTED) / attachments{ctx}   ← 每次执行现建
        │
        ▼
  Express4Runner.execute(String, Map, QLOptions)     ★ 必须是这个重载（§1.5）
        │
        └─ 脚本调到 member_getLevel(...) 时
              └─▶ QLExpressFunctionAdapter.call(QContext, Parameters)
                     ├─ injectContext ? 从 QContext.attachment() 取回 EngineContext
                     ├─ ParametersTypeConvertor.cast 只作用于脚本实参
                     └─ method.invoke，拆 InvocationTargetException
```

### 五个必须先记住的事实

| # | 事实 | 违反 / 忘记后的症状 |
|---|---|---|
| 1 | **`EngineFunctionScanner` 是唯一的函数绑定入口** | 绕过它手动 `addFunction`，函数不会出现在 `/script/engine/view` 文档里，前端补全永远缺一块 |
| 2 | **脚本里的函数名一律带域前缀**（`member_` / `mall_` / `task_`…） | 写 `getLevel()` 会报「未知函数」。前缀不是命名规范，是引擎生成的 |
| 3 | **`ScriptEvaluator` 是防腐层边界**，它以上不允许出现 `com.alibaba.qlexpress4.*` | 一旦泄漏，「换引擎」这条退路就没了，而 SPI 存在的唯一理由就是这条退路 |
| 4 | **构造脚本必须显式选 `trusted()` 或 `untrusted()`** | 没有默认工厂。不受控内容误走 TRUSTED，QL 编译缓存以脚本原文为 key 且无上限，直接 OOM |
| 5 | **`allow-java-reflect` 任何环境都是 `false`** | 打开等于把 RCE 面暴露给脚本内容 —— 而脚本是运营在写的 |
| 6 | **`EngineContext` 有两条通道**：`bind` 脚本可见 / `bindInternal` 脚本不可见 | 把 traceId、幂等键之类 `bind` 进去，等于把内部实现细节变成运营看得见的事实契约 |

## 1. 顶层设计：为什么是这个形状

### 1.1 三层的职责切分

| 层 | 包 | 知道什么 | 不知道什么 |
|---|---|---|---|
| **契约层** | `spi` | 脚本、上下文、业务域、函数处理器 | 任何引擎实现 |
| **实现层** | `core` | QLExpress 的一切 | 具体业务 |
| **能力层** | `handler` + 各业务模块 | 具体业务 | 引擎怎么跑的 |

`domain` 包是三层共用的数据模型，`annotation` 是能力层写给扫描器看的标记。

这个切分的检验方法很简单：**在 `spi` 包里 grep `qlexpress`，应该零命中。**
现在确实是零。哪天不是了，说明防腐层破了。

### 1.2 为什么函数分类是 enum 而不是 sealed interface

原始设想是用 `sealed interface` 把各业务域封起来。**这条路在本工程编译不过。**

JLS 8.1.6：未命名模块（本工程没有 `module-info.java`）下，`permits` 列出的实现类必须与
接口**同包**。而各域的 Handler 必然散落在 `sa.member` / `sa.mall` / `sa.task`，还跨
`common-api` 和 `sa-marketing` 两个 Maven 模块。

所以拆成两层（[ScriptDomain.java:23](../smart-admin-api/common-api/src/main/java/sa/scriptengine/spi/ScriptDomain.java#L23)、
[ScriptFunctionHandler.java:20](../smart-admin-api/common-api/src/main/java/sa/scriptengine/spi/ScriptFunctionHandler.java#L20)）：

- **域的取值集合**用 `enum` 封闭 —— enum 天生是封闭集合，且能 switch 穷举、能直接当数据库字段值，
  在这个位置比 sealed 更合适
- **Handler 本身**用普通 interface 开放，业务模块随便实现

> **认知点**：Java 的"封闭性"有三档 —— `enum`（值封闭，最强）/ `sealed`（类型封闭，但有同包同模块约束）/
> `interface + 扫描`（开放）。选哪档要看**你想封闭的到底是什么**，以及**实现者住在哪个包**。

### 1.3 为什么 `domain()` 是抽象方法而不是注解

旧版是空标记接口 + 可选的 `@ScriptFunctionGroup` 注解，注解可以不写，不写就落到"默认通用工具"。
这条路的终点是所有函数挤在默认分类里，**而且没有任何人会发现**。

改成抽象方法后，忘了归类 = 编译不过。

> **认知点**：把"应该做"变成"必须做"的最短路径，是把它变成**方法签名的一部分**。
> 加校验、写文档、给注解设默认值，都是更弱的手段。

### 1.4 切面为什么切在接口上

这是重构前一个隐藏了很久的 bug：切点写的是实现类所在包，**一个方法都没拦到**。

因果链：`ScriptEngine` 是通过 `@Bean` 返回**接口类型**装配的
（[ScriptEngineAutoConfiguration.java:45](../smart-admin-api/common-api/src/main/java/sa/config/ScriptEngineAutoConfiguration.java#L45)）
→ Spring 选 JDK 动态代理 → 代理对象只实现接口、不继承 `DefaultScriptEngine`
→ 按实现类写的切点必然落空。

现在切点是 `execution(* sa.scriptengine.spi.ScriptEngine+.evaluate(..))`
（[EngineExecutionMonitorAspect.java:31](../smart-admin-api/common-api/src/main/java/sa/aspect/EngineExecutionMonitorAspect.java#L31)）。

> **认知点**：切面作用于**运行时结构**，不是源码结构。
> Bean 的暴露方式决定代理方式，代理方式决定切点该写在哪一层。
> 同类陷阱还有：自调用不走代理、`final` 方法 CGLIB 拦不住。

⚠️ 顺带记住：`DefaultScriptEngine.evaluate(script, ctx, Class<T>)` 内部调用了两参版
（[DefaultScriptEngine.java:46](../smart-admin-api/common-api/src/main/java/sa/scriptengine/core/DefaultScriptEngine.java#L46)），
这是**自调用，不走代理**。所以三参版只被切一次，不会重复计时 —— 这是期望行为，不是漏切。

### 1.5 `execute` 的重载陷阱

`Express4Runner` 有两个签名相近的重载：

| 重载 | 语义 |
|---|---|
| `execute(String, Map<String,Object>, QLOptions)` | Map 的 key 就是脚本里的变量名 ✅ |
| `execute(String, Object, QLOptions)` | 把对象当"属性根"，脚本按属性访问 ❌ |

重构前传的是 `EngineContext` 对象，命中了第二个重载 —— **`bind()` 进去的变量在脚本里一个都取不到**。
现在显式拷贝成 `HashMap` 再传（[QLExpressEvaluator.java:74](../smart-admin-api/common-api/src/main/java/sa/scriptengine/core/QLExpressEvaluator.java#L74)）。

这条被 `ScriptEngineTest.bound_variables_are_visible_to_script` 钉住了，别再改回去。

### 1.6 上下文注入为什么不用 ThreadLocal

QL 4.x 的 AST 是无状态递归传参的，Java 函数拿上下文走 `QContext.attachment()` 即可
（[QLExpressFunctionAdapter.java:42](../smart-admin-api/common-api/src/main/java/sa/scriptengine/core/QLExpressFunctionAdapter.java#L42)）。

识别规则：**方法首参声明为 `EngineContext` 就自动注入**，脚本侧完全不感知这个参数。

```java
@ScriptFunction(name = "currentLevel", description = "取当前会员等级")
public Integer currentLevel(EngineContext ctx) {          // ← 自动注入
    Long memberId = ctx.getAs("memberId", Long.class);
    ...
}
// 脚本里写：member_currentLevel()      ← 不传参
```

> **认知点**：为什么不发明一个 `@Context` 注解？因为 `EngineContext` 这个**类型本身**
> 在参数位置上已经是无歧义的信号，加注解纯属冗余。
> 反之，如果要注入两个都是 `String` 的东西，类型不够用了，那才轮到注解。

### 1.7 脚本模型上为什么是「来源」而不是「要不要缓存」

QL 的编译缓存以**脚本原文**为 key，且**没有容量上限**。危险不在"缓存会变多大"，而在
**key 的基数是否有界**：

| 脚本来源 | key 基数 | QL 该不该缓存 |
|---|---|---|
| `TRUSTED` —— 项目内 git 管理的 `.ql` 文件 | 有界（几十上百条） | 该，收益极高 |
| `UNTRUSTED` —— 在线试跑 / 动态拼装 | **无界** | 绝对不能，进去就出不来 |

关键在于**这两列分属不同的抽象层**：

- 左列是**业务事实** —— "这段脚本是不是我们自己 git 管理的"，任何引擎下都成立
- 右列是**实现决策** —— "编译缓存"是 QLExpress 独有的东西，换 Aviator 未必有

所以 [`ExecutableScript`](../smart-admin-api/common-api/src/main/java/sa/scriptengine/domain/ExecutableScript.java)
上只放 [`ScriptSource`](../smart-admin-api/common-api/src/main/java/sa/scriptengine/domain/ScriptSource.java)，
从来源推导出缓存决策的那一行住在
[QLExpressEvaluator.isCacheable()](../smart-admin-api/common-api/src/main/java/sa/scriptengine/core/QLExpressEvaluator.java#L150)。

> **认知点一**：**抽象泄漏最常见的形态不是类型穿透，而是概念穿透** —— 编译器不报警，所以更难发现。
> 自查方法：把模型上每个字段拿出来问一句「换掉底层实现之后，这个字段还成立吗？」
> 不成立的，就是漏上来的实现细节，该往下沉。
>
> **认知点二**：看到任何 map-as-cache，第一个问题永远是**"key 的基数上界是多少"**。
> 有界 → 随便缓存；无界 → 必须有淘汰策略或开关。这比"缓存要设上限"通用得多。

⚠️ 没有提供 `of(...)` 这样的短名默认工厂，必须显式写 `trusted()` / `untrusted()`。
**留一个短名默认值，正是不受控内容混进受控通道的典型路径** —— 人总会挑最短的那个名字写。

### 1.8 EngineContext 的两条通道

`EngineContext` 内部是**两个物理隔离的 Map**：

| | 脚本变量通道 | 内部数据通道 |
|---|---|---|
| 写 | `bind(k, v)` / `bindAll(map)` | `bindInternal(k, v)` |
| 读 | `getAs(k, Type)` | `getInternal(k, Type)` |
| **脚本能读到吗** | **能**，按变量名直接引用 | **不能**，完全不可见 |
| Java 函数能读到吗 | 能 | 能 |

**为什么要拆**：脚本是运营在写的，脚本变量是给他们的输入参数。
但 traceId、操作人、幂等键、活动快照这类东西 Java 函数需要、**却不该出现在运营的视野里** ——
暴露出去等于把内部实现细节变成事实契约，以后想改都改不动。拆开之前只能全给或全不给。

实现上是两个独立 Map，不是一个 Map 加 key 前缀约定
（[StandardEngineContext.java](../smart-admin-api/common-api/src/main/java/sa/scriptengine/spi/StandardEngineContext.java)）——
**前缀约定只要有人拼错就漏了，物理隔离漏不了。**

🔴 `getScriptVariables()` 是**脚本可见性的唯一出口**，只有从这里流出去的东西脚本才读得到。
改 `QLExpressEvaluator` 时千万别把整个 context 喂给引擎。

> **认知点**：一个对象同时服务两类读者、而两类读者的可见范围不同时，
> 别用命名约定或文档来区分，**用类型或结构把它们物理分开**。
> 约定要靠人守，结构不用守。

### 1.9 异常的三分法

旧版把一切收敛成 `BusinessException("脚本执行异常，请检查语法或联系管理员！")` —— 语义全丢了。
现在分三类（[QLExpressEvaluator.java:70](../smart-admin-api/common-api/src/main/java/sa/scriptengine/core/QLExpressEvaluator.java#L70)）：

| 情况 | 处理 | 调用方看到 |
|---|---|---|
| 脚本语法 / 运行错误 | 转 `EngineScriptException`，带行列号 | 切面拼成 `msg + 详细原因: 第 2 行…` |
| **Java 函数抛的业务异常** | 从 `QLRuntimeException.getCatchObj()` **拆出来原样抛** | 原始的「积分不足」等业务语义 |
| 超时 | 转 `EngineScriptException("脚本执行超时")` | 明确的超时提示 |

> **认知点**：**异常收敛 ≠ 异常统一**。防腐层要挡的是底层**类型**泄漏（`QLException` 不能露出去），
> 不是把语义差异一起抹平。判据只有一条：**调用方需不需要根据这个差异做不同的事？**
> 需要 → 必须区分。

### 1.10 fail-fast 的位置选择

启动期抛异常的地方有四处，全部是**故意**的：

| 检查 | 位置 |
|---|---|
| `domain()` 返回 null | [EngineFunctionScanner.java:59](../smart-admin-api/common-api/src/main/java/sa/scriptengine/core/EngineFunctionScanner.java#L59) |
| 函数非 public | 同上，`buildMeta` |
| 自己写了域前缀 | 同上 |
| 函数重名 | [EngineFunctionRegistry.java:29](../smart-admin-api/common-api/src/main/java/sa/scriptengine/core/EngineFunctionRegistry.java#L29) |

为什么不打 WARN 继续跑？因为函数没绑上的后果是**运行期报「未知函数」** ——
那时候你面对的是一条线上告警，不是一次启动失败。

> **认知点**：错误发现成本随阶段大致指数上升：
> **编译期 < 启动期 < 首次执行 < 生产偶发**，每往后一档涨约一个数量级。
> 设计任何注册/装配机制时都该主动问：这个错误**最早**能在哪一层被发现？

## 3. 扩展指南

### 3.1 给某个业务域加一个脚本函数

三步，没有第四步：

```java
// 1. 在业务模块里建 Handler（一个域可以有多个 Handler，按子领域拆）
@Component
@RequiredArgsConstructor
public class MemberLevelScriptHandler implements ScriptFunctionHandler {

    private final MemberService memberService;

    @Override
    public ScriptDomain domain() {
        return ScriptDomain.MEMBER;          // 2. 声明域 —— 决定前缀和文档分组
    }

    // 3. 标注函数，写域内短名，不要自己加 member_ 前缀
    @ScriptFunction(name = "getLevel", description = "查会员当前等级，不存在返回 0")
    public Integer getLevel(Long memberId) {
        return memberService.getLevel(memberId);
    }
}
```

脚本里调用：`member_getLevel(memberId)`。重启后自动出现在 `/script/engine/view` 里。

需要拿执行上下文就把首参声明为 `EngineContext`（见 §1.6），注意读的时候分清两条通道：

```java
@ScriptFunction(name = "deductPoint", description = "扣减积分，不足时抛业务异常")
public Boolean deductPoint(EngineContext ctx, Long amount) {
    Long memberId = ctx.getAs("memberId", Long.class);          // 脚本变量：运营写脚本时看得见
    String traceId = ctx.getInternal("traceId", String.class);  // 内部数据：运营完全不感知
    ...
}
```

调用方组装上下文时同理：

```java
EngineContext ctx = EngineContext.create()
        .bind("memberId", memberId)          // 脚本可见，运营会在脚本里引用
        .bind("orderAmount", amount)
        .bindInternal("traceId", traceId)    // 脚本不可见
        .bindInternal("operator", operator);

scriptEngine.evaluate(ExecutableScript.trusted("task/sign_streak_7", content), ctx);
```

**🔴 写 Handler 时必须知道的两件事：**

1. **方法里的耗时操作必须自己做超时控制。**`script.timeout-millis` 是"假超时" ——
   它只能中断脚本自身的指令循环，**无法强行中断已经进入 Java 的 HTTP / DB 调用**。
   脚本会无视超时配置一直阻塞在你的方法里。
2. **方法抛的 `BusinessException` 会原样冒到调用方**（§1.9），所以异常信息要写成运营看得懂的话。

### 3.2 加一个新的业务域

在 `ScriptDomain` 里加一个枚举常量，完事。这是唯一的登记处。

### 3.3 换掉 QLExpress

1. 实现 `ScriptEvaluator`（5 个方法）
2. 在 `ScriptEngineAutoConfiguration` 加一个带 `@ConditionalOnProperty` 的 `@Bean`
   （文件里已经留了 Aviator 的注释模板）
3. 改 yaml 的 `script.engine`

上层业务代码**一行都不用动** —— 这是 SPI 存在的唯一理由，也是为什么 §0 事实 3 是条红线。

## 4. 红线

| # | 红线 | 理由 |
|---|---|---|
| 1 | 任何环境不得开 `script.allow-java-reflect: true` | 等于把 RCE 面暴露给脚本内容，而脚本是运营写的 |
| 2 | 不受控脚本必须走 `ExecutableScript.untrusted()` | 编译缓存 key 无界 → OOM（§1.7） |
| 3 | `spi` 包不得出现 `com.alibaba.qlexpress4.*` | 防腐层破了就没有换引擎的退路 |
| 4 | 不得复活 ThreadLocal 传上下文 | 3.x 时代在 Tomcat 下漏内存的老路，4.x 有 attachments（§1.6） |
| 5 | 不得绕过 `EngineFunctionScanner` 手动 `addFunction` | 函数会从文档里消失，前端补全缺块 |
| 6 | 执行路径上不得调用 `check()` | 每次执行多一遍解析，且会撑大编译缓存 |
| 7 | 内部数据一律走 `bindInternal`，不得 `bind` | `bind` 的东西脚本读得到；traceId/幂等键暴露给运营 = 内部细节变成事实契约（§1.8） |

## 5. 排查手册

| 症状 | 先看哪里 |
|---|---|
| 应用起不来，日志有「脚本函数名冲突」 | 同一个域里两个 Handler 写了同一个短名，改掉其中一个 |
| 脚本报「未知函数」 | 忘了写域前缀；或 Handler 没加 `@Component`；或方法不是 public |
| 脚本取不到变量 | ① 是不是误用了 `bindInternal`（那条通道脚本看不见）；② 确认 key 与脚本里的变量名完全一致 |
| 脚本改了不生效 | 该脚本是 `trusted()`（QL 开了编译缓存），调 `ScriptEngine.clearCompileCache()` |
| 函数里抛的异常前端看到的是「未知异常」 | 抛的不是 `BusinessException` 子类，穿透逻辑只认它（§1.9） |
| 慢日志刷屏 | 调 `script.slow-log-millis`；默认 200ms |
| 想确认引擎起来时是什么配置 | 启动日志搜 `[ScriptEngine]`，三行：引擎初始化 / 门面装配 / 函数绑定统计 |

启动日志长这样，能一眼确认安全姿态和绑定结果：

```
[ScriptEngine] QLExpress 引擎初始化完成，安全策略=isolation, 超时=3000ms, 精确小数=true
[ScriptEngine] 门面装配完成，底层实现：QLExpress-4.x
[ScriptEngine] 函数绑定完成，共 5 个：
  TOOL       通用工具     5 个函数
```

## 6. 测试钉住了什么

`ScriptEngineTest`（10 个用例，纯 POJO 装配，不起 Spring）钉的是**契约**不是实现 ——
用例名换掉底层引擎之后依然成立：

| 用例 | 钉住的契约 |
|---|---|
| `bound_variables_are_visible_to_script` | bind 的变量脚本取得到（§1.5 那个 bug 的回归） |
| `internal_channel_is_invisible_to_script_but_readable_by_java` | **内部数据脚本读不到、Java 函数读得到**（§1.8） |
| `script_variables_view_excludes_internal_channel` | `getScriptVariables()` 是可见性唯一出口 |
| `two_channels_are_independent_for_the_same_key` | 两条通道同名 key 互不串味 |
| `script_source_must_be_explicit` | 来源必须显式声明，为 null 直接拒绝构造 |
| `both_sources_execute_identically` | 来源只影响引擎内部优化，不影响执行语义 |
| `script_local_variables_do_not_pollute_host_context` | 脚本局部变量不回写宿主 |
| `functions_are_registered_with_domain_prefix` | 域前缀自动生成 |
| `duplicated_function_name_fails_fast` | 重名抛异常不覆盖 |
| `exported_docs_carry_domain_and_signature` | 文档字段契约（前端依赖） |
| `engine_context_is_injected_into_first_parameter` | 上下文自动注入 |
| `business_exception_from_java_function_propagates_as_is` | 业务异常穿透 |
| `isolation_strategy_blocks_arbitrary_java_access` | 隔离策略拦得住 `getClass()` |
| `syntax_error_is_reported_with_line_number` | 语法错误带行号 |
| `return_type_mismatch_is_rejected` | 返回类型校验 |

> **认知点**：测试名如果在换掉底层实现后依然成立，它钉的就是契约；
> 如果写成「evaluate 调用了 execute(String, Map, QLOptions)」，那钉的是实现，换引擎时会全红。

|---|---|---|

#### 待办

| # | 短板 | 为什么现在改便宜、以后改贵 |
|---|---|---|
| 1 | **缺"场景契约"抽象** | 现在只有执行后的 `Class<T>` 返回值校验。应该有 `ScriptScene`：某场景的脚本必须接受哪些变量、返回什么类型，才能在**加载期**就校验"这脚本挂这槽位合不合法"。数据库侧已经规划了 `t_script.scene`，代码侧还没有对应类型 —— 典型裂缝 |
| 2 | **没有可观测性出口，只有日志** | 脚本是**运营会频繁改动的生产逻辑**。按 scriptName 维度的执行次数、耗时分位、失败率是刚需 —— 运营改坏了脚本，这是唯一能看出来的地方。切面有拦截点，埋点位置现成 |
| 3 | **两阶段注册无原子性** | scanner 先全量入 registry 再逐个入 evaluator，第二阶段中途失败两边不一致。当前无害（启动直接失败），但将来要支持热加载函数就是真问题 |
| 4 | **内部数据通道仍是字符串 key** | `bindInternal("traceId", ...)` 拼错 key 只会静默拿到 null。等 traceId / 操作人 / 幂等键这组字段稳定下来，应该收敛成一个 typed record，由编译器保证 |

### 7.2 下一轮的存储方案（已决策，未实施）

已确认的三条决策：

1. **脚本文件是唯一权威，DB 只读镜像。**`scripts/**/*.ql` 走 git 管理，后台编辑器降级为
   「查看 + 在线试跑」，改脚本必须走 git + 发版
2. **两张表**：`t_script`（脚本注册表：code / domain / scene / file_path / content / hash /
   version / params_schema）+ `t_script_ref`（引用关系：script_code / ref_type / ref_id / ref_slot）。
   `ref_slot` 不能省 —— 一个奖池可能同时挂准入脚本和结算脚本
3. **存量三处一次性迁走**：`t_activity_config.script_id`、`t_prize_pool_config.script_id`、
   `t_task_template.rule_script` 全部 DROP，引用统一走 ref 表

内核这边已经把接口留好了：`ScriptEngine.check()` 给启动期校验用，`ExecutableScript.trusted()`
给项目内脚本用（加载器是 TRUSTED 的唯一合法生产者），加载器要做的事：
扫描 `classpath*:scripts/**/*.ql` → 解析文件头元数据 → `check()` 语法校验（**有错直接启动失败**）
→ upsert 进 `t_script` → 常驻缓存。

`t_script_ref` 存在的唯一价值是回答一个问题：
**`select * from t_script_ref where script_code = ?` —— 改这个脚本会影响哪些活动。**
设计取舍时以能不能干净地回答这个问题为准。
