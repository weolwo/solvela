## 2. 🔴 三个必须先定死的口径

指标算错比没有指标更糟。这三条是本方案的地基，界面上也要写出来。

### 2.1 「发了多少条」与「发出多少价值」是两个数

实测活动 `12278CBYW7`：**315 条发奖记录**，但按资产类型拆开——

| 资产 | 记录数 | 实际发出价值 |
|---|---|---|
| 优惠券 | 51 | **1020 元** |
| 积分 | 200 | **0** |
| 现金 | 11 | **0** |
| 实物 | 53 | **0** |

除了券**一分钱都没真正发出去**：积分那 100 条预算耗尽失败，现金 11 条、实物 53 条全挂在待审批。

> 首屏写「累计发奖 315 次」会让运营以为活动跑得很好。
> **两个数必须并列展示，且价值必须按资产类型拆开。**

```sql
-- 发奖条数 vs 发出价值（营销域口径：status=1 才算发出）
SELECT activity_code, prize_type,
       COUNT(*)                                                      AS 记录数,
       SUM(status = 1)                                               AS 成功数,
       SUM(CASE WHEN status = 1 THEN CAST(prize_value AS DECIMAL(18,4)) ELSE 0 END) AS 发出价值
FROM t_prize_log
GROUP BY activity_code, prize_type;
```

### 2.2 漏斗末端是「已发出」，不是「已到账」

营销域只知道自己**发出了发奖指令**，钱有没有真到用户手上是账务域的事。

界面上必须写「已发出」而不是「已发放/已到账」，否则运营看到会以为用户收到了。
真正到账的数据去账务系统看，两边的差额靠 §8 的对账任务查。

### 2.3 「进行中」按时间窗算，不按 status

`t_activity_config.status` 的 DDL 注释是 `0-未开始/1-上线/2-下线`，
但管理端已改为「启用(1)/禁用(2)」，且**库里 6 条里有 5 条是历史值 0**。

所以：

- **「是否启用」看 status**：`status != 2` 为启用（历史 0 值按启用处理，与列表页口径一致）
- **「是否进行中」看时间**：`start_time <= now <= end_time`

```sql
CASE WHEN status = 2                        THEN '已禁用'
     WHEN now() < start_time                THEN '未开始'
     WHEN end_time IS NOT NULL AND now() > end_time THEN '已结束'
     ELSE '进行中' END AS 活动状态
```

> ⚠️ 若直接 `WHERE status = 1` 过滤「开启中的活动」，当前只会查出 **1 个**活动，
> 而界面上能看到 6 个。这是最容易踩的一脚。

**实测**（本方案所有 SQL 均已在开发库跑通）：按上面口径算出来是
**进行中 4 个、已结束 2 个**；而 `WHERE status=1` 只有 1 个。

## 3. 指标体系

### 板块一：活动总览（顶层入口）

| 指标 | 口径 |
|---|---|
| 活动状态分布 | 按 §2.3 的四态分组计数 |
| 活动卡片 | 活动名 / 类型 / 状态 / 起止时间 / **挂了几个玩法** / **完备度** |

**完备度**复用已有的 `ActivityRefProvider.checkConfigured` ——
判据是「**能不能上线**」而不是「有没有记录」（一个没配奖级规则的彩票玩法能存进库，但上不了线）。

```sql
-- 玩法数量（三个玩法表各自 count，按 activity_code 汇总）
SELECT a.activity_code, a.activity_name, a.activity_type, a.status, a.start_time, a.end_time,
       (SELECT COUNT(*) FROM t_task_config    t WHERE t.activity_code = a.activity_code) AS 任务数,
       (SELECT COUNT(*) FROM t_prize_pool_config p WHERE p.activity_code = a.activity_code) AS 奖池数,
       (SELECT COUNT(*) FROM t_lottery_config  l WHERE l.activity_code = a.activity_code) AS 彩票玩法数
FROM t_activity_config a;
```

> 🔴 **别把这三个子查询硬编码在大屏里**。项目已有 `ActivityRefProvider` SPI
> （common-api 定接口、各玩法实现、`List` 注入自报 `supportType()`）。
> 统计也走它，**新增第四种玩法时只加一个实现类，大屏代码一行不用改**。

### 板块二：发奖健康度（大屏 C 位）

当前实测分布：成功 217 / 失败 100 / 待审批 64 —— **43% 不在成功态**。

| 指标 | 口径 |
|---|---|
| 状态分布 | `status`：1-成功 / 2-失败 / 0-等待；**按 prize_type 拆开** |
| 待审批积压 | `approve_status = 1`，含最长等待时长 |
| 失败原因 TOP | `status = 2` 按 `fail_reason` 分组（实测只有一种：预算耗尽 100 条） |
| 发出价值趋势 | 按天 × 资产类型 |
| **逾期未开奖** | 彩票期号 `plan_draw_time` 已过但 `status <> 2`，见板块三 |

```sql
-- 待审批积压（prize 域自己的审批，属营销域；财务侧审批归账务系统）
SELECT activity_code, prize_type, COUNT(*) AS 积压数,
       MIN(create_time) AS 最早一条,
       TIMESTAMPDIFF(HOUR, MIN(create_time), now()) AS 最长等待小时
FROM t_prize_log WHERE approve_status = 1 GROUP BY activity_code, prize_type;
-- 实测：实物 53 条 + 现金 11 条，最早一条已挂 140 小时（近 6 天）——
-- 这正是大屏该第一个喊出来的东西，而它在任何"发奖总数"里都看不出来

-- 失败原因 TOP
SELECT fail_reason, COUNT(*) cnt FROM t_prize_log
WHERE status = 2 AND fail_reason IS NOT NULL
GROUP BY fail_reason ORDER BY cnt DESC LIMIT 10;
```

### 板块三：玩法运行态

**抽奖** —— `t_draw_prize_log.status`：0-未中奖 / 1-已中奖 / 2-库存不足 / 3-异常
当前 500 条：中奖 315、库存不足 185。

```sql
SELECT activity_code, pool_code, status, COUNT(*) cnt,
       COUNT(DISTINCT member_name) 参与人数
FROM t_draw_prize_log GROUP BY activity_code, pool_code, status;
```

⚠️ **库存水位要读 Redis 不读 DB**：真实剩余在 `draw:stock:*`，
`t_prize_pool_item.used_stock` 是最终一致性兜底，读 DB 会偏小
（压测第 3 轮踩过 Redis 与 DB 不同步，整轮结论作废）。

**彩票**

```sql
-- 售卖进度 + 开奖倒计时
SELECT i.lottery_code, i.issue_no, i.status,
       i.sold_count, c.total_count,
       ROUND(i.sold_count / NULLIF(c.total_count,0) * 100, 2) AS 售出率,
       i.plan_draw_time, i.settle_time
FROM t_lottery_issue i JOIN t_lottery_config c ON c.lottery_code = i.lottery_code;

-- 🔴 逾期未开奖告警（实测就命中了一个：0ELCRIFHGF 的 plan_draw_time 是 2026-07-31，
--    已过期但 status 仍是 0-销售中）。这是"对外承诺了开奖时刻却没开"，属客诉级异常，
--    比任何参与量指标都该优先展示
SELECT i.lottery_code, i.issue_no, i.plan_draw_time, i.status,
       TIMESTAMPDIFF(HOUR, i.plan_draw_time, now()) AS 逾期小时
FROM t_lottery_issue i
WHERE i.status <> 2 AND i.plan_draw_time IS NOT NULL AND i.plan_draw_time < now();

-- 各奖级中出（win_status: 0-未开奖 1-未中奖 2-已中奖；prize_level 99=未中奖）
SELECT issue_no, prize_level, COUNT(*) cnt,
       SUM(dispatch_status = 0) AS 待派发
FROM t_lottery_record WHERE win_status = 2 GROUP BY issue_no, prize_level;
```

**任务 —— 阶梯流失漏斗（本方案里我认为最有运营价值的一块）**

```sql
SELECT m.stage_level,
       JSON_UNQUOTE(JSON_EXTRACT(m.stage_condition, '$.target')) AS 达标条件,
       m.prize_code,
       (SELECT COUNT(*) FROM t_task_record r
         WHERE r.task_config_id = m.task_config_id
           AND r.current_metric >= CAST(JSON_UNQUOTE(JSON_EXTRACT(m.stage_condition,'$.target')) AS DECIMAL(18,4))
       ) AS 到达人数
FROM t_task_prize_mapping m
WHERE m.task_config_id = #{taskConfigId}
ORDER BY m.stage_level;
```

直接回答「1000 人签到 1 天，只有 50 人连到 7 天」，运营据此调难度。

### 板块四：事件健康度

```sql
SELECT DATE(create_time) 日期, event_code, flow_type, COUNT(*) cnt
FROM t_task_record_flow
WHERE create_time >= #{from}
GROUP BY DATE(create_time), event_code, flow_type;
```

🔴 **按丢弃原因聚类要先加 `discard_code` 枚举列** —— 见 §5。

⚠️ **重复投递在这张表里看不见**：幂等命中走的是撞唯一索引 → 直接 return，
**不写流水行**（`TaskRecordAdvanceService:102-106`）。
要监控重复上报量得单独埋计数器，别指望从流水里统计。

### 板块五：用户维度

```sql
-- Top 获奖用户（营销域口径：已发出价值）
SELECT member_name,
       COUNT(*) 获奖次数,
       SUM(CASE WHEN status = 1 THEN CAST(prize_value AS DECIMAL(18,4)) ELSE 0 END) 获得价值
FROM t_prize_log
WHERE create_time >= #{from}
GROUP BY member_name ORDER BY 获得价值 DESC LIMIT 20;
```

> ⚠️ 「一键拉黑」**没有现成机制可复用**：`t_promotion_config` 里只有
> `identify_limit`/`phone_limit`/`ip_limit` 这类限次和 `mutex_rule` 互斥，
> **没有黑名单字段**；抽奖的白名单在 `t_prize_pool_item.white_list`。
> 要做拉黑得新建，且它属于风控域而非统计范畴，本方案不含。

## 4. 接口设计

统一前缀 `/marketingStat`，权限串写全（别再出现缺前缀的裸串）。

| 接口 | 用途 | 冷/热 |
|---|---|---|
| `GET /overview` | 活动状态分布 + 活动卡片列表 | 热 30s |
| `GET /prizeHealth?activityCode=&days=` | 发奖状态分布 / 待审批 / 失败 TOP / 价值趋势 | 热 30s |
| `GET /gameplay/{activityCode}` | 按活动类型返回对应玩法运行态 | 热 30s |
| `GET /taskFunnel/{taskConfigId}` | 阶梯流失漏斗 | 冷 5min |
| `GET /eventHealth?days=` | 事件推进/丢弃趋势 | 冷 5min |
| `GET /topMembers?days=` | 用户榜 | 冷 5min |

**冷热分开是刻意的**：大屏轮询时热接口 30 秒、冷接口 5 分钟，
避免为了刷一个每天只变几次的漏斗把整套接口都拉高频。

权限：统计接口全部只读，建议统一挂 `marketingStat:query`，
再按需要给下钻操作挂各自模块已有的串。

## 5. 前置：`t_task_record_flow` 加 `discard_code`

`discard_reason` 是**自由文本**，而且刻意带了具体数值
（「单笔金额 99 未达门槛 100」）—— 它的设计目标是**给人读**（客诉自证），不是给机器聚合。
直接 `GROUP BY` 会炸成几百个不同的值。

建议加一列枚举：

| discard_code | 含义 |
|---|---|
| `AMOUNT_BELOW_MIN` | 未达单笔门槛 |
| `AMOUNT_MISSING` | 事件未携带金额 |
| `STREAK_SAME_DAY` | 连续型当日已计入 |
| `RECORD_NOT_RUNNING` | 记录已不在进行中 |
| `AUDIENCE_MISMATCH` | 人群不符 |
| `AUDIENCE_UNKNOWN` | 上游未告知会员属性 |
| `ROUND_LIMIT_EXCEEDED` | 本周期轮次已用尽 |
| `CONFIG_INVALID` | 配置异常 |
| `CONCURRENT_EXHAUSTED` | 并发重试耗尽 |
| `POOL_REJECTED` | 线程池拒绝 |

🔴 **这个前置越晚补越贵**：流水表在持续写入，晚补就要回填历史数据。
而且 code 与文案分离之后，以后改提示文案不会让大屏的分类图悄悄裂开。

## 6. 数据陷阱清单

| 陷阱 | 后果 | 处理 |
|---|---|---|
| **活动 `status=0` 历史值** | `WHERE status=1` 只查出 1 个活动（实有 6 个） | 按 §2.3 口径 |
| **`prize_value` 是 varchar** | 同一种券存了 `20` 和 `20.0000` 两种写法 | 求和用 `CAST`；**分组必须按 `prize_code` 而不是 `prize_value`**，否则同一个奖被拆成两组 |
| `prize_value` 语义不统一 | 注释是「积分数/券ID」，将来真存 ID 会让 `CAST` 静默变 0 | 统计 SQL 加非数字过滤，并把过滤掉的条数显示出来 |
| **BigDecimal 全局序列化成字符串** | `JsonConfig` 输出 `"1020.0000"`，图表库当字符串排序 | 前端 `Number()` 归一化（本项目踩过） |
| **`t_task_record.status=3` 永不出现** | 没有过期扫描，状态饼图里「已过期」恒为 0 | 要么不画这一项，要么先补扫描任务 |
| **`t_draw_prize_log` 没有 `update_time`** | 只能按 `create_time` 做时间维度 | 已确认，无 update 场景 |
| **重复投递不可见** | 幂等命中不写流水 | 见板块四 |
| **库存 DB 与 Redis 不同步** | 读 DB 偏小 | 水位读 Redis |

## 7. 性能与刷新

**当前体量（实测）**：最大表 `t_member_coupon` 556 行，`t_prize_log` 381 行，
`t_draw_prize_log` 500 行，`t_task_record_flow` 53 行。

结论：**直查业务库 + 接口级缓存即可**，不需要 Redis 预聚合、更不需要 OLAP。

现在上 Redis 计数器等于**用一个确定的一致性问题去换一个还不存在的性能问题** ——
而这个一致性问题本项目已经踩过（压测第 3 轮 DB 与 Redis 不同步）。

**唯一有增长风险的是 `t_task_record_flow`**（每个事件一行）。它的索引已经建好：
`idx_t_tsk_flw_rec(record_id, create_time)`、`idx_t_tsk_flw_mbr(member_name, create_time)`。
统计走 `create_time` 范围时要确认能命中索引；到千万级再考虑按天预聚合到一张汇总表。

**升级路径**（真慢了再走，且要先测出慢在哪）：
接口缓存 → 定时汇总表（落在自己库里）→ 只读从库 → OLAP。

## 8. 跨域的事怎么做（不在本方案范围，但要说清）

账务域的数据（提案、预算、实际到账）**不进这个大屏**。真实做法是分开：

| 场景 | 做法 | 时效 |
|---|---|---|
| 各域运营大屏 | 各查各库，不关联 | 实时 |
| **跨域对账** | T+1 批处理，**只输出差异清单** | 每日 |
| 资损告警 | 差异超阈值报警 | 分钟级 |

不做实时跨域关联的原因：两域本来就有最终一致性延迟
（营销已落库、账务还在审批或异步派发中），实时关联会持续产出**假差异**。

关联的接缝已经现成：`t_prize_log.external_biz_no` ↔ 账务侧的来源单号
（任务是 `recordId:stageLevel`，抽奖是 traceId）。**跨域只共享业务单号，不共享外键。**

⚠️ 做对账时注意：存量提案的 `source_type` 全是 `LOTTERY_DRAW`（v3.45 才修），
按来源分类会让历史数据失真。

## 9. 分批落地

**第一批（数据现成，无前置）**
活动总览（走 SPI）、发奖健康度（双口径）、抽奖/彩票运行态、任务阶梯漏斗、用户榜。

**第二批（需前置）**
`discard_code` 枚举列 → 事件丢弃聚类。

**明确不做**
预算水位、提案审批拥堵、实际到账（账务域）；
PV/UV 漏斗（营销中台不接曝光埋点，属上游）；
新老客占比（无会员表，只有上游传了 `isNewMember` 的事件才有数据，覆盖不全）。
