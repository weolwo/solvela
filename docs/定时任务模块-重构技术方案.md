# 定时任务模块 重构技术方案

> 目标：把 `sa-base/module/support/job`（SmartJob）从「每节点各自定时 + Redis 抢锁」重写成
> **数据库抢占式调度 + 角色化部署**，让定时任务能独立于业务服务发布。
> 三个目标按优先级排：**好用 > 简单 > 先进**。凡是让运营多面对一个旋钮的"先进"，都要先证明它值。
> 前置阅读：`docs/营销中台-会话交接文档.md` §0 铁律（尤其 9 / 10 / 11 / 16）
> 撰写 2026-08-11 · **v4 终稿 2026-08-11**（三轮评审全部并入，见 §0.2 / §0.3 / §0.4）· 状态：**可施工**
>
> 本文所有「现状」结论均来自实际读码，不是从注释推断。凡标注 🔴 的是**动手前必须先修**的既有缺陷。

## 0. 一句话结论

**现有模块不是"功能少"，是调度的真源放错了地方。**

现在每个节点各自维护一份内存里的 `ScheduledFuture`，靠 Redis 锁在触发的瞬间抢一次执行权，
用 JVM 时钟判断"该不该跑"。这套模型有三个连带后果：停机期间漏掉的调度**无法被发现**、
JVM 时钟漂移会让任务重跑或漏跑（撞铁律 9/10）、
以及**任何配置都无法在不重启的情况下被可靠地感知**（pub/sub 丢消息就是丢了）。

重写的核心是把 `next_trigger_time` 落到数据库、用一条 `UPDATE ... WHERE trigger_version = ?` 抢占执行权。
这一个改动同时解决上面三件事，并且**天然支持角色化部署**——因为节点之间不再需要协商，只需要抢同一张表。

### 0.4 v4 修订记录（第三轮评审并入）

第三轮定位到**两个执行时序上的硬伤**——"逻辑图上看着对，代码写出来跑不通"的那一类。全部采纳。

| # | 问题 | 处置 |
|---|---|---|
| 1 | 🔴 **重试状态机自相矛盾**：§5.4 说重试插新记录，§3.9 的 SQL 却把 FAIL 记录改成 RUNNING | **统一手动与重试的状态机**：失败时插一条全新的 `PENDING`，扫描只认 `status = 0 AND fire_time <= NOW()`。详见 §5.4 |
| 2 | 🔴 **`block_strategy` 判定时序未定义**：若"发现阻塞就不抢占"，长任务运行期间 `next_trigger_time` 无法推进 | **先抢占推进时间，再判阻塞**。并抽出通用规则：**节点级判据跳过、集群级判据抢占**。详见 §5.2 |

**对问题 1 失效模式的订正**：v3 的 SQL 是 `UPDATE ... SET status=1 WHERE status IN (0,3)`，
它会改掉 FAIL 行，所以**不会无限循环**。真正的毛病是另外两条，且更严重——
① **抹掉了历史现场**，§5.4 承诺的「失败 → 重试 → 成功」链条永远不会出现；
② 🔴 **与 `uk_job_trigger` 的设计自相矛盾**：索引里 `retry_seq` 这一列存在的唯一意义就是
「重试是新行」，复用旧行则该列恒为 0，索引对重试路径完全失效。
**索引设计本身已经假定了重试=新行，是 §3.9 的 SQL 写反了。**

本轮自行补入五条：`next_retry_time` 更名 `fire_time`（§6.2）、
`trigger_source` 删除 `RETRY` 取值（§6.2）、写 FAIL 与插重试必须同事务（§5.4）、
手动触发路径的 job 状态校验（§3.9）、抢占-投递之间的拒绝竞态处理（§5.2）。

## 1. 现状

### 1.1 🔴 阻塞独立部署的那一条（优先级最高）

`SmartJobService`（后台管理接口）与 `SmartJobClientManager` 都挂着
`@ConditionalOnBean(SmartJobAutoConfiguration.class)`，而 `SmartJobAutoConfiguration` 是
`@ConditionalOnProperty(prefix = "smart.job", name = "enabled", havingValue = "true")`。

**后果**：业务节点想「不执行任务但仍能在后台管理任务」做不到——
把 `enabled` 关掉，管理接口、消息通道一起消失，后台菜单直接报错。

**「执行」和「管理」被同一个开关焊死**，而独立部署要的正是把这两件事分开。这是本次重构的第一刀。

### 1.2 其余八个缺陷

按「会不会造成资损 / 静默失效」排序，不是按代码整洁度。

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| 1 | 🔴 **handler 按全限定类名匹配** | `SmartJobLauncher:90` + `SmartJob:17` | Job 实现类一旦被 CGLIB 代理（挂 `@Transactional`/`@Async` 即会），`getClass().getName()` 变成 `Xxx$$SpringCGLIB$$0`，`jobImplMap.get()` 返回 null，代码 `continue` 掉。**不报错、不打日志、任务从此不跑**。而新增时 `Class.forName` 校验必过 —— 「配置校验通过 + 运行期永不执行」，铁律 16 的形状 |
| 2 | 🔴 **手动与自动不是同一把锁** | `SmartJobExecutor:62` vs `SmartJobClientManager:140` | 自动锁 `smart-job-lock-execute-{jobId}`，手动锁 `smart-job-lock-msg-execute-{msgId}`，**互不排斥**。运营点「立即执行」撞上自动调度 = 同一任务并发跑两遍。对发奖/结算类任务是资损 |
| 3 | 🔴 **锁 30 秒定死，长任务必然重复执行** | `SmartJobExecutor:64` | 显式传了 leaseTime，Redisson 看门狗不再续期。任务跑 31 秒锁自己掉。兜底靠 `last_execute_time` 复算，而那个判断用 `LocalDateTime.now()` —— **JVM 时钟，撞铁律 9/10** |
| 4 | **手动执行跑在 Redisson 回调线程上** | `SmartJobClientManager:153` | 同步执行，慢任务占住 Redisson 消息线程池，波及全局分布式锁与缓存 |
| 5 | **一个执行类只能配一个任务** | `SmartJobService:143` | 「A 活动每天 2 点跑、B 活动每小时跑」做不到，只能复制类。对运营是硬伤 |
| 6 | **无超时、无重试、无告警、无隔离** | `SmartJobScheduler:177` `cancel(false)` | 卡死任务永久占住调度线程，而 `core-pool-size` 默认 **2** —— 两个慢任务让全部定时任务停摆。失败只写一行 `success_flag=0`，没有任何人会知道 |
| 7 | **`success_flag` 是布尔，表达不了「执行中」** | `SmartJobExecutor:149` | 执行前先写 `successFlag=true`，进程崩了就永久留着一条「成功」的假记录 |
| 8 | **日志表无清理、`log_id` 是 int、配置轮询全表拉** | DDL + `SmartJobLauncher:131` | `selectList(null)` 每 60 秒全表；`isNeedUpdate` 手工逐字段比对，注释自己写着「新增字段的话在这个方法里增加判断」—— 教科书级漏改点 |

另有一处死代码：`sa-base/config/ScheduleConfig.java` 的 `destroy()` 全工程无引用，随本次重构删除。

### 1.3 为什么仍然自研

引 XXL-JOB 要多部署一个调度中心进程 + 一套独立的库和账号体系，且与现有菜单权限体系割裂
（运营要在两个后台之间跳）。你们几十个任务的规模，Redis + MySQL 已经够了。

**换血条件**（写死成判据，到时候别拍脑袋）：

1. 执行节点超过 ~10 个，或要跨多个**独立服务**调度；
2. 出现单任务几十分钟、必须分片并行的大批量任务；
3. 需要任务编排（DAG：A 成功后跑 B、失败走 C）。

命中任意一条就迁 XXL-JOB / PowerJob，别自己写第 4 个调度器。

## 2. 🔴 部署形态：角色化，而不是拆仓库

这是本次重构的**第一性约束**，先定它，后面的设计都是它的推论。

### 2.1 三种角色，同一份 jar

```yaml
smart:
  job:
    role: ALL          # ADMIN / WORKER / ALL / NONE
    env: prod          # 环境隔离，只抢 app_env 匹配的任务
```

| role | 装配什么 | 用在哪 |
|---|---|---|
| `WORKER` | 调度扫描线程 + 快慢两个执行池 + handler 注册表 | **定时任务专用节点** |
| `ADMIN` | 管理接口（CRUD / 手动触发 / 日志查询）+ handler 注册表（只读，供对账与参数表单） | 业务节点 / 后台节点 |
| `ALL` | 两者都装 | 开发环境、小规模单机 |
| `NONE` | 都不装 | 纯 C 端网关节点 |

**关键点：不拆代码仓库，不拆 Maven 模块。** 同一个 fat jar，靠启动参数区分：

```bash
# 业务节点
java -jar sa-admin.jar --smart.job.role=ADMIN

# 定时任务节点
java -jar sa-admin.jar --smart.job.role=WORKER --server.port=8081
```

理由：定时任务需要调用几乎所有业务 Service（清文件要 file 模块、扫任务过期要 marketing 模块）。
拆仓库意味着要么复制业务代码，要么引入 RPC——**为了一个部署诉求付架构的钱，不值**。
同一份代码不同角色，是这个规模下唯一划算的做法，而且**从 `ALL` 演进到 `ADMIN` + `WORKER` 时代码零改动**。

### 2.2 这样部署换来什么

| 场景 | 现在 | 角色化之后 |
|---|---|---|
| 业务代码改了要发版 | 所有节点重启，正在跑的任务被打断，启动窗口内的 cron 漏跑且无补偿 | **只滚 ADMIN 节点，WORKER 不动**，任务一次都不受影响 |
| 定时任务逻辑改了 | 同上 | 只滚 WORKER 节点，且可以挑低峰期 |
| WORKER 节点要重启 | —— | 抢占式调度天然支持：起两个 WORKER 滚动重启，另一个自动接管 |
| WORKER 停机时长 | 全局 10 秒（`awaitTerminationSeconds`） | **可以放到几分钟**——它不接流量，没有健康检查压力 |

⚠️ **WORKER 节点不要暴露到网关**。它虽然起了 web 端口（Spring Boot 应用的常态），
但只应开放 actuator。挂到负载均衡上会导致 C 端请求被路由到一个本该专心跑批的节点。

### 2.3 环境隔离

`t_smart_job.app_env` + 启动时的 `smart.job.env`，扫描时带上 `AND app_env = ?`。

不加会怎样：四套环境共用一份 DDL，一旦 dev 连到与 prod 同源的库（或共用 Redis），
**dev 机器会去抢生产任务并执行**。现在的 pub/sub topic 名是写死的 `smart-job-instance`，
跨环境串台没有任何阻拦。这个坑爆起来极难查，成本远高于加一列。

pub/sub 的 topic 名同步改为 `smart-job-instance:{env}`。

## 3. 核心设计：抢占式调度

### 3.1 为什么换掉「每节点自转 + 抢锁」

| | 现状（内存 Trigger + Redis 锁） | 抢占式（DB `next_trigger_time`） |
|---|---|---|
| 时钟源 | 每个节点的 JVM 时钟 | **只有数据库一个**（铁律 9） |
| 停机期间漏掉的调度 | 无痕消失，无法发现 | `next_trigger_time` 已过期，**在库里看得见**，可按策略补跑 |
| 配置变更感知 | pub/sub（不可靠）+ 全表轮询兜底 | 扫描时天然读到最新值，pub/sub 只做加速 |
| 「下次执行时间」 | 前端按 cron 估算 | **库里的真值** |
| 节点增减 | 每个节点都要重建全量内存状态 | 无状态，随便加减 |
| 一次性任务 | 表达不了 | 天然支持（执行完置终态） |

### 3.2 调度循环

每个 WORKER 节点起**一个**扫描线程（不是每任务一个 Trigger），
每轮**分两步查两张表**——主任务扫 `t_smart_job`，手动/重试扫 `t_smart_job_log`，
两者抢占的对象不同、互不干扰（详见 §3.9）。本节先讲主任务这一步。

```java
// ① 取 DB 时钟 + 到期任务
//    🔴 只捞「已经到点」的，绝不预读。曾经这里是 dbNow + 5s 的预读窗口，
//       实测（2026-08-12）导致三个连锁问题：任务真的提前 5 秒执行、
//       schedule_delay_ms 变成负数、以及**把 jitter 的打散效果整个抵消**
//       （打散让两个任务错到 :05/:06，预读又把它们一起拽回 :00 执行）。
//       扫描间隔本就 1 秒，不预读的最大迟到也就 1 秒，远比提前执行安全。
//    🔴 db_now 必须由 SQL 返回，绝不用 LocalDateTime.now()
SELECT NOW() AS db_now;

SELECT job_id, job_code, handler_name, trigger_type, trigger_value, jitter_seconds,
       next_trigger_time, trigger_version, misfire_strategy, block_strategy, ...
  FROM t_smart_job
 WHERE enabled_flag = 1 AND deleted_flag = 0
   AND app_env = #{env}
   AND next_trigger_time <= NOW()
 ORDER BY next_trigger_time
 LIMIT 200;

// ② 逐条处理（背压判断见 §3.5）
// ③ 抢占：影响行数 = 1 才算抢到
// ④ 抢到 → 插日志（唯一索引兜底，见 §6.2）→ 投递到对应 lane 的池
```

扫描间隔取 **1 秒**（可配）。这个频率下 200 行的索引扫描对 MySQL 是无感的，
而它换来的是「任何节点挂掉，最多 1 秒后别的节点接管」。

**索引**：`idx_next_trigger (app_env, enabled_flag, deleted_flag, next_trigger_time)`。

### 3.3 抢占 SQL：必须带状态防御

```sql
UPDATE t_smart_job
   SET next_trigger_time = #{nextTime},      -- Java 按 cron 算，基准是 db_now
       prev_trigger_time = #{thisTime},
       trigger_version   = trigger_version + 1
 WHERE job_id        = #{jobId}
   AND trigger_version = #{version}           -- 乐观锁：别人抢过就失败
   AND enabled_flag  = 1                      -- 🔴 防「扫描到 → UPDATE」之间被停用
   AND deleted_flag  = 0                      -- 🔴 同上，防被删除
```

没有后两个条件会出现「**幽灵执行**」：运营在扫描到数据和执行 UPDATE 之间的几毫秒里点了停用，
任务依然被抢占并投递。窗口很小但真实存在，而且它出现时运营的认知是"我明明关了"——
属于最难自证的那类故障。

⚠️ 配套：**更新任务配置时必须重算 `next_trigger_time`**，否则改了 cron 要等到下一次原定触发后才生效。
这是个容易漏的点——改 cron 的人默认它立刻生效。

### 3.4 misfire：停机期间漏掉的怎么办

抢占时判断 `db_now - next_trigger_time > misfire_threshold`：

| 策略 | 行为 |
|---|---|
| `SKIP`（默认） | 把 `next_trigger_time` 直接推到 `db_now` 之后的第一个点，**并写一条 `status=MISFIRE` 的日志** |
| `FIRE_ONCE` | 立即补跑一次，再推到下一个点 |

🔴 **`SKIP` 也必须记日志**。「跳过」和「从来没触发」在运营那儿是两件事——
不记录，运营永远不知道昨晚那次统计没跑。这是现状最大的可观测性缺口。

#### 🔴 `misfire_threshold` 不能是全局固定值 —— 它与背压跳过直接冲突

**冲突**：§3.5 的背压会让池满时的任务「跳过、留在库里等下一轮」。
若 SLOW 池被一个 5 分钟的长任务占着，被跳过的任务在库里就等了 5 分钟——
它**不是因为宕机漏掉的，是在排队**，却会被固定 60 秒的阈值判成 misfire。
策略若是 `SKIP`，就被静默丢弃了，**完全违背背压排队的初衷**。

先看这个误判在各档位的**实际危害**，它决定了该修哪里：

| 档位 | 池 | misfire 策略 | 误判后果 |
|---|---|---|---|
| `LIGHT` | FAST | SKIP | 跳过一次探活 —— **这正是它配 SKIP 的原因**，危害≈0 |
| `NORMAL` | SLOW | SKIP | 🔴 **清理/扫描任务被静默跳过**，危害最大 |
| `HEAVY` | SLOW | FIRE_ONCE | 立即补跑一次 —— **效果等同排队后执行**，危害≈0 |

所以**真正需要放宽阈值的是 `NORMAL` 档**。阈值纳入三档预设（§9.1）：
`LIGHT` 60s / `NORMAL` 5min / `HEAVY` 30min。

⚠️ **已知的残留局限（刻意不根治）**：阈值随档位只是缓解。
misfire 判据仍然分不清「系统没在跑」和「系统在跑但没排上」，
SLOW 池若持续堵塞超过档位阈值，依然会误判。
**这是可接受的退化**——那种情况下真正的问题是容量不足，正确动作是扩容而不是继续调阈值，
而 §7.2 的调度延迟指标就是发现它的手段。
根治需要引入「本节点跳过了哪些任务」的内存状态，那会破坏抢占式设计的无状态性，不划算。

### 3.5 背压：跳过，而不是消耗

**痛点**：WORKER 池满时若照常抢占，抢到了却投递不进去，只能 `DISCARD` ——
**本该被其他空闲节点接走的任务被就地误杀**。

评审建议的做法是「水位超 80% 则扫描线程 `sleep(2s)` 熔断」。本方案**不采用**，两个原因：

1. **所有节点都满载时，所有节点一起 sleep，任务全停且无人知晓。** 现实规模是 2 个 WORKER，
   负载大致均匀——一个满了另一个大概率也快满。sleep 只是把问题延后。
2. **sleep 是全局的**：第 1 条是 SLOW 任务且 SLOW 池满，但第 5 条是 FAST 任务而 FAST 池空着，
   sleep 把后者也一起饿死。

**采用的做法**：

```
遍历到期任务：
  ├─ 读该任务 handler 声明的 lane
  ├─ 对应 lane 的池已满 → continue，看下一条      ← 不抢占，不消耗
  └─ 有空位 → 抢占（UPDATE）→ 抢到就投递
```

**关键差别**：任务没被抢占，`next_trigger_time` 原封不动留在库里，
下一轮任何一个有空位的节点自然会接走。不需要水位阈值、不需要熔断、不需要 sleep，
**"被误杀"这个担忧被彻底消除——因为它压根没被消耗掉**。

配套可观测：某条任务连续多轮因池满被跳过、直到超过 misfire 阈值，就走 misfire 逻辑记日志。
**这样"因容量不足而漏跑"是可见的**，而不是静默 sleep 掉。这条日志也是扩容信号（配合 §7.2）。

### 3.6 Jitter：确定性打散，`ONE_TIME` 豁免

**痛点**：运营和开发最爱配 `0 0 0 * * ?`（零点）和 `0 0 * * * ?`（整点）。
50 个任务同时触发，DB 瞬时压力陡增，抢占的锁冲突也集中爆发。

`t_smart_job.jitter_seconds`（默认 0）。计算 `next_trigger_time` 时叠加偏移：

```java
// 🔴 确定性打散，不是 Random
int offset = jitterSeconds <= 0 ? 0 : Math.floorMod(Long.hashCode(jobId), jitterSeconds);
nextTriggerTime = cronNext.plusSeconds(offset);
```

**为什么不用 `Random(0, jitter)`**：

- 「未来 5 次执行时间」预览会失真，运营看到的和实际跑的对不上；
- 排查时"昨天 0:37、今天 0:12"很难与其他系统的日志对齐。

确定性打散下同一任务每天固定偏移，可预测、可预览、日志能对齐。
几十个任务的规模下 hash 撞车概率可忽略。

🔴 **`ONE_TIME` 强制 `jitter_seconds = 0`，保存时校验。**
「活动 8/20 00:00 开始」是**业务时间点**，不是调度时间点——打散 60 秒等于活动晚开 1 分钟。

### 3.7 阻塞策略：上一次还没跑完

判据用两层，缺一不可：

- **快判**：Redis 上一把 `smart-job-exec-{jobId}` 的并发锁（毫秒级）
- **兜底**：DB 里该 job 是否存在 `status = RUNNING` 且未超时的日志（节点崩溃时锁没了，DB 记录还在）

🔴 **DB 兜底那一查必须排除本次自己的记录**（`countRunning(..., excludeLogId)`）。
手动 / 重试路径是「先把日志行抢成 RUNNING、再判阻塞」，不排除自己就会<b>数到自己</b> ——
**那两条路径会永远被判定为阻塞、永远跑不起来**，而界面显示的是
「上一次执行尚未结束」，指向一个根本不存在的上一次。2026-08-12 实测复现。

| 策略 | 行为 |
|---|---|
| `DISCARD`（默认） | 丢弃本次，写 `status=BLOCKED` 日志 |
| `SERIAL` | 排进本节点执行队列（队列有界，满了降级为 DISCARD） |
| `OVERRIDE` | 中断上一次（`cancel(true)`），跑本次 |

🔴 **判定时序：必须在抢占之后**。完整时序见 §5.2——这一条极易写反，写反了长任务会卡死。

🔴 **锁不再传 leaseTime**，改用 Redisson 看门狗自动续期。理由：任务时长不可预测，
定死 30 秒一定会有长任务撞上（现状缺陷 #3）。看门狗的代价是节点崩溃后要等约 30 秒才释放——
可接受，且有 DB 兜底和僵尸扫描（§7.5）。

### 3.8 手动触发与自动调度统一

现状两把锁不互斥（缺陷 #2）。新设计里**手动触发不再是一条独立链路**：

```
后台点「立即执行」
  → ADMIN 节点写一条 t_smart_job_log（status=PENDING, trigger_source=MANUAL）
  → pub/sub 通知 WORKER 立刻扫一次（加速，丢了也不影响正确性）
  → WORKER 扫描线程发现 PENDING 记录 → 抢同一把 smart-job-exec-{jobId} 锁 → 执行
```

好处有三：手动和自动天生互斥；ADMIN 节点不需要有 handler 实现也能触发；
pub/sub 退化成纯加速通道，**丢消息最多晚 1 秒，不影响正确性**。

### 3.9 🔴 双表扫描：手动与重试走日志表，抢的对象不同

§3.8 的手动触发写的是 `t_smart_job_log` 的 PENDING 记录，§5.4 的重试锚在
`t_smart_job_log.fire_time` —— **两者都不在 §3.2 的主扫描 SQL 覆盖范围内**。
扫描线程每轮必须分两步：

🔴 **手动与重试共用同一个状态机**（v4 修订）：两者都表现为一条 `status = 0 (PENDING)`
的日志记录，区别只在 `fire_time`——手动是 `db_now`，重试是 `db_now + retry_interval`。
**扫描线程只认一个条件，没有分支。**

```java
// 第一步：主任务（读 t_smart_job）—— 见 §3.2 / §3.3
//        抢占对象：t_smart_job.trigger_version

// 第二步：手动 + 重试（读 t_smart_job_log）
SELECT log_id, job_id, job_code, handler_name, param_snapshot, biz_date, trigger_time, retry_seq
  FROM t_smart_job_log
 WHERE app_env = #{env}                    -- 冗余列，避免每秒 join
   AND status    = 0                        -- 🔴 只认 PENDING，手动与重试统一
   AND fire_time <= NOW()
 ORDER BY fire_time
 LIMIT 100;

// 抢占：🔴 抢日志行的 status，不抢 job 表的 trigger_version
UPDATE t_smart_job_log
   SET status = 1,                          -- RUNNING
       node_ip = #{ip}, node_id = #{nodeId}
 WHERE log_id = #{logId}
   AND status = 0;                          -- 乐观锁
// 影响行数 = 1 → 抢到，投递；= 0 → 别人抢走了
```

🔴 **为什么不让手动/重试也去抢 `trigger_version`**：那会把版本号顶掉、
连带改写 `next_trigger_time`，**扰乱正常的 cron 节奏**——
运营点一次「立即执行」，下一次定时就漂了。两条链路抢两个不同的对象，互不干扰。

四个配套细节：

1. **抢日志行之前也要先判该 lane 的池水位**，与 §3.5 保持一致。
   否则抢到了却投递不进去，记录卡在 `RUNNING` 直到僵尸扫描才被回收 ——
   比留在 `PENDING` 让别的节点接走差得多。
2. **`t_smart_job_log` 加冗余列 `app_env`**。否则日志表扫描要 join `t_smart_job`
   才能做环境过滤，每秒一次的 join 不划算。
3. **手动触发时的 `biz_date`**：默认按 handler 的 `bizDateOffset` 算（§4.5），
   **运营可覆盖**（重跑历史日期用）。这是「一键重跑」（§9.2）的入口。
4. 🔴 **抢到日志行后、投递之前，必须再查一次 job 的状态**。这条路径没有经过 §3.3 的
   抢占 SQL，拿不到那里的状态防御。校验口径与主链路**刻意不同**：

   | 字段 | 主链路（SCHEDULE） | 日志链路（MANUAL / 重试） |
   |---|---|---|
   | `deleted_flag` | 必须为 0 | 必须为 0 |
   | `handler_missing_flag` | 必须为 0 | 必须为 0 |
   | `enabled_flag` | 必须为 1 | **不检查** |

   `enabled_flag` 刻意放行是**保留现有语义**——现状 `SmartJobService.execute` 的
   javadoc 写着「忽略任务的开启状态，立即执行一次」，运营需要这个能力来测试未启用的任务。
   但 `deleted_flag` 和 `handler_missing_flag` 必须挡，否则会执行一个已删除或已失联的任务。

### 3.10 🔴 为什么砍掉 `FIXED_DELAY`

**它与抢占式调度在概念上不相容。** `FIXED_DELAY` 的语义是「上一次**执行结束**后再等 N 秒」，
而抢占发生在任务**开始之前**——那一刻根本不知道它什么时候结束，算不出真正的下一次触发时间。

若强行保留，只有两条路，都不可接受：

**① 直接按 `触发时刻 + N 秒` 算** —— 那产出的是 `FIXED_RATE`（固定频率）。
名字没变、配置没变、日志没变，**语义悄悄换了**。
库里 `示例任务2`（`fixed_delay=120`）的行为会静默改变。这正是本项目铁律反复在防的那种形状。

**② 抢占时把 `next_trigger_time` 推到极大值（如 2099-12-31），执行完在 `finally` 里回填** ——
🔴 **这会让调度器自监控（§7.1）瞎掉**：健康检查的判据是
`next_trigger_time < db_now - 5min`，而 2099 永远不满足。
一旦节点在执行中崩溃、`finally` 没跑到，这个值就永久停在 2099 ——
**任务永久死亡且不会触发任何告警**，是最坏的一类故障。
要救就得让僵尸扫描额外负责重置它，凭空多一条耦合。

**所以直接砍掉。** 代价接近零：

- CRON 支持秒字段（`*/10 * * * * *` = 每 10 秒），短周期场景完全覆盖；
- 「不许与上一次重叠」本来就是 `block_strategy` 的职责（§3.7），
  不该由触发类型来表达——**一个语义只在一处表达**。

**存量迁移**：`示例任务1/2` 随本次重构一并删除（见附表）。
若生产库另有 `fixed_delay` 任务，迁移脚本转成等价 cron，
并在迁移说明里**写明语义变化**：从「上次跑完 + N 秒」变成「每 N 秒」。

## 4. handler 注册协议

### 4.1 注解声明

```java
@SmartJobHandler(
        name  = "fileOrphanClean",              // 🔴 库里存这个，不是类名
        title = "临时文件孤儿清理",
        group = "SYSTEM",
        lane  = Lane.SLOW,                      // 🔴 由 handler 声明，运营不可改
        params = {
                @JobParam(key = "retainDays", type = INT, required = true,
                          defaultValue = "7",   desc = "保留天数"),
                @JobParam(key = "batchSize",  type = INT, defaultValue = "500",
                          desc = "单批处理条数")
        },
        idempotent    = true,                   // 声明可安全重跑 → 才允许配 retry
        bizDateOffset = 0,                      // 🔴 见 §4.5
        defaultTimeoutSeconds = 600
)
@Component
public class FileOrphanCleanJob implements SmartJob {

    @Override
    public String execute(SmartJobContext ctx) throws Exception {
        int retainDays = ctx.intParam("retainDays", 7);
        LocalDate cutoff = ctx.bizDate().minusDays(retainDays);   // 不是 LocalDate.now()
        int total = 0;
        while (true) {
            ctx.checkCancelled();                                  // 🔴 见 §5.3
            List<Long> batch = dao.findUnreferenced(cutoff, ctx.intParam("batchSize", 500));
            if (batch.isEmpty()) break;
            cleanService.deleteBatch(batch);                       // 事务在这个独立 Bean 里
            total += batch.size();
        }
        return "清理临时文件 " + total + " 个，截止日期 " + cutoff;
    }
}
```

扫描时用 `AopUtils.getTargetClass(bean)` 取真实类读注解——**这是整条链路对代理免疫的关键**。

### 4.2 🔴 启动时双向对账

这是终结缺陷 #1 的机制，比换注册方式本身更重要：

| 情况 | 处理 |
|---|---|
| 库里配了、代码没有 | job 标记 `MISSING_HANDLER`，**不执行**，后台列表红显，启动日志 `ERROR` |
| 代码有、库里没配 | 启动日志 `WARN` + 后台「未挂载 handler」列表，提供一键创建 |
| 同名 handler 注册两次 | **启动直接失败**（`IllegalStateException`）。静默取其一是最坏的结果 |

ADMIN 节点也装 handler 注册表（只读），用途有二：新增任务时校验 `handler_name` 真实存在、
以及按 `@JobParam` 渲染参数表单（§4.3）。

### 4.3 参数：从裸 String 变成声明式表单

现状 `param` 是一个裸 `varchar(1000)`，运营在文本框里手填 JSON——
「谁也不知道该填什么」的典型退化点。

新设计：`@JobParam` 声明 → 后台按声明渲染表单（int 渲染数字框、enum 渲染下拉、必填带红星）
→ 提交时按声明校验 → 存 JSON。**结构可校验、可提示、可测试，自由文本不是。**

### 4.4 执行上下文

```java
public record SmartJobContext(
        String jobCode,
        String handlerName,
        Map<String, Object> params,
        LocalDate     bizDate,        // 🔴 见 §4.5
        LocalDateTime triggerTime,    // 🔴 DB 时钟，本次调度的"原定"触发时刻
        LocalDateTime dbNow,          // 🔴 DB 时钟。禁止 handler 内 LocalDateTime.now()
        String traceId,
        Long   logId,
        int    shardIndex,            // 本期恒为 0
        int    shardTotal,            // 本期恒为 1
        BooleanSupplier cancelled
) {
    public int intParam(String key, int def) { ... }
    public void checkCancelled() { if (cancelled.getAsBoolean()) throw new JobCancelledException(); }
}
```

🔴 **`dbNow` 的存在是为了消灭 handler 里的 `LocalDateTime.now()`**。
同一条铁律在 `TaskPeriodResolver` 里已经立过一次
（"一旦 period_key 在 A 处算、过期扫描在 B 处用 now() 算，就又是两个时钟源"，
交接文档记着 497 行数据的实测代价）。定时任务是这个坑的重灾区——
每个 handler 都天然想写 `LocalDate.now()`。**注入它，并在 code review 里禁掉裸调用。**

### 4.5 `bizDate` 的定义（明确否决"默认 T-1"）

```
bizDate = triggerTime.toLocalDate() + bizDateOffset      // 自动调度
bizDate = 运营指定的日期                                   // 手动重跑
```

**两个决定：**

**① 基准是 `triggerTime`，不是 `dbNow`。** misfire 补跑时 `triggerTime` 是原定触发时刻、
`dbNow` 是现在——用 `dbNow` 会让**所有补跑处理错日期**，而补跑恰恰是 `bizDate` 存在的意义。

**② `bizDateOffset` 默认 0，由 handler 显式声明，框架不猜。**

评审建议「通常定时任务处理 T-1 数据，默认应为 `dbNow().minusDays(1)`」——**本方案否决**。
理由：这对数据统计类是对的，对其余全错。文件孤儿清理、任务过期扫描、活动状态流转的
`bizDate` 就是当天；每小时跑一次的任务谈 T-1 更没有意义。

框架给一个"通常"的默认值，恰恰是在**制造**评审想避免的那类
「手工执行是对的、自动跑就不对」的 bug，只是方向反了——
以后每个非统计类 handler 的作者都要记得覆盖它，忘一个错一个，而且错得很安静。

**这是 handler 的语义，不是框架的默认**，与 `idempotent` 同理。统计类 handler 写 `bizDateOffset = -1`。

## 5. 执行模型

### 5.1 🔴 快慢车道：物理隔离

**痛点**：所有任务共用一个池时，2 个跑 30 分钟的清洗任务能瞬间吃光线程，
让每分钟一次的 100ms 探活任务全部 `DISCARD`。**隔离是稳定性的第一要义。**

```yaml
smart.job.executor:
  fast:                        # < 10 秒的轻任务
    core-size: 4
    max-size: 8
    queue-capacity: 64         # 队列可以大：短任务堆积很快消化
  slow:                        # 长任务
    core-size: 2
    max-size: 4
    queue-capacity: 1          # 🔴 队列近 0：排 30 分钟才开始跑，不如直接拒绝并告警
```

**三条强制约束**（否则是纸面隔离）：

1. 🔴 **`lane` 由 `@SmartJobHandler` 声明，运营在后台不可修改。**
   否则运营把一个慢任务标成 FAST，快车道当场被毒死。handler 作者才知道自己快慢。
2. 🔴 **FAST lane 的 `timeout_seconds` 上限强制 30 秒**，保存时校验，超时即中断。
   **声明必须被执行强制**，否则一个"声称 FAST 实则 5 分钟"的 handler 照样毒死快车道。
3. **就两条车道，不做 N 条可配的。** SLOW 池 `core=2` 本身就是慢任务的全局并发限流器——
   用池大小当限流器，比引入独立的限流概念简单得多，也够用。

与扫描线程彻底分离——**扫描线程永远不执行任务**。现状是同一个 `ThreadPoolTaskScheduler`
既调度又执行，`core-pool-size=2` 时两个慢任务就能让全局停摆。

⚠️ 两个池都用 `sa-base` 现成的 `ThreadPoolUtil` 构建——它已实现 **MDC 跨线程透传与优雅停机**，
不要自己 new（详见 §7.3）。

### 5.2 执行流程

🔴 **四步顺序不可调换**（v4 修订。写反第 ①②③ 步会导致长任务永久卡死）：

```
① 判池水位（节点级）  → 满则 continue，不抢占，留给别的节点
② 抢占              → UPDATE 推进 next_trigger_time / 抢日志行 status
③ 判 block_strategy（集群级）→ 阻塞则写 status=BLOCKED 日志，终止本次投递
④ 插 status=RUNNING 日志（唯一索引兜底，见 §6.2）
  → MDC.put(traceId)                        // §7.3
  → 投递到 lane 对应的池
  → Future.get(timeoutSeconds)
  → 落 status / result_summary / error_detail / 耗时（DB 时钟）
  → catch (Throwable)                       // 🔴 不是 Exception，见 §5.3
  → finally: MDC.clear()  +  释放锁
```

#### 🔴 为什么 ① 是"跳过"而 ③ 是"抢占后再判" —— 两者看似矛盾，规则只有一条

实现者会同时面对两个「现在跑不了」的条件，却要**反着处理**，不说清楚一定写错。判据是：

> **节点级的判据 → 跳过（不抢占）；集群级的判据 → 抢占（推进时间）后再处理。**

| 条件 | 性质 | 换个节点有用吗 | 处理 |
|---|---|---|---|
| 池满（①） | **节点级** | **有用**，别的节点可能空着 | 不抢占，`next_trigger_time` 留在库里等人接 |
| 上一次还在跑（③） | **集群级** | **没用**，换谁都一样被挡 | 抢占推进时间，写 BLOCKED 日志 |

**③ 若写成"发现阻塞就不抢占"会怎样**：一个 1 分钟触发、实际跑 5 分钟的任务，
`next_trigger_time` 永远停在过去 → 每秒被扫到、每秒被判阻塞 → **时间轮再也不转**。
更糟的是它会顺带触发 §7.1 的「超期未触发」告警，把一个正常的长任务报成"调度器挂了"。

**先抢占的附带收益**：长任务运行期间 `next_trigger_time` 一直向前走，
健康检查看到的是正常值，**不会误报**。

⚠️ **①④ 之间的残留竞态**：判完水位到真正 `submit` 之间，别的 lane 的任务可能把池占满，
导致投递被拒。此时已经抢占过，只能写 `BLOCKED`。概率低且可见，接受——
但代码里必须 `catch (RejectedExecutionException)` 并落日志，
别让它变成一个没人接的未捕获异常（执行池的拒绝策略是 `ABORT`，见 §5.1）。

### 5.3 超时与中断

`Future.get(timeoutSeconds)` 超时后 `cancel(true)`，日志置 `status=TIMEOUT`。

🔴 **必须在 `SmartJob` 的 javadoc 里写死一条**：

> `cancel(true)` 只是 `Thread.interrupt()`。**不响应中断的任务砍不掉。**
> 凡是循环处理批量数据的 handler，每批开头必须调 `ctx.checkCancelled()`；
> 凡是发起 HTTP / 远程调用的，必须自带连接与读取超时。

这和 QLExpress 那个"假超时"是同一类问题
（`common-api/.../QLExpress 3.x 升级 4.x 避坑与架构演进备忘录.md` §二）——
**框架给的超时只能保证「不再等你」，不能保证「你停下来」**。提前说清楚，比事后排查便宜得多。

#### 🔴 执行外层必须 `catch (Throwable)`，而且它还不够

`OutOfMemoryError` / `NoSuchMethodError`（发版引入不兼容包时的典型症状）属于 `Error` 不是 `Exception`。
只 `catch (Exception)` 的话线程直接暴毙，`UPDATE status = FAIL` 和 `MDC.clear()` 统统不执行，
**记录永久停在 `RUNNING`**，还会让 `block_strategy` 的 DB 兜底判据永久误判为「上一次还在跑」。

⚠️ **现状代码已经是 `catch (Throwable t)`**（`SmartJobExecutor` 的 `run()` 与 `execute()` 两处）。
本条不是新增防护，而是**「重写时别改坏」**——别在重构时顺手"规范化"成 `catch (Exception)`。

⚠️ **但 `catch (Throwable)` 不能替代僵尸扫描（§7.5）**：OOM 之后 `finally` 里的写库本身
也要分配内存、拿连接，同样可能失败；进程被 `SIGKILL` 时更是一行都跑不到。两层分工是：

| 机制 | 挡什么 |
|---|---|
| `catch (Throwable)` | 99% 的情况，让状态**立刻**正确 |
| 僵尸扫描（§7.5） | 「连写库都失败了」和「进程直接没了」 |

写清楚这个分工，是为了防止有人看到 `catch (Throwable)` 就把僵尸扫描当冗余砍掉。

### 5.4 重试

🔴 **不在内存里 sleep 重试**——节点崩溃时重试计划全丢，且白占执行线程。
重试是**一条新的日志记录**，由扫描线程（§3.9）在到点时捞起来。

#### 状态机（v4 修订，与手动触发完全统一）

```
                 ┌──────────────────────────────────────────┐
执行失败 ────────►│ ① 原记录置 status = 3 (FAIL)              │
（同一事务）      │    fire_time 保持 NULL  🔴                 │  ← 历史现场，永不改动
                 ├──────────────────────────────────────────┤
                 │ ② 若 retry_seq < job.retry_times，        │
                 │    INSERT 一条新记录：                     │
                 │      status         = 0 (PENDING)         │
                 │      retry_seq      = 原 + 1              │
                 │      trigger_time   = 原样继承  🔴          │
                 │      trigger_source = 原样继承             │
                 │      param_snapshot = 原样继承  🔴          │
                 │      biz_date       = 原样继承  🔴          │
                 │      retry_of_log_id= 原 log_id            │
                 │      fire_time      = db_now + interval    │
                 └──────────────────────────────────────────┘
                                    ↓
                     §3.9 扫描：status = 0 AND fire_time <= NOW()
```

手动触发插的是同样形状的记录，只是 `fire_time = db_now`、`trigger_source = MANUAL`。
**扫描线程因此只有一个条件、没有任何分支。**

🔴 **三条必须写死的约束**（缺一条就会出问题）：

1. **失败记录的 `fire_time` 必须留 NULL**，只有新插入的 PENDING 记录带时间。
   ——这才是"不会被反复扫到"的真正保证。光说"插新记录"不够：
   老记录只要还带着 `fire_time`，下一秒就会被再次扫到，**变成无限重试**。
2. **置 FAIL 与插 PENDING 必须在同一个事务里**。
   否则 FAIL 写成功、重试记录插失败 → **重试静默丢失**，而日志上看起来一切正常。
3. **`trigger_time` / `param_snapshot` / `biz_date` 必须原样继承**，不能重读当前配置。
   重试的是"当时那一次"，配置可能已经被人改过；`trigger_time` 继承还同时保证了
   `uk_job_trigger` 靠 `retry_seq` 递增来区分同一触发点的多次尝试（§6.2）。

这样一来，后台能看到完整的「失败 → 重试 → 成功」链条，且每一环的现场都完整保留。

**重试的前提是幂等**：只有 `@SmartJobHandler(idempotent = true)` 的 handler 才允许配
`retry_times > 0`，保存时校验。不幂等的任务自动重试 = 把一次失败变成两次副作用。

### 6.2 `t_smart_job_log`

```sql
log_id             bigint        -- 🔴 int → bigint
job_id / job_code / job_name / handler_name
app_env            varchar(16)   -- 🔴 冗余列：日志表扫描要按环境过滤，避免每秒 join（§3.9）

trigger_time       datetime      -- 🔴 本次调度的原定触发时刻（唯一索引组成）
retry_seq          int  default 0-- 🔴 第几次重试（唯一索引组成）
biz_date           date          -- 🔴 业务日期，补跑的锚点

                                 -- 0-PENDING 1-RUNNING 2-SUCCESS 3-FAIL
                                 -- 4-TIMEOUT  5-BLOCKED 6-MISFIRE 7-INTERRUPTED
execute_start_time datetime NULL -- 🔴 DB 时钟。PENDING（待执行/待重试）记录为 NULL —— 它还没开始
execute_end_time   datetime      -- DB 时钟
execute_time_millis bigint

result_summary     varchar(512)  -- handler 返回的人话
error_detail       varchar(2000) -- 截断的堆栈（保留现状 1800 截断）

retry_of_log_id    bigint        -- 这次是哪次的重试
fire_time          datetime      -- 🔴 何时该被捞起执行。PENDING 才有值，其余状态恒 NULL
ip / process_id / program_path   -- 🔴 均可空：抢占到该记录时才知道，PENDING 为 NULL
create_name / create_time

UNIQUE KEY uk_job_trigger (job_id, trigger_time, retry_seq, trigger_source)   -- 🔴 见下
KEY idx_job_time  (job_id, execute_start_time)
KEY idx_pending   (app_env, status, fire_time)         -- 🔴 §3.9 日志表扫描用
KEY idx_running   (status, execute_start_time)         -- 僵尸扫描用
```

🔴 **`uk_job_trigger` 是本方案对"不重复执行"的物理保证。**

抢占式调度理论上保证单次执行，但网络分区、长 GC 停顿、时钟跳变下仍有窗口。
加这个唯一索引后，抢到调度权的节点**先插日志**，插失败（重复键）即说明别人已经执行了这个触发点，
直接放弃。这把"靠逻辑正确"变成了"靠数据库约束"——
和你们已有的 `biz_id_required`、`uk_pool_code` 是同一个套路：**把口头约定变成表里的强制契约**。
成本只是一个索引。

🔴 **索引里必须带 `trigger_source`**，否则手动触发会撞车：
`MANUAL` 记录的 `trigger_time` 取的是点击时刻（`db_now`），若恰好与该任务的 CRON 触发时刻
撞在同一秒，唯一键冲突会让手动执行直接失败。
带上 `trigger_source` 后两类记录物理隔离——语义上本就该分开：
**`SCHEDULE` 的 `trigger_time` 是「原定调度时刻」，`MANUAL` 的是「点击时刻」，不是一个概念。**

⚠️ 加了之后仍有一个碰撞：**同一秒内连点两次「手动执行」**。
**这个保留，它是防重特性**——但必须捕获重复键并转译成人话
（「该任务 1 秒内已被触发，请勿重复点击」），
理由同铁律 8：「唯一索引直接抛 SQL 异常对运营不友好」。

🔴 **`trigger_source` 删掉 `RETRY` 取值**（v4 修订）。重试记录**原样继承**原记录的
`trigger_source`（定时的重试仍是 `SCHEDULE`，手动的重试仍是 `MANUAL`），
靠 `retry_seq > 0` 表达「这是一次重试」。两个好处：

- **`retry_seq > 0` 本身就是重试标记**，不需要第二处表达同一件事；
- 避免边角碰撞：若重试统一记 `RETRY`，「手动触发的重试」与「定时的重试」
  可能在同一 `trigger_time` 上撞进同一个键空间。

**同一触发点的多次尝试靠 `retry_seq` 递增区分**：
`(job_id, T, 0, SCHEDULE)` 失败 → `(job_id, T, 1, SCHEDULE)` → `(job_id, T, 2, SCHEDULE)`。
这正是 §5.4「`trigger_time` 必须原样继承」那条约束存在的原因。

🔴 **PENDING 记录的四个「执行时才有」的列必须可空**（`v3.59.0` 订正）：
`execute_start_time` / `ip` / `process_id` / `program_path`。

原本它们是 `NOT NULL` 无默认值，而失败重试要插的正是一条**还没开始执行**的 PENDING 记录 ——
插入直接报 `Field 'execute_start_time' doesn't have a default value`。
致命的是连带效应：置 FAIL 与插 PENDING 在同一事务里（那是为防「重试静默丢失」刻意设计的），
插入失败让整个事务回滚，**连那条本该置 FAIL 的 UPDATE 也一起没了** ——
记录停在 RUNNING，而 RUNNING 又让阻塞判断永久误判为「上一次还在跑」，
<b>这个任务从此再也不会被执行</b>。**为防静默丢失而加的安全机制，自己成了放大器。**

⚠️ 修法不是填占位值（`ip='-'`、`execute_start_time=now`）—— 那是在数据里写谎话，
列表页会给一条根本没跑的记录显示「开始时间」，而且下一条创建 PENDING 记录的路径迟早再撞一次。
**让模型说实话：没开始执行，这几列就是 NULL。**

🔴 **`status` 必须是多态而不是布尔**。现状 `saveLogBeforeExecute` 先写 `successFlag = true`，
进程崩了就永久留一条假「成功」——运营看到的是绿的，实际那次根本没跑完。

## 7. 可观测与自愈

### 7.1 告警（三条，第三条最容易漏）

| 触发条件 | 说明 |
|---|---|
| 连续失败 ≥ N 次 | `continuous_fail_count`，成功时清零 |
| 单次执行超时 | `status = TIMEOUT` |
| 🔴 **任务超期未触发** | 存在 `enabled=1 且 next_trigger_time < db_now - 5min` 的任务 —— **说明调度器本身挂了** |

第三条是「调度器自监控」。前两条只能告诉你任务跑错了，**只有第三条能告诉你任务根本没在跑**。
现状完全没有这个能力：调度线程死掉，系统安静如常。

通道复用现有的消息模块（`sa-base/module/support/message`）或企微机器人，本期不新建。

### 7.2 调度延迟指标 —— 扩容信号

`schedule_delay_ms = execute_start_time - trigger_time`，每次执行落库。

**背压（§3.5）解决的是"满了怎么办"，但它回答不了"什么时候该扩容"。**
延迟持续增长就是容量不足的信号。这个数应在后台任务列表直接可见
（如「平均延迟 1.2s / 昨日最大 45s」），而不是等 `MISFIRE` 告警响了才发现。

### 7.3 MDC / TraceId —— 基础设施已就位，只差接线

定时任务发起的调用报错时，没有网关请求介入，链路串不起来。解法是执行前注入 MDC。

**好消息：这条的成本远低于预期，因为地基全都有了：**

| 已有 | 位置 |
|---|---|
| web 请求的 traceId 注入 | `sa-admin/.../filter/LogTraceFilter.java` |
| 日志 pattern 已含 `%X{traceId}` | `sa-admin/src/main/resources/logback-spring.xml` |
| **MDC 跨线程池透传 + 防串台** | `sa-base/.../util/ThreadPoolUtil.java`（提交时快照、子线程恢复、执行后还原） |

所以定时任务要做的只有两件：

1. 执行前 `MDC.put("traceId", ...)`，`finally` 里还原；
2. 执行池挂一个 **`TaskDecorator`** 做 MDC 快照透传。

> ⚠️ **v4 撰写时此处写的是「两个池都用 `ThreadPoolUtil` 构建」，实施时发现该说法不成立，已订正。**
> `ThreadPoolUtil` 是一个**全局静态单例池**（固定 5/10、`CallerRunsPolicy`），**不是构建器** ——
> 定时任务用它就等于和其它业务异步共用队列，正好破坏「定时任务不能拖垮业务、
> 业务也不能饿死定时任务」这个隔离前提，而资源隔离恰恰是本次重构要立起来的东西。
> 正确做法是**自建池 + 搬它那套 MDC 透传逻辑**，落地为
> `SmartJobMdcTaskDecorator`（`core` 包）。
>
> 🔴 装饰器的 `finally` 里必须**还原快照**而不是 `MDC.clear()`：
> 线程池的线程是复用的，直接 clear 会抹掉下一个任务的上下文；
> 只 put 不还原则会串号 —— 看到的 traceId 属于上一个任务，比没有 traceId 更误导人。

放**第一档**。半小时的改动，收益立竿见影。

### 7.4 执行日志绑定与实时查看

**痛点**：任务执行到一半卡住时，`t_smart_job_log` 只有结束时才写入的 `error_detail`，
中间的 `log.info` 全在服务器滚动文件里，运营和开发看不到，只能登机器 grep 还得按时间猜。

**分两步做，不要一步到位：**

**第一步（第三档前半）：日志与执行记录绑定。**
自定义 Appender 按 `ThreadLocal` 里的 `logId` 捕获本线程日志，任务结束时把片段落到文件模块。
**这一步就解决了 80% 的痛**——不用再 grep、不用按时间猜，点开那次执行就能看到它自己的日志。

**第二步（第三档后半）：实时查看。**
片段暂存 Redis List（`key = job-log:{logId}`），后台提供【查看实时日志】按钮。

⚠️ 第二步的三个坑，做之前先想清楚：

1. 🔴 **Redis List 必须 `LTRIM` 限条数**（建议 2000 条）+ 设 TTL（1 天）。
   一个疯狂打日志的任务能写爆 Redis。
2. **Appender 必须异步批量写**，否则每条日志一次 Redis 调用，日志量大时 Appender 本身成瓶颈。
3. **任务内部起了子线程/线程池时 ThreadLocal 会丢**——用 `ThreadPoolUtil` 可缓解，
   但仍需在文档写明，否则"为什么我的日志没被收集"会变成新的排查负担。

### 7.5 僵尸记录回收

节点崩溃会留下 `status = RUNNING` 且永远不会结束的记录，
它会让 `block_strategy` 的 DB 兜底判据永久误判为「上一次还在跑」。

内置任务定期扫描 `status = RUNNING AND execute_start_time < db_now - max(timeout*2, 10min)`
→ 置为 `INTERRUPTED`，写明「疑似节点异常退出」。

⚠️ **`INTERRUPTED` 要不要自动补一条重试记录？** 要，但**沿用 §5.4 的同一套状态机**：
若 `retry_seq < job.retry_times` 就插一条新的 PENDING。
不要为僵尸场景另写一套恢复逻辑——**一个状态机能表达的事，不要写第二个**，
否则两套逻辑迟早在 `retry_seq` 的推进上打架。

### 7.6 内置任务（自举）

启动时若不存在则自动写入库，`job_group = SYSTEM`，**后台不可删除、可停用**：

| handler | 作用 | 默认调度 | lane |
|---|---|---|---|
| `_jobLogClean` | 清理 N 天前执行日志 + 终态 ONE_TIME 任务 | 每天 03:00 | SLOW |
| `_jobZombieScan` | 僵尸 RUNNING 记录回收 | 每 5 分钟 | FAST |
| `_jobHealthCheck` | 超期未触发检测 + 告警 | 每 5 分钟 | FAST |

**这三个任务同时也是重构的第一批验收用例**——它们跑通了，说明调度器自己是对的。

## 8. 优雅停机与发布流程

### 8.1 停机顺序

```
① 扫描线程立即停止（不再抢新任务）
② 等待执行中的任务完成，最长 smart.job.shutdown-await-seconds（默认 60）
③ 仍未完成的 → 日志置 INTERRUPTED，写明「节点停机」
④ 释放所有 Redis 锁
```

现状 `awaitTerminationSeconds = 10` 且超时被硬砍，留下悬挂的「执行中」记录。
WORKER 节点独立部署后这个值可以放宽——它不接流量，没有健康检查压力。

### 8.2 发布流程（这是独立部署的收益兑现处）

**业务代码变更**：只滚 ADMIN 节点。WORKER 不动，任务零影响。

**定时任务逻辑变更**：滚 WORKER 节点。两种做法——

- 单 WORKER：低峰期停机发布，靠 misfire 策略处理窗口内漏掉的调度（`SKIP` 会留 MISFIRE 日志，看得见）
- 双 WORKER：滚动重启，抢占式调度天然接管，**零漏跑**

⚠️ 发布前建议先在后台把长耗时任务临时停用，等排空再发——虽然停机会等 60 秒，
但一个跑 10 分钟的对账任务仍然会被砍。这条应写进发布 checklist。

### 8.3 🔴 容器环境：改成启动自检，别靠文档提醒运维

K8s 默认 `terminationGracePeriodSeconds = 30`，30 秒后直接 `SIGKILL`。
**Java 里配 60 秒优雅停机，在 K8s 上永远不会被完整执行**——而这个事实只在第一次发版、
任务被硬砍时才暴露。

> 说明：本项目当前仓库内**没有 Dockerfile 也没有 k8s manifest**，所以这是**上容器时**的条件项。

与其写进文档等人记得，不如让配置错误在启动时自己喊出来：

```java
// WORKER 节点启动时自检
if (terminationGracePeriodSeconds > 0
        && terminationGracePeriodSeconds < shutdownAwaitSeconds + 30) {
    log.error("==== SmartJob ==== terminationGracePeriodSeconds({}) 小于 shutdown-await({})+30，"
            + "优雅停机会被 SIGKILL 打断，请调整 deployment.yaml", ...);
}
```

符合铁律 16 的精神：**前提不成立时，"通过"和"空过"要能分得出来。**

## 9. 运营体验（"好用"的集中落点）

前面八节大多在解决"先进"和"稳"。这一节专门管"好用"——**它和另外两个目标是有张力的**。

### 9.1 🔴 三档预设：不要让运营直面 11 个旋钮

把前面所有能力加完，一个任务的配置项会是：
cron、jitter、timeout、retry_times、retry_interval、misfire、block、bizDateOffset、alarm、param…

**运营面对这一屏下拉框会直接懵。"先进"做到了，"好用"会被这堆旋钮毁掉。**

做成三档预设，每档是一组捆绑好的参数，勾「高级」才展开细调：

| 档位 | 典型场景 | timeout | block | misfire | **misfire 阈值** | jitter | retry |
|---|---|---|---|---|---|---|---|
| **轻量高频** `LIGHT` | 探活、状态流转 | 30s | DISCARD | SKIP | **60s** | 30s | 0 |
| **常规** `NORMAL` | 清理、扫描 | 5min | DISCARD | SKIP | **5min** | 60s | 1 |
| **重批处理** `HEAVY` | 统计、对账 | 30min | SERIAL | FIRE_ONCE | **30min** | 0 | 2 |

🔴 **`misfire 阈值` 这一列不是凑数的，它是背压跳过能否成立的前提**（详见 §3.4）：
阈值若全局固定 60 秒，被背压跳过、在库里排队 5 分钟的任务会被误判成 misfire 而静默丢弃。
`NORMAL` 档危害最大（SLOW 池 + SKIP），所以它的阈值必须放宽到 5 分钟。

这几个参数本来就高度相关——FAST 的任务几乎必然 `DISCARD`（错过一次无所谓），
重批处理必然要 `FIRE_ONCE`（那天的数据不能少）。
**用档位把相关性表达出来，比让运营自己去悟这些组合便宜得多。**

两条实现约束：

- **档位与 handler 声明的 `lane` 必须兼容**，保存时校验：
  `lane = FAST` 的 handler 只能选 `LIGHT`（其余档位的 timeout 突破 FAST 的 30 秒上限）。
- **`preset_code` 只记录来源**，落库的是展开后的具体值。
  以后调整档位默认值**不回溯**已建任务——否则改一次预设，几十个线上任务的行为一起变。

### 9.2 一键重跑（从第三档提到第二档）

任务失败后运营的第一反应就是重跑。**没有这个，所有告警都退化成"通知开发去查"。**
它比实时日志更基础，因此提前到第二档。

要点：**重跑必须带上原始 `param_snapshot` 和原始 `bizDate`**，
而不是拿当前配置重跑——配置可能已经被人改过了。

### 9.3 衍生任务：全局可见、就地只读、可跳转（§13 问题 2 结案）

向导生成的任务（`source = SYSTEM`）：

- **在定时任务列表全局可见**，打上「衍生任务」标签；
- **禁止就地修改 param / cron / 启停**；
- 提供【跳转至来源】链接（如 → 双11活动配置页）。

这样既满足排障需要的全局视图（藏起来会导致"明明有任务在跑却哪儿都找不到配置"），
又避免了配置入口脑裂（同一个东西两个地方能改，迟早不一致）。

### 9.4 内置通用 HTTP 任务 —— 带闸门

**痛点**：「每天凌晨调一下某个内网 API 触发刷新」，为此新建 Java 类 + 发一次版不划算。

内置 `@SmartJobHandler(name = "httpCaller", group = "OPS", lane = FAST)`，
用 `@JobParam` 声明 `url` / `method` / `headers` / `body`。

🔴 **这等于在后台开了一个 SSRF 入口，必须配套四道闸门**：

1. **目标地址白名单**（网段或域名列表，配在 yaml 里，**后台不可改**）
2. 只允许 `http` / `https`，禁 `file://` / `gopher://` 等协议
3. 强制连接与读取超时上限
4. **响应体截断**（别把 10MB 响应塞进 `result_summary`）

🔴 **定位必须写死**：`job_group = OPS`，文档写明「用于运维探活与触发，**不承载业务逻辑**」。
否则它会退化成"什么都用 HTTP 任务糊"——那是配置化脚本的另一种形态，且更没有版本管理。

### 9.5 `ONE_TIME` 任务的生命周期

一次性任务执行完置 `terminal_flag = 1` 后会永久留在表里。
几百个活动之后 `t_smart_job` 会非常脏，列表页被历史任务淹没。

- 列表页**默认过滤掉 `terminal_flag = 1`** 的任务（可勾选查看）；
- `_jobLogClean` 一并软删 N 天前的终态 ONE_TIME 任务。

### 9.6 变更审计：复用 `datatracer`，不新建表

定时任务能触发发奖和结算，改 cron / 改参数 / 启停都属高危操作，改动无痕不可接受。

`sa-base/module/support/datatracer` 是现成的数据变更追踪模块，**直接挂上去**。
不要为这个模块单独建审计表——能力已经有了，新建等于多一份要维护的东西。

## 10. 避坑清单（照此验收）

1. **handler 名注册 + 启动双向对账**，杜绝 CGLIB 静默失效（缺陷 #1）
2. **时间只认 DB 时钟**：`next_trigger_time`、执行起止时间、`ctx.dbNow` 全部来自 SQL（铁律 9/10）
3. **`bizDate` 基于 `triggerTime` 而非 `dbNow`**，否则补跑处理错日期（§4.5）
4. **抢占 SQL 必须带 `enabled_flag = 1 AND deleted_flag = 0`**，防幽灵执行（§3.3）
5. **更新配置时要重算 `next_trigger_time`**，否则改了 cron 不立刻生效
6. **手动与自动共用同一把 job 级并发锁**（缺陷 #2）
7. **手动执行不在 Redisson 回调线程上跑**，改走扫描线程 + 执行池（缺陷 #4）
8. **锁不传 leaseTime**，用看门狗 + DB 兜底 + 僵尸扫描（缺陷 #3）
9. **`lane` 由 handler 声明、运营不可改；FAST 强制 timeout ≤ 30s**（§5.1）
10. **背压用「跳过」而不是「sleep」**，被跳过的任务不能被消耗掉（§3.5）
11. 🔴 **四步顺序不可调换**：判池水位 → 抢占 → 判阻塞 → 投递。
    通用规则：**节点级判据跳过、集群级判据抢占**。
    把「判阻塞」放到抢占前，长任务会让 `next_trigger_time` 永远不前进、**时间轮卡死**（§5.2）
12. 🔴 **重试 = 插一条全新的 PENDING 记录，绝不改动 FAIL 记录**；
    FAIL 记录的 `fire_time` 必须留 NULL（否则无限重试）；
    置 FAIL 与插 PENDING **必须同事务**（否则重试静默丢失）；
    `trigger_time` / `param_snapshot` / `biz_date` **原样继承**（§5.4）
13. **手动 / 重试走日志表扫描，抢 `t_smart_job_log.status`，不抢 `job.trigger_version`**——
    抢版本号会连带改写 `next_trigger_time`，**扰乱 cron 节奏**（§3.9）
14. **日志链路要单独校验 job 状态**（`deleted_flag` / `handler_missing_flag` 必挡，
    `enabled_flag` 刻意放行以保留「忽略开启状态立即执行」的现有语义）（§3.9）
15. **执行外层 `catch (Throwable)` 而非 `Exception`**，防 `Error`/OOM 留下永久 RUNNING；
    但它**不能替代僵尸扫描**，两层都要有（§5.3）
16. **投递被拒要 `catch (RejectedExecutionException)` 并落 BLOCKED 日志**，
    别让判水位与 submit 之间的竞态变成未捕获异常（§5.2）
17. **唯一索引必须含 `trigger_source`**，且 `trigger_source` **不设 `RETRY` 取值**——
    重试继承原值、靠 `retry_seq` 区分（§6.2）
18. **jitter 用确定性 hash，`ONE_TIME` 强制豁免**（§3.6）
19. **handler 里禁止 `LocalDateTime.now()` / `LocalDate.now()`**，一律用 `ctx`
20. **handler 内的 `@Transactional` 不能同类自调用**（铁律 11）。定时任务是重灾区——
    job 入口天然没有事务，`@TransactionalEventListener(AFTER_COMMIT)` 在没有事务上下文时**根本不投递**
21. **不幂等的 handler 不许配重试**，保存时校验
22. **长任务必须响应中断**（`ctx.checkCancelled()`），否则超时形同虚设
23. **`SKIP` 的 misfire 也要记日志**，否则漏跑无痕
24. **MDC 用 `TaskDecorator` 透传，`finally` 里还原快照而不是 `clear()`**（否则串号或抹掉下一个任务）
25. 🔴 **注入 `SmartJob` 用 `ObjectProvider` 而不是 `List`**（铁律 14）——
    一个执行器实现都没有时（示例任务已删、业务执行器还没写），按 `List` 注入会以
    「expected at least 1 bean」**直接让整个应用启动失败**。调度模块不该因为「还没有任务」就拖垮启动
26. 🔴 **角色条件用 `@ConditionalOnExpression` 而不是 `@ConditionalOnBean`** ——
    后者在普通 `@Configuration` 里依赖 Bean 定义的注册顺序，官方明确不推荐；
    顺序一变，症状是「WORKER 节点悄悄不跑任务」，又是一个静默失效
27. **日志表要有清理任务**，`log_id` 用 bigint，Redis 实时日志要 `LTRIM` + TTL
28. 写并发用例时，先确认**待验证的机制是唯一能产生该现象的机制**（铁律 18）——
    测「重复执行」时，别让 `last_execute_time` 的兜底掩盖了锁失效

## 11. 分档落地

每档独立可上线，不做大爆炸式切换。

### 第一档：止血（不改调度模型）—— ✅ **已实施 2026-08-11**

改动小、风险低，解决「会出事」的部分。**DDL：`v3.57.0.sql`**
（本档并非零 DDL —— 第 2、6 两项都要改表结构，撰写时曾误判为「不动 DDL」）。

| # | 项 | 落地位置 |
|---|---|---|
| 1 | 拆 `role` 开关，解开管理与执行的耦合（§1.1） | `SmartJobRoleEnum` / `SmartJobAutoConfiguration` / `SmartJobService` |
| 2 | handler 名注册 + 启动双向对账（缺陷 #1） | `@SmartJobHandler` / `SmartJobHandlerRegistry` / `job_class`→`handler_name` |
| 3 | 手动 / 自动统一并发锁（缺陷 #2） | `SmartJobExecutor`，锁只剩 `smart-job-exec-{jobId}` 一把 |
| 4 | 手动执行移出 Redisson 回调线程（缺陷 #4） | `SmartJobClientManager` 只做校验与投递 |
| 5 | 执行超时 + 中断（缺陷 #6 的一半） | `SmartJobExecutePool`，独立池 + 定时哨兵 `cancel(true)` |

## 12. 明确不做的

### 12.1 本期不接 QLExpress

`rule_script` 通道在任务中台建好了，**至今零调用**（`任务中台-改进技术方案.md` §57 / §977）。
在定时任务上先建脚本通道，很可能重演同一件事。

更硬的理由是形态不匹配：定时任务是**批处理**，分页游标、事务边界、分批提交、断点续跑、
`bizDate` 幂等——这些在 QLExpress 里没有对应概念。而脚本调用的 Java 函数一旦卡死，
引擎的 `timeoutMillis` 也管不住（备忘录 §二「假超时」）；
真出现死循环或 OOM，**整个 WORKER 节点陪葬**。

将来真要开，口子只开在**「筛哪些数据」**（返回 boolean / where 条件）和**「算派生值」**，
骨架永远是 Java。判据一句话：**脚本可以决定「对谁做」，不能决定「怎么做」。**

前置条件：脚本引擎先修三处——`QLOptions` 开 `cache(true)`（现在 `DEFAULT_OPTIONS` 是
`cache=false`，每次执行重新编译，而 `checkScript` 又在往一个**只写不读**的无界缓存里塞东西）、
配 `timeoutMillis`（现在是 -1 无超时）、`@ScriptFunction` 加副作用标记。

### 12.2 不做分片、不做 DAG

分片留接口位（`shardIndex` / `shardTotal`）不实现；任务依赖编排完全不做。
这两项一旦真需要，是**换 PowerJob 的信号**（§1.3 换血条件 2 / 3），不是自己写。

### 12.3 不做 N 条可配车道

只有 FAST / SLOW 两条。SLOW 池 `core=2` 本身就是慢任务的全局并发限流器。
引入"可配置车道数"会带来一个新的运营旋钮，而它解决的问题用池大小就能解决。
