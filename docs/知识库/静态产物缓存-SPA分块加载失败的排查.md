# 静态产物缓存：SPA 分块加载失败的排查

> 撰写 2026-10-18 · 类型：**知识库**（通用原理，脱离本项目也成立）
> 起因是一次真实故障：管理端三个风控页面点不开，控制台只有一句
> `Failed to fetch dynamically imported module`，而文件在服务器上好好的、服务端日志里全是 200。
> 本项目的修复在 `deploy/nginx/nginx.conf`（两个 server 块各改三处）与
> `solvela-admin-web/src/lib/chunk-reload.js`。
>
> 读完应该能回答：为什么这条报错指向的文件**往往不是真正坏掉的那个**；
> 为什么「文件明明在、服务端明明 200」还会失败；
> SPA 的 `try_files` 兜底为什么是一台**缓存投毒机**；
> 要彻底治住它必须同时做对哪三件事。

---

## 0. 一句话

**把找不到的静态产物兜成 `index.html`，等于给浏览器发了一份「HTML 冒充 .js」，并且允许它长期缓存。**

从此同一个 URL 在那台浏览器上**再也取不到正确内容**——重新部署也救不回来，因为请求根本不出网；
而报错指向的是**另一个**文件，于是人会一直在无关的文件上找原因。

---

## 1. 现象

管理端（hash 路由 SPA，路由组件懒加载）点三个风控菜单，页面卡在顶部进度条上不渲染，控制台各一条：

```
Uncaught (in promise) TypeError: Failed to fetch dynamically imported module:
  https://admin.<域名>/js/risk-rule-list-DoSWQnPN.js
  https://admin.<域名>/js/risk-event-list-CXdL8oYB.js
  https://admin.<域名>/js/risk-stat-CZIuyYva.js
```

特征很具体，值得记住：

| 现象 | 当时的解读（错的） | 实际含义 |
|---|---|---|
| 「转半天加载不出来」 | 网络慢 / 接口挂了 | 导航失败，`afterEach` 不执行，进度条没人收 —— 跟耗时无关 |
| 三个页面报三个不同的文件 | 这三个文件都坏了 | 它们**共用**的一个依赖坏了 |
| 其它页面（限流规则、安检门、名单、处罚）全正常 | 只有风控模块有问题 | 只有风控模块 import 那个依赖 |
| 刷新一次就好了 | 偶发 | 刷新绕过了那条坏缓存 |

---

## 2. 为什么这条报错一定会把人带偏

三件事叠在一起，让「真正坏掉的文件」在报错和日志里都**不出现**：

1. **浏览器报的是最外层那个动态 import，不是真正失败的嵌套依赖。**
   `import('./risk-rule-list.js')` 里面 `import` 的某个同级 chunk 挂了，Chrome 仍然只说
   「取不到 risk-rule-list」。于是你会去查一个完全健康的文件。
2. **依赖挂了的时候，页面 chunk 自己的请求可能压根不会发出。**
   vite 的预载辅助函数先为依赖插入 `<link>` 并等它们就绪，再执行真正的 `import()`；
   依赖这一步就 reject 的话，后面那个请求不会发生。
   （本次故障里 `risk-rule-list` 的 CSS 请求有、JS 请求没有，就是这一步的痕迹——**此处为推断**，
   不同 vite 版本的预载实现细节有差异。）
3. **命中浏览器缓存的请求不出网，服务端日志里什么都没有。**
   「日志里没有这条请求」常被当成「客户端没请求」，其实是「客户端用了自己缓存的那一份」。

> 🔴 所以排查这条报错，**第一步永远不是看报错里那个文件**，而是看
> 「它的嵌套依赖有哪些，这些依赖在服务端日志里出现过吗」。

## 3. 经过：每一步排除了什么

| # | 做了什么 | 结果 | 排除了 |
|---|---|---|---|
| 1 | 进容器 `ls /srv/admin/js \| grep risk` | 三个文件都在 | 「产物没打出来 / 镜像没更新」 |
| 2 | 查 nginx 访问日志里这三个文件 | 全是 `200 0.000` | 「文件丢了」「服务端慢」「隧道挂了」 |
| 3 | 把日志里请求过的 **153 个路径**与容器里实际文件逐一对照 | 没有一个缺 | 「老 hash 残留 / 旧 index.html 引用了死链接」 |
| 4 | 列出 `risk-rule-list` 的静态依赖，逐个查日志时间戳 | **`member-risk-api-CJZhdZUT.js` 在整个故障窗口里一次都没被请求过**，直到刷新后 00:52:32 才第一次拿到 200 | —— 定位完成 |

第 4 步是决定性的。这个文件是三个风控页**共用**的依赖，所以：

- 三个页面一起坏 → 共用依赖；
- 页面 chunk 自己却是 200 → 坏的不是它；
- 服务端没有它的请求记录 → 浏览器用的是缓存里的那一份；
- 刷新之后第一次真正取到（`200`，不是 `304`）→ 缓存里原来那份**不是**这个文件的正确内容。

日志关键节选（已去掉 UA 与真实 IP）：

```
00:43:07  200 0.000 GET /js/risk-const-Dg6PXqqr.js        ← 共用依赖之一，这个是好的
00:44:10  200 0.000 GET /js/risk-event-list-CXdL8oYB.js   ← 页面 chunk 本身一切正常
00:44:17  200 0.000 GET /js/risk-stat-CZIuyYva.js
00:44:38  200 0.000 GET /css/risk-rule-list-BUfieRnQ.css  ← 只有 CSS，没有 JS
          （整段窗口内没有任何 member-risk-api 的请求）
00:52:32  200 0.000 GET /js/member-risk-api-CJZhdZUT.js   ← 刷新后第一次真正取到
```

## 4. 起因：两个配置缺陷相乘，一个部署习惯点火

### A. 缺失的静态文件被兜成首页（投毒源）

```nginx
location / {
    try_files $uri $uri/ /index.html;   # 🔴 "一切"找不到的路径都变成 200 + text/html
}
```

SPA 需要这条兜底是真的（history 路由刷新要靠它），但它的作用范围**不能包含静态产物**：
一个不存在的 `/js/x-<hash>.js` 会得到 `200` + `Content-Type: text/html` + 一整页 HTML。

此时 `X-Content-Type-Options: nosniff` 会让浏览器拒绝把它当模块执行——**这是对的**，
它把一次静默的「内容不对」变成了一次明确的失败。问题不在 nosniff，在于服务端本该回 404。

### B. 这些产物身上一个 `Cache-Control` 都没有（让毒留下来）

配置里是有一条永久缓存规则的，但它写的是 `location ^~ /assets/`，
而管理端的 rollup 输出被改成了按扩展名分目录：

```js
chunkFileNames: 'js/[name]-[hash].js',
assetFileNames: '[ext]/[name]-[hash].[ext]',   // → css/、png/ ……
```

**`/assets/` 下一个文件都没有，这条规则长期形同虚设。**
于是 `/js/*.js` 的响应只有 `ETag`/`Last-Modified`，没有任何 `Cache-Control` ——
这种响应浏览器会按 **启发式缓存** 自己决定能用多久（常见做法是
`(Date - Last-Modified) × 10%`）。而兜底回来的那份 HTML 带的是 `index.html` 的
`Last-Modified`（镜像构建时间），于是这份「HTML 冒充 .js」被**合法地**存进了磁盘缓存。

> ⚠️ 这是一类很隐蔽的失效：规则写错了目录，表现不是报错，而是**什么都照常工作**，
> 只是少了一层保护。同一份配置里 `^~ /assets/` 这条在 C 端是对的（vite 默认布局），
> 复制到管理端就失效了——两个站的构建配置不一样。

### C. 点火：浏览器拿着新 hash、服务端还跑着旧镜像

`A × B` 只是装好了枪，还需要一个「请求了一个服务端当时没有的 chunk」的窗口期。
`docker-compose.yml` 里 web 服务的镜像标签是写死的：

```yaml
image: solvela-web:3.0.0     # docker compose up -d 命中已有镜像就不会重建
```

前端构建过、页面加载到了新的 `index.html`，而容器还在跑旧镜像时，这个窗口就打开了。
**窗口只要开过一次，那台浏览器上的坏缓存就会一直留着**——哪怕之后镜像更新到正确版本，
请求也不出网，现象就成了「服务器明明是好的，就我这里打不开」。

### 四件事的因果链

```
前端构建出新 hash ──┐
                    ├─► 请求了服务端当时没有的 chunk
镜像标签写死没重建 ──┘            │
                                  ▼
                try_files 兜底 → 200 + text/html（投毒）
                                  │
                   没有 Cache-Control → 启发式缓存存下来（留毒）
                                  │
                   nosniff 拒绝执行 → Failed to fetch ... module
                                  │
                   报错指向最外层的页面 chunk（误导）
```

---

## 5. 解决方案：三层，缺一不可

### 第一层：缺失的产物必须回 404（堵住投毒源）

```nginx
location ~* ^/(?:js|css|png|jpe?g|gif|svg|webp|woff2?|ttf|eot)/ {
    try_files $uri =404;
}
```

这是**根本的那一条**。404 不会被当成这个 URL 的内容缓存下来，
下次请求照样出网；而「200 + 错误内容」会被缓存，并且永远不再出网。

按「目录名 = 扩展名」匹配，是因为这些目录里的文件名**全都带 hash**，
而不带 hash 的 `index.html`、`favicon.ico` 在根目录，不会被这条规则碰到。

### 第二层：缓存头两端都要写明（别让浏览器猜）

| 对象 | 头 | 为什么 |
|---|---|---|
| 带 hash 的产物 | `expires 1y` + `public, immutable` | 内容变了文件名就变，永久缓存是安全的 |
| `index.html` 与 SPA 兜底响应 | `no-store` | 它写死了当前这批 chunk 的文件名，缓存它等于缓存一张**过期的清单** |

> 🔴 `index.html` 不发 `Cache-Control` ≠ 不缓存。不发 = 让浏览器按启发式自己决定，
> 这正是「重新部署后老浏览器还在用旧入口」的来源。

### 第三层：前端自愈（兜底，不是主力）

换版本后老页面取不到 chunk 时，自动重载一次换成新的入口。三个入口都要挂，少一个就有漏网：

| 入口 | 接住的是 |
|---|---|
| `vite:preloadError`（window） | vite 预载 chunk / CSS 失败 |
| `router.onError` | 路由自己 `await` 组件时失败 |
| `unhandledrejection` | 代码里**裸着的** `import()`（没人 `await`、没有 `catch` 的那种） |

两个必须有的细节：

- **冷却窗口**（本项目 10 秒，时间戳存 `sessionStorage`）。没有它就是死循环：
  刷回来的入口要是还旧，就会立刻再失败、再重载，变成停不下来的白屏。
  时间戳不能放内存变量——重载会把内存清空，永远读不到「上次」。
- **冷却期内要提示手动强刷**，并且顺手把进度条收掉（路由已经失败，`afterEach` 不会再执行）。

> ⚠️ **`location.reload()` 冲不掉已经被污染的缓存条目**（它只重新校验，子资源仍可能来自缓存）。
> 所以自愈能救「入口旧了」，救不了「缓存里存着一份 HTML」——那种只有强制刷新（Ctrl+Shift+R）
> 或等缓存过期。**第一层才是治本的，这一层只是让换版不再打断正在用的人。**

### 第四层（流程）：前端改了必须重建镜像

镜像标签写死 + `up -d` 不重建 = 窗口期的来源。要么每次 `docker compose build web`，
要么让标签带上构建信息。

### 改前 / 改后

| 请求 | 改前 | 改后 |
|---|---|---|
| 存在的哈希产物 | 200，**没有任何缓存头** | 200 + `public, immutable` |
| 不存在的 chunk | **200 + `text/html`（首页）** | **404** |
| `index.html` / 兜底路由 | 200，无 `Cache-Control` | 200 + `no-store` |

---

## 6. 速查

**配置静态站时，三条一起写，缺一条就留一个坑：**

1. 带 hash 文件名的产物目录 → `immutable` **且** 缺失回 `=404`；
2. SPA 入口 HTML → `no-store`（至少 `no-cache`）；
3. `try_files` 的兜底范围限定在「路由」，不是「一切」。

**看到 `Failed to fetch dynamically imported module` 时的排查顺序：**

| 顺序 | 查什么 | 这一步能排除 |
|---|---|---|
| 1 | 文件在服务器上吗 | 产物没打出来 / 镜像没更新 |
| 2 | 服务端日志里**有没有这条请求** | 没有 → 命中了浏览器缓存，别再查服务端 |
| 3 | 有请求的话，状态码和 `Content-Type` | 200 + `text/html` → 就是本文这个坑 |
| 4 | 报错那个文件的**嵌套依赖**各自是什么状态 | 真正坏掉的几乎总在这里 |
| 5 | 换个干净 profile / 强制刷新能不能复现 | 能复现 → 服务端问题；不能 → 缓存问题 |

**两条反直觉的结论：**

- 报错里那个文件名**不是**坏掉的那个文件。
- 「服务端日志全是 200」不代表服务端没问题——**200 可能是一份错误的内容**，
  而且恰恰因为是 200，它才会被缓存下来。
