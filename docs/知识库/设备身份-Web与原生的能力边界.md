## 0. 一句话

**设备身份要么持久，要么不可复制，Web 上两者都很难，原生上也不能兼得。**
所以设计的重点不是"让标记清不掉"，而是**让清除没有好处**：新身份拿到要有成本、起点信任为零。

---

## 1. 两个维度：持久性 与 不可复制性

| 维度 | 问的是 | 失败表现 |
|---|---|---|
| 持久性 | 用户清数据 / 重装 / 换浏览器后还认不认得出 | 同一台设备被当成新设备（误报、计数被洗白） |
| 不可复制性 | 标记能否被拷到另一台机器上冒用 | 攻击者拿着"老设备"的标记绕过新设备验证 |

只要标记**能被读出来随请求发送**，它就能被复制。唯一不可复制的是**硬件里的私钥签名**，而它又活不过卸载 / 恢复出厂。

---

## 2. 原生 App 能拿到什么

| 平台 | 手段 | 什么情况下丢 | 可否复制 |
|---|---|---|---|
| iOS | Keychain 条目 | 删 App 通常仍在；恢复出厂丢 | 可（能读出来就能复制） |
| iOS | DeviceCheck（苹果服务端为每台设备存 2 bit） | 仅恢复出厂清 | 由苹果服务端保证 |
| iOS | App Attest | — | 证明"真机 + 官方 App" |
| Android | Android ID（8.0 起按签名隔离） | 恢复出厂变 | 可 |
| Android | OAID（国内移动安全联盟标准） | 用户可在系统设置重置 | 可 |
| Android | Play Integrity | — | 证明"真机 + 未篡改 App" |
| 双端 | Keystore / Secure Enclave 硬件密钥 | 卸载即消失 | **不可导出** |

### GCash 类"设备绑定"大概是怎么做的（推断）

用户可见行为：换手机登录要 OTP + MPIN，新设备通过后旧设备被踢，同时只有一台有效。

1. **设备绑定**：首次绑定时在 Keystore / Secure Enclave 生成不可导出的密钥对，公钥报给服务端；此后每次登录用私钥签名。换手机就没有这把私钥。配合 Play Integrity / App Attest 识别模拟器、root、改包。
2. **KYC 兜底**：受监管的电子钱包要求证件 + 人脸；换设备或可疑时要求重新刷脸。**买号在这一步基本过不去**——卖家能给密码和 OTP，给不了脸。
3. **设备-账号关系图**：买来的号"正常消费也被封"，多半是多个信号叠加评分——长期老设备突然永久切换、新设备历史上绑过多个账号（**最强信号**）、行为画像突变（地点 / 时段 / 交易对象）、SIM 与注册号码不一致。

**结论**：强设备绑定的前提是**原生 App**。Web 拿不到 Keystore、Integrity、SIM。

## 3. Web 能拿到什么

### 3.1 所有存储都归用户管

| 存储 | 清除方式 |
|---|---|
| cookie、localStorage、IndexedDB | Chrome "Cookie 及其他网站数据"一次全清 |
| HTTP 缓存 | "缓存的图片和文件"（**不影响** cookie 和 localStorage） |

所以"只清缓存"两边都不会掉线；看到掉线，实际清的是网站数据。

### 3.2 为什么清了数据 Google 不掉、B 站会掉

**这是浏览器给 Google 的特权，不是网站技术。** 登录了 Chrome 的 Google 账号时，浏览器 profile 自己持有一份凭证；
cookie 被清后，Chrome 用它重新换出 Google 的登录 cookie。清除对话框里写着"您将保持 Google 账号的登录状态"。
用 Firefox / Safari 登 Google，清数据照样掉线，和 B 站一样。

### 3.3 "清不掉的标记"为什么做不到

| 历史手段 | 结局 |
|---|---|
| Flash LSO、Silverlight 存储 | 插件已淘汰 |
| evercookie（多处存储互相恢复） | 被各浏览器专门封堵 |
| HSTS 超级 cookie、ETag 缓存、favicon 缓存 | 浏览器按站点分区缓存后基本失效 |

这类技术在浏览器厂商眼里是**追踪**，发现一个封一个。在国内还有合规风险：
《个人信息保护法》要求收集设备标识需告知并取得同意，用户清除后偷偷恢复，正好违背这一点。

### 3.4 Safari ITP 的 7 天清理

Safari 会删除 **JS 写入**、7 天无用户交互的存储（localStorage、`document.cookie` 写的 cookie）。
**服务端 `Set-Cookie` 下发的第一方 cookie 不受这 7 天限制**（前提：同源 / 同站部署，不是 CNAME 伪装的第三方）。
这是 Web 端设备令牌应由服务端以 cookie 下发、而不是放 localStorage 的主要理由。

### 3.5 DBSC（Device Bound Session Credentials）

Google 推动的开放标准，是 Web 上最接近"设备绑定"的东西：
- 浏览器在 TPM 里生成不可导出的密钥，会话与之绑定；
- 会话 cookie 设得很短，浏览器定期用这把密钥签名续期；
- cookie 被复制到别的机器很快过期，且没有私钥无法续期。

**国内覆盖极难**：需要浏览器厂商主动启用并对接本机安全芯片。华为 / OPPO / vivo / 小米自带浏览器 Chromium 版本滞后且常关闭 Google 新特性，
鸿蒙 NEXT 用 ArkWeb；微信 / QQ 内置浏览器是腾讯自有内核；UC、夸克、360 各自为政。实际能覆盖的多为桌面 Chrome / Edge，
在国内移动场景里占比很小。它是渐进增强，将来可作为加分项接入，但现在投入产出很低。

### 3.6 WebAuthn / Passkey

浏览器 API `navigator.credentials.create / get`。能拿到的是**公钥与签名**，拿不到私钥、TPM 句柄或任何稳定设备 ID——
**它是登录凭证，不能当设备指纹。**

- 主流 Passkey 是**同步型**（iCloud 钥匙串、Google 密码管理器），跟账号走，不绑单台设备；attestation 通常为 `none`，服务端无法验证来自 TPM。
- "防钓鱼"成立：签名绑定域名。
- 限制：必须 HTTPS 且绑定 RP ID（换域名全部作废）；**微信内置浏览器支持很差**；App 需走原生 API 并配置 `assetlinks.json` / `apple-app-site-association` 才能与 Web 共用凭证；服务端用 `webauthn4j` 或 Yubico `java-webauthn-server`，别自己验签。

## 4. 商业设备指纹

国内：数美、顶象、同盾、网易易盾等；海外：FingerprintJS Pro 等。

### 4.1 怎么认出你
- **浏览器特征**：Canvas、WebGL、音频、字体、屏幕、CPU 核数、时区、语言等几十项；
- **服务端特征**：IP / 运营商、TLS 握手指纹（JA3/JA4）、HTTP 头顺序——不经页面 JS，清数据影响不了；
- **自有存储**：能存的地方都存一份，作辅助；
- **模糊匹配**：浏览器升级后部分特征变化，按相似度判断；
- **跨客户数据**：某设备在别家已被标为羊毛党，你这边直接看到。**这一项自研做不出来，是花钱的主要理由。**

### 4.2 局限
- **碰撞（误报）**：同型号 iPhone + 同版本 Safari 特征几乎一样（Safari 主动降低可采集熵），微信内置浏览器也很统一。**不能当硬闸门。**
- **可伪造**：国内有成熟的"指纹浏览器"产业（每个窗口一套自洽的独立指纹）。厂商靠特征矛盾识别一部分，是攻防对抗，不是 100%。
- **合规**：设备指纹属个人信息，需在隐私政策中说明并取得同意；交给第三方处理需披露；**海外厂商涉及数据出境**，国内用户为主基本只能选国内厂商。

### 4.3 接入原则
**只信服务端查询的结果，不信客户端上报的设备 ID。**

```
前端 SDK 采集 → 一次性 token → 随请求发给我们的后端
后端拿 token 去厂商服务端查询 → 设备 ID + 风险标签（模拟器 / 指纹浏览器 / 黑产库命中）
```

与自有设备令牌**叠加**而不是替代：自有令牌是精确身份（可验签、清掉就没）；厂商 ID 是模糊关联（清掉后还能把新令牌和老设备关联起来）。
营销系统里**最值的用法在发奖前的风控链**，而不是登录。

### 4.4 决策方式
多数厂商可免费试用。先**影子模式**（只采集、只记录、不拦截），对照已有拦截日志与发奖数据，
看它多识别出的羊毛所对应的奖品价值是否超过年费。

## 5. 国内实际在用的强身份手段

与其在浏览器层死磕设备绑定，国内产品通常把强身份放在别处：

| 手段 | 证明的是 | 适用 | 注意 |
|---|---|---|---|
| **运营商本机号码校验** | 当前网络连接的 SIM 就是这个手机号 | H5 可用，用户无感 | 仅蜂窝数据，Wi-Fi 下降级短信；按次收费；三网分别对接或走聚合商 |
| **微信 openid** | 稳定的微信用户身份，清缓存、换设备都不变 | 微信内 H5 | 需网页授权 |
| **短信 OTP** | 此刻持有这个号码 | 通用 | 要花钱；发码接口是短信轰炸的目标 |
| **把资产动作推到原生 App** | 可用 Keystore + 设备证明 | 有 App 时 | H5 拉新浏览，兑换 / 提现进 App |

本机号码校验证明的是"人和手机号在一起"而不是"设备没变"——但对防盗号、防买号而言这正是更有用的：
**卖家能给你密码和 OTP，给不了他的 SIM 卡。**

## 6. 设计原则：不追求清不掉，让清除没好处

刷子清除的动机是"洗白"：计数清零、换新身份继续刷。只要**新身份比旧身份更差**，清除就没有意义：

1. **新身份拿到要有成本**：设备令牌签发本身要限频（按 IP 等维度）。
2. **起点信任为零**：新设备做资产动作（兑换、改地址、提现）要求二次验证；老设备积累的信任不随新身份走。
3. **计数不只挂在设备上**：IP、账号、手机号、openid 这些维度，清浏览器数据清不掉。

结果：普通用户清了缓存，代价是下次兑换多验一次码；刷子清了缓存，得到一个受限频、零信任的新设备，比没清更差。
这也是 GCash 实际的逻辑：**它不在乎你能不能换设备，在乎的是换了之后你得重新证明自己。**

## 7. 速查：谁解决什么

| 需求 | Web 可行方案 | 原生可行方案 |
|---|---|---|
| 认出"同一台" | 服务端下发的 HttpOnly 设备 cookie（弱）+ 商业指纹（模糊） | Keystore 密钥 / Android ID / Keychain |
| 防标记被复制 | DBSC（国内覆盖差） | 硬件密钥签名 + Integrity / App Attest |
| 清除后仍关联 | 商业指纹、账号 / 手机号 / openid 维度 | DeviceCheck、Android ID |
| 证明是本人 | 短信、本机号码校验、Passkey、openid | 同左 + 生物识别 + KYC |
| 识别黑产设备 | 商业风控（跨客户数据） | 同左 + 模拟器 / root 检测 |
