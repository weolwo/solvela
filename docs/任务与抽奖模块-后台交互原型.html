💡 设计说明

原表单把 task_type（SIMPLE/COUNT/AMOUNT）当普通文本输入，运营容易填错，且后面「达标规则」也是裸 JSON 输入框。

改成先选模板 → 模板自带 task_type → 第二步的规则表单据此自动切换控件类型，运营不需要理解底层字段。

活动大类包裹原子任务：架构上以「活动 Activity」为大类统筹底层多个原子任务。通过选择所属活动（activity_code），系统在C端会自动将该原子任务聚合并展示在对应的大类UI下，运营无需单独为聚合页做配置。

任务模板设计器 · ui_schema 驱动 仅技术/开发角色可见

对应字段：t_task_template.ui_schema + rule_script。本页面通过菜单权限只对开发开放；运营只使用「任务配置向导」，看到的是 ui_schema 渲染出的参数表单，永远接触不到 rule_script。左侧编辑 schema，右侧两个渲染器实时消费同一份定义：① 管理端「达标规则」动态表单（即向导第2步）② C端任务卡片。

📝 ui_schema 定义（可直接编辑）
⚙️ rule_script（QLExpress · 后端判定逻辑）运营不可见
与 ui_schema 是同一模板的两个独立字段：ui_schema 管「配置界面长什么样」，rule_script 管「后端如何判定达标」。运营在向导里填的参数（rule_config）会作为变量注入本脚本，如 targetDays、excludeRefund。脚本仅在本设计器中由开发维护。
📖 Schema 规范速查
params[] — 管理端动态表单：widget 支持 number / text / select / radio / switch / slider / image_upload；visibleWhen 做字段联动显隐；辅以 unit / min / max / default / required / help。
image_upload — 多端异构图片：一个 key 即一张图，按「用途_端」命名（如 icon_app / banner_mp），值为图片 URL 随 rule_config 一起保存；哪个模板需要哪些端的图，只改模板 schema，前端零改动。配合 visibleWhen 可由开关字段控制是否展示上传项（见「每日签到」模板的 customImage 联动示例）。
render — C端渲染：cardType = simple｜progress｜amount｜checkin-grid（自定义交互按组件名注册，schema 只引用、不实现）；progressText 支持 {current} / {target} 及任意参数占位符；buttonText 按任务状态 0~3 配按钮文案。
taskType — 决定后端累计逻辑（SIMPLE / COUNT / AMOUNT），params 收集的值最终拼装为 rule_config，供 rule_script（QLExpress）作为变量读取。
🖥️ 渲染器① 管理端达标规则表单
任务配置向导第2步将由此 schema 动态生成，新增模板不需要改前端代码。

这份原型解决了什么问题

现状
管理后台代码生成器已跑出 draw/lottery/task 全部表的裸 CRUD 页面（一个字段一个 input），能用但不体现业务逻辑，运营用起来容易配错（如概率总和不校验、JSON规则手填、阶梯奖励无结构）。
本次范围
按你的选择，本次只做「奖池转盘抽奖」+「任务」两个模块的后台管理交互设计，暂不涉及 C端 用户页面，也不含「彩票期号」抽奖玩法。
四个核心交互点
① 任务配置从裸表单→向导式，按 task_type 动态切换规则控件；② 阶梯奖励从 JSON 输入→可视化搭建器，支持 FIXED/RATIO/FORMULA 三种模式；③ 奖池概率从裸数字输入→转盘可视化+实时求和校验+模拟抽奖验证；④ 记录类表格（任务记录/抽奖流水）从纯分页表→状态看板+快照审计+异常处理。
任务模块本期补全
① 向导第2步达标规则表单不再写死，与模板设计器共用同一 ui_schema 渲染引擎（现场可演示：设计器里加/改模板 → 向导交互自动就绪）；② 新增「任务数据看板」：完成/发奖趋势、各任务占比、分任务转化明细；③ 新增「奖励派发记录」：公共派发链路可视化（达标 → 派发单 → 风控 → 资产入账），支持失败重试、风控拦截转提案提示。
尚未覆盖，值得后续再设计
t_proposal_record 的一审/二审审批工作台（风控拦截、批量审批）；彩票期号玩法（t_lottery_*）单独一套开奖交互；C端用户页面本身。
