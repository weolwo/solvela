## 放置规则

新文档按这张表决定放哪，别再往根目录平铺：

| 目录 | 放什么 | 判断标准 |
|---|---|---|
| `知识库/` | 通用原理与技术选型的底层知识 | 把本项目删掉，这份文档还成立吗？成立就放这里。可以拿本项目举例，但结论不绑定实现 |
| `架构/` | 跨业务的平台、框架、基础模块、升级 | 不属于任何一个业务域 |
| `业务/<域>/` | 某个域的方案、说明书、原型、验证脚本 | 同一功能的方案 / 原型 / 报告放同一目录 |
| `治理/` | 一次性改造战役（迁移、对账、清理） | 有明确的开始和结束 |
| 根目录 | 只放入口文档 | — |

## 写作约定

- **文件名**：`<主题>-<文档类型>`。类型用：实现技术方案 / 架构设计文档 / 白皮书 / 操作说明书 / 实测验证报告 / 原型（`.html`）。知识库用 `<领域>-<主题>`。
- **文件头**：一级标题 + 引用块，写明撰写日期、状态、输入 / 前置阅读。状态变化时改文件头，不要只在正文里改。
- **引用其他文档**：写从仓库根起的完整路径 `docs/...`。移动文档时全仓搜索替换——代码注释里也有引用。
- **对着代码写**：结论核对过代码的要写明；文档与代码不一致时**以代码为准**，并订正文档。
- **外部信息**（第三方产品行为、浏览器特性覆盖面）标明来源性质与时效，别写成定论。
