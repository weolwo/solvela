### 已确立的工程铁律（贯穿全程，务必延续）
1. **浮点比较用容差**：任何概率/金额求和判等，前端用 decimal.js、后端用 BigDecimal，容差 `0.0001`，严禁 `=== 100`。（曾因此出现"界面显示100%却保存不了"死锁）
2. **前端 UI 校验只是防呆**，后端必须服务端重算一遍（防绕过页面直接 POST）。
3. **消除魔法值**：状态码/类型/默认值一律具名常量。
4. **单一状态源**：向导类表单收拢在一个 `reactive` 对象。
5. **Tailwind v4 important 是后缀**：`text-purple-600!`（不是 `!text-purple-600`）。
6. **in-DOM 模板陷阱**（仅限 CDN 直写 HTML 的原型）：浏览器把 camelCase 属性强制小写。
   - prop 可以靠 kebab 绕过：`:customRow` → `:custom-row`、`valueFormat` → `value-format`（Vue 会 camelize 回去）。
   - **⚠️ 插槽名没有 kebab 退路**：`#bodyCell` 被小写成 `#bodycell`，而 **Vue 不会 camelize 插槽名**，antd 查的是 `slots.bodyCell`，永远匹配不上 —— 表现是**表格自定义列整片渲染成空白且不报错**。
   - **正解：整个模板挪进 `<script type="text/x-template">`**，script 内容浏览器按纯文本存储、不做 HTML 解析，驼峰原样保留，一次堵死整类问题，不用逐个属性打地鼠。做法见 `docs/彩票中台-实现技术方案.md` §0.1，`彩票中台原型-FPE彩票.html` 已按此改造并实测。
   - SFC（.vue）编译期处理模板，完全不受影响。
7. **SmartBeanUtil.copy** 同名同类型自动拷贝——加实体字段后 Form→Entity 自然带过去。
8. **业务编码统一规范**：活动编码、奖品编码、奖池编码、任务模板编码一律「**10 位大写字母 + 数字**」随机组合（如 `H88JHKJFNE`），**全局唯一**。
   - 唯一真源：`sa-base` 的 `SmartCodeUtil`（`BIZ_CODE_REGEX` / `generateBizCode()` / `generateUniqueBizCode(判重函数)` / `isValidBizCode()`）。前端同源常量在 `constants/regular-const.js` 的 `regular.bizCode`。
   - 运营两条路径：手工输入 or 点「生成」按钮（`GET /activityConfig/generateCode`、`GET /prizeConfig/generateCode`、`GET /prizePoolConfig/generateCode`、`GET /taskTemplate/generateCode`，服务端生成时已判重）。
   - **手输路径必须服务端重校验**：AddForm 上挂 `@Pattern(SmartCodeUtil.BIZ_CODE_REGEX)`，Service 再查一次重（表上的唯一索引直接抛 SQL 异常对运营不友好）。
   - **编码创建后不可改**：UpdateForm 本就不含编码字段，前端编辑态把输入框和生成按钮一起禁掉；否则改一次编码，奖品/奖池/流水的引用全断。
   - 编码是随机码，凡是「填别人的编码」的地方一律改成下拉选择，别让人手打（奖品表单、奖池 CRUD 表单的「归属活动」均已改为 select）。
   - **落点清单**（新增编码类字段时照此三处补齐）：① AddForm 挂 `@Pattern`；② Service 的 add / 聚合保存里判重并给人话提示（唯一索引只是兜底）；③ 前端表单挂 `regular.bizCode` 规则 + 生成按钮 + 编辑态禁用。
   - 奖池编码有两个创建入口，都已统一：工作台「新建奖池」弹窗（打开即预填一个编码，可改可重新生成）与奖池 CRUD 表单。`workbenchSave` 里对每个 poolCode 都做了格式校验与跨活动占用判重。
   - **模板编码同时是 upsert 唯一键**：设计器进页面即预填一个新编码（并入基线，不算脏改动）；手输一个已存在的编码 = 覆盖那个模板，这是刻意保留的能力，`save()` 的返回值 `Boolean` 会告诉前端是新建还是覆盖。
   - **存量数据要迁移**：编码规范是后加的，老库里 `DAILY_SIGN_TPL` 这类编码存不进新规则。迁移脚本见 `数据库SQL脚本/mysql/任务模块-编码规范迁移与造数.sql`，改 `template_code` 必须级联 `t_task_config.template_code`。
9. **时间戳只认数据库一个时钟**：`create_time` / `update_time` 全部由 DDL 的 `DEFAULT CURRENT_TIMESTAMP` 与 `ON UPDATE CURRENT_TIMESTAMP` 产生，**代码里不要再填**。
   - `MybatisPlusFillHandler` 已停止填充时间字段，21 个实体上共 41 处 `@TableField(fill = FieldFill.*)` 已全部摘除。新建实体时**不要再加回来**。
   - **✅ 2026-08-02 已用 MP 3.5.17 源码坐实**：`TableFieldInfo#getInsertSqlPropertyMaybeIf` 里
     `if (withInsertFill) return sqlScript;` —— 直接返回、不走 `convertIf`，而
     `withInsertFill = fill == INSERT || fill == INSERT_UPDATE`。本条铁律成立。
     同日发现两处与之冲突、会让它复发的地方，均已修正：
     ① **代码生成器实体模板 `Entity.java.vm` 硬编码了这两个注解**（每生成一张新表就复发一次），
     ② `MybatisPlusFillHandler` 的 javadoc 写着"注解无需摘除"，结论正好说反。
     实测代价：`t_task_prize_mapping` 已有 2 行 `create_time` 为 NULL。
   - **⚠️ 只改 handler 不够**：`@TableField(fill=...)` 只要存在，MyBatis-Plus 生成 INSERT 时就会**直接带上该字段且跳过 `<if>` 判空**（源码里 `withInsertFill` 为 true 即 `return`，不走 `convertIf`），null 会被显式写入并覆盖 DDL 默认值 —— 实测曾导致 `create_time` 整列为 NULL。**注解必须一起摘。**
   - **新建表必须给这两列写全** `DEFAULT CURRENT_TIMESTAMP` 和 `ON UPDATE CURRENT_TIMESTAMP`，否则时间不会自动产生/刷新。自查：
     ```sql
     SELECT table_name FROM information_schema.columns
     WHERE table_schema='smart_admin_v3' AND column_name='update_time' AND extra NOT LIKE '%on update%';
     ```
   - 自定义 `<update>` 里**不要写** `update_time = now()`：DDL 的 ON UPDATE 已覆盖，显式写属于冗余且多引入一个时钟源。但 `approve_time` / `first_review_time` 这类**没有** ON UPDATE 兜底的列必须显式写。
10. **JDBC 连接串必须锁定会话时区**：`connectionTimeZone=Asia/Shanghai&forceConnectionTimeZoneToSession=true`（四个环境的 `sa-base.yaml` 均已加）。
   - **`serverTimezone` 解决不了这个问题**：它只影响 JDBC 读写 TIMESTAMP 时的 Java 对象转换，**不改变会话时区、也不影响 `now()` 的求值**。这是个很常见的误解。
   - 不加会怎样：MySQL 部署在 UTC（云厂商默认很常见）而应用在东八区时，`now()` 与 `ON UPDATE CURRENT_TIMESTAMP` 比 Java 时间早 **整 8 小时**。曾导致 `t_member_wallet` 497 行「更新时间早于创建时间」，上游 `NoticeMapper` 的 `publish_time < now()` 也会让公告晚 8 小时才显示。
   - 排查一句话：`SELECT @@session.time_zone, now();` 与 JVM 时间对比，不一致即中招。
   - **写诊断脚本时自己也要带这两个参数**，否则脚本里的 `now()` 同样是 UTC，统计口径全错（本项目排查时踩过）。
11. **`@Transactional` 绝不能被同类自调用**（2026-07-28 彩票开发中**连踩两次**，都是同一个人写的）：
   注解靠 Spring AOP 代理生效，**同类内部方法互调不经过代理**，注解<b>静默失效</b> —— 没事务、不报错、
   `mvn compile` 和单测全都通过，只在数据不一致时才暴露。
   - 判别口诀：**凡是「循环调用一个带 `@Transactional` 的方法」，先问一句它俩是不是同一个类。**
   - 修法：把事务方法拆到独立 Bean（如 `TicketPersistService` / `LotteryDispatchBatchService`）。
   - 后果的隐蔽程度取决于场景：领号那次是「记录插进去了但 sold_count 没加」；
     派奖那次更毒 —— `PrizeDispatchHandler` 挂在 `@TransactionalEventListener(AFTER_COMMIT)` 上，
     **没有事务上下文事件根本不会投递**，表现是「记录都标成已投递了，但下游一条都没收到」。
12. **实现 `BaseEnum` 的枚举，字段必须叫 `value`，且不要手写 `getValue()`**：
   `@CheckEnum` 的校验器是用 `map(BaseEnum::getValue)` 建合法值白名单的。
   字段叫 `code` 会导致 Lombok 生成不出 `getValue()`，若再手写一个 `return null` 糊过编译，
   白名单就成了 `[null,null,null]`，**任何取值都判非法**（`TicketStatusEnum` 曾因此让「按中奖状态筛选购彩记录」恒返回 400）。
   编译器和 IDE 都不会报警，只在运行期以「校验莫名不过」的形式出现。对齐 `sa-base` 的 `GenderEnum` 写法。
13. **判空口径必须全项目一致，尤其别用 `!arr` 判空数组**：`[]` 是 truthy，
   `!item.children` 会把「有属性但是空数组」判成「有内容」。
   四套菜单组件的 `sub-menu.vue` 都犯了这个错，而它们的顶层 `recursion-menu.vue`
   用的是 `$lodash.isEmpty` —— **同一份数据两种判法**，只是恰好当前数据构造不出空数组才没爆。
   （空 `a-sub-menu` 会让 antd 抛 `Cannot destructure property 'prefixCls' of useInjectMenu(...)`。）
   新写判空一律 `isEmpty`，并检查同一数据的其它判断点是否同口径。
14. **跨模块调用要看依赖方向，别想当然**：`sa-marketing` 依赖 `common-api`，
   所以 common-api 里的类**不能引用** sa-marketing 的 Dao（循环依赖）。
   需要反向取数时用依赖倒置：common-api 定接口、sa-marketing 实现并注册为 Bean
   （见 §4.5 的 `ActivityRefProvider`）。
   **多实现装配优先用 `List` + 各实现自报 `supportType()`，不要 `Map<Enum, Handler>`** ——
   后者正是铁律里那个「枚举键 Map 用字符串查」的温床，本项目已因此踩过三次静默失效。
   若 common-api 可能单独运行（如自身单测），用 `ObjectProvider` 而非直接注入 `List`，
   否则找不到候选 Bean 会直接启动失败。

15. **前端「看到的值 ≠ 模型里的值」**：本会话踩了三次，全都是同一族 ——
   `a-input-number` 程序化赋值不触发 Vue 模型、`form_input` 对 `RangePicker` 无效、
   `@blur` 里读 `e.target.value` 拿到的是 DOM 字符串而非组件状态。
   **统一做法：用 `@change` 维护本地草稿，提交时只读草稿、不碰 DOM。**
   另外 `@pressEnter` 在本项目的 `a-input-number` 上**不触发**，要用原生 `@keyup.enter`。
   自动化验证时同理：**每次操作前重新取元素，不复用上一次的坐标**（布局位移会让点击落偏）。
16. **断言前必须先确认前提条件真实成立**，否则「通过」和「空过」分不出来。
   本会话空过三次：`includeInactive`（库里没有已下线数据，过滤分支根本没执行）、
   `online` 接口路径写错（404 也返回 `!ok`，断言照样通过）、
   活动启用守卫（假定某活动未配置、实际已配好，「应被拦截」的断言全部落空）。
   **反证类断言要同时校验 http 状态与失败原因，不能只看 `ok=false`。**
17. **「捕获 DuplicateKeyException 后就地重查」在 REPEATABLE READ 下是失效的**
   （2026-08-01 任务运行态实测踩到：10 并发只推进了 1 笔）。
   MySQL 默认 REPEATABLE READ，事务的一致性视图在**第一次读**时就固定；
   赢家是在那之后才提交的，它插入的行**不在本事务的快照里** ——
   于是出现「INSERT 报重复、重查却查不到」这种看起来自相矛盾的现象。
   - 讽刺之处：这个到处都能见到的写法，只在「记录早已存在」时成立，
     而在「**刚刚被并发创建**」时失效 —— 后者恰恰是它被写出来要解决的那个场景。
   - 两条修法：① 重查改 `SELECT ... FOR UPDATE`（当前读）；
     ② **抛异常回滚、换新事务重试**（新事务有新快照）。任务模块选了 ②，
     因为它顺带把同事务里已插入的幂等流水一并回滚，不会留下「流水占了坑但进度没推」的半截状态。
   - 推论：**「换个事务重试」不只是重来一次，更是为了拿到新快照** ——
     就地循环重试多少次都是同一个结果。这也是事务方法必须拆独立 Bean 的又一条硬理由（配合铁律 11）。
18. **两个不同原因产生同一现象时，用例分不出对错**（铁律 16 的另一种形状）。
   任务并发用例第一版借用了「目标 500」的任务跑 10×100，结果 500 ——
   看起来像 Lost Update，实际是**完成闸门正确挡下了后 5 笔**。两者现象一模一样。
   写并发/边界用例时，先确认**待验证的机制是唯一能产生该现象的机制**，否则修错方向都不会被发现。
19. **跑 `@SpringBootTest` 必须带 `SPRING_PROFILES_ACTIVE=dev`**。
   根 pom 的两个 `<resource>` 指向同一目录，后一个 `<filtering>false</filtering>` + `*.*`
   会把前一个过滤后的 `application.yaml` 覆盖回去，于是 `@profiles.active@` **从未被替换**，
   Spring 启动直接报 `Profile '@profiles.active@' must start and end with a letter or digit`。
   这是既有构建配置的问题，不是测试写错了；用环境变量覆盖即可，未擅自改 pom。
20. **验证之前，先确认跑的是不是刚构建出来的那个包**（铁律 16 的第三种形状，2026-08-02 连踩两次）。
   Spring Boot 启动失败后，Redisson/Netty 的**非守护线程会把 JVM 吊住不退**。
   这个僵尸进程在 Windows 上锁着 fat jar 和日志文件，于是：
   ① `mvn clean` 删不掉 jar，构建**静默失败**，启动的还是旧包；
   ② `rm` 删不掉日志，新日志追加进旧文件，读到的是上一轮的堆栈。
   表现就是「改了配置重启，报的还是一模一样的错」，极易误判成"这个升级做不通"。
   - 识破的线索：两次报错的 netty channel id 和本地端口**完全相同** —— 那不可能是两次独立运行。
   - 做法：重启前先按命令行过滤掉残留进程
     （`Get-CimInstance Win32_Process -Filter "Name='java.exe'"`），
     并且**核对产物时间戳**；端口被占时换端口跑，不要盲目 kill（可能是别人 IDE 里的调试实例）。
21. **「段数不变、位置错位」是最难发现的一类数据格式变更**。
   ip2region 的 xdb 数据 v2 是 `国家|区域|省份|城市|ISP`，v3 是 `国家|省份|城市|ISP|iso-alpha2-code` ——
   都是 5 段，换数据文件既不报错也不长度异常，**只会静默把「省份」读成「区域」**，
   而字符串看上去"还挺像那么回事"，不逐字段比对根本发现不了。
   - 通则：**解析外部数据格式时不要按位置硬编码**，要从数据自带的版本标记推导布局
     （本项目改成读 xdb 文件头的 `version` 字段，见 `SmartIpUtil`）。
   - 并且**归一化后再落库**：让存储内容的含义和形状不随数据文件版本漂移，否则历史数据与新数据没法比。

- **starter 改名**：`spring-boot-starter-aop` 在 Boot 4 已删除，改叫 `spring-boot-starter-aspectj`。
- **Jackson 3**：见上面 §0 前端/后端栈里的警告。新写序列化器一律继承 `ValueSerializer`/`ValueDeserializer`。

- **`spring.jackson` 的枚举/日期开关挪位置了**：`serialization.write-enums-using-to-string` 之类

- **依赖清理**：common-api 的 pom 原先整段抄了 sa-base 的 40 条依赖（它本就 depend on sa-base，那份拷贝对 classpath 零影响），

- **poi 版本必须成对管**：只在 depMgmt 声明 `poi-ooxml` 不够，`poi` 核心会按 Maven「同深度先声明者胜」被 fastexcel 拽回旧版，两者版本错配。

  且它是基于字节码的，**所有靠反射/配置装配的依赖都会被误报成 unused**，不能照着告警删。

### 核心思想
"模板即交互"：新增任务玩法 = 运营在**任务模板设计器**配一条 `ui_schema` + 开发写一个 `rule_script`(QLExpress)，**向导前端零改动**自动就绪；派发/派奖走公共链路。

> ⚠️ 这个设想只实现了一半：`ui_schema` 解决了「长什么样」，
> 但「怎么算」全塞进了 `rule_script` —— 那不是零开发，只是把开发从前端挪到了脚本，
> 而且脚本是自由文本，无法被策略工厂分类。方案 §3 给了三层分离的改法。

### ui_schema 契约（最重要，三方共享）
- `params[]` 驱动管理端动态表单，`render` 驱动 C端卡片。
- `widget`：number/text/select/radio/switch/slider/**image_upload**。
- **`visibleWhen` 契约主形态 `{field, eq}`**，兼容 `{key, value}`（`isSchemaParamVisible` 双兼容）。**新增模板强制用 `{field, eq}`**。
- `image_upload` 值随 `rule_config` 提交时，服务端按 widget 拆分：image_upload → `uiConfig`，其余 → `ruleConfig`（`splitSchemaValues` 前后端同函数语义）。
- 后端 `TaskTemplateService.save()` 保存前做 ui_schema 结构校验；向导提交 `TaskConfigService.wizardSubmit()` 做**按 schema 反向校验**（必填且 visibleWhen 可见的参数必须有值，隐藏字段不校验也不该提交）。

## 4. 彩票模块（2026-07-28 全链路打通，可结案）

> 完整方案与验收记录见 `docs/彩票中台-实现技术方案.md`（16 节）。这里只放**接手前必须知道的硬约束**。

### 定位：号码派发引擎，与业务解耦
消耗多少积分、单人限购几张，**都由上游业务算完再调进来**，本模块只发号。
所以领号链路里没有资产扣减也没有退还，比 `DrawExecuteService` 短得多。
保留的幂等（requestId SETNX）与限流防的是网络重试和恶意刷接口，**与业务限购是两回事** ——
本模块必须假定同一个 memberName 可以合法领任意多张号，别给 `(issue_no, member_name)` 加唯一索引。

后续会通过 `@ScriptFunction` 挂到 QLExpress 上，`TicketIssueService.obtain` 同时提供
平铺参数与收 Form 的两个重载，核心实现只有一份。

### 🔴 四条不可逆约束（违反会造成资损或历史数据失效）

1. **发号游标绝不回滚**。抽奖的库存预扣失败要 `rollback` 回滚 Redis；**彩票方向相反** ——
   回滚游标 = 两个用户拿到同一个 `sequence_no` = 同一个号码。
   **浪费一个号（留空洞）可以接受，发重号不行。** 事务回滚时游标同样不退回。
   任何在发号路径上写 `DECR` 的改动都要按资损处理。
2. **`lottery.fpe.master-secret` 一旦有期号发过号就不可轮换**。号码是「连续游标经 FPE 加密」得来的，
   换密钥等于换一套加密映射：已发号码再也反解不回游标（客服验真、对账自证清白全失效），
   新号码还可能与历史号码重复。dev 已配，test/pre/prod 留的是注释而非 `${VAR}` 占位
   —— 占位符在环境变量缺失时会让整个后台启不来，而彩票只是众多模块之一。
3. **`issue_no` 创建后不可修改**。它是 FPE 的 tweak（`key = HMAC(secret, lotteryCode|issueNo)`），
   改了等于换密钥。`LotteryIssueUpdateForm` 里刻意不定义该字段，让越权意图在编译期就无处安放。
4. **`number_length` / `total_count` 在发过号后永久冻结**（结构锁）。但两者冻结的**理由不同，别混为一谈**：
   前者是密码学约束（FPE 定义域由它决定），后者是业务约束（防已承诺的发行量被追溯篡改）。
   **只冻结这两个引擎参数，名称与奖级规则仍可改** —— 锁太死会逼运营绕过流程。

### 关键设计（省得重新推导）
- **号码固定十进制、长度 4~9 位**。字母对彩票没意义，且 `0/O`、`1/I` 形近会制造「我明明中了」这类
  **无法自证**的纠纷 —— 而本方案的号码本来是可反解验真的。下限 4 位是为了号码空间不小于 1 万。
- **Redis 游标 1-indexed（顺着 INCR 的天然行为），`sequence_no` 0-indexed（直接就是 FPE 输入），
  换算只在 `toSequenceNo` 一处**。放在 Redis 这侧是因为两个边界容错不对等：
  Redis 侧算错只是跳一个号，加密侧算错会越界或号码错位。
- **冷启动回源必须 `SET NX` + 取 `MAX(sequence_no)` 而非 `COUNT`**：有空洞时 COUNT 偏低，回填后必然重号。
- **奖级互斥 = SQL 里 `win_status = 0` 的守卫 + 按 `prizeLevel` 升序执行**，
  等价于 `TicketMatcher` 的「命中即止」。**两者是同一套规则的两种实现，改一边必须同步另一边**，
  `SettleSemanticsTest` 就是防漂移的。
- **期号 `status=1` 被复用为可恢复的核销断点**：开奖号码在抢到闸门那一刻定案且不再变，
  续跑时忽略入参号码，避免「中途换号」。
- **未中奖 `prize_level=99` 而非 NULL**：C 端要按奖级排序，NULL 在 `ORDER BY ASC` 里会排最前、正好排反。
- **派奖与核销分开**，用 `dispatch_status` 列做扫描标记，不靠唯一索引的异常去重
  （本项目已证明基于异常的静默去重会掩盖真问题）。

### 验收强度（都是真跑，不是推断）
- 彩票自身 **36 单测**全绿（FpeCipher 12 / TicketMatcher 12 / SequenceCursor 7 / SettleSemantics 5），
  含 `length=4/5` 的**全域遍历证双射**（零重复零遗漏）。
  加上抽奖的 `DrawEngineTest` 9 个，sa-marketing 全模块共 45 个 —— 旧文档写的「45 单测」是这个全模块数，别误当成彩票一家的。
- 卖光一期：游标恰好 `[0..totalCount)` 无空洞、号码去重 == 记录数、第 N+1 次正确售罄。
- 冷启动：DB 有 206 条时删掉 Redis 游标，再领接上 206/207，没有从 0 重来。
- 200 并发领号零重复。
- 全域 1 万张开奖：分奖级 1/99/990/8910 **与理论值完全吻合**，且反向核对
  （二等奖里无全号命中、未中奖里无任一规则可命中等）**全部为 0**。
- 派奖 1090 == `t_prize_log` 1090 == 幂等键去重 1090，零失败。
- 审批：并发批两次第二次被拒；驳回留痕；通过后立即派发成功。

### 遗留
- C 端页面（产品明确不做）。
- 压测规模上限目前是 1 万张 + 200 并发，未做大规模压测。
- 上游 QLExpress 接入（`@ScriptFunction` 注解由使用方按需添加）。

## 4.5 活动创建向导（2026-07-29 完成，P0~P3）

> 完整方案见 `docs/活动创建向导-实现技术方案.md`（12 节）。交互以
> `docs/活动创建向导原型-一体化向导.html` 为准。这里只放**接手前必须知道的**。

### 形态：一体化向导，不是跳转式

```
活动中心 › 活动配置 →「创建活动向导」
  ① 创建活动（左：名称/时间/类型/编码　右：就地建奖品）
       ↓ 提交即落库（聚合接口，活动+奖品同事务）
  ② 配置玩法 —— 按类型动态挂载对应玩法组件（embedded=true）
       BASIC 无此步，步骤条收缩为两步
  ③ 完成
```

### 🔴 新增第四种活动类型 `BASIC`（基础活动）

**改动了 `t_activity_config.activity_type` 的取值集合**，动活动域前必知。

BASIC = 只有活动外壳、不挂玩法引擎，但**可以挂奖品**（`t_prize_config.activity_code`
是它的归属键且与玩法无关）。引入它是为了消除一处语义歧义：原先「没有玩法配置」同时意味着
**半途放弃**和**本来就不需要**两件事，向导第二步该显示什么、列表该标什么都无从判断。

配套的类型冻结规则**不是一刀切**：

```
BASIC → DRAW / TASK / LOTTERY     ✅ 放行（无玩法下游，升级不产生孤儿数据）
DRAW / TASK / LOTTERY → 任何类型   ❌ 拒绝（含互转与降级回 BASIC）
```

`UpdateForm` 里**不定义** `activityType`（编译期挡死普通编辑），升级走独立窄接口
`POST /activityConfig/upgradeType`，服务端双校验「当前是 BASIC」+「下游玩法表为空」。

### 🔴 三条不要踩回去的约束

**① 完备度判据必须是「能不能上线」，不是「有没有记录」。**
`t_lottery_config` 完全可以在没配任何奖级规则时保存成功，只看「有无记录」会把一个
上不了线的半残废显示成「已配置」。故各玩法把上线前校验抽成可复用方法
（`LotteryConfigService.checkOnlineReady`），`online()` 与完备度统计**共用一份**，防漂移。
⚠️ 注意这与「升级」的判据**刻意不同**：升级问「有没有东西会被孤立」，看有无记录就够。
两个问题不同，别为了统一而合并。

**② 删除守卫的下游统计必须包含资产大库 `t_prize_config`。**
BASIC 活动按定义没有玩法下游，**资产大库是它唯一的引用来源** —— 漏了这张表等于对 BASIC
完全没有守卫，一个挂了 10 个奖品的活动会被判「无引用」而顺滑删除，奖品当场悬空。
另外：**上线过的活动永不可删，只能下线**（`t_prize_log.activity_code` 是发奖流水的追溯键）。
评估过逻辑删除，不采用 —— 会与 `uk_act_code` 唯一索引打架（删掉的记录仍占编码，
运营复用编码被判重却看不到那条记录），且替代不了守卫。

**③ 外壳不持有玩法组件的「保存」按钮。**
`TaskConfigService.wizardSubmit` 是单个 `@Transactional` 一次性提交，`TaskWizard`
**根本不存在可供外部调用的「中途 save」**。保存权留在各玩法组件自己手里，
外壳第二步只放「稍后再配」，推进完成页由子组件 `emit('saved')` 驱动。
离开拦截同理只留内层一处（它注册在子组件里同样对本路由生效），外壳不加第二层，
否则内外各弹一次确认框。

### 三个玩法组件的内嵌契约

统一加 `activityCode` + `embedded` 两个 prop 与 `emit('saved')`。
`embedded=false` 时行为与改造前完全一致（三个独立入口已逐项回归）。

| 组件 | 内嵌时 |
|---|---|
| `DrawWorkbench` | 隐藏活动下拉 |
| `LotteryWorkbench` | 只隐藏活动下拉，**玩法下拉保留**（一个彩票活动可有多个玩法） |
| `TaskWizard` | 活动置灰而非隐藏、抑制自带成功页、跳过草稿恢复 |

⚠️ 三处都必须**同时处理 `onMounted` 与 `watch(props.activityCode)`** ——
外壳从活动 A 切到 B 时若组件没重新挂载，只写 onMounted 会让配置落到上一个活动下。
**外壳自己也踩过同族的坑**：从「继续配置」的 URL 导航回无 query 的菜单入口，
路由 path 没变、组件不重挂载，结果点开菜单看到的是上一个活动停在第二步的配置页。
现已 `watch(route.query)` 与 onMounted 共用 `initFromQuery()`。

### 依赖倒置：ActivityRefProvider

三个玩法表的 Dao 都在 **sa-marketing**，而 `ActivityConfigService` 在 **common-api**（上游），
直接引用会造成循环依赖。故 common-api 定 `ActivityRefProvider` 契约、sa-marketing 提供三个实现。
新增第四种玩法只需加一个实现类。

**装配刻意用 `List` 注入 + 各实现自报 `supportType()`，不用 `Map<Enum, Provider>`** ——
本项目已因「枚举键 Map 用字符串 get」踩过三次静默失效（铁律见 §5）。
用 `ObjectProvider` 而非直接注入 `List`：common-api 单独跑时一个实现都没有，直接注入会启动失败。

### 奖品类型只开放 4 个

`LOTTERY` / `CUSTOM` 两层派发策略都没有（`@PrizeStrategy` 与 `@AssetStrategy`
各只注册了 SCORE/BALANCE/COUPON/PHYSICAL），已从 `PRIZE_TYPE_OPTIONS` 过滤。
**刻意不给它们补优惠配置** —— 缺的是策略不是配置，补了只会让运营建出一个必然发不出去的奖品，
而失败在 `AFTER_COMMIT` 里对主链路无感。补齐策略后把常量里的 `dispatchable` 改 `true` 即可。

这不是「权限配得不够」，是「权限根本无法配对」。

### 🔴 验证时发现的基座缺陷：改角色权限不清缓存

## 4.6 列表页与编码体系的通用改造（2026-07-30）

这几项不属于某一个模块，但**动任何列表页或编码前都要知道**。

### ① 业务编码加了 1 位类型前缀

```
A=活动  P=奖品  D=奖池  T=任务模板  L=彩票
```

实现是「**1 位前缀 + 9 位随机，总长仍是 10**」，见 `SmartCodeUtil.BizCodePrefix`。
这样 `BIZ_CODE_REGEX = ^[A-Z0-9]{10}$` **一个字都不用改**，前后端所有 `@Pattern`、
`regular.bizCode`、唯一索引全不受影响，**存量数据也不需要迁移**
（实测：老编码 `VJR856K8DW`、数字开头的 `12278CBYW7` 依然通过格式校验）。

🔴 **前缀只在生成时加，绝不参与校验。**
存量编码没有前缀，一旦写进 `@Pattern`，老活动一打开编辑就会被判非法；手输的编码也不该被拦。
**前缀是给人看的线索，不是给代码依赖的契约** ——
任何「按前缀判断业务类型」的写法都会立刻把它变成必须迁移存量的硬约束。

> 澄清一个直觉误区：加前缀让随机位从 10 降到 9，碰撞空间**小了 36 倍**（不是变大）。
> 在本系统量级下仍可忽略，且 `generateUniqueBizCode` 本就带判重重试。
> 真正的收益是**跨业务类型不会看混**，不是熵变大。

> 评估过用系统自带的单号管理（`t_serial_number`），**不采用**：它产出递增有序号
> （会泄露业务体量且可枚举，与彩票用 FPE 防猜号的取向相反）、
> `SerialNumberIdEnum` 是硬编码枚举（加业务必须改 Java 发版，「没有新增页面」是设计如此）、
> 格式长度不定会破坏 `BIZ_CODE_REGEX`。它适合订单号/合同号那类**需要人工对账**的单据号。

### ② 列表页「列设置」此前是坏的，已修

## 4.7 前端依赖升级善后与生成器产物缺陷（2026-08-01）

这一节记的是**前端侧**的坑，此前交接文档几乎没覆盖过。

### ① 依赖升级把 dev server 打挂 —— 但根因不是升级

报错是 `NoResourceFoundException: No static resource .`，看着像后端问题，实际是
`vite.config.js` 的 proxy：

原本 proxy 写在 `server.server` 下，**嵌套层级不对、Vite 根本不识别，等于没配** ——
而「没配」恰好是对的：`axios.baseURL` 直连 `VITE_APP_API_URL`(1024)，整条链路不经过代理。
有人把它「修正」到正确层级后 proxy 生效，而模式是 `'/'` **匹配所有请求**，
首页 HTML、`/@vite/client`、每个源码模块全被转发到后端，于是白屏。

🔴 **这个配置长得像 bug，却是靠「错着」才对的。** 现已还原并加注释，别再「顺手修」。
真要加代理必须给具体前缀（如 `/api`）并同步改 axios 的 baseURL。

### ② 三个问题层层遮挡，且前两轮控制台一条错都没有

修好 proxy 才看得见 `main.js` 500，修好它才看得见 `router/index.js` 500：

| 依赖 | 变更 | 影响 |
|---|---|---|
| `vue3-json-viewer` 2.3.1→2.4.1 | CSS 改名 `dist/index.css` → `dist/vue3-json-viewer.css` | ⚠️ 它自己 package.json 的 `style` 字段写的 `dist/style.css` **根本不存在**，别信 |
| `nprogress` 0.2.0→1.0.0-1 | CSS 挪进 `css/` 子目录 | 已借机整个替换掉，见 ③ |

**为什么没有报错**：`main.js` 顶层用了 `await`，模块解析失败时整个入口静默中断。
排查手法：在页面里 `import('/src/main.js')` 把错误逼出来，再逐个 `fetch` 依赖模块定位。

### ③ nprogress 已替换为 `src/lib/progress-bar.js`

项目只用到 `start`/`done` 两个 API，为两个函数扛一个停更十年的包不划算。
**新实现刻意不引任何 CSS 文件、样式由 JS 注入** —— 从根上消灭「依赖改 CSS 路径把构建打挂」
这一整类问题（本次已踩两次）。

顺带比 nprogress 好一点：**延迟 120ms 才显示**，路由在窗口内切完就压根不出现，
避免 SPA 快速跳转时「闪一下」。

> 供应链核对结论：nprogress 包本身是正品（原作者、原仓库、零依赖、无 install 钩子），
> 问题只在于 `1.0.0-1` 是预发布版 —— 其 CHANGELOG 首行就写着 `1.0.0 - unreleased`。

### ④ 🔴 生成器产物的三类系统性缺陷

这三类散布在**所有**生成器产出的页面里，动任何生成器页面前先看这里：

**(a) 用了组件却没 import** —— 全项目 21 处用 `SmartEnumSelect`，1 处漏导入

所以能潜伏很久。已修。

**(b) `enum-name=""` 空串** —— 组件渲染后去查一个空名字的枚举，报

**仍剩 6 处**，分两类：`prizeCode`/`lotteryCode` 2 处应改为**接口驱动下拉**（铁律 8，

### 🕐 时间戳错乱排查纪实（2026-07-26，铁律 9/10 的由来）
起点是提案表里一条记录 `update_time` 比 `create_time` **早整 8 小时**。查下来是两个独立缺陷叠加：

**缺陷一：时区不一致**（连接串修复）
MySQL 服务器在 UTC、JVM 在东八区。`create_time` 走 MyBatis-Plus 的 Java 填充(+08)，
而 raw SQL 的 `now()` 与 `ON UPDATE CURRENT_TIMESTAMP` 走 MySQL 会话时区(UTC)。
实测 `t_member_wallet` 已有 **497 行**受影响。修法与 `serverTimezone` 无效的原因见铁律 10。

**缺陷二：双时钟源的亚秒错位**（收敛时钟源）
时区对齐后仍有残留，且分布很说明问题：
| 记录类型 | 倒挂比例 |
|---|---|
| `status=80` 只 insert 从未 update | **0 / 100** |
| `status=50` 被引擎 update 过 | **18 / 48** |
精确指向「create 走 JVM、update 走 DB」这个双时钟源 —— `datetime(0)` 截断时两边舍入方向不同即差 1 秒。
治本是只留数据库一个时钟，做法见铁律 9。顺带消除了多实例部署时各节点 JVM 时钟漂移的隐患。

**排查过程中的两次误判（值得记）**
1. 先以为「去掉自定义 SQL 里的 `update_time = now()`」是修复 —— 错。`ON UPDATE CURRENT_TIMESTAMP` 照样用 MySQL 时钟，去 `now()` 纯属去冗余。**决定性证据**：`MemberWalletMapper` 根本没写过 `now()`，那 497 行照样倒挂。
2. 再以为「只改 `MybatisPlusFillHandler` 停止填充」就够 —— 错，`create_time` 整列变成 NULL。根因是 fill 注解会让字段跳过判空被硬塞进 INSERT（见铁律 9）。
**教训：验证要覆盖到实际写入的那一层。** 第 2 次误判正是因为只验了「手写 SQL 不带这两列时 DDL 默认值会生效」，却没验「ORM 会不会把这一列带上」。

### 方案A 已实施：提案与资产下发解耦（2026-07-26）
`ProposalRecordService.dispatchAfterCommit()` 用 `TransactionSynchronizationManager` 注册 `afterCommit` 回调，把 `assetDispatchEngine.execute` 挪到**提案事务提交之后**。
- 提交后已无事务上下文，引擎里每次状态更新都是独立自动提交，**回滚再也冲不掉失败痕迹**：提案一定留得下，失败稳稳落在 70。

### 🔴 「状态永远停在 0」的第二层静默：写库字段超长
报错 `Data truncation: Data too long for column 'fail_reason' at row 1`。
`t_prize_log.fail_reason` 只有 **varchar(128)**，而 `doDispatch` 直接把异常 message 塞进去 —— 实测那条 `UnexpectedRollbackException` 的 message 有 **234 字符**。
致命之处在于**这句就写在 finally 回写状态之前**：一抛异常，`status=2` 根本刷不进去，最终表现就是「状态永远停在 0、fail_reason 为空」，把真正的失败原因彻底吃掉。
- 新增 `SmartStringUtil.truncate(text, maxLength)`（null 安全、恰好等长不动、maxLen<=0 原样返回）。
- `PrizeDispatchHandler` 的 fail_reason 按 128 截断；`AssetDispatchEngine` 的 remark 按 255 截断。
- 两处的**状态回写都再包了一层 try/catch**：回写本身失败时至少留日志，不能让兜底动作自己把自己炸掉。
- **通用教训：凡是往库里写异常信息的地方，一律先截断；且这类写入常处在 catch/finally 里，一旦再抛异常，故障就彻底隐身。**

### 🔴 事务边界隐患已被证实（不再是理论问题）
COUPON 那 51 条**连一条 status=70 的失败提案都没留下** —— 因为 `AssetDispatchEngine` 在 `addProposal` 的事务内执行：券插入失败 → 事务被标记 rollback-only → 引擎虽然写了 `status=70`，但**提案记录连同这条失败标记一起被回滚**，失败痕迹彻底消失。
这正是上一节预警的 `executeWalletCharge` REQUIRED 传播问题的同类表现。**后果很严重：资产层任何一次失败，都会让提案表查不到任何线索，只能靠翻日志。**
建议的修法（属公共账务域改造，未擅自动）：把 `assetDispatchEngine.execute` 移出 `addProposal` 的事务（提案提交后再触发），或让引擎的状态记账走 `REQUIRES_NEW` 独立事务。

## 10. 依赖瘦身轮次（2026-08-06 ~ 08-08，✅ 已结案）

> 起初的目标：**删掉 guava 与 hutool，替代一律用 JDK 原生 API**（`List.of` / `Map.of` / `java.time` /
> `ThreadLocalRandom` / `Files` 等）—— 两个都已删完，共省约 5.6MB。
>
> 后续 §11 的 SonicExcel 又连带摘掉了 POI 全家桶（18.66MB）与
> commons-collections4 + commons-text（1.11MB）。
> **累计约 25.4MB**，当前 runtime classpath 为 **202 个 jar / 97.16MB**。

### 10.0 先看这张账：哪些能删、哪些是净亏

跑过 `dependency:tree -Dverbose` 反查每个工具库「除了我们自己还有谁需要它」：

| 库 | 我们的用量 | 还有谁需要 | 抄出来能删掉 jar 吗 |
|---|---|---|---|
| commons-lang3 | 40 处 | commons-text、knife4j、swagger-core、velocity×2、commons-compress | ❌ 删不掉 |
| commons-io | 7 处 | **commons-compress**（←fastexcel-reader）、**tika-core** | ❌ 删不掉 |
| commons-codec / commons-compress | **0 处** | compress 是 fastexcel-reader 的编译期依赖，codec 又挂在 compress 下 | ❌ 本来就不是我们的 |
| **commons-collections4** | 130 处 | ~~poi、poi-ooxml~~ → **无** | ✅ **已删（0.86MB）**，见 §10.5 |
| **commons-text** | 2 处（StringSubstitutor） | 无 | ✅ **已删（0.25MB）**，见 §10.5 |
| **guava** | 44 处 | **无** | ✅ **已删（2.92MB）** |
| **hutool-all** | 36 处 | 无 | ✅ **已删（2.7MB）** |

🔴 **结论仍然成立，但要连着前提一起读**：
**只有「除我们之外没人依赖」的库，换成自研才真的删得掉。**
lang3/io 至今删不掉，只是「谁拖着它们」换了人 —— 从 poi 换成了 compress + tika，
抄进自己的工具类照样是净亏（体积不变、CVE 面不变，还多一份要维护的实现）。

⚠️ **反过来也要留意：这条判据的输入是会变的。**
commons-collections4 原先「删不掉」是因为 poi 要它；2026-08-08 摘掉 POI 之后它变成了
「只有我们在用」，同一条判据就给出了相反的答案。**每摘掉一个大依赖，这张表都要重算一遍。**

### 10.1 ✅ guava 已移除（提交 `40438661`）

- `Lists.newArrayList()` / `Maps.newHashMap()` → `new ArrayList<>()` / `new HashMap<>()`，48 处机械替换
- 带参的 14 处**逐点核过调用方**：进 DAO 查询的用 `List.of(...)`；
  作返回值或交给 Service/框架的用 `new ArrayList<>(List.of(...))`；varargs 用 `Arrays.asList`
- `CaseFormat` → **`SmartCaseFormat`**（sa-base/common/util）
- `ThreadFactoryBuilder` → `Thread.ofPlatform().name("前缀-", 0).factory()`
- `Interners` → `ConcurrentHashMap` + `computeIfAbsent` 规范化锁对象

🔴 **三条不要踩回去的**：

1. **不要把 `new ArrayList<>()` 改成 `List.of()` 图省事。**
   `Lists.newArrayList()` 返回**可变**列表，`List.of()` 不可变 ——
   换过去之后任何 `add/remove` 都在运行期抛 `UnsupportedOperationException`，编译期零信号。
2. **不要改 `SmartCaseFormat` 的语义。** 它不是照感觉写的：删依赖前用
   5×5×33 = **825 种组合**与 guava 逐条比对过，第一版有 48 处不一致（全在「下划线↔中划线」
   这对上 —— guava 那里走的是「只换分隔符、不动大小写」的快捷路径），补上特例后才 0 处不一致。
   `SmartCaseFormatTest` 把语义固化了，**代码生成器的产物命名依赖它**。
3. **发号器那把锁不能简化成 `synchronized(serialNumberId)`。**
   Integer 只缓存 -128~127，超出范围每次装箱都是新对象，两个线程锁的不是同一把锁 ——
   互斥静默失效、并发发重号。见 `SerialNumberInternService` 的注释。

| 提交 | 内容 |
|---|---|
| `128efd35` | ① 低风险：24 处换 JDK 原生 |
| `7c5b965c` | ② 中风险：ServletUtil / NetUtil / BeanUtil / 脱敏 / 雪花自研 |
| `3a4e4da4` | ③ 高风险：SM4/AES 换 BouncyCastle，摘依赖 |

#### 🔴 验证方法论：这轮真正值钱的东西

沿用 §10.1 `SmartCaseFormat` 那次的做法，**每一处自研实现都先跑一次「一次性差异测试」**——
趁 hutool 还在 classpath 上，让新旧两个实现跑同一批输入逐条比对，
0 处不一致之后，才把期望值固化成永久单测、删掉差异测试。

**这不是形式主义，它逮到了三个「看起来对」的真错**：

1. **银行卡脱敏用的是 `cleanBlank`（去掉所有空白）而不是 `trim`（只去首尾）。**
   卡号常带分组空格 `6217 0000 1000 1234`，只 trim 会把空格算进长度，
   分组和保留位数全错 —— 但**不带空格的卡号完全正常**，随手测一个必然通过。
2. **手写的 4 条脱敏期望值有 3 条是错的**（银行卡 17 位的余数分组、
   邮箱无 `@` 时其实原样返回、`USER_ID` 的保留位数）。
   实现是对的，是「凭感觉写的断言」错了 —— 如果没有差异测试做基准，
   会反过来照着错误的断言去「修」正确的实现。
3. `SmartStringUtil.isBlank` 若直接用 JDK 的 `String#isBlank()`，
   不间断空格 U+00A0、BOM U+FEFF 这类字符会从「空白」变成「非空白」，
   而它们恰恰常出现在从 Excel / 前端粘来的文本里。判空口径会在全项目范围内静默漂移。

#### 各档要点

**① 低风险（`128efd35`）**

- 🔴 **`SmartStringUtil` 原本 `extends StrUtil`**，`isEmpty/isNotEmpty/isBlank/isNotBlank/
  trim/equals/join` 全是靠静态方法继承对外供着的，全项目 53 处在用。
  改成本类自实现，调用方一行没改。**`trim` 是 null 进 null 出，不是返回 `""`**。
- `DatePattern`/`DateUtil`/`LocalDateTimeUtil` → 项目本就有 `SmartDateFormatterEnum`
  + `SmartLocalDateUtil`，没有新造轮子
- `RandomUtil`/`IdUtil` → 新增 `SmartRandomUtil`。
  **顺带修了一处安全口径**：邮箱登录验证码原先用可预测的 `ThreadLocalRandom`，
  已改走 `SecureRandom`。该类注释里把「测试数据用 ThreadLocalRandom /
  凭证用 secureRandom()」的分界写死了。
- `FileUtil`/`ZipUtil` → `Files` + `java.util.zip`。
  ⚠️ 代码生成器的打包链路只在「运营点下载代码」时才跑，**编译期和原有单测都盖不到**，
  写坏了要等到有人下到一个打不开的 zip 才知道。为此把三个方法降为包级可见，
  补了 `CodeGeneratorTemplateZipTest` 钉住四件事：追加而非覆盖、
  条目名用正斜杠且不含最外层临时目录、**中央目录真的写出来了**（不 close 就是个空包）、
  非空临时目录能删干净。

**② 中风险（`7c5b965c`）**

- 🔴 **`SnowflakeIdGenerator`（common-api）：位布局与起始纪元 `1288834974657L` 必须与 hutool 逐位一致。**
  库里已有历史 ID，改任何一个参数都会让新旧 ID 落进同一段数值区间从而可能碰撞，
  且不再随时间单调递增（多处隐含依赖这一点排序）。
  验证方式是**拿 hutool 自己的解析器去拆自研生成的 ID**，位段全部对得上。
  `nextId()` 的 `synchronized` 不能拆成两个原子变量，会在「同一毫秒 + 序列回绕」
  的交叉点上发重号，已配 16 线程 × 5000 次的并发用例。
  ⚠️ **类名不叫 `Snowflake`**：门面类 `SnowFlake` 与它只差一个字母的大小写，
  Windows 文件系统大小写不敏感 —— 本次改造真的踩到了，新文件直接把门面覆盖掉了。
- 🔴 `SmartServletUtil.getClientIP`：`X-Forwarded-For` 是代理链
  `客户端, 代理1, 代理2`，取的必须是**第一个非 unknown 段**。
  取成最后一段的话，登录日志和风控里所有人看起来都来自自家网关。
  `getHeaderIgnoreCase` 整个删掉了 —— Servlet 规范本就规定 `getHeader` 大小写不敏感。
- 🔴 `SmartBeanUtil.beanToMap` **没有按原计划用 Jackson `convertValue`**：
  本项目 JSON 层挂了 `LongJsonSerializer`（Long 序列化成 String 防前端精度丢失）
  等自定义序列化器，走 Jackson 会让代码生成器模板里拿到的类型悄悄变掉 ——
  生成的代码照样能编译，只是内容不对。改用 `PropertyDescriptor` 反射，值保持原始对象。
- `DesensitizedType` 那个枚举字段**直接删了**：交接文档原先担心「11 处引用且在注解上」，
  实测这 11 处全在 `DataMaskingTypeEnum` 自己的构造参数里，**从来没有任何地方读过它**，
  打码规则一直是在 `DataMaskingUtil` 的 switch 里按枚举常量分发的。
- `hide()` 按**码点**而不是 char 遍历，否则 emoji 的代理对会被劈成乱码方块。
- `NetUtil` 三处改用项目本就有的 `SmartIpUtil`，没有新增实现。

**③ 高风险 · 加密（`3a4e4da4`）**

`ApiEncryptServiceSmImpl`（SM4）换成 **BouncyCastle**（`bcprov-jdk18on` 本就是现成依赖），
`ApiEncryptServiceAesImpl` 换成 JDK 自带 `Cipher`（AES 不需要 BC）。三点必须对齐：

1. **ECB + PKCS5(=PKCS7) 填充、无 IV** —— 原 `new SM4(key)` / `new AES(key)` 的默认值
2. 🔴 **SM4 那条链路是「双层编码」**：先加密得到十六进制小写串，
   再把这个 hex 串当文本做 Base64。除黑盒断言外，另有一个用例把
   「base64 解开之后必须是 32 位纯 hex」这个结构本身钉住。
   ⚠️ **AES 那条只有一层 Base64，没有 hex 层**，两边别搞混。
3. 密钥字节仍由 `stringToHex`/`hexToBytes` 推导，未动

**三层验证全部实跑**：① 字节级差异测试，14 个明文样本新旧密文串完全相同、

### 10.5 ✅ commons-collections4 + commons-text 已移除（2026-08-08，提交见 git log）

摘掉 POI 之后重算 §10.0 那张账，这两个库变成了「除我们之外没人依赖」，合计 **1.11MB**，
runtime classpath 从 204 个 jar 降到 202 个。

**commons-collections4（0.86MB，130 处）→ `SmartCollectionUtil`**

130 处里 **125 处是 `isEmpty` / `isNotEmpty`**，本质就是一个 null 检查，不属于"要长期维护的实现" ——
这正是它和 lang3/io 的区别所在。剩下 5 处单独处理，其中**一处是真地雷**：

- 🔴 `ErrorCodeRangeContainer` 用 `CollectionUtils.subtract(codeList, distinctCodeList)` 找重复错误码，
  靠的是 commons 的**多重集语义**（按重数扣减）。换成 `removeAll` 会**永远返回空**，
  这条启动期校验静默失效。已改写成显式的「找出出现多于一次的 code」。
- `NoticeService` 的两处 `subtract` 入参都先 `.distinct()` 过，`removeAll` 与原语义等价，安全。
- `RedisService.arrayToList` → `Arrays.asList`（顺带去掉一个 `@SuppressWarnings("unchecked")`）。
- `MapUtils.isNotEmpty` 1 处，并入 `SmartCollectionUtil`。

⚠️ 替换必须**按文件门控**，只改 import 了 commons collections 的文件：项目里有 4 个文件用的是
`org.springframework.util.CollectionUtils`，同名不同物，按方法名盲替换会误伤。

顺带修掉一个坏味道：`EnterpriseController` 在用 `org.apache.commons.collections`（**collections 3**，
另一个 artifact），来源是 `velocity-tools → commons-beanutils` 的传递依赖，**没有任何 pom 声明过它** ——
等于拿传递依赖在编译。jar 摘不掉（那是 velocity 的），但我们不该依赖它。

**commons-text（0.25MB，2 处）→ `SmartTemplateUtil`**

只有邮件和站内信模板用 `StringSubstitutor` 做 `${key}` 替换。摘依赖**之前**先写了个临时用例，
拿真的 `StringSubstitutor` 跑 13 条语料逐条比对（转义 `$${}`、未闭合、空 key、`$100`、解析不到……），
全绿之后才把期望值固化进 `SmartTemplateUtilTest` 并删掉临时用例 —— 和 SonicExcel 第③档摘 POI 同一个套路。

🔀 **一处有意的口径收紧**：`StringSubstitutor` 默认会把替换进去的值**再扫一遍**（递归解析），
值里带 `${...}` 会被继续替换。`SmartTemplateUtil` 不递归 —— 模板参数常来自用户数据，

### 11.1 🔴 三条不能碰的红线

1. **所有文本必须走 `Worksheet#inlineString`，禁止 `value(r, c, String)`。**
   fastexcel 的 `Workbook` 没有关闭 shared strings 的开关，`StringCache` 是个永不清理的 HashMap ——
   漏用一次，千万级高基数文本就会把堆吃穿。`SonicExcelWriteTest` 里有哨兵测试（断言产出包中
   `sharedStrings.xml` 的 `uniqueCount="0"`）。
2. **读侧只接受 `Path`，不接受 `InputStream`。** fastexcel-reader 拿到流会用
   `SeekableInMemoryByteChannel` 把整个 xlsx 读进堆 —— 100MB 上传文件在读第一行前先吃 100MB。
   API 签名就是防线，别加 InputStream 重载。
3. **`SonicStaxIsolation` 不能删。** fastexcel-reader 带进来的 `aalto-xml` 会通过
   `META-INF/services` 抢占 JVM 全局 StAX 实现，实测影响 spring-core / spring-web /
   hibernate-validator / mysql-connector-j / tika-core / **aws-query-protocol（S3 走它）**。
   注意 `XMLEventFactory` 的 JDK 实现类在 **`.events.` 子包**下，写错不会启动报错，
   要等首次使用才抛 `FactoryConfigurationError`。

### 11.2 明确不做的事

- **不兼容非 Excel 工具产出的 xlsx（WPS / Numbers）** —— 产品决策。只影响导入；我们导出的是标准 xlsx。
  这类文件是合法 zip，字节头挡不住，所以读引擎把 `ExcelReaderException` 统一翻译成
  「请用 Excel 另存为 .xlsx 后重试」。
- 水印、模板填充（`fill`）、`.xls`、多级表头、`WriteHandler` 式扩展点 —— 都是有意放弃的，理由见设计文档 §1.2。
- **模板下载还没有对外接口**：框架能力已就绪，加 `/xxx/importTemplate` 要配权限和前端入口，属产品决策。

### 11.3 🔴 顺带修掉一个全系统级 bug：BusinessException 的消息恒为 null

做 D10 时字典歧义的报错信息丢了才暴露出来 ——

`BusinessException` 上有 `@Data`，同时又声明了 `private String message` 字段。
Lombok 为它生成的 `getMessage()` **覆盖掉了 `Throwable.getMessage()`**
（Lombok 只看本类声明的方法，看不到继承来的），返回那个从未被赋值的字段 —— **恒为 null**。

而 `GlobalExceptionHandler` 是直接把 `e.getMessage()` 返给前端的，
**等于全系统每一个业务异常的提示语都是 null**，静默、不报错、不抛异常。

修复是删掉那个字段，让 `getMessage()` 回落到 `Throwable`。全项目没有任何地方调用过 `setMessage()`。
`BusinessExceptionTest` 钉住了四个构造器 + 子类。

⚠️ **接手人注意**：修好之后前端会开始收到**真实的业务错误信息**。
如果某些页面一直靠「提示为空就显示默认文案」兜着，那里的展现会变 —— 这是好事，但属于用户可见的行为变化，上线前值得扫一眼。

⚠️ 另外 `@Data` 打在异常类上还会生成 `equals` / `hashCode` / `toString`，
`toString` 覆盖 `Throwable` 的会让日志里的异常摘要变样。**这次没动**（不阻塞、改了会影响日志格式），留待判断。

### 12.2 🔴 四条不能碰的红线

1. **`storageKey` 不可变，永不覆盖。** 换图 = 传新文件 + 改引用。

   用户传 `evil.html` 而内容是 PNG 时存成 `.png` —— 这一条直接掐死存储型 XSS。
3. **端到端流式，禁止 `byte[]`。** 旧实现名为流式实为全量进堆。

### 12.3 🔴 一个栽了两次的坑：列约束与代码写入面不一致

同一模块两次栽在同一类问题上，**接手时请把它当成检查清单**：

- **第一次**（`0d052fc3` 修复）：删掉旧 `FileService` 后，`t_file.folder_type` / `file_type`
  这两个 `NOT NULL` 且无默认值的列没人写了。MyBatis-Plus 跳过 null 字段不拼进 INSERT，
  MySQL 8 严格模式下**每一次上传都失败**。单测全绿是因为 DAO 全是 mock 的。
- **第二次**（`648cf961` 修复）：`t_file_category.category_name` 同样 `NOT NULL` 无默认值而代码没校验，
  用户收到一整段 `DataIntegrityViolationException` 的 SQL 原文 —— 既看不懂又泄露表结构。

> **规则：DB 上每一个 NOT NULL 且无默认值的列，代码里都必须有一处对应的写入或校验。**
> 这类问题单测结构上发现不了，只有集成测试或真跑一次才行。

## 12.7 素材库选图器（2026-08-10 ✅，附两个「没点过就发现不了」的 bug）

### 做了什么

| 文件 | 作用 |
|---|---|
| `components/support/material-picker/index.vue` | 选图器弹窗：左分类 / 右网格 + 文件名标签检索 + 分页，单选多选可切，**弹窗内可直接上传并自动选中** |
| `components/support/file-thumb/index.vue` | 素材缩略图。存在的唯一理由见下面第 2 个 bug |
| `lib/file-preview.js` | 按 fileId 取字节转 object URL，带 Promise 缓存 |
| `components/support/image-field/index.vue` | 图片字段（选/传/移除），从 `activity-display-form` 的内联渲染函数抽出来 |
| `FileQueryForm.imageOnly` + `FileMapper.xml` | 只列图片。按 `content_type LIKE 'image/%'` 而不是扩展名白名单——扩展名是从嗅探 MIME 反推的，content_type 才是原始结论 |

选图器与素材库页面 (`views/support/file/file-list.vue`) **刻意不共用模板**：那边是「管理」
（多选打标签、看引用、删除、管分类），这边是「挑一张」。硬凑一个组件只会两边都长满
`v-if="pickerMode"`。共用的是接口和取数口径，不是模板。

### 🔴 bug 1：`fileUrl` 少了 `/support` 前缀，下发的每一个文件链接都是死链

`FileAssetService.DOWNLOAD_PATH` 原本是 `/file/download/`，而 `FileController` 继承
`SupportBaseController`，类级 `@RequestMapping` 是 `/support` —— 真实路径是
`/support/file/download/{id}`。少一段的后果是**所有 `fileUrl` 指向不存在的路径**，
而 `<img>` 加载失败是静默的，页面上只是「图没出来」。

- 改法：生成用长形态 `/support/file/download/`，**反查匹配单独留一个短形态常量**
  `DOWNLOAD_PATH_MATCH = "/file/download/"`。两者必须分开：`fileIdFromDownloadPath` 是
  `indexOf` 子串匹配，短形态同时命中新老两种 URL；**若拿长前缀去匹配，历史富文本正文里
  那些 `/file/download/12` 会静默失配** —— 保存活动规则时登记不上引用，图随后被孤儿清理
  任务删掉（红线 4）。`FileAssetServiceTest` 里已加了同时断言三种形态的用例。

### 🔴 bug 2：`<img>` 发不出 Authorization 头，所以后端下发什么 URL 都没用

下载接口要登录态，而 token 存在 localStorage 不是 cookie，`<img src>` 带不上。
浏览器拿回来的是一段 JSON 错误体，表现同样是「图打不开且不报错」。
开发环境还多一层：前端 8081、后端 1024，**相对路径会打到 dev server 上**。

- 改法：预览一律走 `lib/file-preview.js`「带 token 取字节 → `URL.createObjectURL`」，
  收在 `FileThumb` 一个组件里。缓存的是 **Promise 不是结果**，否则同一张图并发挂载三次
  就发三个请求；失败的不留缓存，否则一次网络抖动会让这张图在整个会话里都显示不出来。
- **非图片不去取字节** —— 一个 20MB 的 zip 拿回来只为渲染一个「ZIP」占位。
- 这两个 bug 合起来意味着：**在此之前素材库的缩略图、详情抽屉的预览、展示配置的回显图
  从来没有显示出来过**，而 358 个后端单测 + 前端 build 全绿。§12.6 说的「没真跑过」
  遮住的就是这个。

### 真实后端验过的链路（活动 VJR856K8DW）

选图 → 确定 → 字段显示所选图 → 保存 → 刷新页面回显仍在（`mainImageId=108` 已落库）→
`t_file_relation` 出现 `ACTIVITY_DISPLAY/20` 且文件 `status` 由 TEMP(1) 转 CONFIRMED(2) →

## 12.8 活动公开图（2026-08-10 ✅）：可见性由分类决定 + 免登录读取口

> **C 端用户是匿名的，永远带不上 token。** 所以活动展示图必须有一条无鉴权也能取到的路 ——
> 这不是优化，是 C 端能不能显示图的前提。本节把这条路铺好了，**C 端本身仍未开工**。

### 12.8.1 🔴 修掉一个还活着的越权：`/upload/**` 免登录端出整个上传目录

`FileConfig` 把本地上传目录整个挂成了静态资源，**不看 `visibility`**。实测不带任何 token
请求 `/upload/feedback/202608/10/xxx.jpg` 返回 200 + 完整字节，而同一个文件走
`/support/file/download/{id}` 是要登录态的。

**设计文档声称档⑤ 已经修掉的「本地模式下私有文件根本不私有」，其实换了个地方原样活着。**
它一直没暴露，是因为 `FileAssetService` 把每一次上传的 `visibility` 都写死成公开 ——
全库没有一个私有文件，这个矛盾就没有机会显形。**两个错误互相掩护。**

修法（v3.55.0 + 代码）：

| 改动 | 说明 |
|---|---|
| `t_file_category.default_visibility` | 可见性**由分类决定**，上传处不再写死。DB 默认值取「私有」——加分类的人没想过这件事时，结果是"图看不见"而不是"附件被公开了"，前者会被立刻发现 |
| 新分类 `ACTIVITY`（活动素材） | 唯一默认公开的分类。它的 code 会成为 storageKey 第一段（`activity/...`），将来在 CDN 上按前缀配规则靠它 |
| 存量文件一律转私有 | 原先全是公开，只是因为上传处写死了 1，不代表有人判断过 |
| 删掉 `/upload/**` 静态映射 | 换成 `FileController#publicAccess`（`/support/file/public/**`）：同样免登录、同样能被 CDN 回源，但**会查 visibility**，私有文件一律 404（不是 403 —— 不告诉外面"这个 key 存在但你没权限"） |
| `Cache-Control: immutable` | 敢这么写是因为 storageKey 不可变、永不覆盖（红线 1）。换图 = 换 key = 换 URL |

**为什么不做「公私分目录、静态映射只挂公开那棵树」**：决策 D2 写着**权限进 DB 不进路径**，
把可见性编回目录名就是在重犯 `private/` 前缀那个错。代价是每次公开请求多一次主键查询，
用 immutable 缓存头挡在浏览器与 CDN 之外。

### 12.8.2 URL 是后端拼的，不是前端拼的

常见做法是「后端给前缀、前端拼域名」。**本项目刻意多走半步**：库里只存 `storage_key`（相对），
但**完整 URL 由后端 `urlOf()` 产出**。这样「这张图该走 CDN 还是走鉴权接口」只在一处决定；
前端拼的话，每个页面都要知道一遍规则，将来加 CDN 就是满地改。

配置：`file.storage.public-url-prefix`，dev 指向 `http://127.0.0.1:1024/support/file/public/`，
上了对象存储/CDN 换成 CDN 域名 + 同一个 storageKey 即可，**业务代码与前端都不动**。
test/pre/prod **留空并写了理由**：占位符会拼出打不开的 URL，留空则稳稳退回登录态接口 ——
管理端照常可用、C 端图不显示，后者一眼能发现。

前端 `FileThumb` 因此有两条路且并存：公开图直接进 `<img>`（浏览器/CDN 缓存生效），
私有图仍走「带 token 取字节 → object URL」。**同一个网格里两种图各走各的**，
实测活动素材直接用公开 URL、意见反馈的图走 blob，都正常渲染。

### 12.8.3 🔴 「移除主视觉」曾经是完全无效的——两个 bug 互相掩护

实测点「移除」再保存：界面提示保存成功、图也消失了，刷新回来图还在，引用也没解除。
查下去是**两处**，而且**只修一处的话表面现象一点都不会变**：

1. **`updateById` 默认跳过 null 字段** → `mainImageId=null` 压根没进 UPDATE 语句。
   修法：`ActivityDisplay` 上九个可清空字段标 `@TableField(updateStrategy = ALWAYS)`
   （本表的保存语义是整表单覆盖，null 表示"运营清空了它"）。
   ⚠️ **不要顺手加到 `createTime`/`updateTime` 上** —— 那两列由 DDL 产生，标了会被写成 NULL（铁律 9）。
2. **`FileAssetService.confirm` 空集合直接 return** → 「清空最后一张图」时那句先清后建从没执行。
   3 张变 2 张是对的、1 张变 0 张是错的，**差一个元素，行为完全相反**。
   后果：那张图从此删不掉（守卫说"正被 1 处业务引用"），而实际上没有人在用它。

两条都补了测试，但性质不同，**这个区别值得记住**：
- `confirm` 那条是**行为测试**（断言 DAO 上发生了 deleteByBiz），mock 测得出来；
- `updateStrategy` 那条只能做**注解固化测试** —— null 跳过是 MyBatis-Plus 生成 SQL 时干的事，
  DAO 一 mock 前后都是绿的（§12.3 同一类陷阱）。所以固化的是「这九个字段必须能写回 null」
  这条约定，外加「时间列不许标 ALWAYS」的反向断言。
