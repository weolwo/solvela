### 已确立的工程铁律（贯穿全程，务必延续）
1. **浮点比较用容差**：任何概率/金额求和判等，前端用 decimal.js、后端用 BigDecimal，容差 `0.0001`，严禁 `=== 100`。（曾因此出现"界面显示100%却保存不了"死锁）
2. **前端 UI 校验只是防呆**，后端必须服务端重算一遍（防绕过页面直接 POST）。
3. **消除魔法值**：状态码/类型/默认值一律具名常量。
4. **单一状态源**：向导类表单收拢在一个 `reactive` 对象。
5. **Tailwind v4 important 是后缀**：`text-purple-600!`（不是 `!text-purple-600`）。
6. **in-DOM 模板陷阱**（仅限 CDN 直写 HTML 的原型）：浏览器把 camelCase 属性强制小写，`:customRow`/`valueFormat` 等 antd prop 必须写成 kebab（`:custom-row`/`value-format`）。SFC（.vue）不受影响。
7. **SmartBeanUtil.copy** 同名同类型自动拷贝——加实体字段后 Form→Entity 自然带过去。
8. **业务编码统一规范**：活动编码、奖品编码、奖池编码、任务模板编码一律「**10 位大写字母 + 数字**」随机组合（如 `H88JHKJFNE`），**全局唯一**。
   - 唯一真源：`sa-base` 的 `SmartCodeUtil`（`BIZ_CODE_REGEX` / `generateBizCode()` / `generateUniqueBizCode(判重函数)` / `isValidBizCode()`）。前端同源常量在 `constants/regular-const.js` 的 `regular.bizCode`。
   - 运营两条路径：手工输入 or 点「生成」按钮（`GET /activityConfig/generateCode`、`GET /prizeConfig/generateCode`、`GET /prizePoolConfig/generateCode`、`GET /taskTemplate/generateCode`，服务端生成时已判重）。
   - **手输路径必须服务端重校验**：AddForm 上挂 `@Pattern(SmartCodeUtil.BIZ_CODE_REGEX)`，Service 再查一次重（表上的唯一索引直接抛 SQL 异常对运营不友好）。
   - **编码创建后不可改**：UpdateForm 本就不含编码字段，前端编辑态把输入框和生成按钮一起禁掉；否则改一次编码，奖品/奖池/流水的引用全断。
   - 编码是随机码，凡是「填别人的编码」的地方一律改成下拉选择，别让人手打（奖品表单、奖池 CRUD 表单的「归属活动」均已改为 select）。
   - **落点清单**（新增编码类字段时照此三处补齐）：① AddForm 挂 `@Pattern`；② Service 的 add / 聚合保存里判重并给人话提示（唯一索引只是兜底）；③ 前端表单挂 `regular.bizCode` 规则 + 生成按钮 + 编辑态禁用。
   - 奖池编码有两个创建入口，都已统一：工作台「新建奖池」弹窗（打开即预填一个编码，可改可重新生成）与奖池 CRUD 表单。`workbenchSave` 里对每个 poolCode 都做了格式校验与跨活动占用判重。
   - **模板编码同时是 upsert 唯一键**：设计器进页面即预填一个新编码（并入基线，不算脏改动）；手输一个已存在的编码 = 覆盖那个模板，这是刻意保留的能力，`save()` 的返回值 `Boolean` 会告诉前端是新建还是覆盖。
   - **存量数据要迁移**：编码规范是后加的，老库里 `DAILY_SIGN_TPL` 这类编码存不进新规则。迁移脚本见 `数据库SQL脚本/mysql/任务模块-编码规范迁移与造数.sql`，改 `template_code` 必须级联 `t_task_config.template_code`。

## 2. 任务模块（已完成，前后端联调就绪）

### 核心思想
"模板即交互"：新增任务玩法 = 运营在**任务模板设计器**配一条 `ui_schema` + 开发写一个 `rule_script`(QLExpress)，**向导前端零改动**自动就绪；派发/派奖走公共链路。

### ui_schema 契约（最重要，三方共享）
- `params[]` 驱动管理端动态表单，`render` 驱动 C端卡片。
- `widget`：number/text/select/radio/switch/slider/**image_upload**。
- **`visibleWhen` 契约主形态 `{field, eq}`**，兼容 `{key, value}`（`isSchemaParamVisible` 双兼容）。**新增模板强制用 `{field, eq}`**。
- `image_upload` 值随 `rule_config` 提交时，服务端按 widget 拆分：image_upload → `uiConfig`，其余 → `ruleConfig`（`splitSchemaValues` 前后端同函数语义）。
- 后端 `TaskTemplateService.save()` 保存前做 ui_schema 结构校验；向导提交 `TaskConfigService.wizardSubmit()` 做**按 schema 反向校验**（必填且 visibleWhen 可见的参数必须有值，隐藏字段不校验也不该提交）。

### 前端文件
- `task-wizard/TaskWizard.vue`（5步向导 + 成功页 + 离开拦截 + 本地草稿）。**活动大类与模板列表均已接口化**：活动来自 `/activityConfig/optionList?activityType=TASK`，模板来自 `/taskTemplate/optionList`；模板拉回后自动选中第一个；模板为空时第1步渲染引导去设计器建模板。
  - ⚠️ 模板异步化带来的坑：模板切换的 watch 里必须先判 `selectedTemplate` 是否已解析，否则「恢复草稿」时模板列表还没回来，会把草稿里的 `ruleParams` 冲成 `{}`。
- `task-wizard/task-wizard-const.js`（所有枚举/`isSchemaParamVisible`/`splitSchemaValues`/`buildDefaultWizardForm`）。**`ACTIVITY_OPTIONS` 与 `TASK_TEMPLATES` 两份 mock 已删除**，`buildDefaultWizardForm()` 的 templateCode 改为留空。
- `task-wizard/SchemaFormRenderer.vue`（动态表单渲染引擎，向导第2步与设计器共用）
- `task-wizard/PrizeLadderBuilder.vue`（阶梯奖励）
- `task-template/TaskTemplateDesigner.vue`（双 Monaco：rule_script[java] + ui_schema[json]，右侧实时预览，脏标记/最后保存时间/离开拦截/本地草稿）
- `api/business/task/task-api.js`

### 后端接口
- `POST /taskConfig/wizard/submit` → `TaskConfigService.wizardSubmit`（主子表事务，返回新建ID）
- `POST /taskTemplate/save` → `TaskTemplateService.save`（按 templateCode upsert，返回 Boolean 区分新建/覆盖）
- `GET /taskTemplate/optionList` → `TaskTemplateOptionVO`（record）：**ui_schema 以 JSON 对象下发**（列表VO里是原始字符串），前端拿到即可直接喂 `SchemaFormRenderer`；卡片的 `icon`/`description` 取自 `ui_schema.icon`/`ui_schema.desc`（这两个是约定字段，不入列，只活在 JSON 里，缺省给兜底图标 🧩）。单个模板 ui_schema 解析失败只剔除该模板并告警，不影响整个向导。
- `GET /taskTemplate/generateCode` → 生成模板编码

### 3.5 后端：抽奖引擎（纯内存，9单测全绿）
`draw/engine/` 包，record + sealed 主战场：

- `DrawEngine`（纯函数，随机数可注入供测试）：判定优先级 = **白名单必中(仍受库存约束) → 概率区间命中 → 库存不足降级兜底 → 兜底也干涸则 NoStock**。兜底自己被抽中且无库存不自我降级。
- 测试 `DrawEngineTest`（sa-marketing/src/test）：概率未闭环拒绝构造、区间边界、10万次固定种子分布(±0.5pp)、白名单必中、白名单无库存回落、降级兜底、双干涸NoStock、switch模式匹配消费。

### 3.6 后端：抽奖运行态（已完成，待联调压测）
`draw/runtime/` 包，`POST /drawPrizeLog/execute` → `DrawExecuteService.execute()` `@Transactional`：
链路 = **幂等防重(requestId SETNX) → 防刷限流(RRateLimiter 单用户单活动2次/秒) → 奖池校验 → 抽奖资格扣减 → 组装快照 → DrawEngine判定 → 双层扣减 → 落流水**。
- **双层防超发**：① Redis Lua 原子预扣（`DrawStockService` Text Block，返回1/-1/-2/-3）扛并发；② DB 条件更新 `increaseUsedStock`（`WHERE total_stock=-1 OR used_stock<total_stock`）做最终一致性；DB 拒绝则补偿回滚 Redis。
- **资格扣减**：CREDIT→钱包SCORE资产（`MemberWalletService.executeWalletDeduct`，乐观锁+余额充足双条件SQL）；NONE不扣；TICKET暂返回"未开放"。NoStock 时 `executeWalletRefund` 退还（同事务，流水双向留痕）。

### 方案A 已实施：提案与资产下发解耦（2026-07-26）
`ProposalRecordService.dispatchAfterCommit()` 用 `TransactionSynchronizationManager` 注册 `afterCommit` 回调，把 `assetDispatchEngine.execute` 挪到**提案事务提交之后**。

### 🔴 「状态永远停在 0」的第二层静默：写库字段超长
报错 `Data truncation: Data too long for column 'fail_reason' at row 1`。
`t_prize_log.fail_reason` 只有 **varchar(128)**，而 `doDispatch` 直接把异常 message 塞进去 —— 实测那条 `UnexpectedRollbackException` 的 message 有 **234 字符**。
致命之处在于**这句就写在 finally 回写状态之前**：一抛异常，`status=2` 根本刷不进去，最终表现就是「状态永远停在 0、fail_reason 为空」，把真正的失败原因彻底吃掉。
- 新增 `SmartStringUtil.truncate(text, maxLength)`（null 安全、恰好等长不动、maxLen<=0 原样返回）。
- `PrizeDispatchHandler` 的 fail_reason 按 128 截断；`AssetDispatchEngine` 的 remark 按 255 截断。
- 两处的**状态回写都再包了一层 try/catch**：回写本身失败时至少留日志，不能让兜底动作自己把自己炸掉。
- **通用教训：凡是往库里写异常信息的地方，一律先截断；且这类写入常处在 catch/finally 里，一旦再抛异常，故障就彻底隐身。**

### 🔴 事务边界隐患已被证实（不再是理论问题）
COUPON 那 51 条**连一条 status=70 的失败提案都没留下** —— 因为 `AssetDispatchEngine` 在 `addProposal` 的事务内执行：券插入失败 → 事务被标记 rollback-only → 引擎虽然写了 `status=70`，但**提案记录连同这条失败标记一起被回滚**，失败痕迹彻底消失。
这正是上一节预警的 `executeWalletCharge` REQUIRED 传播问题的同类表现。**后果很严重：资产层任何一次失败，都会让提案表查不到任何线索，只能靠翻日志。**
建议的修法（属公共账务域改造，未擅自动）：把 `assetDispatchEngine.execute` 移出 `addProposal` 的事务（提案提交后再触发），或让引擎的状态记账走 `REQUIRES_NEW` 独立事务。

### 由第3轮引出的两处加固（已改，待验证）
1. **压测脚本改用 run 级隔离的用户名**：原来固定 `stress_user_0..N`，跨轮重复。`user_max_count=1` 时上一轮赢过某奖项的用户在 `draw:user:{活动}:{奖项}:{用户}` 里计数已是 1，之后永远赢不了该奖项，不清 Redis 就会让结果越跑越失真（表现为「明明有库存却一直不中」）。现改为 `stress_{RUN_ID}_{i}`，RUN_ID 每轮不同，`draw:user:*` 再不需要手工清。
2. **`resolveRemainStock` 的回源预热改走 SET NX**（`DrawStockService.warmStockIfAbsent`）：原来复用无条件 SET 的 `warmStock`，缓存冷启动遇上高并发时，A 预热 100 → B 扣成 99 → C 也没读到 key 又预热回 100，**扣减被覆盖直接超发**。现在配置态保存仍用无条件 SET（要的是以 DB 为准强刷），运行态回源用 SET NX（补空洞但绝不覆盖），两种语义分开。
