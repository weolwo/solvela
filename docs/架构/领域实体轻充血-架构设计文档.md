> 撰写日期：2026-11-22

> 前置阅读：`solvela-contract/src/main/java/solvela/enums/MallOrderStatusEnum.java`、`solvela-mall/src/main/java/solvela/mall/order/dao/MallOrderDao.java`
> 已落地：商城订单（`MallOrder` / `MallOrderStatusEnum` / `MallOrderDao`）、外部场景消费单（`ExternalOrder` / `ExternalOrderStatusEnum` / `ExternalOrderDao`）、会员券（`MemberCoupon` / `CouponStatusEnum` / `MemberCouponMapper.xml`）、等级权益发放（`GradeEntitlementGrant` / `EntitlementGrantStatusEnum` / `GradeEntitlementGrantMapper.xml`，顺带从 Integer 常量迁成枚举）、任务记录（`TaskRecord`）、发奖记录（`PrizeLog`，只收派发状态 `status`）、彩票记录（`LotteryRecord`，中奖与派发两列）

## 要解决什么

状态流转的规则分散在三处：Service 里的 `if (status == X)`、DAO 注解里写死的状态数字、以及只写在注释里的状态机。改枚举取值时，SQL 不会报错，只会变成一条永远匹配不到行的 UPDATE。

## 不做什么

**不做标准 DDD**：不拆聚合根、仓储、领域服务、应用服务。项目的 Service 本来就是具体类，没有「一个接口配一个 Impl」，不需要为了分层再造一层类。

🔴 **不把状态迁移改成「读出实体 → 在内存里改 → 整行写回」。** 订单支付、取消、履约，提案抢执行权，预算扣减，钱包扣款，靠的都是带旧状态条件的 UPDATE，按 affected rows 判断成败。改成先读后写，并发下两个线程会同时读到同一个旧状态，结果是重复发券、超发、扣成负数。

## 规则放在哪

| 放什么 | 放在哪 | 订单试点里对应的代码 |
|---|---|---|
| 「谁能变成谁」 | 状态枚举的 `canTransitTo`，用不带 default 的 switch，新增状态时编译器会要求补上分支 | `MallOrderStatusEnum#canTransitTo` |
| 只由状态决定的业务口径 | 状态枚举上的方法 | `MallOrderStatusEnum#isSettled`（是否已扣过款） |
| 并发闸门 | DAO 的条件 UPDATE，**不变** | `MallOrderDao.markPaid` 等五个方法 |
| SQL 里的状态值 | 写成 `${@solvela.enums.XxxEnum@CONST.value}`，不写数字 | `MallOrderDao`、`MallOrderMapper.xml` |
| 落单时的初始状态与配套字段 | 实体上的方法，状态字段去掉公开 setter | `MallOrder#awaitPayment`、`MallOrder#settleOnCreate` |

实体上只放不需要依赖注入的纯行为。实体在 `solvela-model` 里，那个模块只依赖 `solvela-contract`，调不到 DAO 和 Service。这一点正好防止实体越长越胖。

## ⚠️ 推广到其它域前先看

1. **去掉 setter 之前**，先搜有没有 `SolvelaBeanUtil.copy(..., Xxx.class)` 拷贝进这个实体。它遇到没有 setter 的属性会静默跳过，结果是那个字段变成 null，编译器不会报错。订单实体没有被拷贝进去过，其它实体要逐个查。
2. **「部分更新」写法**：有的 Service 会 `new` 一个空实体，只 set 要改的那几列，再交给 MyBatis-Plus 做 updateById，靠 null 跳过其余列（如 `MallCategoryService.updateStatus`）。对这类实体去掉 status 的 setter，那条更新路径就编译不过了，要先改成条件 UPDATE。
3. **常量改名**：`${@...@CONST.value}` 是运行期求值，编译器管不到。每个推广的域都要有一个渲染 SQL 的测试，否则常量改名就是一次静默故障。
4. `${}` 里只放常量，不放入参，否则就是 SQL 注入。
5. **测试里要造「库里读出来就是某状态」的对象**时，用 MyBatis 读库的同一条反射路径写字段（`SystemMetaObject.forObject(x).setValue("status", ...)`），收成测试类里的一个私有方法，例如 `CouponWriteOffServiceTest#loadedAs`。不要为了测试给实体加回 setter。
6. **渲染测试的工具代码各模块自带一份**，不抽成共享的 test-jar：项目没有 test-jar 先例，各模块的守卫测试（如 `*BoundaryTest`）也都是自包含的。为三四十行重复给几个模块的 pom 加一层测试依赖不划算。重复多到改一处要同步改很多处时，再重新评估。

## 收拢时顺带改掉的绕过闸门的写法

下面三处原来是「new 一个实体或拿着读出来的实体，set 状态后 `updateById`」，不带旧状态条件。2026-11-22 经确认后改成了条件 UPDATE：

- **任务记录**：管理端「修改」不再接收 status（后端命令与表单、管理端表单一起去掉），原来它可以把记录直接改成已完成 / 已发奖，绕过运行态。「禁用」改成 `expireByAdmin`，只认进行中；已完成、已发奖的记录影响 0 行，接口把没改动的记录列给运营。
- **发奖记录**：派发处理器的三处整行写回改成 `markDispatchSucceeded` / `markDispatchFailed`（带「仍是等待」条件）与 `markProposalAccepted`（只动提案列，不碰 status）。原来「已受理」那次整行写回会把内存里的「等待」写回去，资产引擎若已先回写了终态，会被盖掉。抢不到时记一条 warn，不算故障。
- **彩票记录**：派奖失败改成 `markDispatchFailed`，只认「中奖且待派奖」，不再覆盖已投递的记录。
