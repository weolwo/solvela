# 领域实体轻充血-架构设计文档

> 撰写日期：2026-11-22
> 状态：商城订单、外部场景消费单、会员券、等级权益发放已落地；任务记录、发奖记录、彩票记录待定（见文末）
> 前置阅读：`solvela-contract/src/main/java/solvela/enums/MallOrderStatusEnum.java`、`solvela-mall/src/main/java/solvela/mall/order/dao/MallOrderDao.java`
> 已落地：商城订单（`MallOrder` / `MallOrderStatusEnum` / `MallOrderDao`）、外部场景消费单（`ExternalOrder` / `ExternalOrderStatusEnum` / `ExternalOrderDao`）、会员券（`MemberCoupon` / `CouponStatusEnum` / `MemberCouponMapper.xml`）、等级权益发放（`GradeEntitlementGrant` / `EntitlementGrantStatusEnum` / `GradeEntitlementGrantMapper.xml`，顺带从 Integer 常量迁成枚举）

## 要解决什么

状态流转的规则分散在三处：Service 里的 `if (status == X)`、DAO 注解里写死的状态数字、以及只写在注释里的状态机。改枚举取值时，SQL 不会报错，只会变成一条永远匹配不到行的 UPDATE。

## 不做什么

**不做标准 DDD**：不拆聚合根、仓储、领域服务、应用服务。项目的 Service 本来就是具体类，没有「一个接口配一个 Impl」，不需要为了分层再造一层类。

🔴 **不把状态迁移改成「读出实体 → 在内存里改 → 整行写回」。** 订单支付、取消、履约，提案抢执行权，预算扣减，钱包扣款，靠的都是带旧状态条件的 UPDATE，按 affected rows 判断成败。改成先读后写，并发下两个线程会同时读到同一个旧状态，结果是重复发券、超发、扣成负数。

## 规则放在哪

| 放什么 | 放在哪 | 订单试点里对应的代码 |
|---|---|---|
| 「谁能变成谁」 | 状态枚举的 `canTransitTo`，用不带 default 的 switch，新增状态时编译器会要求补上分支 | `MallOrderStatusEnum#canTransitTo` |
| 只由状态决定的业务口径 | 状态枚举上的方法 | `MallOrderStatusEnum#isSettled`（是否已扣过款） |
| 并发闸门 | DAO 的条件 UPDATE，**不变** | `MallOrderDao.markPaid` 等五个方法 |
| SQL 里的状态值 | 写成 `${@solvela.enums.XxxEnum@CONST.value}`，不写数字 | `MallOrderDao`、`MallOrderMapper.xml` |
| 落单时的初始状态与配套字段 | 实体上的方法，状态字段去掉公开 setter | `MallOrder#awaitPayment`、`MallOrder#settleOnCreate` |

实体上只放不需要依赖注入的纯行为。实体在 `solvela-model` 里，那个模块只依赖 `solvela-contract`，调不到 DAO 和 Service。这一点正好防止实体越长越胖。

## 用什么守住

- **SQL 渲染测试**（`MallOrderStatusSqlTest`、`ExternalOrderStatusSqlTest`、`MemberCouponStatusSqlTest`、`EntitlementGrantStatusSqlTest`，不连库）：让 MyBatis 渲染出真正发给数据库的 SQL，断言五条闸门的迁移与 `canTransitTo` 的边一条不多、一条不少，`paid_statuses` 与 `isSettled` 口径一致。2026-11-22 四个域各故意改错过三到四次（目标状态写错、常量拼错、只在枚举里加边、查询条件改错），全部变红。
- **真库验收**（`solvela-admin/.../mapper/MallOrderStatusFlowTest`、`solvela-app-biz/.../external/ExternalOrderStatusFlowTest`、`solvela-app-biz/.../entitlement/EntitlementGrantStatusFlowTest`，放在该单据实际运行的进程模块里；会员券已有的 `CouponWriteOffLiveTest`、`BusinessJobTest` 本来就在真库上走锁定 / 确认 / 释放 / 过期并读回实体，没有另写）：落单后走一遍迁移再读回实体，确认 `${}` 在 Spring 装配的 MyBatis-Plus 配置下能求值并真的命中行，也确认去掉 setter 后读库时状态仍能装配进来。数据由用例自己造，结束时回滚。
- **实体单测**（`solvela-model/.../MallOrderTest`、`ExternalOrderTest`、`MemberCouponTest`、`GradeEntitlementGrantTest`）：初始状态方法只能对新对象调用；MyBatis 结果映射用的那套反射仍认为 `status` 可写。

## ⚠️ 推广到其它域前先看

1. **去掉 setter 之前**，先搜有没有 `SolvelaBeanUtil.copy(..., Xxx.class)` 拷贝进这个实体。它遇到没有 setter 的属性会静默跳过，结果是那个字段变成 null，编译器不会报错。订单实体没有被拷贝进去过，其它实体要逐个查。
2. **「部分更新」写法**：有的 Service 会 `new` 一个空实体，只 set 要改的那几列，再交给 MyBatis-Plus 做 updateById，靠 null 跳过其余列（如 `MallCategoryService.updateStatus`）。对这类实体去掉 status 的 setter，那条更新路径就编译不过了，要先改成条件 UPDATE。
3. **常量改名**：`${@...@CONST.value}` 是运行期求值，编译器管不到。每个推广的域都要有一个渲染 SQL 的测试，否则常量改名就是一次静默故障。
4. `${}` 里只放常量，不放入参，否则就是 SQL 注入。
5. **测试里要造「库里读出来就是某状态」的对象**时，用 MyBatis 读库的同一条反射路径写字段（`SystemMetaObject.forObject(x).setValue("status", ...)`），收成测试类里的一个私有方法，例如 `CouponWriteOffServiceTest#loadedAs`。不要为了测试给实体加回 setter。
6. **渲染测试的工具代码各模块自带一份**，不抽成共享的 test-jar：项目没有 test-jar 先例，各模块的守卫测试（如 `*BoundaryTest`）也都是自包含的。为三四十行重复给几个模块的 pom 加一层测试依赖不划算。重复多到改一处要同步改很多处时，再重新评估。

## 待定：三个域里有绕过闸门的状态写入

下面三处的状态写入走的是「new 一个实体或拿着读出来的实体，set 状态后 `updateById`」，不带旧状态条件。直接套用本约定（去掉 setter）编译不过，改成条件 UPDATE 又会改变管理端能力或并发行为，所以在拍板前没有推广：

- **任务记录**（`TaskRecordService`）：管理端「修改」把表单里的 status 原样拷进实体写回，可以把记录直接改成已完成 / 已发奖，绕过运行态；同一个类里的 `updateStatus` 却明文只许置为已过期。「禁用」也是不带条件的 `updateById`，会把已发奖的记录改成已过期。
- **发奖记录**（`PrizeDispatchHandler#doDispatch`）：拿着读出来的整行实体 set 成功 / 失败后 `updateById`，没有「仍是等待」的条件；资产引擎的异步回写（`updateStatusByExternalBizNo`）带着条件。两者的先后顺序还没核实。
- **彩票记录**（`LotteryDispatchBatchService#markDispatchFailed`）：派奖失败用 `new` 出来的实体 `updateById`，没有「中奖且待派奖」的条件。
