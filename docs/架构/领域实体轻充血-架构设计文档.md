## 要解决什么

状态流转的规则分散在三处：Service 里的 `if (status == X)`、DAO 注解里写死的状态数字、以及只写在注释里的状态机。改枚举取值时，SQL 不会报错，只会变成一条永远匹配不到行的 UPDATE。

## 不做什么

**不做标准 DDD**：不拆聚合根、仓储、领域服务、应用服务。项目的 Service 本来就是具体类，没有「一个接口配一个 Impl」，不需要为了分层再造一层类。

🔴 **不把状态迁移改成「读出实体 → 在内存里改 → 整行写回」。** 订单支付、取消、履约，提案抢执行权，预算扣减，钱包扣款，靠的都是带旧状态条件的 UPDATE，按 affected rows 判断成败。改成先读后写，并发下两个线程会同时读到同一个旧状态，结果是重复发券、超发、扣成负数。

## 规则放在哪

| 放什么 | 放在哪 | 订单试点里对应的代码 |
|---|---|---|
| 「谁能变成谁」 | 状态枚举的 `canTransitTo`，用不带 default 的 switch，新增状态时编译器会要求补上分支 | `MallOrderStatusEnum#canTransitTo` |
| 只由状态决定的业务口径 | 状态枚举上的方法 | `MallOrderStatusEnum#isSettled`（是否已扣过款） |
| 并发闸门 | DAO 的条件 UPDATE，**不变** | `MallOrderDao.markPaid` 等五个方法 |
| SQL 里的状态值 | 写成 `${@solvela.enums.XxxEnum@CONST.value}`，不写数字 | `MallOrderDao`、`MallOrderMapper.xml` |
| 落单时的初始状态与配套字段 | 实体上的方法，状态字段去掉公开 setter | `MallOrder#awaitPayment`、`MallOrder#settleOnCreate` |

实体上只放不需要依赖注入的纯行为。实体在 `solvela-model` 里，那个模块只依赖 `solvela-contract`，调不到 DAO 和 Service。这一点正好防止实体越长越胖。

## ⚠️ 推广到其它域前先看

1. **去掉 setter 之前**，先搜有没有 `SolvelaBeanUtil.copy(..., Xxx.class)` 拷贝进这个实体。它遇到没有 setter 的属性会静默跳过，结果是那个字段变成 null，编译器不会报错。订单实体没有被拷贝进去过，其它实体要逐个查。
2. **「部分更新」写法**：有的 Service 会 `new` 一个空实体，只 set 要改的那几列，再交给 MyBatis-Plus 做 updateById，靠 null 跳过其余列（如 `MallCategoryService.updateStatus`）。对这类实体去掉 status 的 setter，那条更新路径就编译不过了，要先改成条件 UPDATE。
3. **常量改名**：`${@...@CONST.value}` 是运行期求值，编译器管不到。每个推广的域都要有一个渲染 SQL 的测试，否则常量改名就是一次静默故障。
4. `${}` 里只放常量，不放入参，否则就是 SQL 注入。
5. **测试里要造「库里读出来就是某状态」的对象**时，用 MyBatis 读库的同一条反射路径写字段（`SystemMetaObject.forObject(x).setValue("status", ...)`），收成测试类里的一个私有方法，例如 `CouponWriteOffServiceTest#loadedAs`。不要为了测试给实体加回 setter。
6. **SQL 写在 DAO 注解里时**，渲染测试用 `configuration.addMapper(Dao.class)` 注册接口即可，BaseMapper 那些没有注解的方法会被跳过（见 `MemberOperationLimitStatusSqlTest`）。
7. **渲染测试的工具代码各模块自带一份**，不抽成共享的 test-jar：项目没有 test-jar 先例，各模块的守卫测试（如 `*BoundaryTest`）也都是自包含的。为三四十行重复给几个模块的 pom 加一层测试依赖不划算。重复多到改一处要同步改很多处时，再重新评估。

## 收拢时顺带改掉的绕过闸门的写法

下面前三处原来是「new 一个实体或拿着读出来的实体，set 状态后 `updateById`」，不带旧状态条件。2026-11-22 经确认后改成了条件 UPDATE：

- **任务记录**：管理端「修改」不再接收 status（后端命令与表单、管理端表单一起去掉），原来它可以把记录直接改成已完成 / 已发奖，绕过运行态。「禁用」改成 `expireByAdmin`，只认进行中；已完成、已发奖的记录影响 0 行，接口把没改动的记录列给运营。
- **发奖记录**：派发处理器的三处整行写回改成 `markDispatchSucceeded` / `markDispatchFailed`（带「仍是等待」条件）与 `markProposalAccepted`（只动提案列，不碰 status）。原来「已受理」那次整行写回会把内存里的「等待」写回去，资产引擎若已先回写了终态，会被盖掉。抢不到时记一条 warn，不算故障。
- **彩票记录**：派奖失败改成 `markDispatchFailed`，只认「中奖且待派奖」，不再覆盖已投递的记录。
- **发放提案**（2026-11-23）：资产引擎落终态原来是不带旧状态条件的 `updateStatusAndRemark`，审批走一条通用的 `updateReview(from, to, ${reviewerField})`，任何一条边都能走。改成九条具名闸门，各对应 `canTransitTo` 的一条边；审批人列写死在各自的 SQL 里，不再拼 `${}`。引擎多记一个 `claimed`：抢到执行权后失败只从执行中落（`markFailed`）；抢执行权那一步自己抛异常时只从待执行落（`markFailedUnclaimed`），不认执行中，否则会把别的线程正在下发的提案改成失败。失败回写影响 0 行时不再往发奖侧发失败，因为发奖记录是先到先写，会把随后真正的成功挡在外面；成功回写影响 0 行时照样通知，因为钱已经出去了。
- **发奖记录的审批列与提案列**（2026-11-23）：审批原来走通用的 `updateApproveStatus(from, to)`；会员服务拒收时 `markDispatchFailed` 用一个可空参数顺带改提案列，任何值都能写进去；`markProposalAccepted` 不带旧状态条件。改成具名闸门 `markApproved` / `markApprovalRejected` / `markProposalRejected`，`markProposalAccepted` 补上「仍是待提交」。审批通过后改为重读记录再派发，不改内存里那份。后台人工补发原来把表单里的审批状态原样拷进实体，「补发必须待审批」只靠前端写死；现在表单不收审批字段，由 `PrizeLogService#add` 调 `awaitApproval`。⚠️ 这里正是「推广前先看」第 1 条的坑：去掉 setter 后拷贝会静默跳过审批状态，漏了那一句，库里按列默认值落成「无需审批」。
- **实物履约单**（2026-11-23）：后台修改表单带状态下拉、回填导入的状态列，原来都是整行 `updateById`，已签收的单也能改回待发货，只有作废带条件。迁移规则经确认为：待发货 → 已发货 / 已签收 / 已取消，已发货 → 已签收 / 异常退回，其余是终态（待发货可直接签收，回填时一步到位）。修改表单与命令去掉状态，状态只经回填与作废推进。回填导入在落库前按 `canTransitTo` 校验每一行，有一行不合法整批退回；状态列为空或与当前相同只补物流信息（`updateLogistics`）；改状态走 `markShipped` / `markSigned` / `markReturned` / `discardById`，影响 0 行（校验后被别人改了）整批回滚。发货通知改为只在 `markShipped` 拿到 1 之后发，不再靠比对新旧对象。
- **彩票期号与玩法**（2026-11-23）：开奖两条闸门、上下线原来都是通用的 `(from, to)` 形参，改成具名闸门。顺带修了两处「不报错、只是不起作用」：发号的 `increaseSoldCount` 注释写着「DB 兜底不让已发数超过上限」，但 `TicketPersistService` 不看它的返回值，0 行照样落票；它也不认期号状态，「待开奖才能发号」只是发号前读一次。现在它带「仍是待开奖」条件、调用方 0 行即抛出回滚这张票，与 `startSettle` 抢同一行锁，开奖开始之后发不出号。删除期号原来是先读后删，改成 `deleteUnsold` 把「待开奖 + 零发号」压进 WHERE。彩票四条不可逆约束（游标不回滚、主密钥、`issue_no`、结构锁）都没有动：回滚的只是记录，Redis 游标照旧不退回。
- **活动**（2026-11-23）：新增、修改表单都带状态并原样拷进实体，能直接新建成上线（绕过上线前完备度检查），也能把上过线的活动改回未开始（绕过「上过线的活动不能删」，发奖流水的追溯链就断了）。表单与命令去掉状态，新建由 `ActivityConfigService` 调 `awaitLaunch`。上下线原来是 `new` 一个实体 set 状态再 `updateById`，改成 `markOnline` / `markOffline`，已是目标状态的跳过，读后被改了整批回滚。删除原来先读后删，改成 `deleteNotStarted` / `deleteNotStartedBatch` 把「未开始」压进 WHERE。迁移规则经确认：未开始 → 上线 / 下线，上线 ↔ 下线，任何状态回不到未开始（未开始直接下线保留现状）。
- **会员钱包**（2026-11-23）：没有任何代码会改钱包状态（建钱包落正常，冻结 / 解冻只能直接改库），所以没加 `canTransitTo` —— 没有 UPDATE 就不该有边。收的是「能不能动余额」：`WalletStatusEnum#allowsBalanceChange` 一处定义，`MemberWallet#checkAvailable` 与加减余额的 UPDATE 各用一次。以前 UPDATE 只有乐观锁，人工冻结不动 version，读完到写之间被冻结的钱包照样能扣（真库实测过：去掉条件后扣款影响 1 行）。将来做冻结 / 解冻功能时再按本文补状态机与闸门。
- **会员实名认证**（2026-11-23）：枚举注释写着「只有认证中能被审核，这既是幂等闸门也是并发闸门」，实现却是先读、判一下、再 `updateById`，两个运营同时点都会成功、后写的覆盖先写的。改成 `markVerified` / `markRejected` 把「仍是认证中」压进 WHERE，通过时间改用数据库的 `NOW()`。顺序执行时新旧代码表现相同，差别只在并发下，所以这一条靠 SQL 渲染测试与反证守，没有真库并发用例。目前没有代码会建核验记录（C 端提交未做）。
- **安全名单**（2026-11-23）：后台撤销原来先读后 `updateById`，注释说「连点两次不会覆盖第一次记的人」只在顺序执行时成立，改成 `SecurityListDao#revokeValid` 带「仍是有效」。自动写入 `SecurityListWriter` 的延长 / 复用原来也是读完就写，改成延长带「仍是有效的自动条目」、复用带「仍不是有效」，影响 0 行时像插入撞唯一键一样重读再决定一次，再撞就抛出 —— 不让自动条目把读完之后被人工加上的长期条目改成 24 小时。这几条是 JdbcTemplate 写的 SQL，状态值绑枚举取值，渲染测试管不到，重读的逻辑由 `SecurityListWriterTest` 用 mock 盯，SQL 本身由 app-biz 的 `SecurityEventPipelineTest` / `SecurityListAdminTest` 在真库上跑；「读完之后被人工加上」这个并发时序没有真库用例。
- **公告**（2026-11-23）：发布 / 下架随时都合法、不涉资金，没加状态机，也没去掉 setter（发布就是保存表单带状态）。只把 C 端查询里写死的 `status = 1` 换成常量，并用 `AnnouncementVisibleSqlTest` 逐条断言四条 C 端查询带齐「已发布、到了发布时间、没过期」—— 其中强制确认那条带 LEFT JOIN、是另写的一份，以前没有东西盯着它和公共片段一致。
- **任务配置**（2026-11-23）：上下线原来 `new` 一个实体 set 状态再 `updateById`，接受任意目标值（包括没有任何代码认的「生效中」）。迁移规则经确认为待生效 ↔ 已下线（下线后可再上线），生效中只留一条到已下线的边给可能的存量。改成 `markPending` / `markOffline`，目标是生效中直接拒绝。生成器留下的 `/taskConfig/add`、`/taskConfig/update` 经确认删掉：管理端没有页面在用，它们绕过向导的全部校验、能写任意状态，新增不传状态时落 DDL 默认值 0、读出来就抛异常。
- **奖池**（2026-11-28）：开关本来就是条件更新，只是通用的 `updateStatus(from, to)`，改成 `markOpen` / `markClosed`。要留意的是复制活动：以前 `SolvelaBeanUtil.copy` 把源奖池的开关原样带过去，去掉 setter 后拷贝会跳过它、按 DDL 默认值 1 落成开启 —— 被运营关掉的池复制过去又开了（真库实测过）。所以复制时按源奖池显式调 `startOpen` / `startClosed`，工作台新建也从隐式的 DDL 默认值改成显式 `startOpen`。顺带删掉了没人引用的 `PrizePoolConfigAddForm` / `PrizePoolConfigAddCommand`（新增接口早已移除，只剩带状态字段的空壳）。
- **会员账号状态**（2026-11-28）：后台冻结 / 解冻原来先读、判「不是已注销」、再 `updateById`，读完之后若被注销会被改回正常。改成 `markFrozen` / `markNormal`，已注销不是任何闸门的前置状态。注销目前没有代码会写入（C 端注销未做），所以状态机里没有到已注销的边，做注销时补上。注册仍是 `MemberRegisterService` 用 JdbcTemplate 直接落正常，状态值绑的是枚举取值。
- **文件**（2026-11-28）：业务保存时的 `confirm` 与孤儿清理 / 后台手动删除会同时碰同一个文件。以前清理是「读到临时、无引用 → 无条件标删除 → 删字节」，confirm 夹在中间提交，刚配好的图字节就没了；confirm 查的行也不排除已删的，会把字节已没的文件确认成在用。现在三处靠 `t_file` 的行锁串起来：confirm 先 `lockLiveFiles`（`FOR UPDATE`）核对都没被删再 `markConfirmed`，清理 `softDeleteOrphan`、删除 `softDeleteUnreferenced` 把「临时 / 未删 / 无引用」压进 UPDATE 的 WHERE。这一条有真库并发用例 `solvela-admin/.../file/FileConfirmPurgeRaceTest`：两个事务真的并发，并实测过把清理改回无条件后用例变红。
- **定时任务执行日志**（2026-11-28）：执行器（本次执行的主人）与僵尸扫描都会给同一条「执行中」记录落终态，以前都是无条件 `updateById`：扫描读到执行中之后执行器恰好跑完，「成功」会被盖成「中断」并多排一次重试（幂等任务多跑一遍、连续失败数 +1 触发告警）。改成 `SolvelaJobLogDao#finishRunning` 只认执行中，`SolvelaJobRepository#finishAndScheduleRetry` 返回是否生效，晚到的一方不排重试、不计失败。只收了这一处，没给八个执行状态做完整的 `canTransitTo`：抢占早就是条件更新，阻塞 / 放弃都由抢到的那个节点写。真库用例 `solvela-admin/.../module/system/job/SolvelaJobFinishRaceTest`，实测过去掉条件后变红。
- **刻意没做：MQ 消息记录**（`MqMessageLogService`）。全工程目前没有调用方（见 `docs/架构/C端网关-API契约方案.md`）。它的幂等有两处先读后写：两次并发重投一条失败消息会都被放行，落终态也是无条件写。修它要先定「停在已接收的那行是进程挂了该重来，还是还在处理中不该重来」—— 那取决于第一个真实调用方，接入时一并定。
