## 0. 为什么改

`t_security_incident` 记的是网关和会员域**检测到的情况**：蜜罐命中、关键字命中、限流判罚升档，以及标注为「低置信，只记录」的未知字段。按安全领域的通行用法（如 NIST SP 800-61 对 event 与 incident 的区分），event 是任何被观测到的情况，incident 是已确认造成影响、需要响应处置的事。这张表里绝大多数行都够不上 incident。表注释写的中文本来就是「安全事件流水」，叫 incident 把每一行都说重了。

## 1. 改了哪些名字

| 位置 | 改名前 | 改名后 | 过渡期怎么兼容 |
|---|---|---|---|
| 表 | `t_security_incident` | `t_security_event` | 同名兼容视图（§3） |
| 列 | `t_security_incident.incident_type` | `t_security_event.event_type` | 视图里映射回旧列名 |
| 索引 | `idx_sec_inc_{ip,device,member,type}` | `idx_sec_evt_{ip,device,member,type}` | 只改元数据，无需兼容 |
| 列 | `t_security_list.last_incident_id` | `last_event_id` | 两列并存，新代码双写 |
| Redis 队列 | `sec:incident`、`sec:incident:processing` | `sec:event`、`sec:event:processing` | 落库任务新旧两对一起清 |
| 消息字段（JSON） | `incidentType` | `eventType` | `@JsonAlias("incidentType")` |
| 定时任务 `handler_name` | `securityIncidentDrain` | `securityEventDrain` | 新旧两个名字都注册处理器 |
| 管理端接口 | `POST /security/incident/queryPage`，入参 / 出参字段 `incidentType` | `POST /security/event/queryPage`，字段 `eventType` | **不兼容**：管理端前后端同一次发布（§4.3） |
| 菜单 `t_menu` | 路径 `/security/incident`，组件 `security-incident-list.vue` | `/security/event`，`security-event-list.vue` | 旧文件名保留成转发壳 |
| Java 类 | `SecurityIncidentEvent` / `…Queue` / `…Store` / `…DrainJob` / `…AdminService` / `…Controller`、`IncidentPublisher` | `SecurityEvent` / `SecurityEventQueue` / `…Store` / `…DrainJob` / `…AdminService` / `…Controller`、`SecurityEventPublisher` | 编译期全量替换，无需兼容 |
| 管理端常量 | `SECURITY_INCIDENT_*`、`queryIncidentPage` | `SECURITY_EVENT_*`、`queryEventPage` | 同上 |

**没有改的**：任务编码 `job_code = 'JOBSECINCD'`。它是那一行任务的稳定标识（唯一键 `uk_job_code`），可能已被告警规则、日志检索引用；它不出现在任何界面上，改它的收益抵不上找全引用方的成本。

## 2. 🔴 三个会让改名静默出事的地方

这三处是设计分步发布的原因，每一处都有测试盯着。

### 2.1 定时任务：标了「处理器缺失」就永远不再调度

调度器按 `t_solvela_job.handler_name` 找处理器，找不到就把那一行标成 `handler_missing_flag = 1`；而扫描只挑 `handler_missing_flag = 0` 的行 —— **标上之后，处理器后来出现了也不会自己恢复**（`SolvelaJobScanner#markHandlerMissing`，`SolvelaJobMapper.xml` 里两处 `AND handler_missing_flag = 0`）。

所以无论哪个时间点，库里的名字和正在跑的代码对不上，安全事件落库任务就会永久停掉。停掉的表现：处罚照常生效（处罚在 Redis 里），但不再自动拉黑 / 拉灰，事件也不再落库，后台安全事件页一片空白，没有任何报错。

**做法**：新版代码同时注册新旧两个名字（`LegacySecurityIncidentDrainJob` 原样转给 `SecurityEventDrainJob`），库里的名字等新版上线之后再改（§4 第 ③ 步）。
**测试**：`solvela-admin` 的 `SecurityEventDrainHandlerNameTest` 用真实 Spring 上下文断言两个名字都已注册。

### 2.2 线上消息：旧格式会被当成坏事件丢掉

网关（app）与后台（admin）分开发版。发版间隙里旧版网关还在往 `sec:incident` 写、字段名还是 `incidentType`。

`eventType` 是 `int`。消费方不认 `incidentType` 时，Jackson 3 默认开着 `FAIL_ON_NULL_FOR_PRIMITIVES`，解析直接抛异常，落库任务把它当坏事件**丢弃**，只留一行 ERROR —— 发版间隙里的事件一条条丢掉。（实测过：去掉别名后，兼容测试就是这样红的。）

**做法**：`SecurityEvent.eventType` 上加 `@JsonAlias("incidentType")`；落库任务按顺序清空新旧两对队列，共用同一份条数与时间预算（`SecurityEventDrainJob.Lane`）。新版生产方只写新键、新字段名。
**测试**：`solvela-member` 的 `SecurityEventWireCompatTest`（旧格式能读、新格式不再出现旧字段名）；`solvela-app-biz` 的 `SecurityEventPipelineTest#legacyQueueStillDrained`（旧队列里的旧格式事件真实落库，四个键全部清空）。

### 2.3 表改名的那一刻：旧版代码还在读写旧表名

表改名是一个瞬间完成的切换，而新旧代码不可能在同一瞬间切换。

**做法**：改名的同时建一个同名兼容视图 `t_security_incident`，每一列都直接引用新表的列（`event_type AS incident_type`），所以它**可插入**。旧版落库任务的 INSERT、旧版安全事件页的 SELECT 都能原样穿过去。
**实测**（MySQL 8.4，`podman` 起的临时库）：用从 `HEAD` 取出的旧版代码原样的 SQL，经 JDBC 执行 —— INSERT 穿过视图成功，`getGeneratedKeys()` 拿回了自增 id（旧版写名单证据要用它），按 `incident_type` 过滤的查询正常，新表里用新列名能读到同一行；旧版只写 `last_incident_id` 的名单 INSERT 在新表结构下也能执行。

## 3. 数据库脚本

都在 `数据库SQL脚本/mysql/`，都可重复执行（每一步先查 `information_schema`），都在临时库上实测过两遍。

| 脚本 | 何时执行 | 做什么 |
|---|---|---|
| `生产升级-20261120-安全事件改名-①发版前.sql` | **发版前** | 表 / 列 / 索引改名；建兼容视图；`t_security_list` 加 `last_event_id` 并回填；分区维护任务的参数里手工写过旧表名的换成新表名 |
| `生产升级-20261120-安全事件改名-②发版后.sql` | **新版后台与管理端都上线之后** | 落库任务 `handler_name` 改新名并清 `handler_missing_flag`；菜单改路径；两行描述里的旧键名、旧表名一并换掉 |

**基线**：`schema-baseline.sql`、`data-baseline.sql` 已用 `DumpSchema` / `DumpSeedData` 从「① + ② 执行后」的库重新导出，`VerifyFreshInstall` 结果 PASS（见 `数据库SQL脚本/mysql/README.md`）。新装环境直接得到新表名、新菜单、新任务名，**不需要**跑这三个脚本，也不会有兼容视图（`DumpSchema` 只导真表）。

> 重新导出时带出了三处与本次无关的订正：10-19 删代码生成模块时手改基线删了行、没改计数（`t_menu` 319 → 318、`t_role_menu` 97 → 96、「系统底座」21 → 20 张）。这正是基线只许工具导出的原因。

## 4. 发布顺序（扩展阶段）

```
① 跑「①发版前」脚本
② 发新版：admin、app（网关）、app-biz 三个后端 + 管理端前端（顺序不限，但管理端前后端要同一次）
③ 跑「②发版后」脚本
```

### 4.1 每个时间点都安全吗

| 时间点 | 库 | 在跑的代码 | 落库任务 | 事件会不会丢 |
|---|---|---|---|---|
| ① 之后、发版前 | 新表 + 兼容视图；任务名仍是旧名 | 全是旧版 | 旧版认旧名，照跑；写兼容视图 | 不丢 |
| 发版过程中 | 同上 | 新旧混跑 | 新版两个名字都认 | 旧版网关写旧队列、新版写新队列，新版落库任务两边都清；旧版落库任务只清旧队列，新队列里的等新版来清 |
| ② 之后 | 任务名改成新名 | 全是新版 | 新版认新名 | 不丢 |

### 4.2 ① 与发版之间不要隔太久

旧版后台的分区维护任务默认清单里还是 `t_security_incident`（代码里的常量）。① 之后它变成了视图，对视图做分区维护会报错。分区已预建到 2027-01 再加 `pmax`，报错不会造成数据问题，但会触发告警。这个任务每天 03:50 跑一次 —— ① 和发版放在同一个维护窗口里就碰不到。

### 4.3 管理端接口没有做兼容

`/security/incident/queryPage` 直接改成了 `/security/event/queryPage`，字段 `incidentType` 改成 `eventType`。理由：只有一个调用方（管理端前端），而管理端入口 HTML 不缓存、换版有分块自愈，前后端同一次发布即可，没必要为它留兼容代码。
**代价**：发版那一刻还开着「安全事件」页的人，再点查询会报错或类型列为空，刷新页面即恢复。

## 5. 收口阶段（以后单独做）

### 5.1 前置条件（全部满足才做）

1. 所有环境都执行过「②发版后」脚本；
2. 没有任何旧版网关 / 后台 / 会员服务在跑；
3. 生产 Redis 里 `LLEN sec:incident` 与 `LLEN sec:incident:processing` 都为 0。

### 5.2 要删的 TEMP 代码

全仓 `grep -rn 'TEMP(安全事件改名-收口)'` 列出全部位置，收口后这条 grep 必须为空。
后端的标记数由 `solvela-api/solvela-admin/src/test/java/solvela/admin/arch/TempMarkerRatchetTest.java` 盯着（登记的是 10 处），
删掉标记时同一次提交把那里的登记行删掉，否则它会红。截至扩展阶段完成时是这些：

| 位置 | 删什么 |
|---|---|
| `solvela-contract/.../security/SecurityKeys.java` | `LEGACY_INCIDENT_QUEUE`、`LEGACY_INCIDENT_PROCESSING` |
| `solvela-contract/.../security/SecurityEvent.java` | `eventType` 上的 `@JsonAlias("incidentType")` |
| `solvela-member/.../risk/security/SecurityEventDrainJob.java` | 构造器里的第二对 `Lane`（`Lane` 机制本身可以留） |
| `solvela-member/.../risk/security/LegacySecurityIncidentDrainJob.java` | 整个类 |
| `solvela-member/.../risk/security/SecurityListWriter.java` | 三处 SQL 里的 `last_incident_id` |
| `solvela-model/.../member/SecurityList.java` | `lastIncidentId` 字段 |
| `solvela-admin-web/.../security/security-incident-list.vue` | 整个文件 |
| `solvela-admin/.../job/SecurityEventDrainHandlerNameTest.java` | 旧名那条断言反过来（必须不存在），或整个测试删掉 |
| `solvela-app-biz/.../risk/security/SecurityEventPipelineTest.java` | `legacyQueueStillDrained` 整段、`last_incident_id` 那条断言 |

两个升级脚本里也出现了这个标记：①里标的是兼容视图（由③删除），③里是前置条件的说明。它们是历史脚本，跑完即留档，不用改。

### 5.3 顺序

🔴 **代码先删双写、再删列**：③脚本删掉 `last_incident_id` 列时，如果还有代码在写这一列，名单写入会全部失败。所以删 TEMP 代码的那个版本先上线，再跑③。③自己会核对②是否执行过，但核对不了「代码是否已删双写」—— 这一条靠发布顺序保证。

收口完成后，重新导出一次基线（`last_incident_id` 列会从基线里消失）。
