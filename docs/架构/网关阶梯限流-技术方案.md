# 网关阶梯限流 —— 技术方案

> 撰写 2026-10-14 · 类型：**方案（待评审，代码未动）**
> 前提：生产还没上线，只有本地 docker —— 不做新旧并存，直接按目标形态建。
> 姊妹篇：`docs/业务/会员/登录风控-技术方案.md`（边界见 §1）
>
> 这份文档回答：**对登录、注册、发码、兑换这些接口，按 IP 与账号两个维度，怎么数、超了怎么罚、罚了怎么升级；
> 蜜罐与注入探测命中后怎么处置，以及怎么不误伤共用出口的真人。**

---

## 0. 一句话

**每个接口归一个场景；每个场景按 IP、账号、设备（匿名场景再加 IP 段）各数四个窗口（突发 / 3 分钟 / 5 分钟 / 10 分钟）；
任何一个窗口超了记一次违规，违规次数决定罚多久（60 秒 → 5 分钟 → 30 分钟 → 1 小时 → 2 小时 → 8 小时）；
踩了蜜罐或命中关键字，IP 与设备直接封 24 小时，到期再背 30 天灰名单；被封的请求在网关第一个安全过滤器就结束，进不了业务层。**

## 1. 和登录风控的边界

两份方案都会「拦登录」，必须分清谁管什么，否则同一件事有两个阈值、两套文案：

| | 网关限流（本文） | 登录风控 |
|---|---|---|
| 数的是什么 | **请求次数**：不管成功失败、不管账号存不存在 | **请求的含义**：失败了几次、试了几个不存在的号、设备认不认识、网络熟不熟 |
| 在哪 | 网关 `solvela-app`，请求进业务之前 | 会员域 `MemberAuthService` 内部 |
| 覆盖面 | 所有接口 | 只有登录（之后扩到注册、找回密码等） |
| 回答的问题 | 「这个量正不正常」 | 「这个人是不是本人」 |

**判据一句话：只看「来了多少次」的归网关；要看「结果」或「是谁」的归风控；「来了就该挡」的归网关安全闸。**

### 1.1 与已落地风控的合并清单（2026-10-17）

登录风控已经全部落地（P0–P3 均已提交），覆盖登录、注册、重置密码、换绑、资产出口五条链路。
对着代码核对，有 **16 条规则**（外加滑块出图的一处限频）与本方案在做同一件事 —— 同一个 IP 被两套计数器、两种窗口、两种处罚语义各数一遍，
出了问题要查两处，调阈值要改两处，而且两处迟早不一致。生产没上线，**按「一件事只有一个地方管」直接合并**：

| 风控里的规则 | 它在做什么 | 去向 | 理由 |
|---|---|---|---|
| `IP_ATTEMPT_LIMIT` | 单 IP 登录请求数（1h） | → 网关 `LOGIN` 场景 IP 维度 | 纯计次 |
| `DEVICE_LOGIN_LIMIT` | 单设备登录次数（1d） | → 网关 `LOGIN` 场景设备维度 | 纯计次 |
| `REG_IP_LIMIT`、`REG_DEVICE_LIMIT` | 注册提交次数 | → 网关 `REGISTER` 场景 | 纯计次 |
| `RESET_IP_LIMIT`、`RESET_DEVICE_LIMIT` | 重置密码提交次数 | → 网关 `PASSWORD_RESET` 场景 | 纯计次 |
| `IP_BLACKLIST`、`REG_IP_BLACKLIST`、`RESET_IP_BLACKLIST`、`BIND_IP_BLACKLIST`、`ASSET_IP_BLACKLIST` | 五条链路各查一遍 IP 黑名单 | → 网关安全闸 ①（§5.5），**删掉这五条** | 黑名单 IP 在网关第一道过滤器就被挡，根本到不了这五条链路；而且安全闸挡的是**所有**接口，不只这五条 |
| `DEVICE_BANNED` 及 `REG_` / `RESET_` / `BIND_` / `ASSET_` 四条同名规则 | 五条链路各查一遍设备封禁 | → 网关安全闸 ①，**删掉这五条** | 同上。今天被封的设备只在这五条链路上被拦，照样能抽奖、签到、浏览 —— 挪到安全闸后，封禁才真的是「封禁」 |
| `CaptchaService` 里同 IP 每分钟出图 ≤ 20 | 纯计次 | → 网关 `CAPTCHA` 场景 | 纯计次 |

**留在风控的**（都依赖结果或身份，网关做不了）：`IP_FAIL_LIMIT`、`IP_UNKNOWN_LIMIT`、`IP_ACCOUNT_FANOUT`（数的是不同身份）、
`DEVICE_FAIL_LIMIT`、各链路的 `*_DEVICE_FANOUT`、`PWD_COOLDOWN`、两个矩阵、`GLOBAL_CAPTCHA`、打分规则、`DEVICE_OBSERVE`。
`IP_GREYLIST` 留在风控（灰名单的「加分」是风控语义），但名单数据与网关共用一份。

**长窗口怎么办**：迁过来的几条原来是 1 小时、1 天的窗口，抓的是「每 10 分钟都卡在阈值下、慢慢滴」的脚本。
本方案四个窗口最长 10 分钟，所以每个场景**可选再配一个长窗口**（1h 或 1d），只有迁过来的那几个场景默认开（阈值沿用风控里的现值）。

**同一个滑动窗口实现**：风控已经有 `RedisService.slidingWindowCount`（分桶计数，一次往返、原子）。网关**不再写第二份**：
把那段 Lua 挪到网关与 app-biz 都依赖、且不带 Redisson 的模块（网关刻意不依赖 `solvela-base-redis`，见 `solvela-app/pom.xml` 的注释），两边调同一份。

**同一个对外回答**：两边被挡都是 `429 OPERATION_LIMITED` + `Retry-After` + `details.retryAfterSeconds`（登录风控 §6.4 的约定），前端只有一套处理。

**同一个后台入口**：后台菜单合成一个「安全中心」，下面是 风控规则 / 限流规则 / 蜜罐与关键字 / 名单 / 安全事件 / 风控流水 / 看板。
规则仍是两张表（形状不同：风控规则是阶段 + 类型 + 分值 + 参数，限流规则是场景 × 维度 × 窗口阈值），但运营只认一个入口。

**名单是两边共用的**：表结构以本文 §6.3 为准，**改名为 `t_security_list`**。各名单在登录风控里豁免什么，仍以登录风控方案 §5.2 为准。

**发码的业务配额也不动**：同一目标 60 秒冷却、每天 10 条，同一 IP 每天 20 封 / 5 条（`VerificationCodeProperties`）。
那是「成本配额」（短信花钱、邮件影响域名信誉），与「请求频率」是两件事 —— 本方案在它前面再加一层频率控制。

## 2. 模型

### 2.1 场景

每个接口归一个场景，用注解标在 Controller 方法上：`@RateLimit(Scene.REDEEM)`。没标注的写接口落 `DEFAULT_WRITE`，读接口落 `DEFAULT_READ`。

| 场景 | 接口 |
|---|---|
| `LOGIN` | `/auth/login`、`/auth/login/challenge/code`、`/auth/login/challenge/verify` |
| `REGISTER` | `/auth/register` |
| `CODE_SEND` | `/auth/email/code`、`/auth/sms/code`、`/auth/step-up/code` |
| `PASSWORD_RESET` | `/auth/password/reset` |
| `REDEEM` | `/mall/redeem`、`/mall/order/{orderNo}/pay`、`/recharge/order`、`/recharge/order/{orderNo}/pay`、`/lottery/{activityCode}/obtain`、`/activity/{activityCode}/draw` |
| `SIGN` | `/task/sign` |
| `CAPTCHA` | `/captcha`、`/captcha/verify`（出图本身有同 IP 每分钟 20 张，本场景管验证频率） |
| `DEFAULT_WRITE` | 其余写接口 |
| `DEFAULT_READ` | 其余读接口（阈值很宽，只挡爬虫级别的量） |

**注解而不是按 URL 前缀匹配**：URL 会改，注解跟着方法走；新加一个兑换接口忘了标，它落进 `DEFAULT_WRITE`，
而不是落进「没有任何限流」。启动时打印一份「场景 → 接口」清单，评审时一眼能看出哪个接口归错了。

### 2.2 维度

| 维度 | 键 | 说明 |
|---|---|---|
| **IP** | 客户端 IP；**IPv6 取 /64** | 永远有，但最不准（§2.3）。取值走现有的 `ClientIp`（nginx 已把真实 IP 归一化） |
| **账号** | 登录后：会员号。匿名接口：请求里的目标身份（登录的邮箱 / 手机号、收码的邮箱 / 手机号）的 HMAC | 匿名接口上的账号维度有特殊处理（§2.4） |
| **设备**（建议加） | 验过钢印的设备号 | 网关每个请求本来就验设备令牌（`DeviceFilter`，零 IO），多一个维度没有成本；它恰好补 IP 在共用出口下的短板 |
| **IP 段** | IPv4 取 /24，IPv6 取 /48 | 只用在四个匿名场景，阈值更宽、处罚更轻（§2.5） |

**账号键不放明文，也不放裸 SHA-256**：手机号的取值空间很小，裸哈希能被穷举还原，等于把手机号明文写进了 Redis。
用网关自己的 HMAC 密钥（配置项，不入库），规范化规则与会员域 `MemberEmailUtil.normalize` / `MemberPhoneUtil.normalize` 一致 ——
否则 `A@x.com` 和 `a@x.com` 会被数成两个账号。

匿名接口的账号从请求体里取：`@RateLimit(scene = LOGIN, account = "#req.identity")`，在参数绑定之后执行（切面），
不在过滤器里自己读请求体 —— 那会把请求体读空，后面的 Controller 拿不到。

### 2.3 🔴 IP 维度最容易误伤

国内移动网络大量用户共用一个出口 IP（运营商级 NAT），校园网、公司出口也一样。给这样一个 IP 判 8 小时，误伤的是一大片真人。所以：

1. **IP 阈值比账号、设备宽一个数量级**：它挡的是脚本的量级，不是一个人的手速。
2. **老设备豁免 IP 维度的处罚**：设备令牌签发早于 7 天的请求，不受 IP 维度的判罚约束（账号、设备维度照常）。
   签发时间就在令牌里（`dv_1.{设备号|端|签发时间}.{钢印}`），验签时读出来，**零 IO**。
   同一个出口后面的真人基本都带着自己的老设备；攻击者要提前养令牌，而领令牌同 IP 一天只给 10 块。
3. **IP 白名单跳过 IP 维度**。白名单与登录风控共用一份（`t_security_list` 的 IP 白名单），不维护两份。

### 2.4 🔴 匿名接口上的账号维度：会被拿来锁别人

登录、注册、发码时还没有登录态，「账号」是请求里填的**目标**。按目标判 8 小时，意味着
**任何人知道你的邮箱，往登录接口打一阵，你就 8 小时登不上** —— 限流本身成了攻击手段。

处理：

| | 登录后接口 | 匿名接口 |
|---|---|---|
| 账号维度计数与拒绝 | ✅ | ✅ |
| 阶梯处罚 | 完整六档（到 8h） | **封顶 30 分钟** |
| 老设备豁免 | 不需要（会员号就是他自己） | ✅ 设备令牌签发早于 7 天的请求，不受这个目标的账号维度处罚约束 |

主人通常在自己的老设备上登录，攻击者用的是新设备 —— 处罚落在攻击者身上，主人照常能用。
目标维度上真正的长时间保护由业务域里专门防过「恶意锁人」的机制负责：登录的密码阶梯冷却（按可信设备分桶、只锁密码通道）、发码的冷却与日限。

### 2.5 IP 段：抓同网段轮换，但更宽、更轻

**它抓的是什么**：代理池、云主机分到的 IP 往往成段出现。脚本在同一个 /24 里轮换 IP，每个 IP 都不超限 ——
按单 IP 数，这类流量一条都数不到。

**它的代价**：一个 /24 有 256 个地址，背后的真人比单个 IP 还多（运营商给手机网络的地址池就是按段分的）。
所以 IP 段是**误伤面最大**的维度，用法收得最紧：

| 项 | 规定 |
|---|---|
| 网段 | IPv4 `/24`；IPv6 `/48`（IPv6 的「单 IP」已经是 /64，再上一级就是 /48） |
| 场景 | **只用在** `LOGIN`、`REGISTER`、`CODE_SEND`、`PASSWORD_RESET` 四个匿名场景。登录后的场景有会员号，用不着它 |
| 阈值 | 约为同场景 IP 维度的 **5 倍**（§3.1） |
| 处罚 | **封顶 30 分钟**，不走完整的六档；老设备豁免与 IP 维度相同（§2.3）；IP 白名单里的地址不计入它所在网段的计数 |
| 自动名单 | **同段连坐只拉灰，不拉黑**：24 小时内同一个 /24 里有 ≥ 3 个 IP 被自动拉黑 → 整段（CIDR）灰 7 天（§5.5） |

最后一条是它最值钱的地方：一个网段里已经有几个 IP 被确认在干坏事，同段的其它 IP 多半也是 ——
但只是「多半」，所以只让它们多过一道滑块 / 验证码（灰名单的效果），而不是直接挡在门外。

## 3. 窗口

| 窗口 | 算法 | 超了 |
|---|---|---|
| **突发**（10 秒） | 令牌桶：容量 N，10 秒补满 | 拒绝；**同一个键 10 分钟内第二次超突发才记违规** |
| **3 分钟** | 滑动窗口（分钟粒度） | 拒绝 + 记一次违规 |
| **5 分钟** | 同上 | 同上 |
| **10 分钟** | 同上 | 同上 |

- **突发第一次只拒不罚**：双击提交、弱网连点、网络抖动后客户端自动重试，真人都会撞上它。第一次就判 60 秒，用户感受到的是「点了两下就被封了」。
- **被拒的请求照样计入时间窗口**：持续猛打的脚本很快会在 3 分钟窗口上记到违规。
- **阈值是亚线性的**（3 分钟 30、10 分钟 60，不是 100）：短窗口抓打得快的，长窗口抓刻意放慢、每个短窗口都卡在阈值下的。
  三个阈值如果按时间等比，长窗口永远不会先触发，就是白算。

### 3.1 首批阈值

都是拍的，按「真人几乎不可能撞到、脚本几分钟就撞到」给，上线后按数据调（§8）。设备维度与账号维度同一档。

| 场景 | 维度 | 突发 / 10s | 3 分钟 | 5 分钟 | 10 分钟 |
|---|---|---|---|---|---|
| `LOGIN` | 账号 / 设备 | 5 | 10 | 15 | 20 |
| | IP | 10 | 30 | 45 | 60 |
| | IP 段 | 50 | 150 | 225 | 300 |
| `REGISTER` | 账号 / 设备 | 2 | 3 | 4 | 5 |
| | IP | 3 | 6 | 8 | 10 |
| | IP 段 | 15 | 30 | 40 | 50 |
| `CODE_SEND` | 账号 / 设备 | 2 | 4 | 5 | 6 |
| | IP | 3 | 8 | 12 | 15 |
| | IP 段 | 15 | 40 | 60 | 75 |
| `PASSWORD_RESET` | 账号 / 设备 | 3 | 8 | 10 | 12 |
| | IP | 5 | 15 | 20 | 30 |
| | IP 段 | 25 | 75 | 100 | 150 |
| `REDEEM` | 账号 | 3 | 10 | 15 | 20 |
| | IP | 10 | 40 | 60 | 100 |
| `SIGN` | 账号 | 3 | 5 | 6 | 8 |
| | IP | 20 | 100 | 150 | 200 |
| `CAPTCHA` | 设备 | 5 | 20 | 30 | 40 |
| | IP | 10 | 40 | 60 | 80 |
| `DEFAULT_WRITE` | 账号 / 设备 | 10 | 100 | 150 | 200 |
| | IP | 30 | 500 | 750 | 1000 |
| `DEFAULT_READ` | 账号 / 设备 | 20 | 300 | 450 | 600 |
| | IP | 50 | 1000 | 1500 | 2000 |

### 3.2 实现：一个键、一次往返

每个（场景, 维度, 值）一个 Redis 哈希，字段是令牌桶状态加最近 10 个分钟桶，TTL 11 分钟：

```
rl:c:{场景}:{维度}:{值}
  b:tokens, b:ts        令牌桶
  m:{分钟序号} → 计数    最近 10 个分钟桶
```

一段 Lua 原子完成：查处罚 → 取令牌 → 当前分钟 +1 → 汇总 3 / 5 / 10 分钟 → 判断 → 必要时记违规并写处罚。
按分钟桶近似滑动窗口，误差不到一分钟，比用有序集合记每一次请求省得多。
一个请求两到三个维度就是两到三个键；Redis 单节点时合成一次 `EVALSHA`，将来上集群给同一请求的键加相同的哈希标签。

## 4. 阶梯处罚

```
违规第 1 次  60 秒
     第 2 次  5 分钟
     第 3 次  30 分钟
     第 4 次  1 小时
     第 5 次  2 小时
     第 6 次及以后  8 小时
24 小时内没有新的违规 → 次数清零
```

- **处罚的范围是（场景, 维度, 值）**：在 `REDEEM` 上被罚的会员，照样能浏览、签到。一个场景出问题不该连坐整个账号。
- **两个维度封顶 30 分钟**：匿名场景的账号维度（§2.4）与 IP 段维度（§2.5）。它们背后可能是无辜的人，六档走满的 8 小时不该落在它们头上。
- **处罚期间直接拒绝，不计数、不延长**：被罚的人一直点只是在收 429；处罚结束后再犯，才升下一档。
- 状态存在 Redis：`rl:p:{场景}:{维度}:{值}` → `{level, until}`，TTL = max(处罚剩余, 24h)。丢了的后果是「少罚了一次」，不值一张表。
- **对外回答**：`429 OPERATION_LIMITED`，带 `Retry-After` 头与 `details.retryAfterSeconds`（与登录风控 §6.4 同一个约定）。
  前端只做倒计时提示，不给其它按钮。文案不说「你被罚到第几档」「触发了哪个窗口」。

## 5. 蜜罐、关键字与安全闸

### 5.1 两种蜜罐

| | 是什么 | 谁会碰 | 在哪判 |
|---|---|---|---|
| **蜜罐接口** | 真实客户端**永远不会调用**的路径（后台配置） | 扫接口的脚本 | 网关过滤器（这些路径没有 Controller，拦截器接不到） |
| **蜜罐账号** | 库里真实存在、但从不对外使用的几个账号 | 拿到了我们用户名单的人 | 会员域（登录风控里加一条强规则 `CANARY_ACCOUNT`） |

**蜜罐账号是唯一能发现「我们的用户库泄露了」的手段**：这些账号的邮箱从没出现在任何地方，有人拿它来登录，
说明他手里有我们的用户名单。命中时除了处罚，还要**立即告警**。它对外的回答与普通的「账号或密码错误」逐字相同。
统计口径里要排除这几个账号（建号时用单独的注册来源值）。

### 5.2 处罚

命中 → **IP 24 小时、设备 24 小时**，作用于**所有场景**（不是某一个场景），不走阶梯、不清零到阶梯里。
IP 部分同样**豁免老设备**（§2.3）：共用出口后面的真人不会因为别人碰了蜜罐而被封一天。

蜜罐接口的响应与「访问一个不存在的路径」**完全一样**（同样的 404 与响应体），让对方分不出自己碰了什么。

### 5.3 🔴 三道保险：防止蜜罐被拿来误伤

1. **不认跨站发起的请求**：别的网站可以让访客的浏览器去请求我们的任意地址（一个图片标签就够），
   如果这也算命中，攻击者就能让任何访问过他网页的人被封 24 小时。所以只有 `Sec-Fetch-Site` 为 `same-origin` / `none`，
   或者没有这个头也没有外站 `Origin` 的请求（非浏览器）才算命中；跨站来的只记日志。
2. **集中命中自动熔断**：10 分钟内超过 N 个不同 IP 命中蜜罐，更可能是**我们自己的前端出了 bug**（或者某个蜜罐路径被公开链接了），
   而不是同时来了 N 个攻击者。此时停止处罚、只记录，并告警。
3. **蜜罐路径不能与真实路由重叠**：网关启动时检查，配置里的任何一个蜜罐路径能匹配到真实 Controller → 启动失败。
   否则一次路由调整就会把真实用户全部送进 24 小时。

### 5.4 关键字拦截

**目的是省成本**：参数里带着 `sleep(`、`or(` 这类片段的请求，一看就不是正常用户。在网关最前面挡掉，
它就不会走到会话查询、限流计数、app-biz、数据库、Argon2 —— 越往后，每个请求越贵。

> 它**不是**防注入的主防线。全仓 MyBatis mapper 只有一处 `${}`（`ProposalRecordMapper.xml`，值经枚举收敛、不接外部输入），
> 其余全是参数化的 `#{}` —— 注入在代码层本来就没有口子。关键字拦截挡的是「来探测的人」，让他尽早停在门外。

**命中 → IP 与设备封 24 小时**（与蜜罐同一档，作用于所有场景，IP 部分豁免老设备），记一条事件。
对外回答与参数校验失败**逐字相同**（`400 INVALID_ARGUMENT`），不告诉对方「你被拦了」；之后的请求才开始收到 429。

#### 规则怎么写

- **带词边界的正则，不用裸子串。** 裸子串 `or(` 会命中 `color(`、`floor(`、`error(`、`for(` ——
  搜「Floor(落地灯)」、昵称「Doctor(医生)」的人会被封一天。写成 `\bor\s*\(` 这种形式。
- **每条规则配一组「正常输入」反例**，进单测：反例里任何一条命中，规则不允许保存 / 上线。
  反例至少覆盖：中英文商品名、带括号的昵称、地址（「XX路(东门)」）、常见符号密码长什么样（只用于测规则，不落任何地方）。
- 先 URL 解码一次再匹配；不追求覆盖所有编码变形 —— 绕过编码的人会撞上限流、蜜罐与风控，这一层只负责把**低成本的探测**挡在最前面。
- 规则存在 `t_config`（随 §6 的快照下发），可以在后台单独停用某一条。

#### 扫哪里、不扫哪里

| 位置 | 扫不扫 |
|---|---|
| URL 路径 | ✅ |
| 查询串 | ✅ |
| JSON 请求体（≤ 8KB） | ✅ 解析后按字段扫值 |
| 超过 8KB 的请求体、文件上传、表单 | ❌ 不扫（成本不成比例） |
| 🔴 **密码与验证码字段**：`password`、`credential`、`currentPassword`、`newPassword`、`code` 以及所有同类字段 | ❌ **不参与匹配、绝不落库** |
| 请求头 | 只扫 `User-Agent`，只认已知扫描器的标识 |

🔴 **密码字段为什么必须排除**：密码里带括号很常见（`Color(2024)!`）。被关键字命中的话，
这个人**用正确的密码登录，换来的是被封 24 小时** —— 而且他永远想不明白为什么。

#### 🔴 跨站发起的请求不处罚

与蜜罐同一个理由（§5.3 第 1 条）：别的网站可以用一个图片标签让访客浏览器请求 `/api/xxx?id=1 or(1)`，
这个请求从**访客自己的 IP** 发出。只认 `Sec-Fetch-Site` 为 `same-origin` / `none`、或非浏览器的请求；
跨站的照样**拒绝这一次**（不让它进业务），但不封、只记录。JSON 请求体从别的网站发不过来（要 CORS 预检），所以这条只影响路径与查询串。

**熔断同样适用**（§5.3 第 2 条）：10 分钟内大量不同 IP 同时命中同一条关键字规则，更可能是规则写错了或前端在发这类字符，停止处罚并告警。

### 5.5 安全闸：越便宜的检查越往前

```
请求 ─► TraceFilter
     ─► DeviceFilter          验设备令牌（只做 HMAC，零 IO），读出签发时间
     ─► SecurityGateFilter
          ① 查封禁            IP / IP 段黑名单、设备封禁、各类处罚键（先查进程内缓存，再查 Redis） ← 被封的请求在这里结束
          ② 蜜罐路径          纯内存比对                                          ← 命中：封 24h、记录
          ③ 关键字            纯 CPU                                              ← 命中：封 24h、记录
     ─► AuthenticationFilter  会话查询（Redis）
     ─► CrossOriginGuard / 设备要求 / 二次验证 ……（现有拦截器）
     ─► 限流切面               场景 × 维度计数（Redis Lua）
     ─► Controller ─► app-biz
```

- **被封的请求在第 ① 步结束**：不验会话、不计限流、不调下游。对方在封禁期间一直刷，每次只花一次进程内缓存查找。
- **第 ① 步查四样东西**，取代风控里五条链路各自重复的黑名单与设备封禁规则（§1.1）：
  - **IP / IP 段黑名单**：来自名单快照（§6），内存里匹配 CIDR。**人工黑名单不豁免老设备** —— 那是有人看过之后签的字；
  - **自动处罚**（蜜罐、关键字、限流阶梯）：Redis 处罚键。IP 部分豁免老设备（§2.3）；
  - **设备封禁**：`t_device.status = 封禁` 的设备号，由会员域在处置时**同步镜像**到 Redis 集合 `sec:dev:banned`（解封时移除），
    网关 `SISMEMBER` + 进程内缓存。镜像丢了由会员域的定时任务按库全量重建 —— 库是真相源；
  - **身份黑名单**不在这里查：网关不知道请求里的身份是不是登录身份，它留在风控（登录、注册、重置密码时按身份摘要判）。
- **进程内缓存**：最近被判定为「在处罚中」的键缓存几秒（处罚刚解除时最多晚几秒放行，可以接受）。
  被封的 IP 每秒打几千次，也不会每次都去 Redis。
- `DeviceFilter` 排在安全闸前面：要先知道设备令牌有多老，才能判断 IP 处罚的老设备豁免。它本身零 IO。
- 关键字排在会话查询之前：命中的请求连那一次 Redis 都省了。
- **再往前一步是边缘**：把黑名单 IP 通过 Cloudflare 的 IP Access Rules 接口推到边缘，请求连 nginx 都到不了。上线后真遇到大流量再做。

#### 写入时机：只在「状态变化」时写

被限流的、碰蜜罐的、命中关键字的，都进 §6.3 / §6.4 的名单与事件流水。但**写的频率决定这件事是省成本还是添成本**：

| 时刻 | 写不写 |
|---|---|
| 第一次命中蜜罐 / 关键字 → 开始封禁 | ✅ 一条事件 + 名单拉黑 |
| 限流判罚、处罚升档 | ✅ 每次升档一条事件 |
| 🔴 **封禁期间被挡掉的每一个请求** | ❌ 只给 Redis 计数器 +1 |
| 封禁到期 → 转灰 | ✅ 更新名单 |

每挡一次就写一条的话，一个每秒一万次的脚本就是每秒一万条记录 —— 我们替攻击者把自己的库打满。
按状态变化写，一次攻击只有几条事件；被挡掉的量由计数器定期同步到名单的 `blocked_count`，
回答「这个 IP 被我们挡掉了多少请求」这笔成本账。

#### 什么事件进什么名单

| 事件 | 立即处罚（Redis，马上生效） | 名单 |
|---|---|---|
| 蜜罐接口 / 蜜罐账号 / 关键字 | IP 与设备 24h，所有场景 | IP **拉黑 24h**，到期**自动转灰 30 天** |
| 限流处罚升到第 4 档（≥ 1h） | 已在处罚中 | IP 维度的：IP 灰 7 天。**登录后场景的账号维度**：会员灰 7 天（见下）。匿名场景的账号维度：只记事件 |
| **同段连坐**：24h 内同一个 /24（IPv6 /48）里 ≥ 3 个 IP 被自动拉黑 | 不处罚（已被拉黑的那几个 IP 照旧） | 整段 **IP 段灰 7 天**（`source_rule = SEGMENT`）。**只拉灰，永远不自动拉黑整段** |
| 人工 | — | 后台手动加黑 / 灰 / 白 |

「黑名单到期转灰」就是「以后只要是记录里的 IP 就提高风控」：封禁结束后，它还背着 30 天的前科。

**灰名单的效果**：

- **网关**：这个 IP 在所有场景的限流阈值减半；
- **登录风控**：`IP_GREYLIST` 加分（条目上的 `score`，自动条目默认 30）→ 前置至少滑块（全局滑块关掉之后也一样），叠上新设备就要 OTP；
- **会员灰名单**（新增；放开登录风控里「会员维度只许白名单」的校验，黑名单仍不允许 —— 会员的「黑」就是冻结，有自己的状态位）：
  - 登录矩阵里**可信设备也按新设备算** → 不熟悉的网络上要 OTP；
  - 资产出口（兑换、充值、加地址）**每次都要二次验证**，不看设备是否可信；
  - 这个会员在网关所有场景的**账号维度阈值减半**。
  - 来源：人工；或登录后场景（`REDEEM`、`SIGN`、`DEFAULT_WRITE`……）账号维度被罚到第 4 档。
    **匿名场景的账号维度永远不会让一个会员进灰名单** —— 那里的「账号」是别人填的目标，进了就成了拿别人的号去拉灰的手段（§2.4）。
  - 对会员本人**不可见、不提示**：他只会感觉「这几天验证码多了一点」。

**设备不进名单**：设备有自己的状态位。设备的 24 小时处罚只放在 Redis 处罚键里；设备拉灰复用现有的观察档（`DeviceDispositionService.observe`）。

## 6. 规则走 Redis

网关不连数据库（`solvela-app` 没有数据源，只有 Redis）。规则的流向：

```
后台（solvela-admin，连库）
  │ 保存规则 → 写 t_rate_limit_rule / t_config
  │ 同时把全部规则拼成一份快照写进 Redis：gw:rl:snapshot = {version, rules, ladder, honeypot, keywords, ipLists}
  │ （ipLists = 名单表里有效的 IP / IP 段黑、灰、白名单；名单一变也触发重发）
  ▼
Redis
  ▲ 网关启动时读一次；之后每 15 秒只读 version，变了才拉整份
网关（本地缓存一份，请求路径上不读 Redis 拿规则）
```

- **库是真相源，Redis 只是分发**：Redis 不适合当配置的唯一存储 —— 一次 flush 或内存淘汰，规则就没了，也没有修改留痕。
  库里的表走 `DataTracer` 留痕，与其它后台配置一样。
- **快照丢了怎么办**：Redis 如果开了会淘汰键的内存策略，快照可能被挤掉。两层兜底：
  后台每 5 分钟把快照重发一次（自愈）；网关读不到快照时用**代码里内置的默认值**（与种子数据相同的那一套）并打 ERROR 日志。
  不允许出现「读不到规则 = 不限流」。
- **为什么不走接口**：走接口意味着网关要定时调 app-biz 拉规则，多了一条服务间依赖；而网关每个请求本来就在用 Redis（会话、设备、滑块），
  走 Redis 不增加任何新的依赖。

### 6.1 表

```sql
CREATE TABLE `t_rate_limit_rule` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT 'id',
  `scene` varchar(32) NOT NULL COMMENT '场景：与代码里 RateLimitScene 枚举一一对应',
  `dimension` tinyint NOT NULL COMMENT '维度：1-IP, 2-账号, 3-设备, 4-IP段（只允许四个匿名场景）',
  `burst` int NOT NULL COMMENT '突发：10 秒令牌桶容量',
  `limit_3m` int NOT NULL COMMENT '3 分钟阈值',
  `limit_5m` int NOT NULL COMMENT '5 分钟阈值',
  `limit_10m` int NOT NULL COMMENT '10 分钟阈值',
  `mode` tinyint NOT NULL DEFAULT '2' COMMENT '档位：0-关闭, 1-陪跑（只记日志）, 2-生效',
  `description` varchar(256) DEFAULT NULL COMMENT '为什么是这个数',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_rl_rule` (`scene`,`dimension`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='网关限流规则（后台维护，经 Redis 快照下发到网关）';
```

- 保存时校验：`burst ≤ limit_3m ≤ limit_5m ≤ limit_10m`，且三个窗口是亚线性的（否则提示「长窗口永远不会先触发」）。
- 全局参数放现有的 `t_config`：处罚阶梯（`60s,5m,30m,1h,2h,8h`）、清零时间（24h）、匿名账号维度封顶（30m）、
  蜜罐处罚时长（24h）、蜜罐路径列表、熔断阈值。
- 场景是代码里的枚举，表里缺某个场景时网关用内置默认值并 WARN；表里多出代码不认识的场景，后台保存时直接拒绝。
- 首批数据（§3.1）进 `data-baseline.sql`。

### 6.2 后台页面

| 页面 | 内容 |
|---|---|
| 限流规则 | 场景 × 维度的阈值与档位；全局阶梯参数 |
| 处罚查询 | 按 IP / 账号 / 设备精确查当前处罚（直接 GET 对应的 Redis 键，不扫库），可手动解除 |

### 6.3 名单表 `t_security_list`（网关与登录风控共用）

**从 `t_member_risk_list` 改名**。它已经不是「会员风控」的表了：网关读它、往里自动写，登录风控也读它。
名字说错了归属，下一个人就会照着错的归属去改它（比如在会员域里加一条「只有会员风控能写」的校验）。
改名是机械重构：表、实体 `MemberRiskList` → `SecurityList`、三个枚举 `MemberRiskList*Enum` → `SecurityList*Enum`、DAO、后台页、前端 API、测试。
**上线前是这件事最便宜的时候** —— 没有数据要迁、没有线上依赖，以后只会更贵。

在现有结构（2026-10-17 对着 `schema-baseline.sql` 核对）之上，**新增五列**、把「自动」来源用起来：

**自动条目的写入规则**（唯一键冲突时）：

- 已有**有效的自动**条目：`hit_count + 1`、更新 `last_hit_time` / `last_incident_id`，`expire_time` 取两者中更晚的。
- 已有**有效的人工**条目：**不覆盖**。人工设的长期黑名单不会被自动的 24 小时缩短；人工的白名单也不会被自动拉黑改掉 ——
  但白名单 IP 碰蜜罐 / 关键字照样处罚（白名单只豁免限流），并且**告警**：办公室出口去碰蜜罐本身就值得有人看。
- 已有**已撤销**的条目：复用这一行，重新置为有效，撤销三列清空、`hit_count` 归 1。撤销的历史留在 `t_security_incident` 与 `DataTracer` 里。
- **黑到期转灰**：定时任务把到期的自动黑名单改写一条灰名单（`source_rule = ESCALATE`，30 天）。黑、灰是不同的 `list_type`，各占一行。

### 6.4 安全事件流水 `t_security_incident`（新建）

```sql
CREATE TABLE `t_security_incident` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT 'id',
  `incident_type` tinyint NOT NULL COMMENT '1-蜜罐接口, 2-蜜罐账号, 3-关键字, 4-限流判罚 / 升档',
  `rule_code` varchar(32) DEFAULT NULL COMMENT '命中的蜜罐路径 / 关键字规则 / 限流场景编码',
  `action` tinyint NOT NULL COMMENT '实际处置：0-仅记录, 1-拉灰, 2-拉黑',
  `suppress_reason` tinyint NOT NULL DEFAULT '0' COMMENT '处罚被压下的原因：0-无, 1-跨站发起, 2-熔断中, 3-老设备豁免（仅 IP 部分）',
  `penalty_level` tinyint DEFAULT NULL COMMENT '限流判罚的档位（1–6），其它类型为 NULL',
  `client_ip` varchar(39) DEFAULT NULL COMMENT '客户端IP',
  `device_id` char(32) DEFAULT NULL COMMENT '设备号',
  `member_id` bigint DEFAULT NULL COMMENT '会员号（已登录时）',
  `identity_hash` binary(32) DEFAULT NULL COMMENT '蜜罐账号命中时的登录身份摘要',
  `http_method` varchar(8) DEFAULT NULL COMMENT '请求方法',
  `request_path` varchar(256) DEFAULT NULL COMMENT '请求路径，不含查询串',
  `matched_field` tinyint DEFAULT NULL COMMENT '命中位置：1-UA, 2-路径, 3-查询参数, 4-请求体字段',
  `matched_param` varchar(32) DEFAULT NULL COMMENT '命中的参数 / 字段名',
  `matched_sample` varchar(128) DEFAULT NULL COMMENT '命中片段，截断。🔴 攻击者可控：后台只能按纯文本展示',
  `user_agent` varchar(256) DEFAULT NULL COMMENT 'UA，截断。🔴 同上',
  `penalty_until` datetime DEFAULT NULL COMMENT '处罚到期时间',
  `trace_id` varchar(64) DEFAULT NULL COMMENT '全链路追踪ID',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '发生时间',
  PRIMARY KEY (`id`,`create_time`),
  KEY `idx_sec_inc_ip` (`client_ip`,`create_time`),
  KEY `idx_sec_inc_device` (`device_id`,`create_time`),
  KEY `idx_sec_inc_member` (`member_id`,`create_time`),
  KEY `idx_sec_inc_type` (`incident_type`,`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='安全事件流水（append-only，按月分区，保留 6 个月）'
/*!50500 PARTITION BY RANGE COLUMNS(create_time) ( ...与登录风控的决策流水相同，由同一个分区维护任务管... ) */;
```

- 🔴 **`matched_sample` / `user_agent` 是攻击者能控制的内容**。后台若用 `v-html` 渲染，一次探测请求就能在运营打开页面时执行脚本 ——
  管理端现有 3 处 `v-html` 都按「后台内容可信」处理，这两个字段绝对不能进那条路。
- **只存命中的那一小段**，不存完整查询串、不存请求体：别人的手机号、地址不该因为请求里恰好夹了一个关键字就进了安全日志。密码与验证码字段本来就不参与匹配（§5.4）。
- 只有状态变化才写（§5.5），量级是「攻击次数」而不是「请求次数」。

#### 写入链路（网关不连库）

```
网关命中 ─► ① 写 Redis 处罚键 —— 马上生效，不等数据库
        └─► ② XADD 到 Redis Stream sec:incident（MAXLEN 约 10 万，防止被刷爆）
                   │
            app-biz 消费：写 t_security_incident，按 §6.3 的规则更新 t_security_list
                   │
            名单变化 → 触发规则快照重发（§6）→ 网关拿到新的 IP 黑 / 灰 / 白名单
```

- **处罚以 Redis 为准，库是留痕与后台查询**。后台解封 = 撤销名单条目 + 删除 Redis 处罚键，两步在同一个后台操作里完成。
- 消费者宕机时事件在 Stream 里排队（有上限），恢复后补写；超出上限丢掉的是最老的事件，**处罚本身不受影响**（已经在 Redis 里）。
- 蜜罐账号由会员域在登录风控里判定（`CANARY_ACCOUNT`），它同样写处罚键 + 投递到同一个 Stream。键格式与事件格式放在网关、会员域都依赖的 `solvela-contract` 里。

### 7.1 风控那边要删、要改的（§1.1 的落地）

**删**（规则类 + 种子数据 + `LoginCounters` 里对应的计数器 + 用例）：

> 验收：迁过来的每一条，在网关侧有一个「同样的请求序列、同样被挡下」的用例。

**改**：

- 名单表改名 `t_security_list` 与配套重命名（§6.3）。
- 放开会员维度的灰名单（域里与后台的校验同时改），并在登录矩阵、资产出口的二次验证判断里接上会员灰名单（§5.5）。

- 后台菜单合成「安全中心」。
