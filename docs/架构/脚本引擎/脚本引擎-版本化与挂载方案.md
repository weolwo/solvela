# 脚本引擎：版本化与多值挂载方案

> 2026-08-31 落地。前身见《C 端网关-API 契约方案》，那份文档不涉及脚本存储。

## 0. 一句话结论

**脚本从「部署的代码」变成「发布的配置」**：权威从 `resources/scripts/` 搬进 `t_script`，
一行 = 一个版本，同一编码至多一行激活。git 继续管演化历史，数据库管「此刻线上跑哪一版」。

---

## 1. 原设计为什么用不了

| 症状 | 根因 |
|---|---|
| 改一行脚本要发一次版 | 权威在 jar 里的文件 |
| 一个活动挂不了多个脚本 | 唯一键 `(ref_type, ref_id, ref_slot)`，槽位内只能一个 |
| 后台没有新增脚本的地方 | 这是当时的<b>设计</b>：脚本必须走 git + 发版 |

第二条曾经被误诊过。原始判断是「活动:脚本 = 1:N 做不到」，实际拆开看：

- **奖池编排** → `ACTIVITY_PLAY` 槽位早就有，能挂；
- **领奖** → 缺槽位，但单值就够；
- **监听登录送机会** → 缺槽位，且天然多值（一个活动订阅登录、下单、分享…）。

所以「N」里大部分是**槽位不够**，只有事件订阅是真的一对多。

> 🔴 **槽位不能变成数据。** 一个槽位就是 Java 里的一个调用点；后台建出来的槽位没有任何
> 代码会去调它，只是一行永远不生效的配置。`ScriptRefPoint` 保持枚举是对的。

## 2. 数据模型

### 2.1 `t_script`：一行 = 一个版本

```
UNIQUE KEY uk_script_code_version (script_code, version)
UNIQUE KEY uk_script_active       (script_code, active_flag)
```

`active_flag` 只有两种取值：`1`（当前生效）或 `NULL`（历史版本）。

> 🔴 **历史版本必须是 NULL，不能是 0。** 唯一索引里 NULL 不参与判重，所以历史版本可以有
> 无数行、激活的最多一行 —— 这条约束由**数据库**保证，不依赖代码写得对。
> 填 0 的话 `(code, 0)` 立刻重复，同一个脚本将只能存下**一个**历史版本。

两个配套坑：

1. Java 侧类型是 `Boolean`（可空），不是 `Integer` —— 枚举棘轮测试盯着标记列；
2. MyBatis-Plus 的 `updateById` **默认跳过 null 字段**，所以「取消旧激活」必须用
   `UpdateWrapper.set(Script::getActiveFlag, null)`。拿实体去 update 会静默不生效，
   紧接着新行撞唯一键 —— 症状离病因很远。

### 2.2 `t_script_ref`：槽位内可按 key 分组

```
ref_key varchar(64) NOT NULL DEFAULT ''
UNIQUE KEY uk_script_ref_point (ref_type, ref_id, ref_slot, ref_key)
```

> 🔴 **`ref_key` 不许可空。** 和上面是同一个 MySQL 行为，在这里是坑而不是特性：
> 允许 null 等于单值槽位完全没有约束，同一个活动能挂进两个玩法编排脚本。
> 单值槽位一律归成空串，规整逻辑统一在 `ScriptRefPoint.normalizeKey`。

槽位是不是多值，判据是**「说不说得清 key 是什么」**：`ScriptRefPoint` 的多值构造器要求填
`keyTitle`，`isKeyed()` 就是 `keyTitle != null`。说不清的多半只是想绕开单值约束。

## 3. 两套版本管理的分工

| | git（`resources/scripts/`） | `t_script` |
|---|---|---|
| 管什么 | 怎么演化到今天：diff、review、blame | 线上此刻跑哪一版、出事退回哪一版 |
| 谁写 | 开发 | 后台操作人 |
| 运行期读吗 | **不读** | 读 `active_flag = 1` 那一行 |

文件退回**开发工作区**的位置：写在那里、走 review，上线靠人复制进后台并激活。

`ScriptSeedImporter`（原 `ScriptFileLoader`）只剩两件事：

1. **种子导入** —— 只对「库里一行都没有」的编码插 v1 并激活，让全新环境不是空的；
2. **体检** —— 语法错、工作区与线上不一致、悬空挂载，全部记日志。

> 🔴 **它不再抛异常。** 以前语法错和悬空引用会让应用拒绝启动，当时是对的 —— 文件就是线上逻辑。
> 现在不行：修复这些问题的唯一途径是后台脚本管理页，而后台就在 admin 进程里。
> 让它启动失败等于**把修复它的工具一起锁死**，只能改库或回滚发版才能出来。

这个改动当天就见效了：工作区里有一个手写的 `2026中秋活动抽奖_A8P0Y3ANGI.ql` 没有文件头，
按旧规则**每个服务都起不来**；现在只是一行 ERROR 日志。

## 4. 保存与激活刻意分开

| 动作 | 权限 | 后果 |
|---|---|---|
| 保存 | `script:edit` | 只加一行，**线上不变** |
| 激活 | `script:publish` | **改变线上行为** |
| 挂载 | `script:bind` | 改变某个活动/奖池走哪段逻辑 |

合成一步的话，「我先存一下待会儿再看」会直接改掉生产逻辑。

**激活与回滚是同一个方法** —— 都是把 active 标记挪到某一行上。
所以不存在「回滚功能没测过」这回事：每次发布都在测它。

保存前三道闸：

1. 场景合法，**且与该编码已有版本的场景一致**；
2. 语法 `check()` 通过 —— 坏脚本进不了库；
3. 内容确实变了 —— 与已有版本一字不差时不产生新版本。

> 🔴 **第 1 条里的「一致」是关键。** 换场景 = 换掉入参与返回值契约，而挂载点是按场景校验后
> 才挂上去的。悄悄换场景等于让所有已有挂载失效，且要等真有用户触发时才炸。
> 要换场景请用新的脚本编码。

## 5. 运行期怎么读

`ScriptStore` 是唯一入口，本地缓存 `script_code -> (version, 可执行体)`，
TTL 由 `script.active-cache-millis` 控制（默认 5 秒）。

> 🔴 **缓存必须带 TTL，不能是「永久缓存 + 主动失效」。**
> 后台是在 admin 进程点的激活，脚本在 marketing 进程执行，`evict()` 只能清本进程的那一份，
> **别的进程收不到任何通知**。永久缓存的后果是：运营点了发布、admin 里预览也对，
> 线上却一直跑老版本，而且**重启之前不会自愈**。

TTL 就是跨进程生效的延迟上限。取 5 秒是因为对运营来说「发布后几秒生效」与「立即生效」
没有区别，而代价只是每 5 秒一次唯一索引点查。消息广播能做到毫秒级，但要多一套订阅与重连，
**现在没有证据说明 5 秒不够**。

「没有激活版本」也缓存 —— 绝大多数挂载点没挂脚本，不缓存缺失等于每次抽奖都为
「确认它确实没有」打一次库。

### 安全

DB 存脚本 = 后台账号能写进程内执行的代码。这一条不用额外做：引擎已经是
`QLSecurityStrategy.isolation()` + 3 秒超时，`script.allow-java-reflect` 在
dev/test/pre/prod 四套配置里全是 `false`。所有系统能力只能通过 `@ScriptFunction` 白名单进入。

**没有这一条，这套方案不该上线。**

## 6. 明确不做的

**试跑不卡激活。** 场景契约（`ScriptScene.getParams()` → `/script/engine/scene/view`）
已经能把试跑表单自动生成出来，开发不需要记要传什么。但脚本里调的 `@ScriptFunction` 会查真实
数据，`params` 又是各玩法自定义的，所以试跑的**真实度**没保证；而 `ACTIVITY_PLAY` 试跑会真扣
库存真发奖。做成可选工具，不做发布门禁。

代价说清楚：**「分支没覆盖全 → 静默返回 null → 少发一批奖」这类错误，仍然只能等真实用户触发。**
`ScriptScene.validateOutput` 的注释描述的就是它。

**不造没有调用点的槽位。** `ACTIVITY_CLAIM` 和 `ACTIVITY_EVENT` 要等 `claimPrize()`
和事件分发器写出来再加 —— 现在加只是两个没有代码会调的挂载点，而且入参清单只能靠编。
`ScriptScene` 的类注释写着「变量清单必须来自调用点真实存在的数据」。

## 6.5 挂载点该挂在哪一层（2026-08-31 补）

上线后第一件被绊到的事：挂载表要填「业务对象编码」，而抽奖填什么都不对。

查下来的事实比预期严重——**四个挂载点里只有 `ACTIVITY_PLAY` 有真实调用点**，
全仓 `scriptRuntime.evaluate(...)` 只出现一次。`PRIZE_POOL_ENTRY` / `ACTIVITY_ENTRY` /
`TASK_TEMPLATE_RULE` 挂上去永远不会执行。

根因是抽奖模块少了一层：

| 玩法 | 玩法配置 | 编码 | 脚本挂在 |
|---|---|---|---|
| 彩票 | `t_lottery_config` | `lottery_code` | （待接） |
| 任务 | `t_task_template` | `template_code` | （待接） |
| 抽奖 | ~~没有~~ → `t_draw_config` | `draw_code` | `DRAW_PLAY` |

抽奖原本只有「活动 → N 个奖池」两层，玩法级参数只能挂到奖池上：

- `draw_mode`（抽奖算法）——**死列**，后端从未读过，选「按库存比例」照样按概率抽。已上移；
- `reset_period`（重置周期）——活的。已上移。

### `reset_period` 有两个用途，同一个开关驱动

| 用途 | 表现为 | 出口 |
|---|---|---|
| 单人限领计数记在哪个桶 | Redis key 里的周期段 | `DrawPeriodResolver.resolve` |
| 数「已经抽了几次」时从哪天起算 | SQL 的 `create_time >= ?` | `DrawPeriodResolver.periodStart` |

> 🔴 两者**必须由同一个配置驱动**，否则会出现「限领已经重置了、但次数还没重置」
> 这种谁也说不清的状态。所以两个方法放在同一个类里，改一个必然会看见另一个。

**「能抽几次」不是配置项**，它是业务设计与用户资格问题，由脚本决定。
而「已经抽了几次」直接数 `t_draw_prize_log`——**不另建计数表**：
抽奖记录本来就是每抽一次一行，再维护一个计数器等于同一件事有两份账，
两份账迟早对不上，到那天你不知道该信哪一个。

脚本侧的出口是 `draw_countDrawn()`（只读、可多次调用）：

```
if (draw_countDrawn() >= 3) {
    return null;
}
return draw_executeDrawByScript(pool);
```

⚠️ 未中奖、库存不足、异常的记录**都算一次**——它们都是「用户点了一次抽奖」。
方向与本模块一致：少算一次是资损，多算一次用户会来反馈。

### 挂载点由玩法自己决定

`ActivityFacade` 在 `solvela-activity`，玩法配置在 `solvela-marketing`，而**后者依赖前者**——
引不到。用与 `ActivityRefProvider` 同一套依赖倒置：接口 `ActivityPlayMountProvider`
声明在活动模块，实现放在玩法那边。

- 有实现 → 由它给出挂载点与 refId（抽奖给 `DRAW_PLAY` + `draw_code`）
- 没实现 → 退回 `ACTIVITY_PLAY` + 活动编码（BASIC 一直走这条路）
- 有实现但返回 null → `NO_PLAY_CONFIG`，**不退回老路**

> 🔴 最后一条是关键：退回去的话，运营关掉抽奖配置之后活动照样能抽。
> 「这个玩法没有配置层」和「这个活动的配置没建/被关了」必须分开。
