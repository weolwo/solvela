# 优惠券使用闭环 实现技术方案

> 输入：`t_member_coupon` 现状、`CouponAssetHandler`、`MallRedeemService`、开发库实际数据
> 对齐：`数据库SQL脚本/mall.sql` 的刻意排除清单、`docs/通知与公告-实现技术方案.md` 的模板版本化经验
> 日期：2026-09-15

---

## 0. 现状盘点：券是一个只进不出的资产类型

### 0.1 数据说话

```
t_member_coupon  共 845 张
  已过期 598 张（71%）
  未使用 247 张
  已使用   0 张   ← 从来没有过一张
```

不是没人用，是**用不掉**：

| 事实 | 证据 |
|---|---|
| `CouponStatusEnum.USED` 全仓**零写入** | 没有任何代码把券标成已使用 |
| 管理端**没有核销动作** | `MemberCouponController` 只有 `queryPage` / `stat`。「核销」两个字只出现在一个统计口径的 Swagger 描述里，而那个数永远是 0 |
| C 端**完全没有券** | `solvela-app` 无券端点，用户连自己有哪些券都看不到 |
| 而平台在**持续发券** | 5 个奖品配置 + 1 个商品产 COUPON |

> 📌 2026-09-15 按大厂券系统标准对照过一遍，补了两处本方案原先漏掉的东西：
> **核销流水表**（§5.3）与**实际抵扣额**（§5.2）。对照的结论见 §12。

### 0.2 🔴 真正的问题不是「不够灵活」，是**没有表达能力**

库里实际发出去的券长这样：

```
coupon_code = 0ZXXLZ0RZ1   coupon_type = GENERAL   coupon_name = 满100减20优惠券   × 241
coupon_code = 0ZXXLZ0RZ1   coupon_type = GENERAL   coupon_name = 提案生成成功      × 302
coupon_code = PP0COUPON1   coupon_type = GENERAL   coupon_name = P0-20元券        × 297
```

**「满100减20」这条规则，系统唯一知道它的地方是券的名字字符串。** 没有任何代码能解析它。

`t_member_coupon` 的全部业务列只有：`coupon_code` / `coupon_type` / `coupon_name` / 有效期 / 状态 —— **一个面额、折扣率、门槛、封顶字段都没有**。

而且：

- **没有券模板表。** `coupon_code` 的列注释写着「券模编码」，但那张券模表不存在，编码指向空气；
- **`coupon_type` 全是 `GENERAL`**，一个写死在 `CouponAssetHandler` 里的常量，旁边两个 `TODO` 标着「产品规则待定」；
- **302 张券的名字是「提案生成成功」** —— 那是 `proposal.getAssetName()` 为空时的兜底文案漏进来的，用户在券包里看到的券名就是这五个字。这是个独立的脏数据 bug，见 §10.1。

## 1. 要做成什么

> 发券给用户后，用户可以自己去兑换。比如充话费券，用户支付 100，可以按券抵扣百分比或者固定金额，
> 但是充值金额有最低下限、最大抵扣金额。或者用户去商城兑换某个商品也可以用券抵扣积分或者现金。

拆成三件事：

1. **券要能表达规则** —— 百分比 / 固定金额、最低消费、最高抵扣、适用范围；
2. **券要能被用掉** —— 一套通用的核销机制，商城和充话费共用；
3. **券要有产出与出口** —— 产出（活动 / 任务 / 人工）已有两条，人工那条缺；出口（C 端券包）完全没有。

---

## 2. 规则住哪：模板 + 快照，两者都要

### 2.1 为什么要模板表

运营要能管理「平台有哪些券」、配置规则、看统计。今天这些全靠在券名里写字，改一次文案就等于改了一次「规则」。

### 2.2 🔴 为什么发券时还要把规则**快照**进会员券

这是本方案最重要的一条：**券模板改了，已经发出去的券不能跟着变。**

用户手里那张「满100减20」，运营把模板改成「满200减20」之后，如果核销时读的是模板当前值，**用户手里的券就贬值了**。这不是显示问题，是资损与信任问题 —— 比通知模板那个「历史措辞被改」严重得多，因为它直接影响钱。

两条路都走得通：

| 做法 | 代价 |
|---|---|
| 模板按 `(code, version)` 不可变，券存 version | 省空间，但核销要 join 模板表 |
| **发券时把规则快照进券行** | 多几十字节 × 券数，换核销零 join |

**选快照**，两个理由：

- 券的规则字段很少（类型 + 3 个金额），约 20 字节。100 万张券 = 20MB，不算什么；
- **核销在支付路径上**，零 join 值钱。而且和本项目「单据存快照」的既有约定一致（`t_mall_order` 存商品名、单价快照）。

模板仍然版本化（运营要看「这张券当时是什么规则」），但**核销只读会员券行**，永远不碰模板。

## 3. 规则字段

| 字段 | 说明 |
|---|---|
| `discount_type` | `FIXED`（固定金额）/ `PERCENT`（百分比） |
| `discount_value` | FIXED 时是抵扣额；PERCENT 时是折扣率（如 20 表示减 20%） |
| `min_amount` | **最低消费门槛**。订单金额低于它这张券用不了 |
| `max_discount` | **最高抵扣**。🔴 `PERCENT` 时<b>必填</b> —— 不设上限的话「8 折」碰上一台 iPhone 就是一次资损 |
| `deduct_target` | 抵扣什么：`CASH`（现金）/ `SCORE`（积分） |
| `scope_type` | 适用范围：`ALL` / `COMMODITY` / `CATEGORY` / `EXTERNAL`（充话费这类外部场景） |
| `scope_refs` | 范围明细，json 数组。`ALL` 时为空 |

### 3.1 一单一券，不叠加

`mall.sql` 开头的刻意排除清单里明确写着**「优惠券叠加」不做**。本方案沿用：一笔交易最多用一张券。

不是做不了，是叠加之后「哪张先算、门槛按原价还是折后价、封顶怎么分摊」会立刻变成一堆没有标准答案的产品问题，而它们每一个都能造出资损。

---

## 4. 🔴 核销必须是三阶段，不是一步

> 试算（TRY）→ 锁定（LOCK）→ 确认（CONFIRM）/ 释放（RELEASE）

**为什么不能一步核销**：用户下单用了一张券，订单后来失败或超时取消 —— 券白没了。

这和 2026-09-15 刚修过的「商城超时取消要退积分」是**完全同构的问题**。积分有 `debit` / `refund` 一对，券也必须有 `lock` / `release` 一对，否则一定会出现「订单取消了但券没回来」。

四个动作各自的语义：

| 动作 | 改状态吗 | 用在哪 |
|---|---|---|
| **试算** | ❌ 不改 | 下单页展示「这张券能减多少」、「哪些券可用」 |
| **锁定** | 0-未使用 → **4-锁定中** | 提交订单时。条件更新即并发闸，**防同一张券被两笔订单同时用掉** |
| **确认** | 4-锁定中 → 1-已使用 | 支付 / 履约成功 |
| **释放** | 4-锁定中 → 0-未使用 | 订单取消、支付超时、履约失败 |

`CouponStatusEnum` 因此要加一档 **`LOCKED(4, "锁定中")`**。

### 4.1 试算：一单一券下的「最优券」

一单一券让这件事变得很简单：**对每张可用券各算一次抵扣额，取最大的**。

但有五个细节，每一个漏掉都会出事：

**① 抵扣额不能超过应付金额。**

一张「减 200」的券碰上 150 元的订单，算出来是 200 —— 应付变成 **-50**。
必须 `min(算出来的抵扣, 应付金额)`。这条要写死在试算里，不能指望调用方判。

**② `PERCENT` 和 `FIXED` 谁大不一定，必须逐张算。**

| 订单金额 | 满100减20 | 8折最高减50 | 谁优 |
|---|---|---|---|
| 150 | 20 | min(30, 50) = 30 | PERCENT |
| 500 | 20 | min(100, 50) = 50 | PERCENT |
| 90 | 不满门槛 | 不满门槛 | 都用不了 |

没有「百分比一定更划算」这种捷径。

**③ 🔴 `deduct_target` 不同的券不可比，不要替用户跨类比较。**

一张减积分的券和一张减现金的券，「谁更划算」系统答不了 —— 1 积分 ≠ 1 元，
而汇率是业务定义、还会变。

所以试算的输出是**按 `deduct_target` 分组**的：每组内推荐最优的那张，
跨组让用户自己挑。硬要给一个「全局最优」，就是替用户做了一个它没有依据的决定。

**④ 平局选先过期的那张。**

两张券都减 20，选快过期的 —— 用户手上的券整体价值最大化。
选 id 小的或随便一张，结果是用户攒了一堆快过期的券却总在用新的。

**⑤ ⚠️ 「门槛按原价还是折后价」这个问题，一单一券时不存在。**

只有一次折扣，门槛就是订单原价，没有歧义。

🔴 **但如果将来要做叠加，这是第一个必须先定的口径** ——
它决定「满100减20 + 8折」在 120 元订单上是减 20+24 还是 20+20，
而这两个数字差出来的钱是真金白银。`mall.sql` 把叠加排除掉，
省掉的正是这一类没有标准答案的问题。

### 4.2 锁定后没人释放怎么办

进程在锁定和确认之间挂掉，券会永远停在 4-锁定中。

对策和商城订单同一套：**一个兜底 job**，把锁定超过 N 分钟且对应单据已终态（或不存在）的券释放回去。`t_member_coupon` 需要一列 `locked_biz_id` 记住是被哪一笔锁的，否则 job 无从判断。

⚠️ 这一列也是**幂等的依据**：同一笔订单重复调锁定，看到 `locked_biz_id` 已经是自己就直接放行。

## 5. 表设计

### 5.1 新增 `t_coupon_template` —— 券模板

```sql
CREATE TABLE `t_coupon_template` (
  `coupon_code`    varchar(64)  NOT NULL COMMENT '券模编码：跨环境稳定，发券时引用它',
  `version`        int          NOT NULL COMMENT '🔴 改规则=新增版本，永不原地改',
  `coupon_name`    varchar(128) NOT NULL COMMENT '券名，如「满100减20」',
  `discount_type`  varchar(16)  NOT NULL COMMENT 'FIXED / PERCENT',
  `discount_value` decimal(10,2) NOT NULL COMMENT 'FIXED=抵扣额；PERCENT=折扣率(20 表示减20%)',
  `min_amount`     decimal(10,2) NOT NULL DEFAULT 0 COMMENT '最低消费门槛，0 表示无门槛',
  `max_discount`   decimal(10,2) DEFAULT NULL COMMENT '最高抵扣。🔴 PERCENT 必填，否则一单就能亏穿',
  `deduct_target`  varchar(16)  NOT NULL COMMENT 'CASH / SCORE',
  `scope_type`     varchar(16)  NOT NULL DEFAULT 'ALL' COMMENT 'ALL/COMMODITY/CATEGORY/EXTERNAL',
  `scope_refs`     json         DEFAULT NULL COMMENT '范围明细。ALL 时为空',
  `valid_days`     int          DEFAULT NULL COMMENT '发券后多少天过期。与 valid_end_time 二选一',
  `valid_end_time` datetime     DEFAULT NULL COMMENT '固定失效时间（如活动结束）。与 valid_days 二选一',
  `status`         tinyint      NOT NULL DEFAULT 1 COMMENT '1-启用 0-停用。🔴 只停用不删除',
  ...
  PRIMARY KEY (`coupon_code`, `version`)
);
```

> 有效期给两种表达是因为业务上真的有两种：「领取后 30 天」和「活动结束就作废」。
> 只给前者的话，活动结束后还有一批券在外面飘。

### 5.2 改 `t_member_coupon` —— 加规则快照与锁定

```sql
ALTER TABLE `t_member_coupon`
  ADD COLUMN `template_version` int          NOT NULL DEFAULT 1 COMMENT '发券时的模板版本，排查用',
  ADD COLUMN `discount_type`    varchar(16)  NOT NULL DEFAULT 'FIXED' COMMENT '规则快照',
  ADD COLUMN `discount_value`   decimal(10,2) NOT NULL DEFAULT 0     COMMENT '规则快照',
  ADD COLUMN `min_amount`       decimal(10,2) NOT NULL DEFAULT 0     COMMENT '规则快照',
  ADD COLUMN `max_discount`     decimal(10,2) DEFAULT NULL           COMMENT '规则快照',
  ADD COLUMN `deduct_target`    varchar(16)  NOT NULL DEFAULT 'CASH' COMMENT '规则快照',
  ADD COLUMN `scope_type`       varchar(16)  NOT NULL DEFAULT 'ALL'  COMMENT '规则快照',
  ADD COLUMN `scope_refs`       json         DEFAULT NULL            COMMENT '规则快照',
  ADD COLUMN `locked_biz_id`    varchar(64)  DEFAULT NULL COMMENT '锁定它的单据号。兜底释放与幂等都靠它',
  ADD COLUMN `locked_time`      datetime     DEFAULT NULL COMMENT '锁定时间，兜底 job 按它判超时',
  ADD COLUMN `discount_amount`  decimal(10,2) DEFAULT NULL COMMENT '🔴 本次实际抵扣额。核销时写，释放时清空。权威在流水表，这里冗余一份给券包列表零 join',
  ADD KEY `idx_member_status` (`member_id`, `status`, `valid_end_time`),
  ADD KEY `idx_locked` (`status`, `locked_time`);
```

🔴 **快照列给了 DEFAULT，是为了让存量 845 张券能就地升级**，而不是让新代码依赖默认值。存量券的处理见 §10.2。

`idx_member_status` 是 C 端券包和「可用券列表」的主查询；`idx_locked` 只给兜底 job 用。

### 5.3 🔴 新增 `t_coupon_write_off` —— 核销流水

**这张表是 2026-09-15 按大厂标准对照之后补的，而它补的是一个会在上线三个月后才暴露的洞。**

原方案只在 `t_member_coupon` 上改状态。问题是：**状态列只能表达「现在是什么」，
表达不了「发生过什么」**。

- 券被锁定、然后订单取消、券释放回去 —— 那次锁定的痕迹一点不剩。
  用户来投诉「我的券刚才还能用现在怎么回事」，查无对证；
- 更要命的是**实际减了多少没人记**。规则是「8 折最高减 50」，
  真正减了多少取决于订单金额 —— 不落地的话：
  - 退款时**不知道该退多少**；
  - 「本期核销金额」这个统计**算不出来**（管理端现有的 `stat` 里那个口径至今为 0，
    闭环做完也还是算不出金额）；
  - **财务对不了账**。

```sql
CREATE TABLE `t_coupon_write_off` (
  `id`              bigint       NOT NULL AUTO_INCREMENT,
  `coupon_id`       bigint       NOT NULL COMMENT '会员券 id',
  `member_id`       bigint       NOT NULL COMMENT '会员号。冗余一列，按人查时不用回表',
  `action`          varchar(16)  NOT NULL COMMENT 'LOCK / CONFIRM / RELEASE',
  `biz_type`        varchar(32)  NOT NULL COMMENT 'MALL / EXTERNAL',
  `biz_ref_id`      varchar(64)  NOT NULL COMMENT '订单号 / 外部单号',
  `scene_code`      varchar(32)  DEFAULT NULL COMMENT '外部场景码，如 MOBILE_RECHARGE',
  `original_amount` decimal(10,2) NOT NULL COMMENT '抵扣前应付',
  `discount_amount` decimal(10,2) NOT NULL COMMENT '🔴 本次实际抵扣额',
  `deduct_target`   varchar(16)  NOT NULL COMMENT 'CASH / SCORE 快照',
  `remark`          varchar(255) DEFAULT NULL COMMENT '释放原因等',
  `create_by`       varchar(64)  DEFAULT NULL,
  `create_time`     datetime     DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_coupon` (`coupon_id`, `id`),
  KEY `idx_biz` (`biz_type`, `biz_ref_id`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB COMMENT='优惠券核销流水：只增不改';
```

**三个动作各记一行，不是只记核销成功那一次。**

只记 CONFIRM 的话行数少一半，但「锁了又释放」就查不到了 —— 而券的纠纷恰恰
大多发生在那个窗口里。量级上完全撑得住：百万张券、三成核销率，也就是
三十万次核销 × 3 行，和 `t_member_notification` 那张亿级表不是一个数量级。

`idx_biz` 是给**对账**用的：按订单号反查「这一单用了哪张券、减了多少」。
`idx_create_time` 给按期统计与将来的归档。

> ⚠️ **`t_member_coupon.discount_amount` 是冗余，流水才是权威。**
> 冗余它是为了券包「已使用」那个 tab 能零 join 显示「已抵扣 ¥20」——
> 和 `t_member_notification.summary` 是同一个理由。
> 两者不一致时以流水为准。

## 6. 两个使用场景

### 6.1 商城：抵扣插在哪

`MallRedeemService.redeem` 现有顺序：

```
校验 → 占库存 → 占限购 → 生成订单号 → resolvePoints 算价 → debitPoints 扣分 → 落单
                                          ↑ 抵扣插这里
```

具体：

1. `resolvePoints` 之后得到 `payPoints` / `payCash`；
2. 若带券：**试算** → 得到抵扣额 → 调整应付；
3. **锁定**券，`locked_biz_id = orderNo`。放在占限购之后、扣款之前 —— 它和库存、限购是同一类「已占资源」，失败要一起回滚；
4. 扣款按抵扣后的金额；
5. 订单完成 → **确认**；订单取消 / 履约失败 → **释放**。

⚠️ 第 5 步要挂进 `MallOrderCancelService` 和 `MallFulfillService.settle` —— 就是刚补完超时取消的那两个地方。**别另写一条券的取消路径**，两条路迟早分叉。

### 6.2 充话费：一个「外部核销」的通用出口

充话费不是商城订单，它是「用户在某个外部场景消费了 100 元，用券抵扣」。

抽象成同一套 API，只是 `scope_type = EXTERNAL` + `scope_refs` 指明场景码（如 `MOBILE_RECHARGE`）：

```
试算(memberId, sceneCode, amount)      → 可用券列表 + 各自能减多少
锁定(couponId, memberId, bizId)        → 4-锁定中
确认(couponId, bizId) / 释放(couponId, bizId)
```

⚠️ **充话费本身这个能力不在本方案范围内** —— 它要接运营商或聚合支付，是独立一块。本方案只保证「券能被一个外部场景消费掉」这条路是通的，充话费是第一个接它的场景。

### 6.3 🔴 现金抵扣依赖支付链路，而支付链路还不存在

`deduct_target = CASH` 的券要抵扣的是**现金**，而全仓没有任何支付回调代码（`MallRedeemService` 自己的注释写着「支付链路至今一行代码都没有」）。

所以有一条明确的排序：

- **`deduct_target = SCORE`（抵扣积分）不依赖支付**，纯积分商品立刻能用；
- **`CASH` 与充话费都要等支付**（哪怕是先搞一个假支付）。

## 7. 券的产出

## 10. 待决与风险

### 10.1 ⚠️ 302 张券的名字是「提案生成成功」

`CouponAssetHandler.buildCoupon` 里：

```java
coupon.setCouponName(StringUtils.isNotBlank(proposal.getAssetName())
        ? proposal.getAssetName() : assetRef);
```

`assetName` 为空时回退到 `assetRef`（券模编码）—— 但库里那 302 张的名字是「提案生成成功」，说明**上游把提案的 remark 当 assetName 传下来了**。

这是个独立的脏数据 bug，和本方案无关但要一起修：修发券侧 + 刷一次存量券名。

### 10.2 存量 845 张券怎么办

新表结构的规则列有 DEFAULT，存量券能就地升级，但它们的**真实规则只存在于券名字符串里**（「满100减20优惠券」）。

三个选项：

| 选项 | 说明 |
|---|---|
| **A. 全部作废重发** | 598 张已过期本就不用管；未使用的作废 + 按新模板重发一次。最干净，且用户感知是「收到一张新券」 |
| B. 人工回填规则 | 券名能解析的（满X减Y）按规则回填，解析不了的作废 |
| C. 存量券一律按「无门槛固定额」处理 | 最省事，但会把「满100减20」变成「无门槛减20」—— **资损**，不要 |

> ✅ **2026-09-15 产品定了 A，已执行**，见 §11.5。实际是 **248 张**（不是 247）。

### 10.3 券能不能退

订单退款时券是退回还是作废？本方案默认**释放回去**（回到未使用），但若券已过期则不再释放 —— 那种情况要给用户一个说法，否则就是「退了款券也没了」。

**这一条需要产品定**，且它决定 §4 释放动作要不要额外判有效期。

- `PERCENT` 必须填 `max_discount` —— 不封顶的「8 折」碰上 7999 的 iPhone 就是减 1600，
  而它不报错、只是那一单少收了 1600；

**页面上有三件事是刻意设计的**，都对应一个会被误解的点：

- 顶部横幅写明「改模板**只影响之后发出去的券**」—— 运营的默认预期是「改完立刻全场生效」，

- 没有「修改」按钮，只有「基于此版新建」；没有删除，只有停用 —— 和服务端一致；
- 有效期做成**二选一的单选**而不是两个输入框都摆出来。摆两个的话，「都填了谁说了算」
  就会变成一个没人记得的约定（服务端也会拒，但在页面上就说清楚更好）。

#### 两条路都改，不能只改一条

发券有**两个**入口：发奖（提案链路）和商城兑换。它们的幂等语义不一样，
所以刻意是两个入口 —— 但都落 `t_member_coupon`。只改发奖那条的话，
商城还在发无规则的券，而**没有任何东西会报错**。

`CouponIssueService` 因此只 `build` 不 `insert`：把 insert 收进来就得把两套
幂等语义也收进来（发奖靠撞唯一键当成功、商城是一单 N 张的循环），
那会变成一个谁都看不懂的开关。

#### 🔴 券名：模板名赢过活动侧的展示名

因为**名字和规则必须是同一个人配的**。让活动侧的展示名盖过模板名，
就会出现一张叫「无门槛券」而 `min_amount=100` 的券 —— 用户看着名字去用，
被拦下来，然后来找客服。

调用方的展示名仍然要传：**没有模板时它就是券名**。

#### 🔴 找不到模板：降级照发，不拒发

库里真有这种券，而且**不是配错的**：商城在架商品「华为音乐 音乐VIP（年卡）」
（`XTYUJHUUI`）发的是一张**兑换凭证**，压根没有「减多少」这回事，
硬要给它配个模板才是编数据。

拒发会在运行期把一个在架商品变成兑换必失败，而收益只是少了一行规则为空的券
—— 代价完全不对等。所以照发，规则列**留空而不是填 0**：填 0 会变成一张
「无门槛减 0」的券，看起来配好了，实际减不出钱，而且再也分不清是没配还是配成了 0。

⚠️ 但降级必须**看得见**，否则就是这个仓库一直在骂的那种「不报错，只是没生效」。
两道可见性：发券侧打 ERROR；**券模板页顶部直接列出**会发券但没模板的配置点
（`/couponTemplate/missing`，同时看奖品配置和商城商品 —— 这个查询放在 admin
而不是账务域，因为账务域不能依赖营销域和商城域，有架构守卫盯着）。

#### ⚠️ 固定失效时间已经过去：照发，只是喊得很大声

换成拒发的话，用户中了奖却什么都没拿到，而那是个更难解释的结果。
发出去至少券包里有一张明确写着「已过期」的券，客服查得到、运营也看得出
是哪个模板配错了。

#### ⚠️ 刻意**不**加模板缓存

`NotificationTemplateService` 给「最新版」挂了 60 秒 TTL 缓存，这里没有。
差别在代价：通知模板缓存窗口里发出去的是**旧措辞**，券模板缓存窗口里发出去的是
**旧金额** —— 运营刚把「满100减20」改成「满200减20」，接下来 60 秒还在按老规则发钱。
发券不在高频路径上，这一次 DB 读换的是「改完立刻生效」。

#### 🔴 存量 845 张券仍然没有规则

阶段 2 只管**新发的**券。库里已经发出去的 845 张（其中 249 张还没用、没过期）
规则列全空，到阶段 3 试算时会被判为不可用。这就是 §10.2 那个决定，
**需要产品拍板**（推荐选 A：作废重发）。在那之前，能真正被用掉的券只有
阶段 2 之后新发的。

**验证**：994 个测试通过（新增 `CouponIssueServiceTest` 8 条 + 真库的发券快照用例
+ 体检的不漏报不误报用例）。真库用例验的是「模板改版之后，之前发出去的券
一个字段都不变」—— 那不是在验代码路径，是在验这个设计还在不在。

### 11.4 阶段 3 交付（2026-09-15）

**券第一次能被锁住、用掉、还回来。**

| 产出 | 说明 |
|---|---|
| `CouponWriteOffService` | 试算 / 锁定 / 确认 / 释放。**没有 `@Transactional`**，跑在调用方事务里 |
| `CouponDiscountCalculator` | §4.1 那五个细节的唯一实现 |
| `CouponTrialCmd/Item/Result` + `CouponUnusableReason` | 试算的入参与结果 |
| `MemberCouponDao` 四条手写 SQL | 试算候选 + 锁定 / 确认 / 释放的条件更新 |
| `CouponWriteOffDao.selectLockRow` | 确认 / 释放时回头抄金额 |
| `CouponStuckLockReleaseJob` + `JOBCOUPLCK` 调度行 | 兜底释放 |
| `t_member_coupon` 规则列改可空 | 修阶段 1 的坑，见下 |

#### 🔴 三条 WHERE 就是并发闸本身

锁定 / 确认 / 释放都是**条件更新**，而条件不是防御性写法：

- `WHERE status = 0` —— 两笔订单抢同一张券时只有一笔能成，另一笔拿到 0 行，
  当场知道自己没抢到。先 `SELECT` 再 `UPDATE` 的话两笔都会看到「未使用」，
  然后都以为自己锁上了，最后一张券被两单用掉，**而且不报错**；
- `AND locked_biz_id = ?` —— 只有锁它的那一笔能确认 / 释放它。
  少了这个条件，A 单锁的券会被 B 单确认掉；
- `AND member_id = ?` —— 顺手挡住越权用别人的券，还省掉一次「先查再比对」。

所以真库用例是必须的：mock 里 `lockCoupon` 返回什么都是我写的，**证明不了 SQL 是对的**。

#### 🔴 失败与幂等必须分得开

锁不上有两种情况，混成一种就一定出事：

| 情况 | 该返回 | 混淆的后果 |
|---|---|---|
| 已经是**这一笔**锁的 | 幂等成功 | 当失败的话，重复提交 / 失败重试会被拒掉 |
| 被**别人**锁走 / 已用掉 | 失败 | 当成功的话，抢券失败也会按打折价结算 |

⚠️ 幂等时**不补流水**：补了的话一次锁定会留下 N 行，对账时看着像锁了 N 次。

#### ⚠️ 确认失败时调用方必须处理

最可能的原因是**兜底任务已经把这张券释放了** —— 也就是这一单实际上没有用券。
当没看见的话，订单按打折后的金额结算，而券还躺在用户券包里可以**再用一次**。
所以 `confirm` 返回失败时打的是 ERROR，不是 WARN。

#### ⚠️ 兜底任务判不了「订单是否终态」

§4.2 写的是「锁定超过 N 分钟**且对应单据已终态**」。落地只能做到前半句：
账务域**不能依赖商城域**（`MallLedgerBoundaryTest` 盯着这条缝），这里看不到订单表。

于是阈值必须选得足够宽：商城订单自己的支付超时是 **30 分钟**
（`MallRedeemService.PAY_EXPIRE_MINUTES`），到点由 `mallOrderExpire` 走正常释放路径。
本任务默认 **120 分钟**，并且代码里有 **60 分钟硬下限** ——
配得比 30 分钟还短的话，它会去抢**活着的订单**手里的券，那不是兜底，是制造故障。

误放的后果是**可见**的，不是静默的：那一笔再来确认时匹配 0 行，`confirm` 返回失败并打 ERROR。

#### 🔴 试算：不可用的券也要返回

`CouponUnusableReason` 这个枚举存在本身就是一条产品决定。用户手里有券却在下单页
看不到它，第一反应是**系统坏了** —— 而真实原因往往只是「没到门槛」，
那一句话能省掉一次客服。筛掉券的实现不报错、不告警，只是让用户困惑，
所以永远不会有人去修它。

⚠️ 试算的形状和 §4.1 写的**不一样**：§4.1 说按 `deduct_target` 分组返回，
落地改成了**入参就要求指定抵扣对象**。一笔订单的应付本来就是确定的，
返回两组等于把「1 积分值多少钱」推给调用方，而调用方同样答不了 ——
那正是 §4.1 想避免的事，只是换了个地方发生。

#### 🔴 顺手修掉阶段 1 的一个坑：规则列不该有默认值

阶段 1 为了能在非空表上加 NOT NULL 列，给了默认值
（`discount_type DEFAULT 'FIXED'`、`discount_value DEFAULT 0` …）。
后果是：一张**没有规则**的券，在库里长得像一张**无门槛减 0 的现金券**——
正是阶段 2 注释里说要避免的东西。

代码那边确实留了 null，但 MyBatis-Plus 的默认字段策略把 null 字段整个从 INSERT 里
省掉，于是 MySQL 拿默认值填上：**代码的意图在库这一层被悄悄抹掉了**。
这类不一致最难查 —— 两边单独看都对。

改成可空之后，试算才分得开「没有规则」（`NO_RULE`）和「运营真配成了 0」。

**验证**：1018 个测试。真库用例验的是那三条 WHERE：两单抢同一张券只有一笔能成、
B 单确认不了 A 单锁的券、释放之后券还能被下一笔重新锁上。

| 不动（没有模板） | 1 | `XTYUJHUUI` 华为音乐年卡 —— 见下 |
| 不动（已经有规则） | 1 | `id=3601`，阶段 2 之后由真实发奖链路发的 |

#### 🔴 怎么认出「没有规则」的券：`discount_value = 0`

不是拍脑袋：`CouponTemplateService.validate` 要求 `discount_value > 0`，
所以**任何从模板发出来的券，抵扣值都不可能是 0**。库里那些 0 只可能来自阶段 1 的
DDL 默认值。

反过来说，`id=3601` 那张（13:06 由真实发奖链路发的，`discount_value=20.00`）
不在处理范围内 —— 那正是判据选对了的证据。

#### 🔴 只处理有模板的券编码，用 JOIN 不用 LEFT JOIN

`XTYUJHUUI`（华为音乐 音乐VIP 年卡）是一张**兑换凭证**，本来就没有「减多少」
这回事。作废它等于拿走用户一件真实的东西，而重发出来的还是一张没有规则的券。
同样的 JOIN 纪律见 §11.1。

#### 溯源

新券 `source_type='REISSUE'`、`source_biz_id=旧券 id`，
于是链路是 **新券 → 旧券 → 原始提案**，客服一路查得回去。

#### ⚠️ 顺带踩了一个时区坑

脚本里的 `NOW()` 比应用写进去的时间**早 8 小时**：MySQL 服务端跑在 UTC，
应用的连接串有 `forceConnectionTimeZoneToSession=true` 而临时的脚本连接没有。
248 张重发券的有效期因此整体短了 8 小时，靠一个订正脚本重算修回来。
教训已写进 `数据库SQL脚本/mysql/README.md`。

### 11.6 阶段 4 交付（2026-09-15）

**分水岭过了：券第一次真的被用掉了。**

| 产出 | 说明 |
|---|---|
| `CouponQueryApi` / `CouponWriteOffApi` | 契约<b>拆成只读与可写两个</b> |
| `CouponQueryApiService` / `CouponWriteOffApiService` | ledger 侧实现 |
| `CouponQueryInternalController` | 给网关的 HTTP 薄壳 |
| `t_mall_order` +`coupon_id`/`coupon_discount` | 订单记下用了哪张券、减了多少 |
| `MallRedeemService.applyCoupon` / `confirmCouponIfSettled` | 下单试算 → 锁定 → 确认 |
| `MallOrderCancelService.releaseCoupon` | 取消时和退积分一起放回去 |
| `/coupons` + `/coupons/trial` | C 端券包与下单选券 |
| `CouponWalletView.vue` + RedeemView 选券 | C 端页面，「我的」页有入口 |

#### 🔴 商城不能直接调 ledger，所以先有契约

`MallLedgerBoundaryTest` 一个字都不让商城认识 `solvela/ledger/` ——
目标形态是资产独立成服务，而券是资产。直接调今天完全跑得通，坏的是拆的那一天：
那些调用点要一个个找出来重写，而它们**不会有任何标记**。

契约拆成**两个**，不是一个带权限判断的大接口：

- `CouponQueryApi`（券包 + 试算，只读）—— 网关能用；
- `CouponWriteOffApi`（锁定/确认/释放）—— **网关那一侧连代理 bean 都没有**。

这样「网关不该拿到写能力」这件事由**类型系统**表达，而不是靠谁记得。
和 `AssetApi` / `AssetDebitApi` 完全一样的拆法。

#### 🔴 确认点是「资产结清」，不是「履约成功」

订单落成**待履约**的那一刻积分已经扣了、没有回头路，所以券在那时确认。

两种都是漏钱，方向相反：

| 如果 | 后果 |
|---|---|
| 等履约成功再确认 | 履约失败那条路**刻意不退积分**（「东西还欠着用户」），券却因为一直挂着锁定被兜底任务放回去 —— 积分扣了、折扣享了、券还在 |
| 履约失败时放券 | 用户拿到自相矛盾的结果：券回来了，积分没回来 |

所以 `MallFulfillService.settle` 的失败分支**两个都不动**，那是唯一自洽的选择。
真正会放券的是超时取消那条路，它同时退积分 —— 那一条才是「这单不算数」。

#### 🔴 退积分和放券的 bizRefId 规则**刚好相反**

- 退积分要用**不同**的（加 `:REFUND` 后缀），否则被 `uk(biz_ref_id, asset_type)`
  当成重复提交挡掉，表现是「退款静默不生效」；
- 放券要用**一样**的（订单号本身），因为条件更新是 `WHERE locked_biz_id = ?`，
  传了别的单号什么都不会发生。

两条规则相反、且都**静默失败**，所以 `MallOrderCancelServiceTest` 各钉了一条用例。

#### 🔴 抵扣额由服务端重新试算，客户端连这个字段都没有

下单请求里只有「用哪张券」。让客户端报「减多少」，就是一个可以直接刷钱的口子，
而且不会有任何报错。前端那一侧也**没有**重算规则 ——
两份算法（门槛、封顶、不能超过应付、向下取整）迟早不一致，
而不一致的表现是「页面显示减 30，实际只减了 20」。

#### ⚠️ 只做「券抵扣积分」，`POINTS_CASH` 暂不支持用券

`POINTS_CASH` 落的是**待支付**单，而支付回调至今一行代码都没有 ——
没有任何地方能把券从「锁定中」推到「已使用」。放开的话表现是：
用户付了钱，券被兜底任务放回券包，这一单等于白给了折扣。

`deduct_target = CASH` 的券同理，试算入参写死 `SCORE`。那些券会带着
`DEDUCT_TARGET_MISMATCH` 出现在**不可用列表**里 —— 用户仍然看得见它们，只是点不动。
这正是 §6.3 那条排序。

#### 🔴 C 端：用不了的券也要显示

下单页把不可用的券**置灰列出来 + 一句原因**，券包页把失效的券压暗但不隐藏。
用户手里有券却看不到它，第一反应是系统坏了 —— 而真实原因往往只是「没到门槛」。

规则那句人话由**服务端**拼好下发（`ruleText`），端上不重拼：
组合规则会变，各拼一份的结果是用户在两个地方看到同一张券的不同规则。

⚠️「我的」页上加了券包入口，并把它纳进了 `mine-entries.spec.ts` ——
那条测试对应的正是消息中心那次「路由页面接口全做完了却没有任何地方能点进去」。

**验证**：1030 个后端测试 + 184 个前端测试。新增的用例钉住的都是会漏钱的点：
抵扣额由谁算、锁券在扣款之前、落单即确认、券锁不上要回滚、取消时两样一起退。

## 12. 与大厂券系统的对照

大厂的券系统通常是四层：**券模板**（规则）→ **券批次**（发多少、预算、限领）→
**券实例**（用户手上那张）→ **核销记录**（谁、哪笔、减了多少）。核销走 TCC。

但**大厂真正烧钱的五个难点，这个项目结构上有四个不存在**：

| 大厂的难点 | 为什么难 | 本项目 |
|---|---|---|
| **金额分摊** | 一单多商品，券减的钱要摊到每件上 —— 退款按比例退、发票按实收、财务按商品算收入 | ❌ **不存在**。`mall.sql` 写了两遍「一单一 SKU，不做订单-订单项两级」 |
| **最优券 / 凑单** | 多券叠加是组合优化问题 | ❌ **不存在**。一单一券，遍历取最大（见 §4.1） |
| **商品池 / 标签体系** | 商品几十万，券不能绑商品 id 列表 | ❌ **不需要**。商品个位数，`t_mall_category` 的类目树够用 |
| **高并发领券** | 热门券几万人同时抢，要 Redis 预扣 + DB 兜底 | ❌ **不存在**。券是活动/任务/人工**发**的，不是抢的 |
| **对账** | 发、用、退、过期四条流水要对得上 | ✅ **真需要** —— 这正是补 §5.3 的原因 |

而「券批次 / 预算」那一层**本项目已经有了**，只是叫别的名字：
`t_promotion_config` 按 `prize_type = COUPON` 控着 `total_quota` / `used_quota`，
发券走提案链路时由 `AssetDispatchEngine.deductBudget` 扣。
**不要再建一张券批次表** —— 两个预算口径并存，迟早对不上。

### 12.1 该抄的

- **核销流水 + 实际抵扣额**（§5.3）—— 已补；
- **适用范围用类目，不用商品 id 列表** —— 后者每加一个商品就要改所有券，是维护地狱；
- **「为什么不可用」要返回给端上**（§8）—— 用户手里有券却在下单页看不见，
  第一反应是系统坏了。

### 12.2 不该抄的

- **多券叠加 / 凑单** —— `mall.sql` 明确排除。它会立刻带出「门槛按原价还是折后价」
  这类没有标准答案的产品问题（见 §4.1 ⑤），而每一个都能造出资损；
- **规则 DSL / 规则引擎** —— 这个项目虽然有 QLExpress，但券的维度就那四五个。
  上引擎是把「改一行配置」变成「改一段代码」；
- **独立的券批次表** —— 见上，`t_promotion_config` 已经在管了。

### 12.3 一句话

用大厂标准做，这个方案**不会变复杂，反而更清楚了** —— 因为大厂那套里真正难的
几件事这个项目都没有。补的就是核销流水和实际抵扣额两个洞，它们不大，
但**不补的话会在上线三个月后对账时才发现，那时候券已经发出去几十万张**。

## 附：另外两件相关的事（不在本方案范围）

**积分过期**。目前 `t_member_wallet` 只有单一 `balance`，没有批次，积分永不过期 —— 财务上是只增不减的负债池。

做法上倾向于**「到期生成一条过期流水」**而不是静默扣减：`t_member_asset_transaction` 已经有 `transaction_type` 与 `biz_type`，加一个 `SCORE_EXPIRE` 即可，用户在账单里看得到「过期扣除 X 分」。有流水，余额的减少才有凭据。

⚠️ 但**流水解决的是「看得见」，批次解决的是「扣谁」** —— 要按「先进先出、按发放批次过期」就必须有批次表。两件事互补，不能只做一半。而且它**越晚做越贵**：存量余额没有批次归属，上线要做一次全量拆分。

**POINTS_CASH 的假支付**。库里 2 个商品配成了积分+现金，而没有任何代码把订单从 `UNPAID(0)` 推到 `PENDING(10)` —— 用户下单必被超时取消。先搞一个假支付（一个把 0 推到 10 的内部接口 + 管理端手动标记已支付）就能让这条路通，同时也是 §6.3 现金抵扣的前置。
