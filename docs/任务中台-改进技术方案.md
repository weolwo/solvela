## 0. 一句话结论

**任务模块的配置态是完整的，运行态一行代码都没有。**
当前最紧要的不是调整分类维度，而是补上「事件进来 → 推进进度 → 达标发奖」这条链路；
分类问题里只有一个是**阻塞性**的（`trigger_event` 枚举化），其余可以增量演进。

## 1. 现状盘点（读码实测）

### 1.1 已经有的

| 环节 | 状态 |
|---|---|
| 任务模板设计器（双 Monaco：`rule_script` + `ui_schema`） | ✅ 完整 |
| 任务配置向导（5 步 + 草稿 + 离开拦截） | ✅ 完整 |
| `TaskConfigService.wizardSubmit` 主子表同事务落库 | ✅ 完整，且按 `ui_schema` 反向校验参数 |
| `t_task_record` 表设计 | ✅ **设计得相当到位**，见 §1.3 |
| 内嵌进活动创建向导 | ✅ 已完成（`embedded` 契约） |

### 1.2 🔴 完全没有的

| 缺口 | 实测证据 |
|---|---|
| **`trigger_event` 没有任何消费方** | 全工程 `grep triggerEvent` 只命中实体与 Form/VO，**零处业务代码** |
| **`rule_script` 从未被执行** | 全工程 `grep ruleScript` 在业务代码里**零命中**；QLExpress 引擎只被彩票模块用了 |
| **任务进度无法推进** | `TaskRecordService` 是代码生成器裸产物，只有 CRUD；`add()` 靠人手工调接口插一条 |
| **达标 → 发奖不通** | 没有任何地方 `publishEvent(UserPrizeEvent)`，而抽奖/彩票都是这么接派奖链路的 |

**所以现在的状态是**：运营能在后台把任务配出来、落进库，但**没有任何东西会让它动起来**。
`t_task_config` 里那 3 条 `task_name='ggg'` 的测试数据，就是配置态跑通、运行态从未存在的证据。

### 1.3 表设计里已经做对的地方（不要动它）

`t_task_record` 有三个设计点是对的，后续实现必须沿用而不是绕开：

```sql
period_key      varchar(32) NOT NULL DEFAULT 'NONE'  -- 业务期数：NONE / 20260402
UNIQUE KEY uk_t_tsk_rec_mbr_cfg_prd (member_name, task_config_id, period_key)
rule_snapshot   json NOT NULL   -- 接取时的规则快照
prize_snapshot  json NOT NULL   -- 接取时的奖励快照
```

- **`period_key` + 唯一索引 = 周期幂等**。「每日签到」每天一条记录，靠 `period_key='20260402'` 天然隔离，
  重复领取由唯一索引挡住 —— 不需要额外的分布式锁。
- **两个快照 = 规则变更不影响进行中的任务**。运营改了任务规则，已接取的用户仍按接取时的规则算，
  这是营销系统的通用要求（抽奖的 `DrawPrizeSnapshot`、彩票的奖级快照都是同一思路）。

## 2. 三个分类维度的评估

### 2.1 `task_type`（SIMPLE / COUNT / AMOUNT）—— ✅ 保留，它是策略工厂的正确锚点

这三类区分的是**进度如何累积**，也正是唯一真正需要不同 Java 代码路径的维度：

| 类型 | 语义 | `current_metric` 的推进方式 |
|---|---|---|
| `SIMPLE` | 一次性达成 | 0 → 1 |
| `COUNT` | 计次累加 | 每次事件 +1 |
| `AMOUNT` | 计额累加 | 每次事件 + `event.amount` |

**🔴 建议补第四类 `STREAK`（连续型）。**
「连续签到 7 天」与「累计签到 7 天」是完全不同的规则 —— 前者断签清零，`COUNT` 表达不了。
而连续签到恰恰是任务玩法里最常见的一种，不补它就只能靠 `rule_script` 硬写，
等于把最主流的玩法推给了兜底通道。

`STREAK` 需要在 `progress_data` 里额外记 `lastHitDate`，判断本次事件是否与上次连续。

### 2.2 🔴 `trigger_event` —— 阻塞性问题：枚举化与「零前端改动」直接冲突

**现状**：它是前端常量数组 + DDL 注释里的固定枚举，5 个值写死。

```js
// task-wizard-const.js
export const TRIGGER_EVENT_OPTIONS = [
  { value: 'DAILY_SIGN', label: 'DAILY_SIGN（签到）' },
  ...
];
```

**问题**：加一个「分享商品」事件，要改前端常量、改 DDL 注释、可能还要加后端枚举 —— 这与
「新增任务模板前端不需要新增页面」的目标**正面冲突**。事件本质是**开放集合**，不该用封闭枚举表达。

**建议：改为事件注册表 `t_task_event`。**

```sql
event_code     varchar(64)  -- DAILY_SIGN / ORDER_PAID / GOODS_SHARE
event_name     varchar(64)  -- 展示名：签到 / 支付成功 / 分享商品
metric_source  varchar(32)  -- 该事件的计量来源：NONE(计次) / amount 字段名(计额)
payload_schema json         -- 该事件会带哪些字段，供模板设计器提示与校验
status         tinyint
```

加事件 = **加一行数据 + 上游埋点**，前端从 `/taskEvent/optionList` 拉，零代码改动。
`payload_schema` 还顺带解决一个当前无解的问题：模板作者在写 `rule_script` 时，
**根本不知道这个事件会带来哪些字段**。

### 2.3 `task_group` / `target_audience` —— ⚠️ 非阻塞，建议先留着

这两个与上面两个**不是一类东西**，不该并列讨论：

| 字段 | 本质 | 问题 | 建议 |
|---|---|---|---|
| `task_group` | C 端分栏的**展示标签** | 硬编码 4 个值，运营加「周年庆」要改代码 | 走项目已有的 `t_dict` 字典表 |
| `target_audience` | **人群圈选** | 3 个枚举覆盖不了「注册满30天且消费过3次」 | 将来换成 `crowd_id` 接人群包 |

**都不阻塞主线，建议 P2 之后再动。**
特别是 `target_audience`：在没有人群/标签系统之前，换成 `crowd_id` 也没有东西可接，
现在改属于为想象中的需求做设计。

## 3. 🔴 核心设计：三层分离

### 3.1 问题：`ui_schema` 解决了「长什么样」，没解决「怎么算」

当前设计里，「怎么算」**全部塞进 `rule_script`（QLExpress）**。这带来两个后果：

1. **每个新模板都要写一段脚本** —— 这不是「零开发」，只是把开发从前端挪到了脚本；
2. **脚本是自由文本，无法被策略工厂分类**，也没法静态校验、没法复用、没法测试。

### 3.2 建议的三层

```
① task_type（枚举，少而稳，4 个）
      ↓ 决定用哪个 Java 策略类
   SIMPLE / COUNT / AMOUNT / STREAK

② rule_config（JSON，由 ui_schema 驱动生成）
      ↓ 喂给策略类的参数
   { "targetCount": 7, "resetOnMiss": true, "minAmount": 100 }

③ rule_script（QLExpress，仅兜底）
      ↓ 前两层表达不了的极端 case 才用
```

**判据：新增一个玩法时，改动落在哪一层？**

| 玩法 | 落点 | 是否需要 Java 改动 |
|---|---|---|
| 累计签到 7 天送积分 | ② `{targetCount:7}` | ❌ 不需要 |
| 连续签到 7 天送积分 | ② `{targetCount:7, resetOnMiss:true}` | ❌ 不需要 |
| 累计消费满 500 | ② `{targetAmount:500}` | ❌ 不需要 |
| 「邀请 3 个新用户且他们都下过单」 | ③ 脚本 | ✅ 写脚本，不改 Java |
| 需要新的**进度累积方式** | ① 加策略类 | ✅ 改 Java |

**⚠️ 关键约束：`task_type` 必须少而稳。**
它是策略工厂的 key。一旦有人提出「加个 task_type 来支持新玩法」，那就是设计跑偏的信号 ——
新玩法应该体现在 ②，不是 ①。四个类型能覆盖绝大多数场景。

### 3.3 策略工厂的写法

```java
public interface TaskProgressStrategy {

    /** 本策略负责哪种 task_type */
    TaskTypeEnum supportType();

    /** 事件到达时如何推进进度，返回推进后的 metric */
    BigDecimal advance(TaskRecord record, TaskEvent event, JsonNode ruleConfig);

    /** 是否已达标 */
    boolean isCompleted(TaskRecord record, JsonNode ruleConfig);
}
```

**⚠️ 装配必须用 `List` 注入 + 各实现自报 `supportType()`，不要 `Map<TaskTypeEnum, Strategy>`**
—— 铁律 14，本项目已因「枚举键 Map 用字符串 get」踩过三次静默失效
（`GlobalEventDispatcher` / `PrizeStrategyFactory` / `AssetStrategyFactory`）。

## 4. 运行态链路设计

### 4.1 主链路

```
上游埋点 → TaskEventService.handle(event)
   ↓ 1. 按 event_code + status 查出所有订阅该事件的 t_task_config
   ↓ 2. 人群/时间/频次过滤
   ↓ 3. 取或建 t_task_record（period_key 决定周期，唯一索引兜底幂等）
   ↓ 4. TaskProgressStrategy.advance() 推进 current_metric
   ↓ 5. isCompleted() 判定 → status=1 已完成
   ↓ 6. 按 t_task_prize_mapping 的阶梯发奖 → publishEvent(UserPrizeEvent)
                                              ↑ 复用抽奖/彩票已验证的派奖链路
```

**第 6 步是关键的复用点**：派奖链路（consumer → risk → ledger）已经被抽奖压测与彩票 P4 验证过，
任务模块**不要另造一套**，直接发同样的 `UserPrizeEvent`，`sourceBizId` 用任务记录 id 做幂等键。

### 4.2 🔴 必须避开的三个坑（都是本项目已经踩过的）

**① `@Transactional` 不能被同类自调用**（铁律 11）。
事件处理里「循环处理多个匹配到的任务配置」，每个任务的推进要独立事务 ——
必须拆到独立 Bean，否则注解静默失效，表现是「进度加了但发奖没触发」。

**② 派奖必须在事务提交后**。
`UserPrizeEvent` 走 `@TransactionalEventListener(AFTER_COMMIT)`，
**没有事务上下文事件根本不会投递** —— 彩票派奖那次就是这么表现为「标记已投递但下游一条没收到」。

**③ 写库前先查 NOT NULL 无默认值的列**（铁律：已复发 5 次）。
`t_task_record` 的 `valid_start_time` / `valid_end_time` / `rule_snapshot` / `prize_snapshot`
**都是 NOT NULL 且无默认值**，建记录时必须全部赋值，否则 MySQL 严格模式直接拒。

```sql
SELECT column_name FROM information_schema.columns
WHERE table_schema='smart_admin_v3' AND table_name='t_task_record'
  AND is_nullable='NO' AND column_default IS NULL AND extra NOT LIKE '%auto_increment%';
```

## 5. 关于 QLExpress 的两张表（承接远景规划）

你提到脚本要拆成**脚本表 + 引用表**。这个方向与本方案完全兼容，且现有的
`scriptengine` 模块已经把地基打好了 —— `ScriptEngine.execute(ExecutableScript, EngineContext)`
本来就是「脚本内容 + 上下文 → 结果」的抽象，**它不关心脚本从哪来**。

建议的两张表：

```sql
-- ① 脚本表：脚本本体与版本
t_script
  script_code   varchar(32)   -- 业务编码（铁律 8，建议前缀 S）
  script_name   varchar(128)
  script_type   varchar(32)   -- TASK_RULE / PRIZE_RULE / RISK_RULE …
  content       text
  version       int           -- 每次保存 +1，旧版本保留
  status        tinyint

-- ② 引用表：谁在用这个脚本
t_script_ref
  script_code   varchar(32)
  ref_biz_type  varchar(32)   -- TASK_TEMPLATE / TASK_CONFIG / …
  ref_biz_id    varchar(64)
  UNIQUE KEY (script_code, ref_biz_type, ref_biz_id)
```

**引用表的真正价值不是「查谁在用」，而是让脚本能被安全地改。**
没有引用表时，改一段脚本等于在盲改 —— 不知道会影响多少个正在跑的任务。
有了它就能做两件事：① 改动前提示影响面；② 禁止删除仍被引用的脚本
（与活动/奖品的删除守卫是同一个模式）。

**⚠️ 但建议这两张表放在任务运行态跑通之后再做。**
理由：现在 `rule_script` 一次都没被执行过，脚本管理是在为一个尚未验证的通道做基建。
先让第 ③ 层真正跑起来一两个 case，才知道脚本表需要哪些字段
（比如是否需要 `param_schema`、是否需要灰度版本）。

## 6. 分阶段实施

### P0：策略工厂 + 事件入口（让最简单的链路真的跑通）

| # | 内容 |
|---|---|
| 1 | `TaskTypeEnum`（SIMPLE/COUNT/AMOUNT/STREAK），实现 `BaseEnum`，字段名 `value`（铁律 12） |
| 2 | `TaskProgressStrategy` 接口 + 4 个实现，`List` 注入自报（铁律 14） |
| 3 | `TaskEventService.handle()`：查订阅 → 过滤 → 取/建记录 → 推进 → 判定 |
| 4 | 每个任务的推进拆到独立 Bean，避免 `@Transactional` 自调用（铁律 11） |
| 5 | 达标后 `publishEvent(UserPrizeEvent)`，复用既有派奖链路 |

`t_task_record.current_metric` 依次为 1/2/3、第 3 次 `status=1`、
`t_prize_log` 出现 1 条、钱包积分 +10。**第 4 次事件不再重复发奖。**

`t_task_event` + `/taskEvent/optionList`，前端 `TRIGGER_EVENT_OPTIONS` 改为接口拉取。
**验收**：新增一个事件只改数据，前端零改动即可在向导里选到。
