## 0. 一句话结论

**任务模块的配置态是完整的，运行态一行代码都没有。**
当前最紧要的不是调整分类维度，而是补上「事件进来 → 推进进度 → 达标发奖」这条链路；
分类问题里只有一个是**阻塞性**的（`trigger_event` 枚举化），其余可以增量演进。

**v2 追加一句**：这条链路**不能先写通再补幂等**。
`t_prize_log.uk_external_biz` 是单列全局唯一索引、且 `PrizeDispatchHandler` 靠捕获
`DuplicateKeyException` 做防重（`PrizeDispatchHandler:61`）——
幂等键设计错了不会报错，只会**少发奖**，而且是在日志里悄悄少发。
所以 §4.3 的幂等键格式必须在写第一行发奖代码之前定死。

## 1. 现状盘点（读码实测）

### 1.1 已经有的

| 环节 | 状态 |
|---|---|
| 任务模板设计器（双 Monaco：`rule_script` + `ui_schema`） | ✅ 完整 |
| 任务配置向导（5 步 + 草稿 + 离开拦截） | ✅ 完整 |
| `TaskConfigService.wizardSubmit` 主子表同事务落库 | ✅ 完整，且按 `ui_schema` 反向校验参数 |
| `t_task_record` 表设计 | ✅ **设计得相当到位**，见 §1.3 |
| 内嵌进活动创建向导 | ✅ 已完成（`embedded` 契约） |

### 1.2 🔴 完全没有的

| 缺口 | 实测证据 |
|---|---|
| **`trigger_event` 没有任何消费方** | 全工程 `grep triggerEvent` 只命中实体与 Form/VO，**零处业务代码** |
| **`rule_script` 从未被执行** | 全工程 `grep ruleScript` 在业务代码里**零命中**；QLExpress 引擎只被彩票模块用了 |
| **任务进度无法推进** | `TaskRecordService` 是代码生成器裸产物，只有 CRUD；`add()` 靠人手工调接口插一条 |
| **达标 → 发奖不通** | 没有任何地方 `publishEvent(UserPrizeEvent)`，而抽奖/彩票都是这么接派奖链路的 |

**所以现在的状态是**：运营能在后台把任务配出来、落进库，但**没有任何东西会让它动起来**。
`t_task_config` 里那 3 条 `task_name='ggg'` 的测试数据，就是配置态跑通、运行态从未存在的证据。

### 1.3 表设计里已经做对的地方（不要动它）

`t_task_record` 有三个设计点是对的，后续实现必须沿用而不是绕开：

```sql
period_key      varchar(32) NOT NULL DEFAULT 'NONE'  -- 业务期数：NONE / 20260402
UNIQUE KEY uk_t_tsk_rec_mbr_cfg_prd (member_name, task_config_id, period_key)
rule_snapshot   json NOT NULL   -- 接取时的规则快照
prize_snapshot  json NOT NULL   -- 接取时的奖励快照
```

- **`period_key` + 唯一索引 = 周期幂等**。「每日签到」每天一条记录，靠 `period_key='20260402'` 天然隔离，
  重复领取由唯一索引挡住 —— 不需要额外的分布式锁。
- **两个快照 = 规则变更不影响进行中的任务**。运营改了任务规则，已接取的用户仍按接取时的规则算，
  这是营销系统的通用要求（抽奖的 `DrawPrizeSnapshot`、彩票的奖级快照都是同一思路）。

## 2. 三个分类维度的评估

### 2.1 `task_type`（SIMPLE / COUNT / AMOUNT）—— ✅ 保留，它是策略工厂的正确锚点

这三类区分的是**进度如何累积**，也正是唯一真正需要不同 Java 代码路径的维度：

| 类型 | 语义 | `current_metric` 的推进方式 |
|---|---|---|
| `SIMPLE` | 一次性达成 | 0 → 1 |
| `COUNT` | 计次累加 | 每次事件 +1 |
| `AMOUNT` | 计额累加 | 每次事件 + `event.amount` |

**🔴 建议补第四类 `STREAK`（连续型）。**
「连续签到 7 天」与「累计签到 7 天」是完全不同的规则 —— 前者断签清零，`COUNT` 表达不了。
而连续签到恰恰是任务玩法里最常见的一种，不补它就只能靠 `rule_script` 硬写，
等于把最主流的玩法推给了兜底通道。

`STREAK` 需要在 `progress_data` 里额外记 `lastHitDate`，判断本次事件是否与上次连续。

### 2.1.1 🔴 v2 新增：`STREAK` 与 `period_key` 唯一索引存在硬冲突

v1 上面那句「在 `progress_data` 里额外记 `lastHitDate`」**低估了问题** ——
它不只是多存一个字段，它**改变了 `period_key` 的用法**，而 `period_key` 上有唯一索引：

```sql
UNIQUE KEY uk_t_tsk_rec_mbr_cfg_prd (member_name, task_config_id, period_key)
```

以「连续签到 7 天」为例，两条路都走不通：

| `period_key` 取法 | 后果 |
|---|---|
| `'20260402'`（按天） | 每天新建一条记录，`current_metric` **永远是 1**，「已连续 5 天」这个数**没有地方存** |
| `'NONE'`（整周期一条） | `current_metric` 能累加到 7 ✅，但唯一索引不再承担日内幂等，且 `limit_type=DAILY` 的语义落空 |

**结论：`STREAK` 必须走 `period_key='NONE'`**，并且：

- **日内重复签到的幂等改由 §4.5 的事件流水表承担**，不能靠读 `progress_data.lastHitDate` 再判
  —— 那正是 §4.4 要消灭的读-改-写；
- `STREAK` 因此是**四个类型里唯一不使用周期分片的**，与 `COUNT` 是两套周期模型。
  写策略实现时不要试图统一，`resolvePeriodKey()` 里对 `STREAK` 直接返回 `NONE` 并注释清楚原因。

**`STREAK` 的 `rule_config` 契约**（评审建议，采纳）：

```json
{ "targetCount": 7, "periodUnit": "DAY", "tolerance": 0 }
```

`tolerance` = 允许断档的次数（0 = 断一次即清零）。`advance()` 里比较本次事件周期与
`lastHitDate` 的差值：差值 <= `tolerance + 1` 则 `+1`，否则 `current_metric` 归零再 `+1`。

> ⚠️ 「归零再 +1」而不是「归零」—— 断档当天本身也是有效的一次。
> 这是连续型任务最常见的 off-by-one，写单测时第一个要覆盖的就是它。

### 2.2 🔴 `trigger_event` —— 阻塞性问题：枚举化与「零前端改动」直接冲突

**现状**：它是前端常量数组 + DDL 注释里的固定枚举，5 个值写死。

```js
// task-wizard-const.js
export const TRIGGER_EVENT_OPTIONS = [
  { value: 'DAILY_SIGN', label: 'DAILY_SIGN（签到）' },
  ...
];
```

**问题**：加一个「分享商品」事件，要改前端常量、改 DDL 注释、可能还要加后端枚举 —— 这与
「新增任务模板前端不需要新增页面」的目标**正面冲突**。事件本质是**开放集合**，不该用封闭枚举表达。

**建议：改为事件注册表 `t_task_event`。**

```sql
event_code         varchar(64)  -- DAILY_SIGN / ORDER_PAID / GOODS_SHARE
event_name         varchar(64)  -- 展示名：签到 / 支付成功 / 分享商品
metric_source      varchar(32)  -- 该事件的计量来源：NONE(计次) / amount 字段名(计额)
payload_schema     json         -- 该事件会带哪些字段，供模板设计器提示与校验
-- ↓ v2 新增三列
biz_id_required    tinyint      -- 上游是否必须带幂等单号：1-必须(ORDER_PAID) / 0-可用 period_key 兜底(DAILY_SIGN)
is_high_frequency  tinyint      -- 是否高频事件(PAGE_VIEW)：先建字段，路由优化不在本期实现，理由见下
discard_log_flag   tinyint      -- 是否记录「被丢弃」流水：高频事件必须关，否则写爆流水表（见 §4.5）
status             tinyint
```

加事件 = **加一行数据 + 上游埋点**，前端从 `/taskEvent/optionList` 拉，零代码改动。
`payload_schema` 还顺带解决一个当前无解的问题：模板作者在写 `rule_script` 时，
**根本不知道这个事件会带来哪些字段**。

**v2 追加：`biz_id_required` 是把口头约定变成表里的强制契约。**
§4.5 的事件幂等完全依赖上游传 `eventBizId`（订单号之类）。这不是「建议上游最好带上」，
而是**接入这个事件的前提条件**。写进表里、入口处按此列强校验，缺失直接拒绝并落丢弃流水，
比写在接口文档里靠谱得多。`DAILY_SIGN` 这种天然无单号的事件置 0，用 `period_key` 兜底。

**⚠️ `is_high_frequency` 本期只建字段、不实现路由优化。**
评审建议对高频事件先走 Redis 判定「该用户有没有接这个任务」、没接就在内存丢弃，方向是对的。
但本项目当前**连一个真实事件源都没有**（无 MQ、无上游埋点），`PAGE_VIEW` 目前是纸面上的。
缓存判定要配套一整套缓存一致性与任务配置变更失效逻辑，**没有真实流量剖面就是凭空设计**。
建字段的成本近乎零（将来改表比改字段贵），实现留到有流量之后。

### 2.3 `task_group` / `target_audience` —— ⚠️ 非阻塞，建议先留着

这两个与上面两个**不是一类东西**，不该并列讨论：

| 字段 | 本质 | 问题 | 建议 |
|---|---|---|---|
| `task_group` | C 端分栏的**展示标签** | 硬编码 4 个值，运营加「周年庆」要改代码 | 走项目已有的 `t_dict` 字典表 |
| `target_audience` | **人群圈选** | 3 个枚举覆盖不了「注册满30天且消费过3次」 | 将来换成 `crowd_id` 接人群包 |

**都不阻塞主线，建议 P2 之后再动。**
特别是 `target_audience`：在没有人群/标签系统之前，换成 `crowd_id` 也没有东西可接，
现在改属于为想象中的需求做设计。

## 3. 🔴 核心设计：三层分离

### 3.1 问题：`ui_schema` 解决了「长什么样」，没解决「怎么算」

当前设计里，「怎么算」**全部塞进 `rule_script`（QLExpress）**。这带来两个后果：

1. **每个新模板都要写一段脚本** —— 这不是「零开发」，只是把开发从前端挪到了脚本；
2. **脚本是自由文本，无法被策略工厂分类**，也没法静态校验、没法复用、没法测试。

### 3.2 建议的三层

```
① task_type（枚举，少而稳，4 个）
      ↓ 决定用哪个 Java 策略类
   SIMPLE / COUNT / AMOUNT / STREAK

② rule_config（JSON，由 ui_schema 驱动生成）
      ↓ 喂给策略类的参数
   { "targetCount": 7, "resetOnMiss": true, "minAmount": 100 }

③ rule_script（QLExpress，仅兜底）
      ↓ 前两层表达不了的极端 case 才用
```

**判据：新增一个玩法时，改动落在哪一层？**

| 玩法 | 落点 | 是否需要 Java 改动 |
|---|---|---|
| 累计签到 7 天送积分 | ② `{targetCount:7}` | ❌ 不需要 |
| 连续签到 7 天送积分 | ② `{targetCount:7, resetOnMiss:true}` | ❌ 不需要 |
| 累计消费满 500 | ② `{targetAmount:500}` | ❌ 不需要 |
| 「邀请 3 个新用户且他们都下过单」 | ③ 脚本 | ✅ 写脚本，不改 Java |
| 需要新的**进度累积方式** | ① 加策略类 | ✅ 改 Java |

**⚠️ 关键约束：`task_type` 必须少而稳。**
它是策略工厂的 key。一旦有人提出「加个 task_type 来支持新玩法」，那就是设计跑偏的信号 ——
新玩法应该体现在 ②，不是 ①。四个类型能覆盖绝大多数场景。

### 3.3 策略工厂的写法

```java
public interface TaskProgressStrategy {

    /** 本策略负责哪种 task_type */
    TaskTypeEnum supportType();

    /** 事件到达时如何推进进度，返回推进后的 metric */
    BigDecimal advance(TaskRecord record, TaskEvent event, JsonNode ruleConfig);

    /** 是否已达标 */
    boolean isCompleted(TaskRecord record, JsonNode ruleConfig);
}
```

**⚠️ 装配必须用 `List` 注入 + 各实现自报 `supportType()`，不要 `Map<TaskTypeEnum, Strategy>`**
—— 铁律 14，本项目已因「枚举键 Map 用字符串 get」踩过三次静默失效
（`GlobalEventDispatcher` / `PrizeStrategyFactory` / `AssetStrategyFactory`）。

## 4. 运行态链路设计

### 4.1 主链路

```
上游埋点 → TaskEventService.handle(event)
   ↓ 1. 按 event_code + status 查出所有订阅该事件的 t_task_config
   ↓ 2. 人群/时间/频次过滤
   ↓ 3. 取或建 t_task_record（period_key 决定周期，唯一索引兜底幂等）
   ↓ 4. TaskProgressStrategy.advance() 推进 current_metric
   ↓ 5. isCompleted() 判定 → status=1 已完成
   ↓ 6. 按 t_task_prize_mapping 的阶梯发奖 → publishEvent(UserPrizeEvent)
                                              ↑ 复用抽奖/彩票已验证的派奖链路
```

**第 6 步是关键的复用点**：派奖链路（consumer → risk → ledger）已经被抽奖压测与彩票 P4 验证过，
任务模块**不要另造一套**，直接发同样的 `UserPrizeEvent`，`sourceBizId` 用任务记录 id 做幂等键。

### 4.2 🔴 必须避开的三个坑（都是本项目已经踩过的）

**① `@Transactional` 不能被同类自调用**（铁律 11）。
事件处理里「循环处理多个匹配到的任务配置」，每个任务的推进要独立事务 ——
必须拆到独立 Bean，否则注解静默失效，表现是「进度加了但发奖没触发」。

**② 派奖必须在事务提交后**。
`UserPrizeEvent` 走 `@TransactionalEventListener(AFTER_COMMIT)`，
**没有事务上下文事件根本不会投递** —— 彩票派奖那次就是这么表现为「标记已投递但下游一条没收到」。

**③ 写库前先查 NOT NULL 无默认值的列**（铁律：已复发 5 次）。
`t_task_record` 的 `valid_start_time` / `valid_end_time` / `rule_snapshot` / `prize_snapshot`
**都是 NOT NULL 且无默认值**，建记录时必须全部赋值，否则 MySQL 严格模式直接拒。

```sql
SELECT column_name FROM information_schema.columns
WHERE table_schema='smart_admin_v3' AND table_name='t_task_record'
  AND is_nullable='NO' AND column_default IS NULL AND extra NOT LIKE '%auto_increment%';
```

### 4.3 🔴 幂等键：阶梯发奖会撞唯一索引，第二档被静默吞掉

**这是 v2 发现的最严重问题，且是零并发、单线程下必现的。**

v1 §4.1 写「`sourceBizId` 用任务记录 id 做幂等键」。跟着代码走一遍就会发现它错在哪：

```
UserPrizeEvent.sourceBizId
  → PrizeDispatchHandler.buildPrizeLog():204   log.setExternalBizNo(event.getSourceBizId())
  → prizeLogService.save(prizeLog)             PrizeDispatchHandler:60
  → t_prize_log 的 UNIQUE KEY uk_external_biz (external_biz_no)   ← 单列、全局唯一
  → 撞了就 catch (DuplicateKeyException) { log.warn(...); return; }   PrizeDispatchHandler:61-63
```

而任务**天然支持阶梯奖励**：

```sql
-- t_task_prize_mapping
UNIQUE KEY uk_task_stage (task_config_id, stage_level)   -- stage_level: 1, 2, 3...
```

前端还有专门的 `PrizeLadderBuilder.vue` 在配它。于是：

> 同一条任务记录达到第 1 档发一次奖、达到第 2 档再发一次 →
> 两次 `external_biz_no` **都等于 recordId** → 第二档撞唯一索引 →
> **被防重逻辑当成「重复派发」静默丢弃**。

致命之处在于 `PrizeDispatchHandler` 的跨系统防重**就是**靠捕获这个异常做的
（`task.sql:242` 的注释原话：「缺了这个索引防重就是空转」）。也就是说，
**防重机制会正确地把一个合法的第二档奖品判成重复投递**，不抛异常、不落失败记录，
只在日志里留一行 `warn`。运营侧表现是「用户只收到第一档奖励」，客诉直接来。

#### 修法：幂等键必须带档位

```java
/** 任务发奖的跨域幂等键：记录ID + 档位。缺了档位，阶梯任务的第二档起会被防重逻辑吃掉 */
public static String buildSourceBizId(Long recordId, Integer stageLevel) {
    return recordId + ":" + stageLevel;
}
```

对应到两张表的唯一索引，都能对上：

| 表 | 唯一索引 | 传入值 |
|---|---|---|
| `t_prize_log` | `uk_external_biz (external_biz_no)` | `"1024:2"` |
| `t_proposal_record` | `uk_prop_source (source_type, asset_type, source_biz_id)` | `('TASK', 'SCORE', "1024:2")` |

`external_biz_no` 是 `varchar(128)`、`source_biz_id` 是 `varchar(64)`，长度都够。

#### 🔴 不要为发奖再造一层防重

一个很容易犯的错是：既然要做事件流水表（§4.5），顺手也给发奖做一张防重表。**不要。**
`t_prize_log.uk_external_biz` 已经是这层防重，再加一层只会有两个后果：
① 两处判据不一致时谁也说不清哪个对；② 交接文档已明确记过「基于异常的静默去重会掩盖真问题」，
再叠一层只会让掩盖更深。**这里要修的是键的格式，不是防重的层数。**

#### 单测判据（P0 必须覆盖）

同一 `recordId` 连发 stage=1 与 stage=2 两次 `UserPrizeEvent`，
`t_prize_log` 必须**有 2 行**；重投 stage=2 时必须**仍是 2 行**。
v1 的验收判据是单档任务，跑过了也证明不了这一条 —— 见 §4.8。

### 4.4 🔴 进度并发推进：用条件更新原子累加，不用乐观锁

**问题属实**：`t_task_record` 的 DDL 里**确实没有 `version` 列**（`task.sql:148-175` 核对过）。
两个 `ORDER_PAID` 几乎同时到达，都读到 `current_metric=0`、都在内存 `+1`、都写回 `1`，
用户支付两笔只涨了一次进度 —— 典型的 Lost Update。

**但补 `version` 列 + 乐观锁重试是次优解。** 对 `COUNT` / `AMOUNT` 这类纯累加，
正解是把累加本身压进 UPDATE，一条 SQL 完成，零冲突、零重试：

```xml
<!-- TaskRecordMapper.xml -->
<update id="advanceMetric">
    UPDATE t_task_record
    SET current_metric = current_metric + #{delta}
    WHERE id = #{id} AND status = 0
</update>
```

返回 `rows=0` 有明确语义：**任务已不在进行中**（已完成/已发奖/已过期），
不是并发冲突，不需要重试，直接落一条丢弃流水。

**这与本项目已验证过的模式一致**，跟着走即可：

| 既有先例 | 做法 |
|---|---|
| `t_prize_pool_item.increaseUsedStock` | `WHERE total_stock=-1 OR used_stock<total_stock` |
| `MemberWalletDao.deductBalanceWithVersion` | 余额充足 + 版本号双条件压进 WHERE |
| `PromotionConfigDao.deductBudget` | 「够不够」压进 UPDATE 的 WHERE，靠行锁防超发 |
| `ProposalRecordDao.updateStatus(id, 30, 40)` | 状态流转的并发闸门 |

**乐观锁只在 `STREAK` 上真正必要** —— 它必须先读 `lastHitDate` 才知道是「清零再 +1」还是「+1」，
读-改-写无法避免。所以：

> **`version` 列要加，但它是给 `STREAK` 用的，不是给 `COUNT`/`AMOUNT` 用的。**
> 别因为加了 `version` 就把三个策略都改成读-改-写 —— 那是把一个能一条 SQL 解决的问题
> 主动降级成需要重试的问题。

#### 🔴 「失败就交给事件重试机制」在本项目当前不成立

评审建议「更新失败抛出并发异常，交由事件重试机制处理」。**这个机制目前不存在。**

`GlobalEventDispatcher` 走 `@Async` + `@TransactionalEventListener(AFTER_COMMIT)`，
交接文档 §5 已写死这个代价：**「异常不再沿栈上抛，只能靠日志 + 下游表自查」**。
没有 MQ 就没有重试载体，抛异常 = 静默丢事件，而且丢得比 Lost Update 更难查。

所以本期的取舍是明确的：

- `COUNT` / `AMOUNT`：**原子累加，从源头上不需要重试**；
- `STREAK`：乐观锁 + **进程内有限次重试**（建议 3 次，退避 0），重试耗尽落丢弃流水
  并记 `discard_reason='CONCURRENT_RETRY_EXHAUSTED'`；
- 真正的重试投递能力，等 MQ 立项时一并解决，**不在本期**。

### 4.5 🔴 事件幂等：必须建流水表，`progress_data` 存数组的方案不可用

`period_key` 只保证「用户今天只接一次任务」，**不保证「同一笔订单不被累计两次」**。
上游或 MQ 重投 `order_id=1001`，进度会被推进两次。问题属实。

#### 为什么否决「`progress_data` 里存 `handled_event_ids` 数组」

评审给了这个轻量方案，但它有两个硬伤：

1. **它自己就是一次读-改-写 JSON** —— 与 §4.4 的 Lost Update 同源，
   只是把并发问题从 `current_metric` 挪到了 `progress_data`，没有解决，只是搬家；
2. **数组无上界** —— `AMOUNT` 类任务（累计消费满 500）一个用户一个周期可能几十上百笔订单，
   JSON 只增不减，且每次推进都要整体读出、解析、写回。

#### 建 `t_task_record_flow`：一张表解决三个问题

这张表不只是防重。它同时是**客诉自证**的载体（评审第三点）和 **`STREAK` 日内幂等**的载体（§2.1.1）。
三个需求指向同一张表，不必分别设计。

```sql
DROP TABLE IF EXISTS `t_task_record_flow`;
CREATE TABLE `t_task_record_flow`
(
    `id`             bigint         NOT NULL AUTO_INCREMENT COMMENT 'id',
    `tenant_id`      varchar(16)    NOT NULL DEFAULT '0' COMMENT '租户ID',
    `member_name`    varchar(64)    NOT NULL COMMENT '会员名',
    `task_config_id` bigint         NOT NULL COMMENT '任务配置ID',
    `record_id`      bigint         NULL     DEFAULT NULL COMMENT '任务记录ID：被丢弃的事件可能还没建记录，故可空',
    `event_code`     varchar(64)    NOT NULL COMMENT '事件编码',
    `event_biz_id`   varchar(128)   NOT NULL COMMENT '上游幂等单号；biz_id_required=0 的事件用 period_key 兜底',
    `flow_type`      tinyint        NOT NULL DEFAULT 1 COMMENT '1-进度推进(已生效), 2-事件丢弃(未生效)',
    `delta_metric`   decimal(18, 4) NOT NULL DEFAULT '0.0000' COMMENT '本次增量',
    `after_metric`   decimal(18, 4) NOT NULL DEFAULT '0.0000' COMMENT '推进后进度值，便于按时间轴复盘',
    `discard_reason` varchar(255)   NULL     DEFAULT NULL COMMENT '丢弃原因：flow_type=2 时必填',
    `event_payload`  json           NULL     DEFAULT NULL COMMENT '事件原文快照，供客诉复盘',
    `create_by`      varchar(64)             DEFAULT NULL COMMENT '创建人',
    `create_time`    datetime                DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_by`      varchar(64)             DEFAULT NULL COMMENT '更新人',
    `update_time`    datetime                DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    -- 幂等主力：一个事件对一个任务配置只能生效一次
    UNIQUE KEY `uk_t_tsk_flw_evt` (`task_config_id`, `member_name`, `event_biz_id`),
    KEY `idx_t_tsk_flw_rec` (`record_id`, `create_time`),
    KEY `idx_t_tsk_flw_mbr` (`member_name`, `create_time`)
) COMMENT ='任务事件流水表：幂等防重 + 客诉自证';
```

**唯一索引里带 `task_config_id` 是必要的**：一个 `ORDER_PAID` 可能同时命中
「累计消费满 500」和「下单 3 次」两个任务配置，它对每个配置都该生效一次。

**时间列按铁律 9 写全** `DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP`，
实体上**不要加** `@TableField(fill = ...)`。

#### 写入顺序：先插流水，再推进进度，同一事务

```java
// TaskRecordAdvanceService（独立 Bean，避免 @Transactional 自调用，铁律 11）
@Transactional(rollbackFor = Exception.class)
public AdvanceResult advance(TaskConfig config, TaskEventContext ctx) {
    try {
        flowDao.insert(buildFlow(config, ctx));      // ① 撞唯一索引 = 该事件已处理过
    } catch (DuplicateKeyException e) {
        return AdvanceResult.duplicated();           // 幂等命中，直接返回，不算失败
    }
    int rows = recordDao.advanceMetric(recordId, delta);  // ② 原子累加
    ...
}
```

**顺序不能反。** 先插流水后推进，两者同一事务：
推进失败则流水一并回滚，事件可被重投；推进成功则流水已落，重投必被唯一索引挡下。
反过来（先推进后插流水）会在两步之间留下一个「进度加了但没留痕」的窗口。

#### ⚠️ 丢弃流水必须可开关

`flow_type=2` 的丢弃记录是客诉自证的关键（「用户下了 99 元的单为什么没进度」），
但 `PAGE_VIEW` 这类高频事件如果每条不匹配都写一行，**会直接把表写爆**。
故 §2.2 的 `t_task_event.discard_log_flag` 控制是否落丢弃流水，高频事件置 0。

被开关关掉时仍要打 DEBUG 日志，**不能什么都不留**。

### 4.6 `period_key` 的生成责任必须钉死在一处

v1 只说「`period_key` 决定周期」，**没说谁来算**。这是个会直接踩上铁律 10 的空白：

- `period_key='20260402'` 里的「今天」是**哪个时区**的今天？
- 跨零点到达的事件算哪一天？
- 如果 `period_key` 在 Java 算、而过期扫描在 SQL 里用 `now()` 算，**两个时钟又分叉了**
  —— 交接文档 §「时间戳错乱排查纪实」已经为这件事付过一次代价。

**定死**：

```java
/** 唯一真源：limit_type → period_key。全项目只此一处，禁止散写 */
public static String resolvePeriodKey(LimitTypeEnum limitType, LocalDateTime eventTime) {
    return switch (limitType) {
        case ONCE, UNLIMITED -> PERIOD_NONE;                 // "NONE"
        case DAILY  -> eventTime.format(YYYYMMDD);
        case WEEKLY -> eventTime.format(YYYY_WW);            // ISO 周，跨年周边界按 ISO-8601
    };
}
```

三条约束：

1. **`period_key` 一律在 Java 侧计算**，入参用**事件自带的时间**而非 `LocalDateTime.now()`
   —— 迟到的事件应归属它实际发生的那一天，而不是被处理的那一天；
2. **JVM 与 MySQL 会话时区已由铁律 10 的连接串对齐**
   （`connectionTimeZone=Asia/Shanghai&forceConnectionTimeZoneToSession=true`），
   前提成立才允许 Java 算周期、SQL 扫过期；
3. `STREAK` 恒返回 `NONE`（§2.1.1），且**在 switch 里显式写出来**，不要靠 default 落下去。

### 4.7 🔴 异步隔离：复用既有基建，但线程池现状有两个坑

**方向完全正确**：任务引擎的任何抖动都不该拖死上游主交易链路。
但本项目**已经有这套基建**，不需要新起，照抄即可 —— 并且有两个已知坑要一并处理。

#### 复用点：`GlobalEventDispatcher` 的手动 submit 模式

```java
// GlobalEventDispatcher:91-93 的注释，直接抄这个结论
// 这里刻意不用 @Async：本类实现了 SmartInitializingSingleton，@EnableAsync 默认走 JDK 动态代理，
// 而 dispatch 不在任何接口上，事件监听器注册时会直接报
// 「Need to invoke method 'dispatch' ... but not found in any interface(s) of the exposed proxy type」
@Resource(name = AsyncConfig.ASYNC_EXECUTOR_THREAD_NAME)
private AsyncTaskExecutor asyncExecutor;
```

`@EnableAsync` 已在 `AsyncConfig` 开启，线程池 bean 已存在。任务事件入口按同样方式手动 submit。

#### 🔴 坑一：这个线程池的队列是**无界**的

```java
// AsyncConfig:38-49 —— 只设了 corePoolSize / maxPoolSize，没设 queueCapacity
taskExecutor.setCorePoolSize(threadCount);   // CPU核数-1
taskExecutor.setMaxPoolSize(threadCount);    // 与核心数相同
// setQueueCapacity 未调用 → ThreadPoolTaskExecutor 默认 Integer.MAX_VALUE
```

评审说「退而求其次走 `@Async` 的**有界**线程池」—— 现状**不是有界的**。后果：

- 拒绝策略永远不会触发，**积压全部堆在堆内存里**，高频事件下是 OOM 风险而非降级；
- 因为队列不满，`maxPoolSize` 也永远不会生效（这是 `ThreadPoolExecutor` 的固有行为，
  与这里 core==max 无关，但会让人误以为调大 max 就能提吞吐）。

**这是个必须当面拍板的取舍**，没有默认答案：

| 拒绝策略 | 后果 |
|---|---|
| `CallerRunsPolicy` | 反向阻塞上游 —— **恰好破坏了异步隔离的初衷**，但不丢事件 |
| `AbortPolicy` / `DiscardPolicy` | 保住上游，**但会丢事件**，必须配套落丢弃流水 |

建议：**给任务事件用独立的有界池 + `AbortPolicy` + 拒绝时落 `flow_type=2` 丢弃流水**，
理由见坑二。

#### 🔴 坑二：与派奖链路**共用同一个池**

`GlobalEventDispatcher` 用的就是 `ASYNC_EXECUTOR_THREAD_NAME` 这个池，
而它承载的是**抽奖/彩票的派奖链路**（已压测验证、直接关系资产到账）。
任务事件如果也塞进去：

> 一次任务事件洪峰会把派奖任务**挤在同一个队列后面排队** ——
> 表现是「抽奖中奖了但积分半天不到账」，而两条链路看起来毫无关系，极难联想到根因。

派奖是资产链路、任务事件是进度链路，**重要性不对等，不该共享隔板**。
建议新增 `task-event-executor` 独立有界池，与派奖池物理隔离。这是舱壁隔离（Bulkhead）的标准动机。

#### MQ 是终局，但不进本期

评审建议事件入口走 RocketMQ/Kafka，方向正确。但：
当前 `pom.xml` 里**没有任何 MQ 依赖**，引入涉及部署、运维、消息可靠性、消费幂等的一整套配套。
**单独立项，不混进 P0。** §4.4/§4.5 的设计对「将来换成 MQ 投递」是兼容的 ——
幂等键在流水表上，换传输通道不影响。

### 4.8 🔴 `t_task_record.status` 表达不了阶梯任务的发奖状态

```sql
`status` tinyint DEFAULT '0' COMMENT '状态：0-进行中, 1-已完成, 2-已发奖, 3-已过期'
```

阶梯任务「第 1 档已发奖、第 2 档还在进行中」——**没有任何一个值能表达**。
写 `2-已发奖` 会让第 2 档不再推进（`advanceMetric` 的 `WHERE status=0` 直接挡住），
写 `0-进行中` 又丢失了「第 1 档已发过」这个事实，重启或重投时会重复发奖
（虽然 §4.3 的幂等键会兜住，但那是**靠防重掩盖状态缺失**，正是本项目反复吃过亏的模式）。

**修法**：档位发放记录放进 `progress_data`，`status` 只表示**最高档是否达标**。

```json
{ "dispatchedStages": [1], "lastHitDate": "20260402" }
```

- `status=0` 进行中（含「低档已发、高档未达标」）；
- `status=1` 已完成 = 最高档达标；
- `status=2` 已发奖 = **最高档的奖也发完了**，此后不再接受事件。

> ⚠️ `dispatchedStages` 是读-改-写，与 §4.4 同源。
> 它必须与 `advanceMetric` 在同一事务内、且用 `version` 乐观锁保护
> —— 或者更简单：**发奖判定只读不写**，靠 §4.3 的 `recordId:stageLevel` 幂等键兜底重复，
> `dispatchedStages` 仅作为运营可读的展示字段（**允许它偶尔滞后**，因为它不是判据）。
> 建议后者：**判据只留一个，就是唯一索引**。两个判据一定会漂移。

#### 🔴 v1 的 P0 验收判据会空过这个问题

v1 §6 的验收用的是「累计签到 3 天送 10 积分」—— **单档任务**。
它跑通了也证明不了阶梯任务能用，而阶梯正是 `PrizeLadderBuilder.vue` 已经在配的能力。

这正好撞上交接文档铁律 16：**「断言前必须先确认前提条件真实成立，否则通过和空过分不出来」**。
本项目已经空过三次（`includeInactive`、`online` 路径写错、活动启用守卫），不能再来第四次。

**故 P0 验收判据必须加一条阶梯任务**，见 §6。

### 4.9 🔴 撞唯一索引后「就地重查」查不到 —— REPEATABLE READ 的快照陷阱

**这条是 P0 实施时实测踩到的**（10 并发只推进了 1 笔），不是推演。

首次接取任务时，N 个并发事件会同时想为同一 `(member, config, period)` 建记录，
唯一索引 `uk_t_tsk_rec_mbr_cfg_prd` 只放行一个。直觉写法是：

```java
TaskRecord existing = dao.selectByUniqueKey(...);   // ① 返回 null
if (existing != null) return existing;
try {
    dao.insert(record);                             // ② 撞索引
} catch (DuplicateKeyException e) {
    return dao.selectByUniqueKey(...);              // ③ 重查 —— 依然是 null ❗
}
```

**第 ③ 步查不到。** MySQL 默认隔离级别是 **REPEATABLE READ**，
本事务的一致性视图在**第一次读（第①步）**时就固定了。赢家是在那之后才提交的，
它插入的那一行**不在本事务的快照里** —— 于是出现「INSERT 报重复、重查却查不到」
这种看起来自相矛盾的现象。实测症状：`current_metric` 停在 100（只有赢家那一笔），
另外 9 笔全部抛 `DuplicateKeyException`。

两条修法，**选了后者**：

| 修法 | 评价 |
|---|---|
| 重查改成 `SELECT ... FOR UPDATE` | 当前读能看到最新已提交版本，可行；但为一个纯读场景引入行锁，且锁的是别人刚插入的行 |
| **抛异常回滚、在新事务里重试** ✅ | 新事务有新快照，自然读得到。顺带把已插入的流水一并回滚，重试时幂等键重新占位，不会留下「流水占了坑但进度没推」的半截状态 |

所以 `TaskConcurrentModifyException` 有**两个来源**（STREAK 乐观锁冲突 + 记录被并发创建），
共性是「重试必须发生在新事务里」。这也让 §4.4 里「`TaskRecordAdvanceService` 必须是独立 Bean」
多了一条硬理由：**不换事务就换不到新快照，就地重试多少次都是同一个结果。**

> 通用教训：**「捕获 DuplicateKeyException 后重查」这个到处都能见到的写法，
> 在 REPEATABLE READ 下只在「记录早已存在」时成立，在「刚刚被并发创建」时是失效的。**
> 而后者恰恰是它被写出来要解决的那个场景。

### 4.10 ⚠️ `rule_config` 的键名是契约，不是自由文本

P0 实施时读库发现：存量模板 `FRWAYF2X6N`（每日签到）的 `ui_schema` 用的参数键是
**`targetDays`**，而策略层读的是 `targetCount`。后果是 `target()` 返回 null，
任务**进度照涨、永远不完成**，且一条报错都没有 —— 正是本方案要消灭的那类静默失效。

这暴露了三层分离里一个没说清的前提：**第②层 `rule_config` 的键名必须是约定集合，
模板作者不能随手起名**。否则「新增模板前端零改动」会退化成「新增模板后端算不出来」。

当前处理（对齐本项目 `visibleWhen` 的既定做法：主形态 + 有限兼容 + 新增强制用主形态）：

- 主形态 `targetCount` / `targetAmount` / `minAmount` / `tolerance`，收敛在 `TaskConst`；
- 兼容形态只保留一个 `targetDays`（存量模板），**名单只出不进**；
- **建议 P1 补一条服务端校验**：`TaskTemplateService.save()` 检查 ui_schema 声明的参数键
  是否覆盖了该 `task_type` 必需的契约键，不满足就拒绝保存并给人话提示。
  这是把「静默算不出来」提前成「保存时就报错」的唯一办法，成本很低。
  本期没做是因为它会改变模板设计器现有的保存行为，属于超出 P0 的范围。

## 5. 关于 QLExpress 的两张表（承接远景规划）

你提到脚本要拆成**脚本表 + 引用表**。这个方向与本方案完全兼容，且现有的
`scriptengine` 模块已经把地基打好了 —— `ScriptEngine.execute(ExecutableScript, EngineContext)`
本来就是「脚本内容 + 上下文 → 结果」的抽象，**它不关心脚本从哪来**。

建议的两张表：

```sql
-- ① 脚本表：脚本本体与版本
t_script
  script_code   varchar(32)   -- 业务编码（铁律 8，建议前缀 S）
  script_name   varchar(128)
  script_type   varchar(32)   -- TASK_RULE / PRIZE_RULE / RISK_RULE …
  content       text
  version       int           -- 每次保存 +1，旧版本保留
  status        tinyint

-- ② 引用表：谁在用这个脚本
t_script_ref
  script_code   varchar(32)
  ref_biz_type  varchar(32)   -- TASK_TEMPLATE / TASK_CONFIG / …
  ref_biz_id    varchar(64)
  UNIQUE KEY (script_code, ref_biz_type, ref_biz_id)
```

**引用表的真正价值不是「查谁在用」，而是让脚本能被安全地改。**
没有引用表时，改一段脚本等于在盲改 —— 不知道会影响多少个正在跑的任务。
有了它就能做两件事：① 改动前提示影响面；② 禁止删除仍被引用的脚本
（与活动/奖品的删除守卫是同一个模式）。

**⚠️ 但建议这两张表放在任务运行态跑通之后再做。**
理由：现在 `rule_script` 一次都没被执行过，脚本管理是在为一个尚未验证的通道做基建。
先让第 ③ 层真正跑起来一两个 case，才知道脚本表需要哪些字段
（比如是否需要 `param_schema`、是否需要灰度版本）。

## 10. 一句话给下一个接手的人

**这个模块要「有生命力」，靠的不是功能多，是两件事：**

1. **`t_task_record_flow` 那张表** —— 它不是防重的副产品，是这个中台唯一能自证清白的东西。
   运营问「用户 A 为什么没拿到奖」，答得上来才有人敢用。查不清账的中台，用几次就被绕开了。
2. **`task_type` 必须少而稳**（§3.2）——
   一旦有人提出「加个 `task_type` 来支持新玩法」，那就是设计跑偏的信号。
   生命力恰恰来自这个克制：新玩法应该落在 `rule_config`，不是落在策略工厂的 key 上。
