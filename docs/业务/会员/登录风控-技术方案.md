# 登录风控 —— 技术方案

> 撰写 2026-10-09 · 修订 2026-10-14（主模型改为处置矩阵、密码阶梯冷却、全局滑块开关、IP 熟悉度，见 §12.2）
> 类型：**方案（待评审，代码未动）**
> 🔴 前提（2026-10-14 确认）：**生产环境还没有上线，只有本地 docker**。没有存量用户、没有存量数据、没有线上配置 ——
> 所以本方案不做新旧并存与数据迁移，旧代码直接替换；「陪跑」是上线**之后**用真实流量校准阈值的手段（§9）。
> 前置阅读：`docs/架构/账号安全全景图鉴.md`（现有每一道门在哪、哪些还只是摄像头）
> 参考：支付宝 / 蚂蚁公开分享里的「可信 + 风险双判」「核身分层」「策略陪跑」。只抄架构，不抄规模（§2）。
>
> 这份文档回答：**现有的设备闸、IP 闸、账号锁、观察档二次验证，怎么收进一个统一的决策中枢；
> 每种情况该给什么处置；要新加哪些信号；建哪几张表；按什么顺序切过去才不误伤。**

## 0. 一句话

**先问「是不是本人」（设备认不认识、网络熟不熟、人多久没来了），按一张处置矩阵给出结论；
弱信号打分只负责在矩阵结论上「再加一档」。**
处置分五级：放行 < 滑块 < OTP < 冷却 / 限流 < 拒绝，多条规则同时命中取最严的那一级。
每一次决策都落库、每一条规则都能单独陪跑、在后台改档位 —— 阈值靠数据校准，不靠拍。

## 1. 现状：零件都有，缺的是一个「脑子」

| 零件 | 位置 | 它在判什么 | 档位 |
|---|---|---|---|
| IP 闸 | `LoginIpGuard` | 单 IP 每小时：总次数 60 / 失败 20 / 不存在账号 10 | **拦截** |
| 设备闸 | `DeviceGuard` | 单设备：日登录 30 / 时失败 10 / 日碰号 3 / 日注册 2 | dry-run |
| （注册那一条已于 2026-10-16 迁成 `REG_DEVICE_LIMIT`，`checkRegister` 连同它的 dry-run 一起删掉） | | | |
| 设备处置 | `DeviceDispositionService` | 正常 / 观察（登录要多验一道）/ 封禁 | 观察档生效、封禁生效 |
| 账号锁 | `MemberOperationLimitService` | 单账号 30 分钟错 5 次，限登录 30 分钟 | **拦截** |
| 滑块 | `CaptchaService` | 每一次密码登录、每一次发码之前都要拖 | **拦截（全量）** |
| 设备信任 | `MemberStepUpService` + `DeviceTrustStore` | 验证过 / 老交情（成功登录早于 7 天） | 二次验证 observe |
| 新设备提醒 | `NewDeviceLoginNotifier` | 从没登录过的设备登录成功 → 邮件 + 站内信 | 生效 |
| 观察档凭票验码 | `LoginChallengeStore` | 密码对了才签票，凭票发码、验码 | 生效 |

每个零件单看都是对的，问题出在**组合**上：

1. **各判各的，每个都是硬门槛。** 真实的盗号登录往往每个维度都没超限：一个号、一次、密码是对的，
   只是**换了台从没见过的设备、在一个从没出现过的网络**。今天这种登录会直接成功，唯一的反应是事后发一封新设备提醒。
2. **「是不是本人」这个问题没有在登录时问。** 设备信任已经能回答「这是不是他的老设备」，但只在加地址、充话费时才被问到。
3. **处置只有「拦」和「放」两档**，外加一个对所有人一视同仁的滑块。老用户在自己家里登录，和脚本从机房打过来，拖的是同一张图。
4. **看不到全貌。** 登录日志 `member_id NOT NULL`，查无此人的尝试一行都不留；规则命中只进应用日志。
5. **陪跑只有整体开关**（`DeviceGuard.dry-run` 四条一起开关）；**改阈值没有留痕、改了要发版或动配置中心**。
6. **🔴 一个现存的枚举缝**（本次核对代码时发现）：查无此人时 `authenticate` 直接返回，**不跑 Argon2**；
   账号存在时要验一次密码哈希（几十毫秒）。响应时间本身就在回答「这个号存不存在」。P0 顺手补上（§3.1）。

## 2. 抄支付宝的什么，不抄什么

| 支付宝的做法 | 抄不抄 | 落到本项目 |
|---|---|---|
| **可信识别优先**：常用设备 + 常用环境直接放行 | ✅ 抄 | §3.3 处置矩阵 —— 设备信任、IP 熟悉度、活跃度三个维度 |
| **风险打分**：多个弱信号叠加 | ✅ 抄，但降为辅助 | §3.4 —— 只负责在矩阵结论上加一档 |
| **核身分层**：决策只说强度，因子由核身层选，避开可能已失守的因子 | ✅ 抄 | §3.7 核身路由 |
| **策略陪跑**：新策略先只记录不拦截 | ✅ 抄，细到每条规则 | §3.6 |
| **应急档**：全量开启强校验 | ✅ 抄 | §3.5 全局滑块开关；P2 的全站应急档 |
| 事前 / 事中 / 事后 + 反馈闭环 | ✅ 最小版 | 决策流水 + 命中明细 + 「这不是我」（§8） |
| 黑白灰名单 | ✅ 抄 | §5.2：IP、IP 段、身份摘要、会员（仅白名单） |
| 机器学习、关系图谱、实时流计算 | ❌ | 没有数据量和标注 |
| 人脸核身、账户安全险 | ❌ | 资损量级不需要 |
| 自研设备指纹 | ❌ | 已有服务端签发的设备令牌；要更强的接商业厂商 |

**为什么矩阵为主、打分为辅：** 矩阵的每一格都能用一句人话说出来（「新设备 + 陌生网络，所以要验证码」），
客服能直接念给用户听，运营能直接在后台改某一格。纯打分模型解释起来是「你得了 45 分」，没人知道该改哪里。
打分保留给那些**单独不足以下结论**的弱信号（机房 IP、换了国家、不可能旅行）。

## 3. 总体设计

### 3.1 两个决策点

```
 /auth/login ─► 规范化身份 ─► 网关：带了滑块通行票就核销，结果作为 captchaPassed 传下来
                   │
             按摘要找人（找不到 = null，照常往下走）
                   │
          ┌────────▼─────────┐
          │  ① 前置决策 PRE   │   IP、设备、名单、全局开关、密码冷却、IP 熟悉度（只能放宽）
          │  （验凭据之前）    │   出口：PASS / CAPTCHA / COOLDOWN / LIMIT / DENY
          └────────┬─────────┘
                   │ PASS（或 CAPTCHA 且 captchaPassed）
             状态 → 验凭据（查无此人也跑一次假的 Argon2）        ← 顺序不动
                   │ 密码对了
          ┌────────▼─────────┐
          │  ② 后置决策 POST  │   处置矩阵（设备信任 × IP 熟悉度 × 活跃度）+ 打分 + 设备观察档 / 一机多号
          │  （验凭据之后）    │   出口：PASS / OTP / OTP_STRONG / LIMIT / DENY
          └────────┬─────────┘
            PASS   │   OTP → 签凭票（现有 LoginChallengeStore）→ 凭票发码 → 凭票验码 → 收尾
                   ▼
             completeLogin（新设备提醒、登录日志 —— 现状）
                   │
            finally：写一条决策流水 + 命中明细
```

**🔴 前置可以查账号，但账号信息只能用来「放宽」，不能用来「收紧」。**

前置决策排在验密码之前。这时候如果因为「这个号存在」而给出**更严**的结论，回答就会随账号是否存在而不同 ——
那正是 `BAD_CREDENTIALS` 合并三种失败原因要堵住的枚举口子。所以约束是：

- 对「查无此人」，前置的结论一律按**最严的默认值**给（要滑块、照常计冷却）；
- 账号存在时，账号信息**只能把结论往松里调**（熟悉的网络免滑块、可信设备单独计冷却）。

攻击者的 IP 不在受害者的熟悉列表里、他的设备不是受害者的可信设备 —— 所以他无论对存在还是不存在的账号，看到的都是同一个默认值。

**响应时间也要一致**：查无此人时对一个固定的假哈希跑一次 `PasswordCipher.matches`，让两条路径的耗时落在同一个量级。
前置多出来的画像查询走 Redis 缓存，差值在毫秒级、淹没在 Argon2 的几十毫秒里。

**后置决策排在密码验对之后**。此时要求 OTP 确实会透露「密码对了」，但这与现在观察档凭票的取舍一致：
不知道密码就拿不到票，拿不到票就发不了码（码是花钱的，也是轰炸的原料）。

### 3.2 处置等级

| 级 | 处置 | 出现在 | 对用户说什么 |
|---|---|---|---|
| 1 | `PASS` 放行 | 两处 | — |
| 2 | `CAPTCHA` 滑块 | 前置 | 现有 `CAPTCHA_REQUIRED`，客户端已经会处理 |
| 3 | `OTP` 验证码 | 后置 | 现有凭票二次验证 |
| 4 | `OTP_STRONG` 换通道验证码 | 后置 | 同上，通道见 §3.7 |
| 5 | `COOLDOWN` 密码冷却 | 前置 | 「密码错误次数过多，请 N 分钟后再试，或用验证码登录 / 找回密码」 |
| 6 | `LIMIT` 限流 | 两处 | 「操作过于频繁，请 N 秒后再试」 |
| 7 | `DENY` 拒绝 | 两处 | **对外与 LIMIT 同一句**，不告诉对方「你被拉黑了」 |

多条规则命中取最严。文案只说「还要等多久、还能走哪条路」，**不说触发了哪条规则** —— 那是给攻击者的调参信号。

**邮箱验证码登录**：滑块已经在发码那一步过过，前置的 `CAPTCHA` 对它视为已满足；后置的 `OTP` 对它视为已满足（它本身就是一道码），
只有 `OTP_STRONG` 才会要求换通道（§3.7）。

### 3.3 处置矩阵（主模型）

三个维度：

| 维度 | 取值 | 判据 |
|---|---|---|
| **设备** | 可信 / 新 | 可信 = `MemberStepUpService.check` 为 `VERIFIED` 或 `HISTORY`，或者是注册时那台（`NewDeviceLoginNotifier` 的注册设备键）。没带设备令牌按「新」 |
| **IP 熟悉度** | 严格熟悉 / 宽松熟悉 / 陌生 | 见下 |
| **活跃度** | 活跃 / 沉睡 | 沉睡 = `t_member.last_active_time` 早于 30 天前（§4.4，**不是**按最后一次登录算） |

**IP 熟悉度**（数据来源：这个会员近 90 天**最近 10 个不同网段**的成功登录 IP，加上注册 IP）：

- **严格熟悉**：本次 IP 的网段在其中。网段 = IPv4 取 `/24`、IPv6 取 `/64`。
  不按完整 IP 比：手机的 IPv6 隐私地址通常一天一换，4G 出口也在一个地址池里漂，按完整 IP 比手机用户几乎每次都是「新 IP」。
- **宽松熟悉**：严格熟悉，**或者**「同城市 + 同运营商」在其中。给在同一个城市里移动的手机用户留余地。
- **陌生**：都不是。

🔴 **前置只认严格熟悉，后置才认宽松熟悉。** 前置的「免滑块」是对未验证身份的人放宽 ——
用「同城市 + 同运营商」的话，一个和受害者在同一个城市、用同一家运营商的攻击者，对一部分账号就能跳过滑块。
后置时密码已经验对，宽松一点的代价小得多。

**前置格（`CAPTCHA_MATRIX`）：** 默认 `CAPTCHA`；账号存在且 IP **严格熟悉** → 放宽为 `PASS`。

> 只看 IP，不看设备：「IP 变了就要滑块」，可信设备换了网络也一样要拖。设备信任在后置里起作用。

**后置格（`LOGIN_MATRIX`）：**

| 设备 | IP（宽松口径） | 活跃度 | 处置 |
|---|---|---|---|
| 可信 | 任意 | 任意 | **PASS** |
| 新 | 熟悉 | 活跃 | **PASS**（新设备提醒照发） |
| 新 | 熟悉 | 沉睡 | **OTP** |
| 新 | 陌生 | 任意 | **OTP** |

- 可信设备沉睡回来直接放行：一台老设备隔一个月再来，大概率是本人；它要是被复制了，由 `IMPOSSIBLE_TRAVEL`（不被可信绕过）去抓。
- 每一格的处置都是规则参数（`params.cells`），后台可改。比如想让「可信 + 沉睡」也要 OTP，改那一格即可。
- **账号白名单**（§5.2）里的会员不走矩阵：前后两格都按 `PASS`。

**复用而不是重做**：设备信任的定义与撤销（重置密码、冻结、下线其他设备时清零）全部沿用二次验证那一套。
登录风控和资产出口二次验证对「这是不是他的老设备」必须是同一个答案。

### 3.4 辅助打分：只负责「加一档」

| 阶段 | 分数 | 结论至少是 |
|---|---|---|
| 前置 | ≥ 30 | `CAPTCHA` |
| 后置（前置分 + 后置分） | ≥ 40 | `OTP` |
| 后置 | ≥ 80 | `OTP_STRONG` |

最终结论 = max(矩阵结论, 强规则结论, 打分结论)。所以打分只会把结论往上推，不会让矩阵判过的东西变松。

- **同组取最大，不累加**：相关的信号编进同一个组（`rule_group`），组内只取最高分。地理组（新国家、不可能旅行）最多贡献 50，
  一个真出差的人不会因为「人在外地」被算两遍。
- **可信设备跳过后置打分**，例外是 `IMPOSSIBLE_TRAVEL`（`bypass_by_trust = 0`）：设备令牌能被复制，
  一台「老设备」20 分钟内从深圳跳到纽约，正是令牌被复制的样子。
- 🔴 **打分永远不会得出 COOLDOWN / LIMIT / DENY**，那三级只来自强规则。打分都是「像不像」的统计信号，没有一条是证据。
- **分档线放配置**（`solvela.member.risk.login.*-score`），不放表：它们是整套打分的标尺，改一次等于改了所有打分规则的效果，应该走发版评审。

### 3.5 全局滑块开关

规则 `GLOBAL_CAPTCHA`：开着时**所有密码登录都要滑块**，矩阵的「熟悉网络免滑块」不起作用。

- **上线初期开着** —— 这正是今天的行为（每次密码登录都要滑块），所以 P0 切过去没有任何变化。
- 它是规则表里的一行，后台规则页上一个开关，30 秒内生效。**被攻击时可以随时一键打开**，等于应急档。
- 取代今天的配置项 `solvela.app.captcha.password-login`（P0 删掉，不留两个真相源）。
  发码前的滑块（`captcha.send-code`）不在登录引擎里，保持不动：发码要花钱，永远全量。
- 白名单（IP、会员）**都不豁免**全局滑块 —— 「全局」就是所有人。

### 3.6 陪跑：每条规则一个档位

| mode | 含义 |
|---|---|
| `OFF` | 不执行（连特征都不取） |
| `SHADOW` | 执行、记命中，**不影响**决策 |
| `ENFORCE` | 执行、记命中、参与决策 |

引擎每次算两个结论都落库：**生效结论** `decision`（只算 ENFORCE）与**陪跑结论** `shadow_decision`（全算）。
「把这条规则切到生效会多打扰多少人」= 两者不一致的那部分（§8.2）。

总开关 `solvela.member.risk.mode: shadow | enforce`：`shadow` 让**除全局滑块、黑名单、设备封禁以外**的规则全部只记录 ——
上线后万一某条规则大面积误伤、又来不及定位是哪条时的保命开关。不设 `off`：旧的硬编码路径会被直接删掉（生产还没上线，不需要并存），
没有可以「退回」的地方；而「所有规则都不执行」等于把门全打开。

### 3.7 核身路由：决策说强度，路由选通道

| 登录方式 | `OTP` | `OTP_STRONG`（换一个通道） | 强通道不可用时 |
|---|---|---|---|
| 手机号 + 密码 | 短信 | 邮箱（已绑） | 退回 `OTP` + `NOTIFY_OWNER` |
| 邮箱 + 密码 | 邮箱 | 短信（已绑） | 退回 `OTP` + `NOTIFY_OWNER` |
| 邮箱验证码 | 视为已满足 | 短信（已绑） | `PASS` + `NOTIFY_OWNER` |

换通道的意义是「避开可能已失守的那个因子」：密码复用时邮箱密码和本站密码往往一起泄露，往同一个邮箱发码证明不了任何事。
🔴 短信厂商还没接，今天 `OTP_STRONG` 几乎总是退回 `OTP`；接上的那天自动生效。

### 3.8 处置动作

决策只说结论，有副作用的动作由引擎按**生效的**决策执行；陪跑中的规则不触发任何动作。

| 动作 | 触发 |
|---|---|
| `OBSERVE_DEVICE` | 设备闸生效命中（现状 `dispositionService.observe`） |
| `NOTIFY_OWNER` | 后置 `OTP_STRONG`，或 `DENY` 且账号已确定：「我们拦下了一次可疑登录」，与新设备提醒同一套模板，**信里没有链接** |
| `RECORD_LIMIT` ✅ | 密码冷却到 60 分钟及以上：往 `t_member_operation_limit` 写一行，后台可见、可人工解除（§4.4）。🔴 按【剩余时间】判，不是按「这一次罚了多久」—— 规则在前置跑，那时它只知道剩多久 |

### 3.9 引擎出错时：放行，但留痕

- 特征取不到 → 那条规则按**未命中**并记 `error` 命中；引擎整体异常 → 本次按 PASS 并打 `ERROR` 日志。**风控挂了不能等于登录挂了。**
  例外：全局滑块开关读不到时按**开**处理（往安全的方向偏，而且它是本地缓存，读不到只可能是启动期）。
- **慢按挂处理**：特征读取总预算 150ms，画像查询带 statement timeout，超了按未命中。不调低 Redisson 全局超时（会连带会话查询）。
  边界：会话登记簿也在这个 Redis 上，Redis 真挂了整站都不可用，与风控无关。
- **决策流水同步写**，不进内存队列（理由见 §12.1）：被攻击时队列满了丢的正是攻击流水。写入包在 try/catch 里，失败只打日志。

## 4. 规则目录

> 🔴 **2026-10-17 起，以下 16 条规则移交网关**（`docs/架构/网关阶梯限流-技术方案.md` §1.1），本章里它们的行保留作历史，**以网关方案为准**：
> 纯计次的 `IP_ATTEMPT_LIMIT`、`DEVICE_LOGIN_LIMIT`、`REG_IP_LIMIT`、`REG_DEVICE_LIMIT`、`RESET_IP_LIMIT`、`RESET_DEVICE_LIMIT` → 网关限流场景；
> 五条 `*IP_BLACKLIST` 与五条 `*DEVICE_BANNED` → 网关安全闸（挡所有接口，不只这五条链路）。
> 新增 `CANARY_ACCOUNT`（蜜罐账号）留在本引擎。见 §12.10。

`P0` 一列是**正式上线第一天**的档位。判据：**确定性的策略直接生效，靠拍脑袋定阈值的先陪跑。**

- 直接生效：全局滑块、黑名单、封禁、观察档、IP 闸（今天就在拦）、密码阶梯冷却、处置矩阵 —— 这些是「要不要这样做」的产品决定，
  不是「阈值多少合适」的统计问题。而且**上线第一天就有的摩擦，用户当成产品本来的样子；上线半年后才加的摩擦，用户当成产品变差了。**
- 先陪跑：设备闸的四个阈值、`IP_ACCOUNT_FANOUT` 的限流档、所有打分规则 —— 数字是拍的，要真实流量来校准。

**分级规则的滑块档在 P0 不产生效果**：全局滑块开着时，任何人都已经要拖图了。它们的作用在 P2 关掉全局滑块之后才显现 ——
那时 IP 规则就成了真正的阶梯：先出滑块，远超阈值才限流。

**IP 白名单**：命中的 IP 跳过 `IP_ATTEMPT_LIMIT` / `IP_FAIL_LIMIT` / `IP_UNKNOWN_LIMIT` / `IP_ACCOUNT_FANOUT`，**连计数都不加**。
不豁免全局滑块、密码冷却、设备规则、后置决策 —— 一个公司出口背后照样可能坐着攻击者。

**老设备豁免 IP 限流** ✅：设备令牌签发早于 7 天、且这台设备上有过成功登录的，不受 IP 规则的 `LIMIT` 档约束（滑块档照常）。
判的是**设备**的年龄，不是某个账号与设备的关系，不依赖账号。它解决的是「一个人在校园网里故意试错，整个出口一小时登不上」。

落点：`risk/dao/RiskDeviceDao`（一条 SQL 同时判年龄与「有过成功登录」）+ `risk/feature/OldDeviceExemption`
+ `risk/rule/IpTieredCountRule`（只有 IP 维度的分级规则继承它）。门槛在 `solvela.member.risk.old-device-age`，配成 `0s` 即关闭。

- 🔴 **两个条件缺一不可**。设备令牌是**匿名领的**（`/device/register` 不要求登录）：只看年龄，攻击者提前领一批养七天就有了免检通行证；
  只看有过成功登录，刚领的令牌登一次就免检，而撞库脚本中一个号就拿到它。
- 🔴 **只压处置，不停观察**：计数照常加、滑块档照常出。整条跳过的话，这个 IP 的真实量级会被老设备的流量抹平 —— 而那正是被攻击时最该看清的数。
- 🔴 **设备维度的规则没有这个豁免**，所以单独一层 `IpTieredCountRule` 而不是在基类上加个布尔开关：
  `DEVICE_FANOUT` / `DEVICE_FAIL_LIMIT` 挡的正是「这台设备在挨个试号」，而一台用了半年的设备开始挨个试号比新设备这么干**更**值得警惕。
  做成参数的话，迟早有人给设备规则也配上（它看起来只是「放松一点」）；分成两层，那件事要先改继承关系。
- 查库失败时**不豁免**（往严的方向偏）：反过来写，数据库一抖动所有人都成了老设备，而被攻击时数据库恰恰最容易抖。
- 黑名单（`IP_BLACKLIST`）**不在豁免范围内** —— 它是人工判过的 `DENY`，不是量级推出来的限流。

### 4.3 现有规则盘点（2026-10-14 对着代码核对）

**计数窗口在 2026-10-16 换成了滑动窗口** ✅（P3 第一步）。

此前是「首次命中起算的固定窗口」（`RedisService.increment`：INCR + 首次设 TTL），
窗口边界前后各打满一次，实际能到阈值的两倍 —— 而这几条限流正好是攻击者有动机去卡这个边界的地方。
第一批刻意先保持固定窗口（把引擎改造和窗口算法两件事分开，出了问题好定位）。

现在：

- **计数类走分桶**（`RedisService.slidingWindowCount`，Redis 哈希 + Lua，一次往返、原子）。
  一个窗口切 60 个桶，一小时窗口的精度 ±1 分钟 —— 而阈值是「几十次」量级，这点误差无关紧要。
  🔴 **不用「逐条记时间戳」的精确做法**：那个内存随攻击量线性增长，而被攻击正是最不希望
  某个 IP 能让我们吃掉几百兆内存的时刻。分桶把一个键的字段数钉死在 60 个，内存与攻击量无关。
- **去重计数走 ZSET**（`slidingSetCount`）：它数的是「几个**不同**的东西」，去重必须留成员本身。
  成员重复出现时**刷新「最近一次」**，否则一个一直在场的账号会在窗口末尾掉出去。
  成员数有硬上限（500），超了从最旧的丢 —— 被撞库时一个 IP 碰过的账号数等于攻击量，
  而阈值只有几十，丢掉最旧的不改变「超没超」的结论。
- 🔴 **「还要多久降下来」不能用键的 TTL 回答**：TTL 是从最后一次写入算的，而滑动窗口里
  先掉出去的是最早那一批。用 TTL 的话，一个还在被打的 IP 会被告知「等一小时」，
  而其实它再过一分钟就降到阈值以下。所以脚本顺带返回「窗口内最旧那个桶」，由它算。
- 🔴 **只读不续期**：否则一个一直被查询、没人再写入的键永远不过期。

`LoginCounters` **对外的方法一个字没变，所以二十条规则一条都没改** ——
这正是把 Redis 键收在一处的回报：换窗口语义这件事，影响面停在那个类里面。

⚠️ `RedisService.increment`（固定窗口）**保留**：设备签发限频、操作限制的失败计数、
验证码日限额还在用它，而那几处没有「卡边界」的动机（它们限的是人，不是脚本）。

### 4.4 规格（照着写代码的那一份）

共同约定：**数据缺失 = 不判**（未命中）；**特征取不到 = error 命中**（§3.9）。前者是常态，后者是故障。

#### 密码阶梯冷却 `PWD_COOLDOWN`

```json
{ "free": 2, "steps": ["60s", "5m", "10m", "60m", "24h"], "idleReset": "24h", "recordFrom": "60m" }
```

| 连续错误次数 | 1 | 2 | 3 | 4 | 5 | 6 | ≥ 7 |
|---|---|---|---|---|---|---|---|
| 冷却 | — | — | 60 秒 | 5 分钟 | 10 分钟 | 60 分钟 | 24 小时 |

- **🔴 按身份摘要计数，不按会员号**：键 `mbr:risk:pwd:{身份摘要}:{桶}`，查无此人照样计数、照样冷却、照样是那一句文案。
  今天的账号锁只对存在的账号生效 —— 故意错几次看会不会出现「已锁定」，就知道号存不存在。阶梯越早触发，这个缝越大。
- **桶**：这台设备是这个账号的可信设备 → 桶 = 设备号；否则 → 桶 = `u`（所有陌生设备共用一个）。
  攻击者从陌生设备错满 7 次，冷却的是 `u` 桶，**主人在自己的老设备上照常能用密码登录**。
  这是「只能放宽」的一个应用：可信桶只对存在的账号存在，攻击者永远落在 `u` 桶。
- **只锁密码这一个通道**：邮箱验证码登录、找回密码不受影响。被恶意冷却的人随时有路可走。
- **计数**：只在密码比对失败（含查无此人的密码登录）时 +1。冷却期间的尝试**不验密码、不加计数**，直接返回剩余时间。
- **清零**：这个身份登录成功（清所有桶）；重置密码成功（清所有桶，并把 `t_member_operation_limit` 里的记录置为解冻、`unlock_type = 2`）；
  24 小时内没有新的失败（键 TTL = 24h，每次失败续期）。
- **留痕**：冷却到 `recordFrom`（60 分钟）及以上、且账号存在时，往 `t_member_operation_limit` 写一行（`operation_type = 1`，
  原因「密码连续错误 N 次」，`expire_time` = 冷却结束）。后台可见、可人工解除（`unlock_type = 3`，同时删 Redis 键）。
  60 秒、5 分钟这种短冷却不落库，否则那张表会被手滑的人刷满。
- **自助解除**：用户走 OTP 找回密码 → 重置成功即清零。这条路今天就有（`MemberPasswordResetService`），只需在成功处加一行清计数。
- **与旧账号锁的关系**：直接删掉 `MemberOperationLimitService` 里 LOGIN 类型的计数逻辑，不并存（生产没有正在被锁的人）。
  `t_member_operation_limit` 表与 CHANGE_PASSWORD 类型保留。邮箱验证码输错不进阶梯：验证码自己有「错 5 次作废」，不需要第二道。

#### IP 被多少账号尝试过 `IP_ACCOUNT_FANOUT`

- 键 `login:ip:ids:{IP}`（Redis ZSET，成员 = 身份摘要前 16 位十六进制，分数 = 最近一次出现的时间）。
  ✅ 2026-10-16 起是**滑动窗口**：成员各自到点掉出去，不再是「整个集合首次写入起 1h 过期」。
- 每次登录请求**在规范化身份之后、找人之前**写入 —— 不管账号存不存在都算，所以不泄露任何东西。
- 数的是「尝试过的不同账号」，不是「登录成功的」：撞库的特征正是一个 IP 挨个试一批号，成功的只是极少数。
- 校园网、公司出口天然会有很多账号，所以第一档是滑块不是限流；限流档受「老设备豁免」（P1）和 IP 白名单约束。

#### 会员最后活跃时间（`LOGIN_MATRIX` 的前提）

**为什么不能按「最后一次登录」算沉睡**：会话令牌 30 天有效、**不续期**（全景图鉴 §6.3）。
一个每天都在用的人每 30 天才重新登录一次 —— 按登录日志算，**每个活跃用户每个月都会被判一次沉睡**。

- `t_member` 加一列 `last_active_time`（§5.5）。
- 写入：网关 `AuthenticationFilter` 认出会员后，`SET mbr:active:{会员号} 1 NX EX 3600` 成功（即这一小时内第一次）才异步通知会员域更新这一列。
  与 `t_device.last_active_time` 同一种节流写法（`DeviceDispositionService.touch`）：一个人一小时最多写一次库。
- 注册成功时同步写入一次（= 注册时间），所以正常情况下这一列不为空。
- 读取时仍为空（异步上报丢了之类）：退回 `MAX(最近一次成功登录, 注册时间)`。

#### 画像（IP 熟悉度、常去国家、上次登录）

来自 `t_member_login_log`：`member_id = ? AND status = 成功 AND create_time >= NOW() - 90 天`，外加 `t_member.register_ip`。

🔴 **不解析登录日志里的 `ip_region` 字符串**：`SolvelaIpUtil.getRegionList` 会把缺失的段**直接删掉、不占位**，
`中国|0|0|0|阿里云` 存下来是 `中国|阿里云` —— 第 2 段是省还是 ISP 分不出来。画像取 `client_ip`，
由 `IpIntel.resolve(ip)` 重新解析成按位置的 `{country, province, city, isp}`（进程内 xdb 查找，一次微秒级）。

画像结构（Redis `mbr:risk:profile:{会员号}`，1 天，成功登录后删）：

| 字段 | 内容 | 用在 |
|---|---|---|
| `recentPrefixes` | 最近 10 个**不同网段**（按时间倒序去重）+ 注册 IP 的网段 | 严格熟悉 |
| `recentPlaces` | 上面那些 IP 的「国家\|省\|市 + ISP」 | 宽松熟悉 |
| `countries` | 90 天内出现过的国家 | `NEW_COUNTRY` |
| `lastSuccess` | 最近一次成功登录的 `{country, province, time}`（任何设备上的） | `IMPOSSIBLE_TRAVEL` |
| `successCount` | 90 天内成功登录次数 | 冷启动判断 |

冷启动：`successCount < 3` 时 `NEW_COUNTRY` 不判。IP 熟悉度没有冷启动豁免 —— 列表为空就是陌生，
新号在新设备、新网络上登录要 OTP，这是矩阵本来的意思（注册设备算可信、注册 IP 算熟悉，所以在注册那台机器上不会被打扰）。

#### 其余

| 规则 | 规格 |
|---|---|
| `IMPOSSIBLE_TRAVEL` | 与 `lastSuccess` 比：国家不同且间隔 < 2h，或省不同且间隔 < 30min。没有 `lastSuccess` 不判；任一侧缺省份时只按国家判 |
| `ACCOUNT_FAIL_BURST` | 🔴 **不能从登录日志数失败**：观察档签票、被账号锁挡下，写的也是 `LOGIN_FAIL`。另起 Redis 有序集合 `mbr:risk:fail:{会员号}`（成员 = IP，score = 时间，1h），在密码错、邮箱码错两处写 |
| `NO_DEVICE` | `deviceId` 为空 |
| `IP_DATACENTER` | ISP 段包含 `params.keywords` 任一（初始：阿里云、腾讯云、华为云、百度云、京东云、Amazon、Google、Microsoft、DigitalOcean） |
| 名单匹配 | 本地缓存，IP 精确命中或落在某个 CIDR 内 |

IP 为空、内网 IP：所有 IP 维度的规则不判。

## 5. 表设计

### 5.0 哪些建表，哪些不建

判据沿用项目已有的两条：**丢了不要紧的东西不值一张表**；**能从库里查出来的，不维护第二份**。

| 东西 | 去处 | 理由 |
|---|---|---|
| 规则参数、分级、矩阵格、档位、全局滑块开关 | **表** `t_member_risk_rule` | 后台逐条改、不发版；改动走 `DataTracer` 留痕 |
| 黑白灰名单（IP、IP 段、身份摘要、会员白名单） | **表** `t_member_risk_list` | 人工判过的东西，丢了会往不安全的方向偏 |
| 每次决策 | **表** `t_member_risk_event` | 追溯与误伤分析的唯一数据源；补上「查无此人一行不留」 |
| 规则命中明细 | **表** `t_member_risk_hit` | 按规则统计命中与误伤，是「陪跑 → 生效」的依据 |
| 会员最后活跃时间 | **列** `t_member.last_active_time` | 矩阵的活跃度维度；Redis 丢了会让所有人变沉睡，不能只放缓存 |
| 画像、设备信任、各维度计数、阶梯计数 | Redis / 现有存储 | 能现算或丢了只是多验一次 |
| 冷却 ≥ 60 分钟的记录 | 复用 `t_member_operation_limit` | 已有「功能级、带到期、可解冻」的语义与后台页面 |
| 打分分档线 | 配置 | §3.4 |

**为什么不和登录日志合并**：登录日志是「这个人的登录轨迹」（`member_id NOT NULL`、给客服和「我的登录记录」看）；
决策流水是「这一次尝试被怎么判了」（可以没有会员、按 IP / 设备 / 身份摘要查）。

所有表在 member 域（`t_member_risk_*`），**不放进 `solvela-risk`**：那是营销发奖前的风控链，与账号安全是两件事。

### 5.1 `t_member_risk_rule` —— 规则

规则的**逻辑在代码里**（每条一个 Java 类），表里只存参数、分值、档位。不做规则 DSL（§10）。

```sql
CREATE TABLE `t_member_risk_rule` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT 'id',
  `rule_code` varchar(32) NOT NULL COMMENT '规则编码，与代码里 MemberRiskRule#code() 一一对应。启动时双向校验',
  `rule_name` varchar(64) NOT NULL COMMENT '给人看的名字',
  `event_type` tinyint NOT NULL COMMENT '适用事件：1-登录。见 MemberRiskEventTypeEnum',
  `phase` tinyint NOT NULL COMMENT '阶段：1-前置（验凭据之前）, 2-后置（验凭据之后）',
  `rule_type` tinyint NOT NULL COMMENT '类型：1-强规则（固定处置）, 2-强规则（分级 / 矩阵，处置写在 params）, 3-打分规则',
  `direct_decision` tinyint DEFAULT NULL COMMENT '固定处置：见 MemberRiskDecisionEnum（1-放行 … 7-拒绝）。分级与打分规则为 NULL',
  `score` smallint NOT NULL DEFAULT '0' COMMENT '打分规则命中时加的分。强规则为 0',
  `rule_group` varchar(16) DEFAULT NULL COMMENT '互斥组：同组命中只取最高分（如 GEO）。NULL 表示独立证据，照常相加',
  `mode` tinyint NOT NULL DEFAULT '1' COMMENT '档位：0-关闭, 1-陪跑（只记录）, 2-生效。GLOBAL_CAPTCHA 的开关就是它',
  `bypass_by_trust` tinyint NOT NULL DEFAULT '1' COMMENT '可信设备是否跳过：1-跳过, 0-照常执行（强规则、不可能旅行必须为 0）',
  `params` json DEFAULT NULL COMMENT '参数，形状由各规则声明并在保存时校验。分级如 {"window":"1h","tiers":[{"over":5,"do":2},{"over":20,"do":6}]}',
  `description` varchar(256) DEFAULT NULL COMMENT '它在抓什么、为什么是这个阈值',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_mbr_risk_rule_code` (`rule_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='会员风控规则（逻辑在代码，参数与档位在表）';
```

- **启动双向校验**：表里有、代码里没有 → WARN 并当 `OFF`；代码里有、表里没有 → **启动失败**（一条没有档位的规则，默认开或关都是错的）。
- **种子数据进 `data-baseline.sql`**，P0 档位即 §4.1 / §4.2 两张表。
- **缓存**：各实例本地缓存全表，30 秒刷新。后台改完最多 30 秒生效。
- **参数在保存时校验**：存进去一个读不出来的 JSON，等于把那条规则静默关掉。
- `LoginIpGuardProperties`、`DeviceGuardProperties`、`captcha.password-login`、`MemberOperationLimitProperties`（LOGIN 部分）
  里的阈值**写进种子数据后删掉这些配置类**。生产没有线上配置，种子数据取代码里的默认值即可；本地 docker 的 yml 里若有覆盖，一并删掉。

### 5.2 `t_security_list` —— 名单（原 `t_member_risk_list`）

**表结构移到了 `docs/架构/网关阶梯限流-技术方案.md` §6.3，并改名为 `t_security_list`**（2026-10-17）：名单现在是网关与登录风控共用的平台级表 ——
网关读 IP 黑 / 灰 / 白名单（安全闸、限流），并且会**自动**写入（蜜罐、关键字、限流重罚，`source = 2`）。
结构以那边为准，这里只保留登录风控**怎么用**名单。

**各名单豁免什么、不豁免什么**（豁免面刻意窄 —— 白名单上的东西恰恰是攻击者最想拿到的）：

| 名单 | 效果 | 不豁免 |
|---|---|---|
| IP 白名单 | 跳过 IP 维度的计数与限流（4 条 `IP_*`） | 全局滑块、密码冷却、设备规则、矩阵、后置 |
| **会员白名单** | 跳过矩阵（前后两格按 PASS）与打分 | 全局滑块、**密码冷却**、IP 限流、设备封禁 / 观察档、黑名单 |
| IP / IP 段 / 身份黑名单 | `DENY`（对外与限流同一句） | — |
| IP / IP 段 灰名单 | 加条目上的分 | — |
| **会员灰名单**（2026-10-17 新增） | 登录矩阵里可信设备按新设备算；资产出口每次都要二次验证 | 不是处罚，不冻结任何功能，对本人不提示 |

- **会员白名单不豁免密码冷却**：否则白名单账号可以被无限次猜密码，而白名单账号（审核账号、内部账号）往往正是最值得猜的。
- 会员白名单的典型用途：App Store / 应用市场审核账号（审核员在海外、每次都是新设备）、自动化测试账号、压测账号。
- **设备、会员没有黑名单维度**：它们有自己的状态位（`t_device.status` 封禁、`t_member.status` 冻结），名单里再放一份就有了两个答案。
- **到期默认 30 天**：IP 会被回收、重新分配。永久黑名单迟早误伤一个无辜的新住户。
- **缓存**：本地全量缓存，30 秒刷新；CIDR 匹配在内存里做。

### 5.3 `t_member_risk_event` —— 决策流水

**一次登录尝试一行**，在 `authenticate` 的 `finally` 里写。凭票验码是另一个请求，写**另一行**并用 `ref_event_id` 指回去。

```sql
CREATE TABLE `t_member_risk_event` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT 'id',
  `event_type` tinyint NOT NULL COMMENT '事件：1-登录, 2-登录二次验证。见 MemberRiskEventTypeEnum',
  `ref_event_id` bigint DEFAULT NULL COMMENT '关联事件：二次验证指向签票的那次登录',
  `member_id` bigint DEFAULT NULL COMMENT '会员号。🔴 可空：查无此人时没有',
  `identity_hash` binary(32) DEFAULT NULL COMMENT '登录身份的 PiiHasher 摘要，与 t_member.phone_hash/email_hash 同算法',
  `login_type` tinyint DEFAULT NULL COMMENT '登录方式：见 MemberLoginType',
  `device_id` char(32) DEFAULT NULL COMMENT '设备号，可空（没带设备令牌）',
  `device_trust` tinyint DEFAULT NULL COMMENT '设备信任：0-无设备, 1-新设备, 2-老交情, 3-验证过, 4-注册设备。查无此人时为 NULL',
  `ip_familiar` tinyint DEFAULT NULL COMMENT 'IP 熟悉度：0-陌生, 1-宽松熟悉, 2-严格熟悉。查无此人时为 NULL',
  `dormant` tinyint DEFAULT NULL COMMENT '是否沉睡：0-活跃, 1-沉睡。查无此人时为 NULL',
  `client_ip` varchar(39) DEFAULT NULL COMMENT '客户端IP',

  `captcha_passed` tinyint NOT NULL DEFAULT '0' COMMENT '本次请求是否带了有效滑块通行票',
  `pre_score` smallint NOT NULL DEFAULT '0' COMMENT '前置得分（只算生效规则）',
  `post_score` smallint NOT NULL DEFAULT '0' COMMENT '后置得分（只算生效规则，不含前置分）',

  `label_source` tinyint DEFAULT NULL COMMENT '标注来源：1-用户「这不是我」, 2-老设备上点「是我」, 3-客服',
  `label_time` datetime DEFAULT NULL COMMENT '标注时间',
```

**结局 `outcome`**（「这次尝试最后怎么样了」，与「风控判了什么」分开）：

| 值 | 含义 | 值 | 含义 |
|---|---|---|---|
| 1 | 登录成功 | 8 | 被前置限流 / 拒绝 |
| 2 | 凭据错误 | 9 | 被后置限流 / 拒绝 |
| 3 | 查无此人 | 10 | 已签二次验证凭票（等待验码） |
| 4 | 账号冻结 | 11 | 二次验证通过（仅 event_type=2） |
| 5 | 密码冷却 / 账号锁定中 | 12 | 二次验证失败（仅 event_type=2） |
| 6 | 格式非法 | 13 | **内部异常** —— 见下 |
| 7 | 需要滑块（没带票） | | |

🔴 **13 存在的唯一理由是守住「每次尝试都有一行流水」**：`RiskSession` 每条返回路径都走 `end(outcome, …)` 当场落库，
而主干抛了未预料的异常时 `end` 根本没被调用 —— 那时由 `close()` 兜底补一行。
没有这一档的话，异常路径就**恰好**没有流水，而「登录报 500 时风控判了什么、命中了哪几条规则」正是最想知道的那一刻。

`device_trust`、`ip_familiar`、`dormant` 三列让矩阵落在哪一格**直接可查**，不用从命中明细里反推 ——
「上周有多少人落在『新设备 + 陌生 IP』」是一条 GROUP BY。

- **写入失败绝不影响登录**；**同步写**（§3.9）。
- **标注是唯一允许的更新**：按 `(id, create_time)` 定位到分区，只改 `label*` 三列。
- **保留 6 个月，过期靠 `DROP PARTITION`，绝不 `DELETE`**。
  ✅ 已落地：定时任务 **【基础】按月分区维护**（`partitionMaintain`，每天 03:50），
  提前 `REORGANIZE pmax` 出下两个月，`DROP` 掉保留期之外的，三张分区表一起管
  （两张风控表 + `t_member_login_log` —— 后者的分区原先只建到 2027-01 而<b>没有任何东西会去补</b>）。
  实现在 `solvela-base-data/partition/`，真实 DDL 由 `PartitionMaintainTest` 在探针表上验过。
  几道安全闸见那个类的注释（只认按 `create_time` 分区且有 `pmax` 的表、名字与上界要对得上、单次删除有上限）。
- **按月分区，不按天**（理由见 §12.1）。
- **查询必须带 `create_time`**：凭票里同时存 `eventId` 与事件时间；后台按 id 查详情也带时间。
- 量级：日活十万、人均 0.3 次登录，一天三万行，一个月百万行级。

### 5.4 `t_member_risk_hit` —— 规则命中明细

```sql
CREATE TABLE `t_member_risk_hit` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT 'id',
  `event_id` bigint NOT NULL COMMENT '决策流水 id',
  `rule_code` varchar(32) NOT NULL COMMENT '规则编码',
  `mode` tinyint NOT NULL COMMENT '命中时规则所处的档位：1-陪跑, 2-生效。规则档位会变，这里存当时的',
  `decision` tinyint DEFAULT NULL COMMENT '这条规则给出的处置（强规则 / 矩阵）。打分规则为 NULL',
  `score` smallint NOT NULL DEFAULT '0' COMMENT '命中时加的分（强规则为 0）',
  `detail` varchar(128) DEFAULT NULL COMMENT '命中依据，给人看：「新设备 + 陌生IP」「本小时第 6 个不同账号」「连续错误第 4 次，冷却 5 分钟」',
  `error` tinyint NOT NULL DEFAULT '0' COMMENT '1 = 特征取不到、按未命中处理（§3.9）',
  `create_time` datetime NOT NULL COMMENT '🔴 写入时显式赋成决策流水的 create_time（不用 DEFAULT）：两表按 (id, create_time) 关联才能裁剪分区',
  PRIMARY KEY (`id`,`create_time`),
  KEY `idx_mbr_risk_hit_event` (`event_id`,`create_time`),
  KEY `idx_mbr_risk_hit_rule` (`rule_code`,`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='会员风控规则命中明细（只记命中，按月分区）'
/*!50500 PARTITION BY RANGE COLUMNS(create_time) ( ...与决策流水相同... ) */;
```

「触发了什么规则、结果是什么」就是这两张表合起来：流水一行说**结论与结局**，明细若干行说**每条命中的规则各自给了什么、依据是什么**。
后台流水详情页把两者并排展示。只记命中，没命中的规则不写行。

**DAO 为什么没有 mapper XML**：四张表的读写都是单表，MyBatis-Plus 的 `BaseMapper` 加两段注解 SQL 就够了。
两段注解是刻意的：
- `insertEvent` 要 `UNHEX(#{identityHashHex})`（`binary(32)` 不进 Java 类型系统，见 `PiiHasher`），所以不能走通用 insert；

### 6.2 `MemberAuthService.authenticate` 的变化

```java
Member member = findMember(loginType, identity);   // 提前到前置之前；null = 查无此人，照常往下走

try (RiskSession risk = riskEngine.open(EventType.LOGIN, loginType, identity, member, cmd)) {

    RiskDecision pre = riskEngine.evaluatePre(risk);           // 原：deviceGuard.checkLogin + loginIpGuard.check
    if (pre.is(CAPTCHA) && !cmd.captchaPassed()) {
        return risk.end(Outcome.CAPTCHA_REQUIRED, MemberAuthResult.captchaRequired());
    }
    if (pre.atLeast(COOLDOWN)) {
        return risk.end(..., MemberAuthResult.limited(pre.retryAfterSeconds()));
    }

    if (member == null) { dummyPasswordCheck(); ... }          // 新增：查无此人也跑一次 Argon2
    ...状态 / 验凭据...                                         // 不变；密码错时 cooldownStore.recordFail

    RiskDecision post = riskEngine.evaluatePost(risk);         // 原：checkDeviceChallenge + checkMemberFanout
    if (post.needsOtp()) {
        String ticket = challengeStore.issue(..., verifyRouter.route(post, loginType, member), risk.eventRef());
        return risk.end(Outcome.CHALLENGED, MemberAuthResult.challenge(ticket));
    }
    ...
    return risk.end(Outcome.SUCCESS, completeLogin(member, cmd));
}
```

**网关侧的滑块从「先拦」改成「先核销、让域来判」：**

- 今天：`MemberLoginController.login` 对密码登录无条件 `captchaService.require(...)`，没票直接 `CAPTCHA_REQUIRED`。
- 之后：带了票就核销（`captchaService.consumeIfPresent`，一张票照旧只能用一次），结果作为 `MemberAuthCmd.captchaPassed` 传给域；
  域判出「需要滑块而没过」时返回 `captchaRequired()`，网关映射成**同一个** `CAPTCHA_REQUIRED` 错误码。
- **客户端不用改**：它本来就是「收到 `CAPTCHA_REQUIRED` → 拖图 → 带票重试」。全局滑块开着时，行为与今天逐字相同。

其余：

- `LoginChallengeStore.Challenge` 加 `channel`（替代 `sendChallengeCode` 里按登录方式的 switch）与 `eventRef`（id + 时间）。
- `MemberPasswordResetService` 重置成功处加一行：清阶梯计数、解冻冷却记录（`unlock_type = 2`）。
- `AuthenticationFilter`（网关）加活跃时间节流上报（§4.4）。

  （客服工具、脚本）绕过去就能写出一条读出来会炸、或者**永远不命中**的名单。
- 🔴 **值要用缓存命中时的同一个解析器（`IpRange`）先试一次**。格式写错的表现是

- 🔴 **写完立刻重载本实例的名单缓存**，其余实例按自己的周期（30 秒）刷。

- 身份摘要**原样显示**，不还原成明文（还原不了，那正是它的用途）。

**密码冷却的人工解除**（第一批刻意没接的那半）：

- 🔴 真正拦住用户的**不是 `t_member_operation_limit` 那张表**，而是 Redis 里那个带 TTL 的冷却键。

  这正是这颗按钮一直没接的原因：一个解除了却不生效的按钮比没有按钮更糟。
- 冷却是按**身份摘要**算的，而后台只知道会员号，所以解冻时按号取回联系方式再算摘要

  手机号和邮箱两条都清：账号可能用任一条登录。
| **看板** ✅ | 每日结论分布、矩阵各格人数、OTP 通过率、按规则的命中（含「取特征失败」数）、生效与陪跑不一致数 | P1 |

看板的几条：

- 🔴 **四组数一个接口返回**，共用同一个时间窗。拆成四个接口，前端就有机会用四个不同的窗去问，
  然后把对不上的数摆在同一个屏幕上 —— 而那种错没人查得出来。
- 🔴 **核身通过数靠 `ref_event_id` 指回签票那一行来数**，不是单独数「验证通过」的条数。
  后者会把窗口**之前**签的票算进来，于是通过率可能大于 100% ——
  那个数字一旦出现过一次，整块看板就没人信了。
- 🔴 **矩阵统计要求三列非空**：查无此人时它们是 NULL，混进来会多出一格「全是空」的，
  而那一格不对应矩阵里的任何位置。
- 🔴 **「取特征失败」单独一列**。一条规则在规则页上写着「生效中」，而它每次都取不到特征，
  实际什么也没拦 —— 那种静默失效只有这一列看得见，所以它在看板上要显眼。
- 窗口**一次最多 90 天，超了直接报错不悄悄截断**：截断的话页面上那个「最近一年」的筛选器
  会给出一个只含 90 天的数，而没人知道。
- 聚合查询单独一个 `MemberRiskStatDao`，不塞进 `MemberRiskEventDao` ——
  一个是「一次尝试的读写」，一个是「一段时间的聚合」，混在一起之后很容易有人
  在点查接口旁边顺手加一条全表聚合，而评审时看不出来。
- 刻意**不引图表库**：四组数里真正要看趋势的只有结论分布，而它一天一行、30 行以内一眼扫得完。
  为此引一个几百 KB 的图表库，换来的是一张更好看但信息量相同的图。

### 6.4 返回给前端的契约：每个码弹什么

#### 五条约定

1. **码说「下一步该做什么」，不说「触发了哪条规则」。** 前端分支只需要知道「要滑块 / 要验证码 / 要等 / 要去绑定」，
   规则名进了响应就是给攻击者的调参手册。触发了什么规则只在后台的流水详情里看。
2. **响应体给事实，不给 UI。** `details` 里放的是 `retryAfterSeconds`、`channel`、`alternatives`、`need` 这类事实，
   弹什么窗、跳哪个路由由前端映射。这是 `ApiErrorResponse` 类注释里已有的原则（「传输信封里不该有 UI 的概念」）：
   后端下发「弹窗类型 / 跳转地址」的话，App 和 H5 的页面结构不同，一个码就得为每个端写一份。
3. **验密码之前的回答，对「有号 / 没号」逐字节相同**，包括 `details`。`PASSWORD_COOLDOWN` 与 `BAD_CREDENTIALS` 的
   次数信息之所以敢给，是因为阶梯按身份摘要计数，没号的身份算出来的数一模一样（§4.4）。
4. **现有的码不改名**（`ApiErrors.code()`：改名等于改接口契约）。`DEVICE_VERIFICATION_REQUIRED` 的触发面变宽了
   （观察档之外，矩阵和打分也会触发），但前端的处理完全一样，所以沿用。前端不认识的新码会落到 `INTERNAL` 但保留后端的 message
   （`errors.ts` 的 `toApiError` 已经这样做），新码先于前端上线也不会让用户看到「未知错误」。
5. **429 同时带标准的 `Retry-After` 响应头**，值与 `details.retryAfterSeconds` 相同。今天剩余时间只写在 message 里
   （「请 5 分钟后再试」），前端没法做倒计时，只能原样展示。

   ✅ 落地时统一加在 `ApiExceptionHandler` 里（429 且 `details` 带 `retryAfterSeconds` 就带上这个头），
   不是每个抛异常的地方自己加。🔴 **只在 429 上加**：403 / 409 上 `Retry-After` 的语义是「这个资源多久后可用」，
   与「你多久后可以再试」不是一回事，带上去会让中间层做出错误的缓存决定。

6. ✅ **`details` 在前端保持 `Record<string, unknown>`，不收紧成按码区分的联合类型**（与原计划相反，理由如下）。
   它来自网络，而网络上的东西没有类型 —— 联合类型只是一句编译期断言：后端改了字段名、或者老版本服务端还没带上
   某个字段时，TypeScript 什么也不会说，而页面代码会对着 `undefined` 读属性。
   所以改成在 `ApiError` 上放几个**运行时校验一次**的取值器（`challenge` / `retryAfterSeconds` /
   `passwordCooldown` / `attemptsBeforeCooldown`）：页面拿到的是已经验过的 `ChallengeDetails | null`，
   既不用自己写 `typeof x === 'string'`，也没有假的类型安全。

| **`PASSWORD_COOLDOWN`** ✅ | 429 | 密码阶梯冷却中 | `retryAfterSeconds`；`alternatives`：`["CODE_LOGIN", "PASSWORD_RESET"]` | 弹窗：「密码错误次数过多」+ 倒计时 + **[用验证码登录] [找回密码] [知道了]**；登录按钮按倒计时置灰 | 登录页 | P1 |
| `OPERATION_LIMITED` ✅ | 429 | IP / 设备限流，以及前置 `DENY`（对外不区分） | `retryAfterSeconds` | 轻提示 + 登录按钮倒计时。**不给任何其它按钮**：这一档的对象主要是脚本，给真人的出路是等 | 登录页 | P0 补字段 |
| `DEVICE_VERIFICATION_REQUIRED` ✅ | 401 | 后置要 OTP（矩阵、观察档、打分） | `challengeTicket`；`channel`：`EMAIL` / `SMS` | 原地展开验证码栏（已有）；文案按 `channel` 说「验证码已发到你的邮箱 / 手机」。**不是登录失败**，不清空表单 | 登录页（已有） | P0 补 `channel` |
| `CHALLENGE_EXPIRED` | 401 | 凭票过期 / 码错满作废 / 换了设备 | — | 收起验证码栏，回到输密码那一步（已有） | 登录页（已有） | 已有 |
| **`LOGIN_VERIFY_UNAVAILABLE`** ✅ | 403 | 要 OTP，但这个账号**没有任何能发码的通道**（今天只可能是：手机号账号 + 短信未接 + 没绑邮箱） | — | 弹窗「暂时无法验证你的身份」+ 文案指向客服（App 还没有客服入口，所以没有按钮） | 登录页 | P2 |
| `ACCOUNT_DISABLED` | 403 | 冻结 / 注销 | — | 弹窗 + [联系客服] | 登录页（已有） | 已有 |
| `DEVICE_REQUIRED` | 401 | 设备令牌 enforce 档下没带令牌 | — | 「请更新到最新版本」 | 拦截器（已有） | 已有 |

`alternatives` 只取决于**登录方式**，不取决于账号：邮箱登录给 `CODE_LOGIN` + `PASSWORD_RESET`；
手机号登录在短信接通之前是**空数组**（手机号找回也要短信，两条都走不通），前端此时只显示 [知道了]。
🔴 硬塞一个 `PASSWORD_RESET` 进去的话，用户点过去会撞上一个发不出码的页面 —— 那比没有按钮更糟。

✅ 前端那颗 [用验证码登录] 点下去时**要把倒计时停掉**：被冷却的只有密码这一条通道。
留着倒计时，用户照我们说的切过去了，却发现按钮还是点不动。

🔴 **`LOGIN_VERIFY_UNAVAILABLE` 绝不能给「去绑定」**。此刻没有登录态，而对面这个人只证明了「知道密码」 ——
让一个没完成验证的人去给账号绑联系方式，等于让他给别人的账号加一条**他自己的**找回通道，之后用它重置密码就是永久接管。

#### 登录之后（有登录态）

| 码 | HTTP | 什么时候 | `details` | 前端怎么做 | 谁处理 | 期 |
|---|---|---|---|---|---|---|
| `STEP_UP_REQUIRED` | 403 | 不受信任的设备上做敏感操作 | — | 弹二次验证框，通过后自动重试原请求（已有） | 拦截器（已有） | 已有 |
| **`CONTACT_BIND_REQUIRED`** ✅ | 409 | 要二次验证，但账号**没绑**能收码的联系方式 | `need`：`EMAIL` / `PHONE` | 弹窗「需要先绑定邮箱」+ **[去绑定邮箱] [知道了]**。去绑定 → 绑定页，带 `redirect` 参数，绑完回到原页面。**不自动重试原请求**：中间隔了一次页面跳转，让用户自己再点一次 | 拦截器（新的全局弹窗） | P1 |
| **`CONTACT_COOLING`** ✅ | 409 | 联系方式是**在不受信任的设备上**新绑的，还在冷静期内（见下） | `availableAt`（时间戳） | 弹窗「它要到 X 月 X 日之后才能用于安全验证；你也可以在常用的设备上操作」+ [知道了]。🔴 **刻意没有「重新绑定」** —— 再绑一次只会再冷静 7 天 | 拦截器 | P1 |

🔴 **找回密码那条路上不给 `availableAt`**：它是未登录接口，而这个时间点属于账号内部状态 ——
任何人输一个邮箱就能问出「这个号最近换过联系方式吗」。那里的文案只说「暂时不可用，请在你常用的设备上操作」。
| **`ASSET_OUT_FROZEN`** ✅ | 403 | 点过「这不是我」，资产出口冻结中 | `unlock`：`PASSWORD_RESET` | 弹窗「账号处于保护状态，重置密码后恢复」+ **[去重置密码]** | 拦截器 | P1 |

`CONTACT_BIND_REQUIRED` 替代今天 `StepUpController` 里 `NO_EMAIL → CONFLICT「请先绑定邮箱」` 的写法：
`CONFLICT` 是个通用码，前端没法据此弹出「去绑定」，只能把 message 当普通错误展示。

#### ✅ 核身通道写在凭票上（落地时补的一条）

原计划只在错误响应里加一个 `channel` 字段给前端看。实际做下来发现**服务端自己也要跟着它走**，
否则换通道这件事只做了一半：

- `sendChallengeCode` 原来按 `challenge.loginType()` 分支（手机号 → 短信、邮箱 → 邮件），
  那等于把核身路由的判断复制了一份 —— 两份一旦漂移，表现是「告诉用户发到了邮箱，码却发去了短信」；
- 更要紧的是 `verifyChallenge` 也在按登录方式验。换通道时码发去了邮箱、这里却拿登录用的手机号去验，
  结果是**用户收到了码、输对了码，却永远被告知「验证码不正确」**。

所以通道由 `VerifyRouter` 在签票时选定、**写进票里**，发码与验码都只看票。
发到/验哪个邮箱、手机号也不再看票上的 `identity`（换通道时那两个根本不是同一个东西），
而是按会员号现取当前绑定的那一个；取不到时回 `CHALLENGE_EXPIRED`，不是「码错了」——
后者会让用户一直重发一个永远验不过的码。

另外 `LOGIN_VERIFY_UNAVAILABLE` 的判断必须排在**签票之前**：票签出去却发不出码，
用户就停在一个「获取验证码」永远失败的界面上。

#### 🔴 「去绑定」必须配冷静期

**首次绑定邮箱今天不要求任何额外验证**（`MemberEmailBindService` 类注释：「首次绑定不要求这一步」），绑定接口也没有挂 `@StepUpRequired`。
于是对一个没有邮箱的账号（手机号注册），一个知道密码的人在新设备上可以：
登录 → 加地址被要求二次验证 → 没有邮箱 → **去绑定他自己的邮箱** → 用这个邮箱通过二次验证 → 把东西搬走；
或者更糟：用这个邮箱走找回密码 → 永久接管。

把「没绑就去绑定」做成显眼的按钮，就是把这条链铺成了主路。所以：

- ✅ **在不受信任的设备上新绑（含首次绑定）的联系方式，7 天内不能用于**：二次验证、登录 OTP、找回密码；
- ✅ 冷静期内需要它时返回 `CONTACT_COOLING`；
- ✅ 在**可信设备**上绑的不受此限 —— 主人在自己的老手机上补绑邮箱，不该被拦。
  而且在可信设备上<b>重绑一次就解除</b>冷静期：主人回到自己的老手机上再绑一遍，没有理由继续拦他；
- ✅ 绑定成功时推一条站内通知「你的账号刚刚绑定了邮箱 a***@x.com」（新模板 `CONTACT_BOUND`，SYSTEM 分类关不掉）。

今天生产只开放邮箱注册，没有「没绑邮箱」的账号，所以这条链暂时打不通；但手机号注册一开放就通了，要在那之前补上。

落点：`solvela-member/contact/ContactCoolingStore`（Redis，到点自动消失）+ 两个绑定服务埋点 +
三处拦截（`MemberStepUpService.sendCode/verify`、`VerifyRouter`、`MemberPasswordResetService`）。

实现时定下来的几条：

- 🔴 **验码那一步也要挡，不只挡发码**。码有 5 分钟有效期 —— 一个在冷静期开始<b>之前</b>发出去的码，
  冷静期内照样能拿来验过。
- 🔴 **登录 OTP 那一处不单独报错，而是把冷静中的通道「当作没有」**。于是
  「还有另一条通道就走另一条、一条都没有才拒绝」这套逻辑一行都不用改 ——
  而那正是对的行为：主人新绑的邮箱还在冷静期，但他的手机号还能收码。
- 🔴 **找回密码的检查排在验码之后**：要先知道是哪个会员才查得到他的冷静期，
  而在那之前这个接口对「有号 / 没号」的回答必须保持一致。
- 🔴 **记不上 / 读不出来时按「不冷静」处理**（往宽的方向偏）。这与大多数风控判断相反，是刻意的：
  往严的方向偏意味着 Redis 一抖动，所有人的邮箱都突然不能用来核身、不能找回密码 ——
  那是一个比漏过更大的故障。
- 通知比冷静期<b>更早</b>起作用：冷静期挡的是「用它核身」，而主人要先**知道**有人动了账号才会去改密码。
  盗号者能把站内信标成已读，但改不了它的存在。

#### 不是错误码、但前端要接的两个接口

| 接口 | 用途 | 前端 |
|---|---|---|
| `POST /auth/security/prompts` ✅ | 列出待确认的「刚才是你吗」（§8.1，只在**受信任的老设备**上才有内容） | 冷启动和回到前台时调一次；有就弹：「你的账号 10:21 在 深圳 的手机 App 上登录，是你吗？」**[是我] [不是我]** |
| `POST /auth/security/prompts/answer` ✅ | `{promptId, isMe}`。`isMe = false` 等同「这不是我」 | 「不是我」要**二次确认**（它会让所有设备下线并冻结兑换），答完提示「已处理」→ 引导到重置密码 |
| `POST /auth/sessions/report` ✅ | 「我的登录设备」里某条会话旁的「这不是我」 | 同上 |

🔴 两颗按钮**刻意不等重**：「是我」是主按钮，「不是我」是次要的文字按钮 + 二次确认。
一样显眼的话，一半的人会随手点错，而点错「不是我」的代价落在他自己身上（兑换被冻住）。

🔴 拉待确认**失败就不弹，也不报错**：用户没有主动做任何事，不该看到一条失败提示；
更不能反过来「拉不到就拦住他」—— 那会让一次接口抖动变成整个 App 打不开。

## 8. 反馈闭环

### 8.1 标注从哪来

- **「这不是我」** ✅：「我的登录设备」每一条会话旁加一个按钮。点了 →
  1. 下线那台、撤销其余设备信任（等同「下线其他设备」）；
  2. **资产出口冻结到改密为止**：`t_member_operation_limit` 加操作类型 `ASSET_OUT`（加地址兑换、充话费），解冻方式「重置密码」；
  3. 那次登录的决策流水标成「确认被盗」。

  落点：`MemberStepUpApi.reportNotMe` + `MemberStepUpService`（冻结 → 撤信任 → 打标）、
  `risk/RiskLabelService` + `MemberRiskEventDao.labelNearestLogin`、网关 `POST /auth/sessions/report`、
  C 端 `SessionsView` 的二次确认 + `AccountNoticeDialog`。

  实现时定下来的几条：

  - **顺序是「冻结 → 撤信任 → 打标」**，按能止损的程度排。冻结是唯一能立刻止损的动作；
    撤信任只是让对方下次登录多验一道，而他此刻手里那个会话可能正在加收货地址。
  - 🔴 **打标失败不影响前两件**。会话与决策流水之间**没有引用**（令牌在网关签发、流水在域里写），
    所以只能按「会员 + 设备 + 时间相近（±5 分钟）」去找 —— 老会话没有设备号、流水已过期被 `DROP PARTITION`
    时压根找不到。为了一条分析数据让「这不是我」失败，等于在用户最需要我们办成事的那一刻办不成。
  - 🔴 **时间窗不只是为了找对**，它也是这条 UPDATE 唯一的分区裁剪依据；而 ±5 分钟的上限是为了
    不把同一台设备上**另一次**登录标错。只标 `outcome ∈ {成功, 二次验证通过}` 的行 ——
    被拦下的那些本来就没进去，标成被盗会让「漏过率」凭空变大。
  - 🔴 **下线会话留在网关**，不进域：令牌库住在 `solvela-auth`，域不认识令牌。
    网关先踢人再调域 —— 万一下游抖了一下，至少对方已经掉线了。
  - 举报一个会话说明账号已经漏了，所以**顺手把其余会话也踢掉**（当前这台除外）。
    只踢被举报那一个，攻击者另开的第二个会话还在，而用户以为自己已经把人赶出去了。
  - **冻结是幂等的**：连点两次不会多出一行，否则客服会看到两条生效中的限制，不知道该解哪一个。

- **资产出口这道闸** ✅：判断挂在现有的 `StepUpInterceptor` 上（`@StepUpRequired` 标注的那三个接口
  恰好就是加地址 ×2 + 充话费），冻结判断与信任判断**合成同一次下游调用**（`MemberStepUpApi.assetOut`）——
  分成两次的话，每个加地址 / 充话费请求都要跨进程两趟。

  - 🔴 **冻结压倒信任**：举报的人很可能正拿着那台「受信任的老设备」。先判信任的话，
    会话被偷的盗号者照样搬得走东西。
  - 🔴 **二次验证的 `off` / `observe` 档也拦冻结**。那个开关管的是「二次验证」这件事，
    而冻结是用户**自己要求**的保护 —— 绑在同一个开关上，意味着关掉二次验证顺带把「这不是我」作废了。
  - 🔴 **不复用 `STEP_UP_REQUIRED`**：那个码会让客户端去弹验证码框，而这一档**验过也过不去**，
    用户会验一次失败、再验一次再失败，完全不知道为什么。
  - 下游挂了时的取舍按档位分，与信任判断一致：`enforce` 不放行（这道闸守的是资产出口），
    `off` 放行（那一档连二次验证都不要，为一次抖动挡住所有人代价更大）。

- **重置密码是两个限制的自助出口** ✅（补上了第一批漏掉的一半）：`MemberPasswordResetService.reset`
  成功处现在会清掉**密码阶梯冷却的两个桶**，并把 `ASSET_OUT` 的冻结解开（`unlock_type = 2`）。
  🔴 少了这两行，用户改完密码还是进不去 / 还是兑换不了，而他已经用完了所有能自己做的事 ——
  它们正是密码阶梯敢用 24 小时那一档、资产出口敢「冻到改密为止」的前提。
- **在老设备上问「是你吗」** ✅：新设备登录成功、风控放行时记一条待确认，由老设备上的会话拉走并弹窗
  「你的账号刚在 XX 登录，是你吗？[是我] [不是我]」。🔴 **绝不在新设备本身上问**：盗号者会点「是我」，污染「确认本人」的样本。

  落点：`risk/SecurityPromptStore`（Redis 哈希）+ `risk/SecurityPromptService`、
  契约 `MemberSecurityApi`、网关 `POST /auth/security/prompts` 与 `/answer`、
  C 端 `SecurityPromptDialog`（挂在外壳上，冷启动与回到前台各拉一次）。

  实现时定下来的几条：

  - 🔴 **「在哪问」有两道判断，缺一不可**：当前这台设备**受信任**，并且问的**不是**当前这一台。
    只滤设备号的话，盗号者在**第二台**新设备上就能替主人回答。
  - 🔴 **答题也要在受信任的设备上**。只在列表那一步拦的话，拿到一个单号（比如从主人的截图里）
    就能直接调答题接口点「是我」。
  - 🔴 **创建点只有一个**：`NewDeviceLoginNotifier`。那里已经在判「这台设备新不新」，
    另写一份判断的话，两份漂移的表现是「发了邮件却没弹窗」或者反过来。
    提问**同步**写（一次 Redis 写），发信照旧异步 —— 发信线程池满了会丢任务，
    而丢掉提问等于丢掉一条标注，比丢一封邮件更难补。
  - 🔴 **Redis 哈希，不是一个装着 JSON 数组的 key**。数组要「读-改-写」，两次登录同时发生时
    后写的会覆盖前一个 —— 丢掉的恰好是并发登录（最可疑）那一次的提问。
  - 「不是我」**走 `reportNotMe` 同一个方法**，不在这里重写一遍三件事：两个入口的后果一旦漂移，
    用户从哪儿点的就决定了他被保护到什么程度。
  - 一个会员同时最多挂 **5** 条：被撞库刷出几十条提问，等于把弹窗变成骚扰。
  - 答题接口对「单号不存在 / 已答过 / 设备不受信任」**一律回 204**，不告诉客户端受理没有 ——
    区分出来就给了一个探测口（拿一堆单号试，看哪个「受理了」）。
  - 为什么单独一个 `MemberSecurityApi` 而不是挂在 `MemberStepUpApi` 上：试过，**编译不过** ——
    `MemberStepUpService` 实现 step-up 契约，而这两个方法的实现要反过来依赖它（判设备信任），
    同一个契约上就是循环。那次编译失败说出了一件真事：step-up 回答「这台设备此刻够不够可信」，
    这里回答「那一次登录到底是不是本人」，后者**用**前者的答案，而不是它的一部分。
- **OTP 通过**：弱的「确认本人」，不写 `label`，统计时单独算。
- **客服**：后台流水详情里手工标。

⚠️ 新设备提醒**邮件里仍然不放任何链接**（§12.1）。

### 8.2 一条规则从陪跑切到生效之前，要看的三个数

✅ **这三个数已经做进看板了**（`每条规则：切到生效会怎样` 那张表，一行一条规则）。
下面这段 SQL 保留作为口径的权威定义 —— 看板那条查询就是它按 `rule_code` 分组的版本。

🔴 做进看板而不是留一段手写 SQL，理由很具体：对着一张**按月分区**的表手写 join，
只会在出了问题之后才有人去做，而到那时该切的早就该切了。

```sql
-- 规则 X 近 14 天：命中多少、其中多少次直接登录成功、多少被确认被盗、多少会改变结论
-- （签了凭票的那些，验码结局在 ref_event_id 指回来的那一行，要再关联一次）
SELECT COUNT(*)                               AS hits,
       SUM(e.outcome = 1)                     AS login_succeeded,
       SUM(e.label = 2)                       AS confirmed_takeover,
       SUM(e.decision <> e.shadow_decision)   AS would_change
FROM t_member_risk_hit h
JOIN t_member_risk_event e ON e.id = h.event_id AND e.create_time = h.create_time
WHERE h.rule_code = 'LOGIN_MATRIX' AND h.create_time >= NOW() - INTERVAL 14 DAY;
```

| 数 | 回答的问题 | 参考线 |
|---|---|---|
| 打扰率 = 会改变结论的命中 / 全部成功登录 | 切过去之后多少真人要多验一道 | < 2%（矩阵可能更高，按格看） |
| 命中中「确认被盗」的占比 | 它是不是真抓到了东西 | 有就是赚的；早期标注少，不能单靠它 |
| `error = 1` 的占比 | 这条规则是不是其实一直没在工作 | ≈ 0 |

矩阵按格看更有用：`GROUP BY device_trust, ip_familiar, dormant`，就知道每一格各有多少人、切生效后各要打扰多少人。

## 9. 分期

生产还没上线，所以分期不再按「线上行为零变化、逐步切换」排，而是按**上线前做完什么、上线后靠数据调什么**排。

| 期 | 做什么 | 验收 |
|---|---|---|
| **上线前 · 第一批**（P0） | 四张表 + `last_active_time` 进基线；引擎骨架、规则表与名单缓存、双向校验、流水与命中写入；§4 全部规则（旧 `LoginIpGuard` / `DeviceGuard` 判断逻辑、账号锁、`captcha.password-login`、设备闸 dry-run **直接替换删除**）；查无此人跑假 Argon2；网关滑块改为「核销后由域判」；后台**规则页**与**决策流水页**；分区维护任务（含登录日志） | 原有用例里**行为本该不变的那部分**原样通过（滑块、观察档凭票、IP 闸、设备封禁）；账号锁相关用例按阶梯冷却**改写**；新规则各自有单测；`VerifyFreshInstall` 空库通过 |

生产上线之后按 §13.3 那张清单逐条过。
| **扩面**（P3） | ①✅ **固定窗口换滑动窗口**（§4.3）；②✅ **四条链路全接完**：注册（`REG_*` 四条，§12.5）、重置密码（`RESET_*` 四条，§12.6）、资产出口（`ASSET_*` 三条，§12.7）、换绑（`BIND_*` 三条，§12.8）；③✅ 已泄露密码检测（本地表，§12.9）；④⛔ 商业 IP 情报（蜂窝判定）/ 设备指纹 —— 要先有厂商和预算，不是写代码的事；⑤✅ 手机号注册开放前确认冷静期已上线（P1 已随「新绑联系方式冷静期」上线） | — |

## 10. 不做什么

- **规则 DSL / 接脚本引擎**：规则写错的表现是「静默放行」或「误伤一片」，都不会报错。规则写成 Java 类能被编译器和单测钉住；
  可调的只是参数、档位、矩阵格 —— 那正好是要频繁调的部分。
- **机器学习评分**：没有标注数据。
- **实时流计算**：所有特征都是「单个 key 在一个窗口里的计数」或「单个会员的历史」，Redis + 点查够用。
- **打分得出冷却 / 限流 / 拒绝**：§3.4。
- **前置用账号信号收紧**：§3.1。

### 12.3 2026-10-16：第二批做完之后，与计划不一样的几处

动手之后才看清的东西，记在这里 —— 它们都不是「换个写法」，而是原计划漏了一环。

| 原计划 | 实际 | 为什么 |
|---|---|---|
| 错误响应里加一个 `channel` 字段给前端看 | **通道由路由选定后写进凭票**，发码与验码都只看票 | 原计划只做了一半：`verifyChallenge` 还在按登录方式验，换通道时码发去了邮箱、却拿手机号去验 —— 用户收到码、输对码，永远被告知「验证码不正确」（§6.4） |
| 前端 `details` 收紧成按码区分的联合类型 | **保持 `Record<string, unknown>`**，改在 `ApiError` 上放运行时校验过的取值器 | 它来自网络，而网络上的东西没有类型。联合类型只是一句编译期断言，后端改字段名时 TypeScript 什么也不会说（§6.4 约定 6） |
| 「刚才是你吗」挂在 `MemberStepUpApi` 上 | 单独一个 `MemberSecurityApi` | 试过，**编译不过**：step-up 的实现类要被这两个方法反过来依赖（判设备信任），同一个契约上就是循环。那次失败说出了一件真事 —— step-up 回答「这台设备够不够可信」，这里回答「那一次登录是不是本人」，后者**用**前者的答案 |
| 第二批做 `RECORD_LIMIT` 与 `NOTIFY_OWNER` | 只做 `RECORD_LIMIT`，`NOTIFY_OWNER` 按 §9 留在 P2 | 「可疑到什么程度才值得打扰主人」要先有线上数据。没数据就上，第一周会把提醒发成垃圾邮件，而用户学会的是忽略这类信 |
| 密码冷却「复用现有页面可人工解除」 | 解冻时**同时清 Redis 冷却键** | 第一批刻意没接这颗按钮，就是因为真正拦人的不是那张表。只改表的话，客服看到「已解冻」而用户照样登不进去 |
| （第一批漏掉的）重置密码清冷却 | 补上，顺带解开 `ASSET_OUT` 冻结 | §6.2 原本就写着这一行，第一批没做 —— 而它正是密码阶梯敢用 24 小时那一档、资产出口敢「冻到改密为止」的前提 |
| （测试基建）两个用例随机失败 | `PhoneBindTest` 补上 `RelaxedRiskRules`；两个发短信的用例把随机 IP 挪进 198.18.0.0/15 | 两个都是「靠运气过」：前者断言「换绑后新号码能登录」，而那是矩阵要验证码的那一格，此前靠别的测试类临时关掉矩阵的 30 秒缓存窗口蒙过去；后者只随机最后一个八位组（250 个地址），而每 IP 每天只能发 5 条短信、计数跨测试运行累积 |

用例**挂得更厉害了** —— 因为后者大半是真实可路由空间，风控查到了真实归属地，
「换了国家」那条 +50 分的规则把后置结论推到了要验证码。
造数用的 IP 必须落在保留段里，这件事以前没人写下来过。

### 12.4 2026-10-16：P2 只做得了一半，这是刻意的

P2 四件事里，只有两件是代码：`NOTIFY_OWNER`、以及「把切生效要看的三个数做进看板」。
另外两件（**逐条切生效**、**何时关掉全局滑块**）的输入是<b>线上流量</b> —— 生产还是白纸，
现在拍的任何一个数都是编的。

所以这一轮做的是**让那个决定变成机械动作**，而不是替将来的自己把它拍掉：

| 原本的样子 | 现在 |
|---|---|
| §8.2 是一段要对着分区表手写的 join SQL | 做进看板「每条规则：切到生效会怎样」，一行一条规则 |
| 「关全局滑块的前置条件」只是文字描述 | 「常用网段」占比在看板上有一行 |
| 切换要改表 | 规则页一个下拉框，30 秒生效，走 `DataTracer` 留痕 |
| 被攻击时该看什么、按什么顺序 | §13 应急手册 |

🔴 **把 ④⑤ 标成「做完」会更难看出问题**：那两件事的产出是一组阈值，而阈值写在文档里
和写在规则表里是两件事 —— 文档里的阈值没人会去对照，而规则表里的阈值错了会误伤一片真人。
所以它们在 §9 里是 ⏳，并在 §13.3 留了一张上线后照着过的清单。

另外两个实现上的决定：

- **`NOTIFY_OWNER` 按会员节流（默认 6 小时一封）**。一次撞库会对同一个账号连试几十次，
  每一次都可能判到 `OTP_STRONG`。不节流的话主人收到三十封一模一样的信，
  而他第一反应是把发件人拉黑 —— 发废了的后果是真出事的那一封也会被忽略。
  节流判断不了（Redis 挂了）时**不发**：宁可漏一封，也不要在故障期间连发几十封。
- **换通道退回时也通知**（§3.7）。退回意味着我们没能避开「可能已失守的那个因子」——
  往同一个邮箱发码，证明不了它没和本站密码一起泄露。通知放在认证主干里而不是让路由自己发：
  路由是个「选通道」的纯函数，让它顺手发信，「查一下走哪条通道」就带上了副作用。
- **看板上删掉了「按规则的命中」那张旧表**：新的「切到生效会怎样」是它的超集，
  留两张等于把同一组数在同一个屏幕上显示两遍，而两处一旦口径不同就没人知道该信哪个。
- 两个新开关挂在 `solvela.member.login.*`（挨着新设备提醒那个），**不是** `solvela.member.risk.*` ——
  后者整个前缀归 `MemberRiskProperties`（`@ConfigurationProperties`）管，
  在那个前缀下再用 `@Value` 塞键，读那个类的人看不到它们。

另外顺手修了第三个「靠运气过」的用例：`DeviceRegisterTest` 的造数 IP 从 `203.0.X.Y`
（6.25 万个，而且只有 203.0.113.0/24 是保留段）换到 `100.64.0.0/10`（RFC 6598，整段保留、约 400 万个）。
原因和前两个同类：「同一 IP 一天最多签发几个设备」的计数器<b>按天累积、跨测试运行不清</b>，
而本类有三个用例会把某个 IP 一路刷到上限 —— 后面某次运行随机到被刷过的那个 IP，
「两次签发都该成功」就会莫名挂掉，而单跑它又是绿的。
🔴 这已经是今天第三次了，三次的共同点是：**测试造数用的随机空间必须大到跨运行不碰撞，并且落在保留段里。**

### 12.5 2026-10-16：注册接进同一个引擎（P3 ②的第一步）

注册原来有两道手写的闸：`MemberRegisterService.consumeAttempt`（一个 IP 一小时 10 次，自己拼 Redis 键）
和 `DeviceGuard.checkRegister`（一台设备一天 2 个号，dry-run）。现在是四条规则，
阈值在 `t_member_risk_rule`，**每一次注册尝试都落一行流水**。

🔴 **换来的不只是「阈值能在后台改」**：注册这条链路以前**完全看不见** ——
批量建号发生过没有、挡下了多少、挡错了多少，一个数都没有，
唯一的痕迹是 `t_member.register_ip` 和一行 WARN 日志。

| 规则 | 档位 | 它是什么 |
|---|---|---|
| `REG_IP_BLACKLIST` | 生效 | 与登录那条同一份判据（直接继承那个类），**单独一行配置** |
| `REG_DEVICE_BANNED` | 生效 | 同上。它补回的是 `checkRegister` 的第一行 —— 删了那个方法而不补这条，等于一台被人工封掉的设备又能建号了，而这件事不会报错 |
| `REG_IP_LIMIT` | 生效 | 1h / > 10，迁自 `consumeAttempt`。阈值刻意宽：公司出口、校园网背后是成百上千个真人，而注册是他们的第一次接触 |
| `REG_DEVICE_LIMIT` | **陪跑** | 1d / > 2，迁自 `checkRegister`（原来是 dry-run，所以这里也先陪跑）。命中生效时顺带把设备降进观察档 |

动手之后才看清的几处：

| 原计划 | 实际 | 为什么 |
|---|---|---|
| 一条规则挂两个场景（黑名单、设备封禁复用） | **一个场景一行配置**，注册那两条直接继承登录那两个类 | 规则表里一行就是「一个可以单独开关、单独调参的闸门」。共用一行的话，「注册这边误伤太多、先关掉」会顺手把登录那边也关掉 —— 而那是最不该在同一个开关上的两件事。代价（两行可能被配成不一致）是**看得见的**，连带关闭是看不见的 |
| 注册也分前置 / 后置 | **只有前置** | 登录分两段是因为「密码对不对」把信号分成了两半。注册没有这条分界线：验证码验过账号就建出来了，没有「验完再判一次」的位置 |
| 处置沿用登录那七档 | **只许放行 / 限流 / 拒绝**，分级规则的 `validate` 与 `RiskRuleRegistry.toConfig` 各拦一道 | 滑块票由网关在**发码**那一步核销，注册接口收不到票；而注册已经验过一次验证码，再要一道 OTP 等于让同一个邮箱收两封信。配上去的后果不是报错，而是注册接口返回一个客户端不认识的结果 —— 而规则页上那一行看着完全正常 |
| 设备维度被限继续回 `DEVICE_LIMITED`（「当前设备操作过于频繁」） | **两维合成一句**「操作过于频繁」，枚举值与那条分支一起删掉 | 与登录那边同一个判据（§6.4）：那句话原本正好告诉了批量注册的人 —— 该换设备，还是该换代理 |
| 结局复用登录那十三档 | 多一档 `IDENTITY_TAKEN`（14） | 「这个号已经有人了」是注册这边**信号最强**的一个结局：真人一辈子撞一两次，而拿着泄露号码库挨个试「哪些号注册过」的脚本，产出的几乎全是这一档。并进「凭据错」的话，这个形状在看板上就看不见了 |
| 看板照常 | 看板上那几个数**仍然只算登录**（`event_type = 1`），只有「每条规则：切到生效会怎样」含 `REG_*` 四条，页面上写了这件事 | 两个口径摆在同一个屏幕上而不说明，看的人会拿注册的命中数去除以「登录尝试总数」。而那张表恰恰必须含注册 —— 它是 `REG_DEVICE_LIMIT` 切生效前唯一的依据 |

另外几处实现上的决定：

- **计数由规则自己 +1**，不再是「注册主干调 `DeviceGuard` 加一次、规则读一次」。
  「超没超」和「+1」在同一个地方，少一处漂移的机会。
- **格式与密码强度两档留在账本之外**（它们在开账本之前就返回了）。
  开了账本就会跑规则，而那几条规则「这一次请求本身就算一次」——
  于是一个手滑打错格式的人会白白消耗掉他今天的注册额度。
- **拿不到 IP 时那句 WARN 没了**：维度取不到时规则直接不判（与登录那边一致）。
  换来的是一行流水：`client_ip` 空着、一条命中都没有 —— 在流水页上看得见，
  而日志里那句话以前从来没人搜。
- **风控流水在注册的事务里**。所以主干抛未预料异常时，`close()` 兜底写的那行 `INTERNAL_ERROR`
  会随事务一起回滚。接受它：那一刻真正要查的东西（traceId、异常栈）在日志里，
  而为了这一行把流水拆到独立事务，代价是注册主干多一次连接往返。

### 12.8 2026-10-16：换绑接进引擎（P3 ② 收尾）

换绑是接管一个账号<b>最彻底的一下</b>：换完之后原主连「找回密码」都走不通了，
挡着的只有那 7 天冷静期。所以这里要数的是「一台设备替几个人换过联系方式」——
那是批量接管的样子，不是家人互助的样子。

| 规则 | 处置 | 档位 |
|---|---|---|
| `BIND_IP_BLACKLIST` | DENY | 生效 |
| `BIND_DEVICE_BANNED` | DENY | 生效 |
| `BIND_DEVICE_FANOUT` | LIMIT | **陪跑**（1d / > 2 个不同账号） |

🔴 **它要不到核身，而资产出口要得到** —— 这是两个场景唯一的实质差别：
换绑本来就要「新地址的码」，而「证明你是原主」那一步对<b>首次绑定</b>压根不存在
（没有旧联系方式可问）—— 偏偏首次绑定才是那条接管链要用的口子。
所以 `BIND_DEVICE_FANOUT` 只能给硬拦档；而<b>新拍的阈值 + 硬拦处置</b>按 §12.6 那条判据
必须从陪跑起步。

动手之后才看清的几处：

| 原计划 | 实际 | 为什么 |
|---|---|---|
| 换绑的碰号数复用资产出口那条规则 | **抽一个基类，两条规则各一本计数** | 搬东西和改联系方式是两件事，一台设备可能只干其中一件。共用一个计数器的话两个阈值就只能一起调，而它们的正常量级不一样。抽出来的 `DeviceMemberFanoutRule` 顺手把「先记后判」「不看信任」两条纪律也收在了一处 |
| 两个场景的档位白名单写在基类里 | 做成抽象方法 | 它正是两边唯一的差别（能不能要核身）。写死在基类里，将来加第三个场景时只会有人顺手放宽它 |
| 失败原因带上剩余秒数 | **不带** | 换绑不是救命操作（他还登得进来，账号也还能用），而加一个字段要同时改两套结果记录与两处映射。重置密码那边<b>必须</b>带 —— 走到那一步的人已经登不进去了 |
| 「还没给原主证明」记成一次失败 | 记成 `STEP_UP_REQUIRED` | 它不是失败，客户端据此弹输入框。与「给了但不对」分开记，看板上才看得出「有多少人卡在原主证明这一步」 |
| 两个 bind 服务各写一遍风控 | **确实各写一遍** | 这两个类本来就是刻意的孪生实现（邮箱 / 手机号各一套，连注释都一字对应）。抽一个「网关式」的 helper 反而会把「每条返回路径都 end 一次流水」那条纪律藏起来 —— 而那条纪律能被 code review 看见，正是因为它写在主干上 |

至此 P3 ② 的四条链路全部接完：**注册、重置密码、资产出口、换绑**。
加上登录与二次验证，`t_member_risk_event` 现在是<b>六个场景</b>的同一本账。

### 12.9 2026-10-16：已泄露密码检测（P3 ③）

一份**打进 jar 的本地表**（`member/weak-passwords.txt`），在<b>注册</b>与<b>重置密码</b>
两处设密码的路上各查一次。

🔴 **它和强度校验是两件事。** `MemberPasswordPolicy` 回答「这个密码够不够复杂」，
这份表回答「这个密码是不是**人人都在用**」—— 而 `Password1` 完全满足
8 位 + 字母 + 数字，它在每一份泄露库的前几十名里，撞库脚本的第一发就是它。
所以失败原因也单独一档（`LEAKED_PASSWORD`）：合成「强度不够」的话，
用户会对着 `Password1` 反复加长度，而每一次都被拒 —— 他不会明白为什么。

| 决定 | 为什么 |
|---|---|
| **本地表**，不是外部 k-匿名接口 | 外部接口覆盖面大得多，但它把注册与改密挂在一个第三方的可用性上 —— 而它挂了的时候，要么放行（等于没做），要么拒绝（等于注册不可用）。本地表覆盖面有限，但失败模式只有一种：打包漏了文件，而那在启动时就炸 |
| **刻意不做成风控规则** | 规则意味着规则页上有一个能把它关掉的下拉框。而这件事没有「误伤」可言：被拒的用户换个密码十秒钟，而放过去的那个账号从创建那一刻起就在别人的字典里了。判据同「新绑联系方式冷静期」（§12.6）：**不该有开关的东西就不要给它开关** |
| 表读不出来 / 是空的 → **启动失败** | 一个<b>静默空掉</b>的黑名单比没有这个功能更糟：页面上、代码里、文档里都写着「我们挡了泄露密码」，而实际一个都没挡 |
| 表里**只收能过强度校验的条目** | `123456`、`password`、`qwerty` 这类根本进不来（强度校验先拒了）。收进来只会让这份表看起来很长，而有效的只有一部分 —— 有一条用例专门钉这件事（`WeakPasswordCheckerTest.没有死条目`） |
| 比对**大小写不敏感** | 漏掉 `PASSWORD1` 的泄露密码表是摆设，而攻击者的字典本来就会把变体都试一遍 |

🔴 **这个功能的第一个产出是：我们自己的测试常量 `Passw0rd!` 命中了。**
它当了很久的「强密码」样板 —— 用户会写出什么可想而知。已换成 `SvRegister2026`。

#### 登录时提醒存量账号（2026-10-17 补上）

上面那两处挡的都是<b>新设的</b>密码。而一个 2024 年就把密码设成 `Password1` 的人，
不会因为我们后来加了那张表而自动变安全 —— 补这一块的是 `LeakedPasswordNotifier`。

🔴 **只能在「密码刚验对」的那一刻判断。** 库里存的是 Argon2 哈希，而哈希<b>不能</b>
拿去跟一张明文表比对 —— 想知道「这个账号的密码在不在泄露库里」，唯一的机会就是
用户自己把明文送上来的那一次。所以这件事既不能做成定时任务，也不能在后台一键扫描。

| 决定 | 为什么 |
|---|---|
| **不拦登录** | 拦了等于把人锁在自己账号外面 —— 而他并没有做错什么，是这个世界变了。能做的只有告诉他 |
| **只发站内信，不发邮件** | 「你的密码不安全」是钓鱼邮件最爱的模板，而这件事<b>没有任何紧急性</b>（没有人正在攻击他）。而站内信恰好是最合适的渠道：他此刻<b>正在登录</b>，离「去改密码」只有两步。与此相对，`SuspiciousLoginNotifier` 发邮件 —— 那一封说的是「有人正拿着你的密码在试」 |
| **按会员节流，默认 30 天** | 说一次是提醒，每次登录都说是骚扰 —— 而他学到的是忽略 SYSTEM 分类的所有消息。30 天也给「我知道了，这周末再改」留了空间 |
| 挂在**验过密码之后、后置决策之前** | 「你的密码在泄露库里」不论这次登录成不成功都是真的，<b>尤其是被拒的那种</b>（有人正拿着这个密码在试）。放在后置之后的话，被判成要验码或拒绝的那些登录就不提醒了 —— 而那恰恰是最该提醒的 |
| 文案里**没有链接** | 与新设备提醒、可疑登录同一条规矩：我们自己的提醒里一个链接都没有，用户才有依据判断「带链接的那条是假的」。而且把这句话写进了文案 |
| 异常一律只记日志 | 它挂在登录主干上，而这条提醒的价值<b>再高也高不过登录本身</b> |

⚠️ 这套用例的造数本身就说明了这个功能为什么存在：`LeakedPasswordNotifyTest`
<b>没法</b>用注册接口造出一个「密码已泄露」的账号（注册那一处已经把它拦了），
只能先正常注册、再直接改库把哈希换掉 —— 那正是「存量账号」的样子。

⏳ 还留着一件：表本身的**扩容**。现在这一份是公开泄露库里长期占前列的那批交集（172 条）。
要上全量（几千万条）就得换载体 —— 本地布隆过滤器或那个外部接口，而那是 ④ 一类的决定
（先有预算与厂商）。

### 12.7 2026-10-16：资产出口接进引擎（P3 ②的第三步）

🔴 **它是唯一一个「风控能要求核身」的非登录场景。** 注册、重置密码那两条链路上没有核身的落点
（票在发码那一步核销，接口本身已经验过一次码），所以只能放行 / 限流 / 拒绝。
资产出口不一样：**二次验证本来就长在这条链路上**（`StepUpInterceptor` + 发码 / 验码两个接口
+ 前端那个弹窗），所以风控可以直接给出 OTP —— **而且可信设备也要验**。

那正是这个场景存在的理由：`MemberStepUpService.check` 回答的是「这台设备可信吗」，
它不回答「这一次操作像不像出事了」。**一台「验证过」的老设备被偷了会话之后，照样是可信的。**

顺序因此成了三段：**冻结 → 风控 → 信任**（中间那一档是新加的）。

| 规则 | 处置 | 档位 |
|---|---|---|
| `ASSET_IP_BLACKLIST` | DENY | 生效 |
| `ASSET_DEVICE_BANNED` | DENY | 生效 |
| `ASSET_DEVICE_FANOUT` | **OTP** | **生效**（1d / > 3 个不同账号） |

🔴 **第三条是新拍的阈值，却上线即生效 —— 这不违反 §12.6 那条判据，而是它的另一半：**
那条判据的理由是「挡错一个人的代价」，而 **OTP 是可挽回的**（用户多收一封信、多输六位数），
LIMIT / DENY 不是。所以这个场景里给 OTP 档的新阈值敢直接生效，给硬拦那两档的只有
人工签过字的黑名单与设备封禁。

它数的那一维以前**一个计数器都数不到**：`DEVICE_FANOUT` 只在**登录**时 add，
而买号的人完全可以在每个号上只登录一次，然后在同一台设备上挨个把它们搬空。

动手之后才看清的几处：

| 原计划 | 实际 | 为什么 |
|---|---|---|
| 把 `MemberRiskDecisionEnum` 直接递给网关 | 域里折成三值的 `AssetOutRisk`（放行 / 要核身 / 硬拦） | 那个枚举有七档，其中滑块、密码冷却在这条链路上**执行不了**。原样递出去，网关就得替域回答「这一档在资产出口上是什么意思」—— 而那正是域该收口的事 |
| OTP 档新增一个错误码 | **复用 `STEP_UP_REQUIRED`** | 对客户端与「新设备要验码」完全一样，所以前端一行都不用改。误判的代价也因此停在「多收一封信」 |
| 硬拦复用 `ASSET_OUT_FROZEN` | 用 `OPERATION_LIMITED` | 前者带着「重置密码后恢复」的提示，而硬拦**改密码也不会恢复** —— 把用户支到一条走不通的路上，比不解释更糟 |
| 构造器直接注入 `MemberRiskEngine` | **`ObjectFactory` 延迟取** | 直接注入是一个真的循环依赖，而那条环说出了一件真事：`step-up → 引擎 → 规则表（构造时实例化所有规则）→ LoginMatrixRule → DeviceTrustProvider → step-up`。**登录风控要用 step-up 算设备信任，而 step-up 要用风控判资产出口** —— 两个方向都对，只是不能在构造器里同时成立。判据与 `LoginCounters` 那个 `ObjectProvider` 一字不差 |
| off / observe 两档也不管风控 | **硬拦照拦，要求核身不要求** | 硬拦和冻结同一类（它不是二次验证，而是人工签过字的结论）；而「要求核身」**就是**二次验证 —— observe 那句「不影响任何请求」不能是假的 |
| 冻结那一档也跑一遍风控 | 不跑（与「刻意不算信任」同一个理由） | 冻结压倒一切，两个答案此刻都没有用途。代价是被冻结账号上的那些尝试没有风控流水 —— 它们记在 `t_member_operation_limit` 那一行上（谁冻的、什么时候、为什么） |
| 结局复用 `CHALLENGED` | 多一档 `STEP_UP_REQUIRED`（15） | `CHALLENGED` 的意思是「签了一张凭票」，而资产出口没有票（用户本来就是登录态）。记成一档的话，看板上那个 OTP 漏斗（签票数 → 验过数）会被资产出口的量冲掉，而它是「打扰了多少人」唯一的分母 |
| 上下文里塞一个只填了 memberId 的 `Member` | `RiskContext` 多一个「只有会员号」的构造器 | 为了填一个 `Member` 去查一次库，是在**每一次加地址 / 充话费**上加一次查询；而造一个空壳对象更糟 —— 它看起来是「加载过的」，于是将来某条规则读 `getStatus()` 时拿到 null，**而那不会报错，只会静默判错** |

### 12.6 2026-10-16：重置密码接进引擎（P3 ②的第二步）

与注册<b>同形</b>：只有前置一个决策点、处置只能是放行 / 限流 / 拒绝（滑块票在发码那一步核销，
接口本身已经验过一次码）。所以那份参数校验提到了 `RiskParams.requireGateOnly`，两个场景共用一份。

🔴 **但这条链路以前一次也没被计数过。** 它只受「单个邮箱 / 手机号每天能发几条码」约束，
而那是按**目标**算的 —— 一台机器拿着泄露的身份库挨个试重置码，每个目标只试一次，
一条限额都碰不到。验证码输错时主干会记一次设备失败（`DeviceGuard.recordLoginFailure`，
跨场景的信号，刻意保留），但**没有任何按 IP 的计数**。

| 规则 | 档位 | 为什么是这个档位 |
|---|---|---|
| `RESET_IP_BLACKLIST` | 生效 | 黑名单是人工判过的具体结论 |
| `RESET_DEVICE_BANNED` | 生效 | 被封设备上的重置密码请求正是接管账号最后那一下 |
| `RESET_IP_LIMIT` | **陪跑** | 1h / > 20。新拍的数 |
| `RESET_DEVICE_LIMIT` | **陪跑** | 1d / > 5。新拍的数 |

**档位这么分是一条判据，不是手感**：
**人工签过字的、以及从旧闸门迁过来的 → 生效；新拍的阈值 → 陪跑。**
前两条属于前者（它们在登录、注册两个场景已经生效，判据一字不差），后两条是后者 ——
而这个场景里拍错一个数的后果比别处重得多：**被挡下的人已经登不进账号了**，
重置密码是他最后一条自助出路。等看板上攒出「它们会改变多少次结论」再切（§13.3）。

动手之后才看清的几处：

| 原计划 | 实际 | 为什么 |
|---|---|---|
| 冷静期那一档也做成规则（`RESET_CONTACT_COOLING`） | **不做成规则**，留在主干里 | 规则意味着规则页上有一个能把它关掉的下拉框，而它挡的是**永久接管**（用新绑的邮箱重置密码之后，原主连验证码登录都进不来）。它现在用 `POST_BLOCKED` 记进流水 —— 可观测，但关不掉 |
| 风控跑在验码之后（那样才知道是谁） | **跑在验码之前** | 被限的请求不该还能去消耗验证码的可错次数 —— 那个计数按**目标**算，一个刷子可以靠挨个试把一堆真人的码刷废。代价是 `member` 恒为 null，于是这四条规则一条都用不上账号信息；而那正好让这一步对「有号 / 没号」的回答完全一致 |
| 设备维度命中也进观察档（照抄注册那条） | **不降档** | 一家人共用一台平板、一个人帮三位长辈找回账号都是真事。把那台设备降进观察档，等于连它接下来的**登录**也一起罚 |
| 限频回 `ACCOUNT_NOT_FOUND` 那种含糊措辞 | 新加一档 `TOO_MANY_ATTEMPTS`，**而且必须带秒数** | 走到这一步的人已经登不进去了，「请稍后再试」对他的意思是「不知道还有没有希望」 |
| （测试基建）两个用例的造数 IP | `203.0.*` 与 `198.51.*` 都挪进 `198.18.0.0/15` | 第四次踩同一个坑（§12.4）：那两段大半是真实可路由空间，而且空间太小 —— 而重置密码**现在有了按 IP 的计数器**，它不随测试结束清零 |

### 12.10 2026-10-17：与网关阶梯限流 / 安全闸合并

网关方案（`docs/架构/网关阶梯限流-技术方案.md`）上来之后，两边有 16 条规则在数同一件事。按「一件事只有一个地方管」合并，
判据：只看来了多少次的归网关，要看结果或身份的归风控，来了就该挡的归网关安全闸。

| 变化 | 内容 |
|---|---|
| 移交网关 | 6 条纯计次规则、5 条 IP 黑名单、5 条设备封禁（§4 顶部列表）；滑块出图的 IP 限频 |
| 名单表 | 改名 `t_security_list`，结构移到网关方案 §6.3；新增来源规则、命中次数、最近命中、最近证据、被挡请求数五列；`source = 2`（自动）启用 |
| 会员灰名单 | **放开**「会员维度只许白名单」：允许白、灰（黑仍不允许，会员的黑就是冻结）。效果：登录矩阵里可信设备按新设备算；资产出口每次都要二次验证；网关账号维度阈值减半。只由人工或登录后场景的限流重罚产生（网关方案 §5.5） |

## 13. 应急手册

被攻击的那一刻没人有时间读设计文档。这一节是**照着做**的东西：三个开关、一张清单、一句话的回滚。

### 13.1 三个开关，从轻到重

| 开关 | 在哪 | 多久生效 | 它做什么 | 代价 |
|---|---|---|---|---|
| **全局滑块** `GLOBAL_CAPTCHA` | 后台规则页，置顶那张卡，切成「生效」 | ≤ 30 秒，全实例 | 所有密码登录都要过滑块，「熟悉网络免滑块」失效 | 所有人多拖一次图。**白名单也不豁免** |
| **单条规则调紧** | 后台规则页，改档位 / 参数 | ≤ 30 秒，全实例 | 只动那一条。IP 阶梯的阈值调小、把某条陪跑切生效 | 只打扰命中那一条的人；改错了只影响一条 |
| **总开关转陪跑** `solvela.member.risk.mode: shadow` | 配置 + **发版** | 发版时间 | 除全局滑块、黑名单、设备封禁外，**所有规则只记录不拦人** | 🔴 风控基本失效。只用于「某条规则大面积误伤、又来不及定位是哪条」 |

**顺序永远是从上往下。** 先开全局滑块（挡住绝大多数脚本，代价只是拖图），
再看看板定位是哪条规则，调那一条。总开关是最后一招，而且它要发版 —— 这是刻意的：
一个能在页面上一键关掉整套风控的按钮，迟早会在某个周五下午被按下去。

### 13.2 被攻击时按什么顺序看

1. **看板**（时间窗调到最近 1 小时）：
   - 「登录尝试」是不是突然翻了几倍 → 量级攻击；
   - 「要了验证码（打扰）」涨而「其中验过」不涨 → 打扰的是脚本，规则在起作用；
   - 「要了验证码」和「其中验过」**一起涨** → 打扰的是真人，规则调过头了；
   - 「取特征失败」不为 0 → 有规则其实没在工作，先修它，别急着调阈值。
2. **决策流水**（勾「只看结论不一致」）：那些就是会被多打扰的人。翻几条看依据合不合理。
3. **名单页**：量级集中在少数 IP / 网段时，直接加黑名单（默认 30 天到期）比调阈值快，
   而且只影响那几个出口。
4. 确认是撞库（一个 IP 挨个试号）而不是单账号爆破：看 `IP_ACCOUNT_FANOUT` 那一行的命中数。

### 13.3 上线之后的校准清单（P2 的 ④⑤）

攒够 **14 天** 数据之后，按这张表逐条过。每一条都只看看板上那三个数，不靠感觉。

| 顺序 | 规则 | 切之前要满足 | 切了之后盯什么 |
|---|---|---|---|
| 1 | 设备闸四条（`DEVICE_*`） | 「会改变结论」占命中 < 2%，`取特征失败` ≈ 0 | 设备维度的打扰率。它们挡的是「一台机器挨个试号」，误伤面本来就窄 |
| 2 | `IP_ACCOUNT_FANOUT` 的限流档 | 同上。另外确认**老设备豁免**真的在生效（校园网那批人应该落不到限流档） | 公司 / 校园出口的投诉 |
| 3 | 打分规则（`NEW_COUNTRY` / `IMPOSSIBLE_TRAVEL` / `IP_DATACENTER` / `IP_GREYLIST`） | 分数叠起来**不会**把常规登录推过 OTP 分档线 —— 看「会改变结论」那一列 | OTP 通过率。它跌下来说明打扰的是真人 |
| 4 | **关掉全局滑块** | ①「常用网段」占比够高（看板上那一行）；②`CAPTCHA_MATRIX` 与 IP 阶梯滑块档的「会改变结论」不成片 | 关掉当天的尝试量与成功率。🔴 这一步的回滚最便宜（切回「生效」，30 秒），所以可以大胆试 |

🔴 **一次只切一条，切完等 24 小时再切下一条。** 同时切两条之后，打扰率涨了也不知道是哪条引起的 ——
而那时唯一的办法是全部切回去重来一遍。

### 13.4 用户侧的三条出路（客服话术用）

被风控挡住的人，按他看到的东西分：

| 他看到的 | 实际是什么 | 让他做什么 |
|---|---|---|
| 「密码错误次数过多」+ 倒计时 | 密码阶梯冷却（只锁密码这条通道） | **用邮箱验证码登录**，或者找回密码 —— 两条都没被锁 |
| 「操作过于频繁」+ 倒计时 | IP / 设备限流 | 只能等。换个网络（切流量）也行 —— 限的是那个出口 |
| 「账号处于保护状态」 | 他自己点过「这不是我」，资产出口冻着 | **重置密码**，这是唯一的解法 |
| 「暂时无法验证你的身份」 | 这个账号一条能收码的通道都没有 | 只能客服处理。🔴 **绝不能让他去绑定** —— 他此刻只证明了「知道密码」 |

客服后台能做的：解冻登录限制（会同时清掉 Redis 里的冷却键）、加 / 撤名单、在决策流水里看他为什么被拦。
🔴 **客服不能改规则档位** —— 那是 `security:rule` 权限，刻意和 `security:query` 分开。
