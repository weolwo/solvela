### 0.1 这个模块最容易做错的地方

行业里这类系统炸库的经典姿势只有一个：**把广播公告也做成了写扩散** —— 一条全员公告给每个用户插一行。

10 万用户 × 100 条公告 = 1000 万行，而真实信息量是 100 条。更糟的是这种故障**现象出现在存储层、根因在写入模型**，排查通常停在「数据库不行」，然后换更贵的数据库，买两三年喘息，期间数据再长十倍。

判据很干脆：**看行数增长的斜率，不看行数本身。**

- 用户数翻 10 倍、行数跟着翻 10 倍 → 正常，扩容的事
- 用户数翻 10 倍、行数翻 100 倍 → 设计缺陷，换什么库都一样，因为存的是 N×M 笛卡尔积

**本方案的每一张表都必须满足：行数只有一个增长维度。** §3 的表格会逐张标注。

## 1. 核心切分：按触达模型，不按内容主题

直觉是按主题切（系统 / 活动 / 交易），**这是错的** —— 主题是消息中心顶部那排 tab，属于展示层。决定存储的是触达模型。

| | 通知 Notification | 公告 Announcement |
|---|---|---|
| 语义 | 告诉**某个人**某件事 | 面向**所有人**公布 |
| 例子 | 您的订单已发货 | 今晚 02:00 系统维护 |
| 收件人 | 业务事件天然决定的 1 个人 | 人群规则 |
| 行数被什么放大 | 业务量 | ⚠️ 用户数 × 公告数 |
| 存储模型 | 写扩散（本来就是 1:1，没问题） | **读扩散 + 已读游标** |
| 是否用模板 | ✅ 用（见 §4） | ❌ 不用（见 §4.4） |

中文的「通知」和「公告」本来就是按触达模型分的，所以命名与存储模型天然对齐 —— 这也是不用 `message` 的额外理由：它同时能指两者，命名帮不上任何忙。

### 1.1 公告内部再分两类：强度

分界线不是主题，是**已读语义**：

| | 普通公告 | 强制确认公告 |
|---|---|---|
| 形态 | 躺在消息中心，用户主动看 | 进 App 弹窗，必须点「我已阅读」 |
| 例子 | 活动预告、规则说明 | 服务条款变更、停机维护 |
| 已读 | 游标推进，**零额外行数** | **必须落到人**（留证据谁确认了） |
| 行数 | 0 | = 实际确认人数 |

第二类是整个设计里**唯一一个「广播但必须写扩散」的例外**。但即使是它，也只写确认记录（`announcement_id + member_id + ack_time`），**不写内容副本**。且这类公告一年也就几条，量级完全可控。

这和 §0.1 那个炸库设计的区别要说清楚：那个是给**每条普通公告**写全员副本（设计错误）；这里是给**极少数必须留痕的公告**写确认记录（业务要求）。

## 2. 命名决策

### 2.1 为什么不叫 Message

`message` 在本仓库已经是 MQ 的词（见 §0 表格第 4 行）。再加一个 `MessageService` / `t_message`，以后每次看到 "message" 都要先判断是站内信还是队列消息。在一个有 `solvela-base-mq` 的项目里这是实打实的歧义。

### 2.2 为什么是 Notification / Announcement

- **名词**：本项目的域前缀全是名词（`member` / `mall` / `task` / `prize` / `lottery` / `draw` / `promotion` / `file`）。`notify` 是动词，不符合规律。
- **`announcement` 而非 `notice`**：`notice` 在英文里太滑（告示 / 注意事项 / 通知期），`announcement` 只有一个意思。
- **`ack` 而非 `confirm`**：合规语境里 *acknowledgment* 恰好是那个标准词（*employee acknowledgment of policy*），比 confirm 更贴「我已阅读并知悉」的法律含义。

### 2.3 `t_member_` 前缀什么时候加

本项目的 `t_member_*` 不是「跟会员有关」，而是**「一人一行（或一人几行）、生命周期跟着会员走」**：

```
t_member_wallet / t_member_coupon / t_member_verify / t_member_operation_limit
```

关联表则是另一套规律，**主体在前、不加双前缀**：

```
t_role_menu / t_role_employee / t_role_data_scope / t_pool_prize_mapping / t_task_prize_mapping
```

按这个口径：

| 表 | 主键 | 生命周期跟着谁 | member_ 前缀 |
|---|---|---|---|
| `t_member_notification` | 自增 id，按 member_id 查 | 会员 | ✅ 加 |
| `t_member_announcement_cursor` | `member_id` 单列主键 | 会员（公告删了游标还在） | ✅ 加 |
| `t_announcement_ack` | **`(announcement_id, member_id)` 复合** | **公告**（公告没了 ack 就没意义） | ❌ 不加 |

🔴 `t_announcement_ack` 是关联表不是会员实体，且主查询方向是运营侧的「这条必读公告确认覆盖率多少」，按 `announcement_id` 聚合。加 `member_` 会误导成会员域的表。

## 3. 表设计

五张表，逐张标注增长维度：

| 表 | 行数 ≈ | 增长维度 | 会不会爆 |
|---|---|---|---|
| `t_notification_template` | 模板数（几十） | 手工新增 | 否 |
| `t_member_notification` | 业务事件数 × 时间 | **时间（只增）** | 🔴 **会，必须有归档策略，见 §9** |
| `t_announcement` | 公告数（几百/年） | 运营发布 | 否 |
| `t_member_announcement_cursor` | 活跃用户数 | 用户数，**与公告数无关** | 否 |
| `t_announcement_ack` | 确认人数 | 必读公告数 × 覆盖人数 | 否（必读公告一年几条） |

### 3.1 `t_notification_template` — 通知模板，版本化

```sql
CREATE TABLE `t_notification_template` (
  `template_code`    varchar(64)  NOT NULL COMMENT '模板编码：跨环境稳定，代码引用它',
  `version`          int          NOT NULL COMMENT '🔴 编辑=新增版本，永不原地改。历史消息靠它锁定当年措辞',
  `category`         varchar(32)  NOT NULL COMMENT '分类：SYSTEM/TRADE/MARKETING。只影响 tab 与免打扰粒度',
  `title_template`   varchar(128) NOT NULL COMMENT '标题模板，${key} 占位符',
  `content_template` text         NOT NULL COMMENT '正文模板，${key} 占位符',
  `param_keys`       json                  COMMENT '本版本用到的占位符清单，发送时校验用',
  `status`           tinyint      NOT NULL DEFAULT 1 COMMENT '1-启用 0-停用。🔴 只停用不删除',
  `create_by`        varchar(64)  DEFAULT NULL,
  `create_time`      datetime     DEFAULT CURRENT_TIMESTAMP,
  `update_by`        varchar(64)  DEFAULT NULL,
  `update_time`      datetime     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`template_code`, `version`)
) ENGINE=InnoDB COMMENT='通知模板：按版本不可变';
```

### 3.2 `t_member_notification` — 定向通知

```sql
CREATE TABLE `t_member_notification` (
  `id`               bigint       NOT NULL AUTO_INCREMENT,
  `member_id`        bigint       NOT NULL COMMENT '会员号：关联键',
  `template_code`    varchar(64)  NOT NULL,
  `template_version` int          NOT NULL COMMENT '指向当年那一版，模板再改也不影响它',
  `params`           json                  COMMENT '🔴 只存显示值，不存 id。理由见 §4.3',
  `summary`          varchar(128) NOT NULL COMMENT '发送时渲染好的短摘要，列表页直接用、不渲染',
  `category`         varchar(32)  NOT NULL COMMENT '模板分类快照：tab 分组与免打扰按它过滤',
  `biz_ref_id`       varchar(64)  DEFAULT NULL COMMENT '关联业务单号：prize_code / order_no 等，排查用',
  `read_flag`        tinyint      NOT NULL DEFAULT 0 COMMENT '0-未读 1-已读',
  `read_time`        datetime     DEFAULT NULL,
  `create_by`        varchar(64)  DEFAULT NULL,
  `create_time`      datetime     DEFAULT CURRENT_TIMESTAMP,
  `update_by`        varchar(64)  DEFAULT NULL,
  `update_time`      datetime     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_member_read` (`member_id`, `read_flag`, `id`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB COMMENT='定向通知：一人一条，写扩散';
```

索引说明：

- `idx_member_read(member_id, read_flag, id)` —— 收件箱列表与未读数都走它。`id` 放第三位是为了让「按时间倒序分页」直接吃索引（自增 id 与时间同序）。
- `idx_create_time` —— **归档 job 专用**。没有它，§9 的清理会全表扫。

### 3.3 `t_announcement` — 公告内容

```sql
CREATE TABLE `t_announcement` (
  `id`            bigint       NOT NULL AUTO_INCREMENT,
  `title`         varchar(128) NOT NULL,
  `content`       text         NOT NULL COMMENT '运营手写，不用模板。理由见 §4.4',
  `category`      varchar(32)  NOT NULL COMMENT 'SYSTEM/MARKETING...',
  `force_ack`     tinyint      NOT NULL DEFAULT 0 COMMENT '0-普通公告 1-强制确认（弹窗+留痕）',
  `audience_type` varchar(32)  NOT NULL COMMENT 'ALL / REGISTER_BEFORE / REGISTER_AFTER / TAG',
  `audience_rule` json                  COMMENT '🔴 存规则，不存名单。物化名单就回到 N 行了',
  `publish_time`  datetime     NOT NULL COMMENT '生效时间，未到不展示',
  `expire_time`   datetime     NOT NULL COMMENT '🔴 必填。过期不参与未读计算，且是游标收敛的依据（§5.2）',
  `status`        tinyint      NOT NULL DEFAULT 1 COMMENT '1-发布 0-下架',
  `create_by`     varchar(64)  DEFAULT NULL,
  `create_time`   datetime     DEFAULT CURRENT_TIMESTAMP,
  `update_by`     varchar(64)  DEFAULT NULL,
  `update_time`   datetime     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_publish_expire` (`status`, `publish_time`, `expire_time`)
) ENGINE=InnoDB COMMENT='公告：一条内容一行，读扩散';
```

🔴 `expire_time` **必填、不允许 NULL**。它同时承担三件事：未读计算的过滤条件、游标自动收敛的依据（§5.2）、公告表归档的依据。允许为空等于三条全废。

附件走文件模块，业务类型用 `NOTICE`（历史 code，语义等同 announcement，见 §11.1）。

### 3.4 `t_member_announcement_cursor` — 已读游标

```sql
CREATE TABLE `t_member_announcement_cursor` (
  `member_id`            bigint   NOT NULL COMMENT '会员号：一人一行',
  `last_read_id`         bigint   NOT NULL DEFAULT 0 COMMENT '此 id 及以前的公告全部视为已读。🔴 不支持跳读，所以只需这一个 bigint',
  `create_time`          datetime DEFAULT CURRENT_TIMESTAMP,
  `update_time`          datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`member_id`)
) ENGINE=InnoDB COMMENT='公告已读游标：一人一行，与公告数无关';
```

这张表**不会爆**，参照物就在库里：`t_member_wallet` 的 `UNIQUE(member_id, asset_type)` 是「一人 × 资产类型数」行，比一人一行**更多**。钱包不爆，游标更不会。

发 10 条公告和发 10000 条公告，这张表行数完全一样 —— 这就是游标模型的全部意义。

### 3.5 `t_announcement_ack` — 强制确认留痕

```sql
CREATE TABLE `t_announcement_ack` (
  `announcement_id` bigint      NOT NULL,
  `member_id`       bigint      NOT NULL COMMENT '会员号：关联键',
  `ack_time`        datetime    NOT NULL COMMENT '确认时间：合规留痕，只增不改',
  `ack_ip`          varchar(64) DEFAULT NULL COMMENT '确认时 IP，合规场景可能要',
  PRIMARY KEY (`announcement_id`, `member_id`),
  KEY `idx_member` (`member_id`)
) ENGINE=InnoDB COMMENT='强制确认公告的确认记录：仅 force_ack=1 的公告产生';
```

主键顺序是 `(announcement_id, member_id)` 而不是反过来 —— 主查询是运营侧的覆盖率统计（按公告聚合）；`idx_member` 覆盖用户侧「我确认过这条吗」。

#### 3.5.1 🔴 只记确认过的，不预建「待确认」行

**已定稿（2026-09-14）：这张表只在用户真的点了「我已阅读」时才 insert 一行。**

反面做法是公告发布时给全部目标人群预建一批 `ack_time = NULL` 的「待确认」行 —— 那就是
§0.1 那个炸库设计原封不动的复刻：行数 = 人群数 × 必读公告数。**绝对不要。**

这个选择有一个必须接受的后果：

| 能回答 | 不能直接回答 |
|---|---|
| 「谁确认了、什么时候确认的」（合规要的就是这个） | 「谁还没确认」 |
| 「这条公告有多少人确认了」= `count(*) where announcement_id=?` | —— |

「谁还没确认」= 目标人群 ➖ ack 集合，是个反连接，人群一大就很贵；而要让它变快就得物化人群名单，
又回到 N 行。**所以不要提供这个查询。**

好在业务上根本不需要它 —— **强制确认公告的机制本身就是「没确认就每次进来都弹，直到确认为止」**，
它自带催办，不需要一份未确认名单再去主动触达。

覆盖率的分母用实时算的目标人群数即可（`ALL` 就是会员总数）。注意跟运营讲清楚：
**人群是动态的，新注册用户会进入分母**，所以覆盖率不会停在 100%，这是正常的，不是掉了。

## 4. 模板版本化

### 4.1 为什么要模板化

注册成功这类通知，正文几百字节且**每个用户都一样**。存 `template_code + version + params` 而不是渲染后的全文：

| | 存全文 | 存模板引用 |
|---|---|---|
| 注册成功 | ~300 字节 | `{"nickname":"张三"}` ≈ 25 字节 | **省 10 倍以上** |
| 中奖通知 | ~200 字节 | params 含奖品名/活动名 ≈ 80 字节 | 省 2.5 倍 |

收益 ≈ **模板中不变部分的占比 × 消息条数**。注册成功是收益最大的一类（条数被用户数放大）；中奖、发货这些条数受业务量约束，模板化主要是顺手。

**但真正的收益不是硬盘，是 IO。** 几百字节的 `text` 还不至于 off-page（16KB 页的阈值约 8126 字节），但它让每个数据页装的行数明显变少 → buffer pool 命中率下降。收件箱是高频读路径，省下的 IO 比省下的硬盘值钱得多。而且 §9 说了这张表行数会到亿级，省的每个字节都要乘以那个数。

### 4.2 🔴 不版本化 = 历史消息被追溯篡改

只存 `template_code` 不存 `version` 的话，运营改一次模板，**所有历史消息的显示跟着变**：

- 用户 1 月收到「恭喜获得 100 积分」，6 月模板改成「恭喜获得 ${amount} 积分，快去商城兑换」→ 旧消息现在长这样了
- 占位符改名（`${amount}` → `${score}`）→ 旧 params 里没有 `score`
- 而 `SolvelaTemplateUtil` 的口径是**解析不到的占位符原样保留**（它刻意的设计，见类注释）→ 用户直接看到字面的 `${score}`
- 模板被删 → 整条消息渲染不出来

在金额 / 奖品类消息上这是**事故级**的：用户截图的「获得 500 积分」和现在显示的对不上。

所以：**模板按 `(template_code, version)` 不可变存储，编辑 = 新增版本，模板只停用不删除。**

### 4.3 🔴 params 存显示值，不存 id

```json
✅ {"prizeName": "iPhone 15 Pro", "amount": "100"}
❌ {"prizeId": 8812, "amount": "100"}
```

存 id 的话渲染时要 join 奖品表，而奖品可能已下架改名 —— 又绕回篡改历史的问题，还顺带把收件箱查询变成 N+1。

这和本项目「单据存快照」的既有约定是一致的（`t_mall_order.commodity_name`、`t_member_coupon.coupon_name`、`t_member_asset_transaction.member_name` 全是快照列）。**快照防的是「后来的改动篡改历史」，模板化省的是「同一段文字存 N 遍」，两个目标正交，不冲突。**

### 4.4 公告不用模板

模板化解决的是「同一段文字存 N 遍」的冗余。而公告本来就只有一行，**没有冗余可省**。运营手写的内容直接存 `t_announcement.content`。

🔴 别做成两边共用的「消息模板」——那会把一个只服务于通知的机制强加给公告，换来的只有复杂度。

### 4.5 渲染器直接用现成的

`SolvelaTemplateUtil.render(template, params)`，`${key}` 语法，已有测试，零生产调用。两个口径要知道：

- **解析不到的占位符原样保留** —— 所以 §4.2 的版本化不是可选项
- **不对替换后的值做递归解析** —— 这是刻意的口径收紧，防模板注入（params 常来自用户数据）。别为了「模板里套模板」把它改回去

## 5. 游标模型

> **已定稿（2026-09-14）：不支持跳读。** 前端公告与通知分两个 tab，各自独立列表，
> 所以公告侧「点开任何一条 = 那条之前全部已读」不会和通知的逐条已读撞在一起。
> 代价是 `t_member_announcement_cursor` 只需要一个 `bigint`，没有 JSON 列、
> 没有例外集合、没有需要收敛的东西。理由见 §5.2。

### 5.1 未读数怎么算

两个 tab 各算各的，**互不相干**：

```
公告 tab 未读 = count(t_announcement
                      where status=1
                        and publish_time <= now()
                        and expire_time  >  now()
                        and 命中 audience_rule
                        and id > cursor.last_read_id)

通知 tab 未读 = count(t_member_notification where member_id=? and read_flag=0)

入口红点     = 上面两个数之和
```

两侧的「全部已读」都是**一次 UPDATE**：公告是把游标推到当前最大 id，通知是
`update ... set read_flag=1 where member_id=? and read_flag=0`。都不是 N 次。

### 5.2 为什么不支持跳读（以及它省掉了什么）

跳读只是**公告**的问题，与通知无关 —— 两边的已读结构不同：

| | 已读怎么存 | 跳读 |
|---|---|---|
| **通知** `t_member_notification` | 每行一个 `read_flag` | **天然支持，零成本**。点第 5 条就标第 5 行，前 4 条照旧未读 |
| **公告** `t_member_announcement_cursor` | 一人一行的游标 | 游标只能表达「这个 id 之前都已读」，**要跳读就得额外存例外集合** |

早期方案给游标加过一个 `read_exception_ids` JSON 列来补跳读能力。**现已删除**，因为它带来一个慢性隐患：

> 用户一直跳读、从不「全部已读」，数组就一直长，几年下来能攒几百个 id。
> 一个不断变宽的 JSON 列被频繁 UPDATE，会导致 InnoDB 页分裂和碎片。
> （当时的收敛办法是靠公告 `expire_time` 自动推进游标丢弃老 exception —— 可行，
> 但那是在为一个可以不存在的列造一套维护机制。）

分 tab 之后这一列失去了存在理由：**两种已读语义各自待在自己的列表里，用户不会在同一个列表看到两种行为。**

🔴 将来若有人提「把两个 tab 合并成一个列表」，必须连带重新评估这里 —— 合并后点公告清一片、点通知清一条，会被当成 bug。

### 5.3 懒创建

**不要在注册时给每个人建游标行。** 只有用户第一次打开消息中心才 insert。

没有游标行 = `last_read_id` 视为 0 = 所有未过期公告都未读（红点亮着），这恰好是想要的行为。

效果是行数从注册用户数降到活跃用户数 —— 对营销平台来说这两个数差得很远。

### 5.4 人群规则存规则，不存名单

`audience_rule` 一旦物化成名单，就又回到 N 行了，前面所有设计白做。

判定放在读路径上。`ALL` 是零成本；`REGISTER_BEFORE/AFTER` 拿 `t_member.create_time` 比一下即可，这些字段在会话里本来就有。

## 6. 收件箱查询

**两个 tab，两条独立的查询路径。没有归并，没有 UNION。**

| tab | 查询 | 走哪个索引 |
|---|---|---|
| 通知 | `where member_id=? order by id desc limit N` | `idx_member_read(member_id, read_flag, id)` |
| 公告 | 未过期 + 命中人群，`order by id desc limit N` | `idx_publish_expire`；公告总量小，整体缓存也行 |

分页各自用自己的 `lastId` 游标，互不干扰。

> 早期方案写的是「两路各自有序、内存归并成一个列表」，并特别强调不要用 SQL UNION 分页
> （两张表的过滤条件完全不同，UNION 之后排序分页会让两边的索引都用不上）。
> **分 tab 之后这段复杂度整个消失了** —— 这是「两个 tab」这个产品决定顺带买到的最大一笔简化。

**列表页不渲染模板** —— 直接用 `t_member_notification.summary`（发送时已渲染好的 128 字摘要）。
只有点进详情才跑一次 `SolvelaTemplateUtil.render`。高频路径完全不碰模板表。

## 7. 🔴 接口形状：发「通知请求」，不是「插入一条站内信」

这条可能比表结构更重要。

站内信不该是一个独立系统，而是**多渠道触达平台的一个渠道**。同一个业务事件（中奖）将来通常要同时走站内信 + App Push + 短信。如果站内信自成一套，加 Push 时就得把事件订阅再写一遍，而且两边的免打扰、频控规则会分叉。

```java
✅ notificationService.send(NotifyRequest.of(PRIZE_WON, memberId, params));
❌ memberNotificationService.insert(memberId, title, content);
```

```
业务方 ──► 发「通知请求」（事件 + 参数），不关心走哪个渠道
              │
              ▼
       ┌─ 触达编排层 ────────────────────┐
       │ 1. 查模板（code + 当前 version）│
       │ 2. 查用户偏好（免打扰 / 退订）  │
       │ 3. 频控与合并（§8）             │
       │ 4. 路由到渠道                   │
       └──────────┬──────────────────────┘
                  ▼
      站内信 / Push / 短信 / 邮件（可插拔）
```

这个差别**今天是零成本的**（实现里就是往 `t_member_notification` 插一行），但它决定了将来加 Push 是「注册一个渠道」还是「重写所有调用点」。

## 8. 频控与合并

消息中心死掉的原因通常不是性能，是**消息泛滥导致用户再也不点那个红点**。

具体到本项目，最容易泛滥的是「券即将过期」—— 8 张券发 8 条。

**规则：同一 category 在时间窗内合并成一条**（「您有 8 张券即将过期」）。这个逻辑放在触达编排层，不是每个业务方各写一遍。

更进一步：**能由现有数据实时算出来的提醒，可以干脆不落库**，C 端拉未读时现算。落库的只留那些「不发就永远丢失」的事件（中奖、发货、冻结）。

## 9. 🔴 保留与归档：`t_member_notification` 才是会爆的那张

游标表不会爆（§3.4），会爆的是它旁边这张。

它的行数 = **业务事件数 × 时间**，只增不减。一个活跃用户一年几百条不夸张：

```
100 万活跃用户 × 300 条/年 = 3 亿行/年
```

**必须在上线前定好保留策略**，两选一：

- **按时间**：只留最近 3~6 个月，超期归档或删除（站内信是时效性内容，没人翻一年前的「您的订单已发货」）
- **按人封顶**：每人只留最近 N 条

清理 job 挂在现有的 `t_solvela_job` 体系下，参照 `MqMessageLogCleanJob` / `MemberCouponExpireJob` / `TaskRecordExpireJob` 的写法。走 `idx_create_time`，**分批删**。

> ⚠️ 这件事必须现在定。等有了 3 亿行再补归档 job，第一次跑就是个大删除 —— 要分批、要避开高峰、还要处理 binlog 膨胀。现在定，它只是建表时多一个索引和一个每天跑的 job。

公告侧没有这个问题：`t_announcement` 一年几百行，`t_announcement_ack` 跟着必读公告数走，都不用归档。

### 10.2 ⚠️ 发货通知里为什么是订单号不是商品名（实现时发现）

原方案写的参数是 `commodityName`，**实现时发现拿不到**：

- `t_physical_delivery` 上只有 `source_biz_id`（订单号 / 提案号），**没有商品名快照列**
- 要查商品得让 `solvela-ledger` 依赖 `solvela-mall`，而那条缝是**单向**的（mall → ledger），由 `MallLedgerBoundaryTest` 守着

所以模板参数改成了 `sourceBizId`，用户看到的是订单号。

**真要显示商品名，正解是给 `t_physical_delivery` 加一个商品名快照列**（由 mall 建履约单时写进来，和 `t_mall_order.commodity_name` 同一个套路），而不是反向打通依赖。那是独立的一个改动，不在本模块范围内。

### 12.2 阶段 0 交付（2026-09-14）—— 以及一处需要更正的判断

🔴 **更正**：早先盘点时我写过「商城订单的失败分支整条没接：`MallOrderStatusEnum.FAILED` 只被读从没被写、`fail_reason` 零写入」。**这是错的。**

`MallOrderDao.markFailed` 存在且被 `MallFulfillService.settle()` 调用，FAILED 与 `fail_reason` 都在正常写入。之所以漏判，是因为那条 SQL 写在 `@Update` 注解里而不是 Mapper XML，按 XML 扫的那一遍没命中。

而且 `markFailed` 的注释写明了一个**刻意的决定**：

> 🔴 **失败不退积分。** 东西还欠着用户，不是没买 —— 退了积分等于单方面取消订单，而运营可能只是漏配了券模，补上就能发。

所以阶段 0 真正缺的不是「失败分支」，而是**取消那一半**：

| 事实 | 证据 |
|---|---|
| 商城**一个 Job 都没有** | `find solvela-mall -name "*Job*"` 为空 |
| **完全没有取消路径** | 全仓 `CANCELLED` / `releaseStock` / `markCancel` 零命中 |
| `releaseLocked` / 限购 `release` 写好了**没人调** | 两者的注释都写着「到期由超时释放 job 调它」 |
| `AssetDebitApi#refund` 零调用点 | 因为退款只发生在取消路径上，而取消路径不存在 |

**后果是真实资损**：`MallRedeemService` 是**先扣积分再建单**的，而 `POINTS_CASH` 商品的单落在 0-待支付等现金回调（那条链路至今没写）。于是每一张这样的单子都是「积分扣了、库存锁了、限购占了，然后永远停在那里」。

**补的东西**：`MallOrderExpireJob` + `MallOrderCancelService`（独立类，避开自调用绕过代理的坑）+ `MallOrderDao.markCancelled/selectExpiredUnpaid`。

顺序是 **先闸门后补偿**：`markCancelled` 带 `AND status = 0`，拿到 0 行就整单放弃 —— 反过来先退款的话，会给一个刚支付成功的订单退积分。退款的 `bizRefId` 带 `:REFUND` 后缀（`AssetDebitApi#refund` 的注释专门警告过：与扣减用同一个 key 会被唯一键当成重复提交挡掉，表现是「退款静默不生效」）。

**两个模板不能混**：`ORDER_FULFILL_FAILED`（东西还欠着你，**不退积分**）与 `ORDER_CANCELLED`（这单不算数了，**积分已退回**）。我最初写的 `ORDER_FULFILL_FAILED` 文案是「相关积分已退回您的账户」，与上面那条刻意的决定直接冲突，已改。

### 12.3 阶段 3 交付（2026-09-14）—— 通用频控没做，这是有意的

**做了的**：

- **免打扰偏好** `t_member_notification_preference`，一人一行、懒创建。闸放在 `NotificationService`，不是让每个业务方各判一遍。SYSTEM 不可关，且**连库都不查**。
- **「券将过期」的合并**：`CouponExpiringNotifyJob`，**一人一条不是一券一条**。三层防线：SQL 按会员 `GROUP BY`、DTO 只有 `count` 没有券列表、模板参数是 `count` 不是券名 —— 让「一人一条」成为唯一写得出来的写法。

**没做的：通用频控限流器。**

盘一遍五个事件，**没有一个需要它**：中奖和发货本来就该每次都通知；账号冻结由「已在限制中就不再叠加」挡住；券将过期由上面的合并挡住；履约失败一单一次。

而且它不便宜：要么给本模块加 `base-redis`（会跟着进 admin 与 app-biz 两个进程，而 pom 里明确写了不要），要么在一张会长到亿级的表上加第四个索引。**为一个没有使用方的功能付这个代价，不如不付。**

真需要时的插入点已经在 `NotificationService.doSend()` 里用注释标出来了。


### 12.4 端侧交付（2026-09-15）

**C 端链路**：网关 `NotificationController`（`/notification/**`）→ 契约 `NotificationApi`（放在 `solvela-member-api`，通知是挂在会员身上的东西）→ app-biz `NotificationInternalController`。

几个刻意的取舍：

| 决定 | 理由 |
|---|---|
| 网关每个方法**都不收 memberId** | 收了就能改 query string 翻别人的收件箱。下游那些 `@RequestParam Long memberId` 是服务间参数，公网不暴露 |
| **详情接口顺手标已读** | 让端上单独调一次，三个客户端里一定有一个忘写，而忘了的表现是「点开了红点还在」 |
| **总红点在服务端相加** | 端上自己拉两个数相加，迟早漏掉公告那一半，且只表现为「红点偏小」，没人对账 |
| **公告的 `unread` 服务端算** | 把游标下发让端上比 id，等于把游标语义散到三份实现里 |
| ack 的 **IP 服务端取** | 合规留痕的字段让被记录方自己填，那条记录就一文不值了 |

⚠️ **组装逻辑在 app-biz 的控制器里而不是 `solvela-notification`**：公告的人群规则要用会员注册时间，而 notification 模块排在全部业务域之前、不认识会员域。app-biz 是两个域唯一能碰面的地方。为此给 `MemberService` 加了 `getCreateTime`（只查一列 —— `t_member` 那行有四列密文，整行捞回来等于每次列表都白解密一遍）。

**app-web**：`MessagesView`（两个 tab）、`MessageDetailView`、`ForceAckDialog`、`NotificationPreferenceView`。7 个组件测试，其中最关键的一条钉住游标语义：**点开中间那条公告，它和更旧的一起变已读**。

**admin-web**：通知模板页（**没有"修改"按钮，只有"基于此版新建"**）、公告页（含确认人数，**只给分子不给百分比** —— 分母是动态的，给百分比运营会以为覆盖率在掉）。菜单与权限已在 `data-baseline.sql` 的 `t_menu` / `t_role_menu` 种子里（原迁移脚本已执行并删除）。


### 12.5 人工发送（2026-09-15 补）

**缺口**：管理端只有「公告」（广播）和「模板」（定义系统触发的措辞），**没有「发给某个人」** —— 客服想给一个会员补一句说明，只能去改库。

> 顺带澄清一件常被问到的事：**公告和模板本来就没关联，这是设计使然**。模板化解决的是「同一段文字存 N 遍」的冗余，而公告只有一行，没有冗余可省。三者的关系是：
>
> | | 谁写的 | 发给谁 | 存储 |
> |---|---|---|---|
> | **模板** | 开发定义、运营改版 | —— | 定义系统通知长什么样 |
> | **公告** | 运营手写 | 人群（广播） | 一条内容一行 |
> | **人工发送** | 运营手写或套模板 | 指定的几个人（定向） | 一人一条 |

**MANUAL 模板是唯一一个正文由发送方现填的**：占位符就是 `${title}` 和 `${content}`，真正的文字落在 `params` 里。

这看着像绕开了模板化，其实不是 —— **模板化要省的是「同一段文字存 N 遍」**，而人工发送一次只面向个位数到几百个会员，那段文字本来就没有重复可消除。为它单开一张带 content 列的表、或给 `t_member_notification` 加一个常年为空的 content 列，都是更差的选择：多一套存储模型，而省不下任何东西。

**🔴 收件人硬上限 200，超了直接拒绝不是截断。**

不是性能考虑，是怕这个入口变成**「用写扩散做广播」的后门** —— 那正是 §0.1 里整套设计最想避免的事，而且它还绕过了公告的人群规则与免打扰。截断更糟：运营会以为发成功了，而实际只发了前 200 个。错误信息里直接指向公告那条出路。

**留痕**：`t_member_notification.create_by` 记操作人，**人工发送必填、系统发送留空**。那一列为空正好等于「不是人发的」，事后查人工发过什么就是一句 `where create_by is not null` —— 比编一个 `"system"` 字符串更有信息量。

⚠️ MANUAL 归在 SYSTEM 分类，意味着**用户关不掉**。人工触达通常是「针对你这个人的事」（工单答复、账号说明、补偿通知），这是刻意的。代价是它成了一条绕过免打扰的路 —— 挡这件事靠的不是技术而是**留痕 + 条数上限**。

### 12.1 阶段 1 交付清单（2026-09-14）

**新模块 `solvela-notification`**，排在 base 之后、`solvela-member` 之前 —— member / ledger / marketing / mall 四个域都要调它。它**不依赖任何业务域**，只收 `memberId` + 参数。

| 类 | 职责 |
|---|---|
| `NotifyRequest` | §7 那个「通知请求」的形状。业务方唯一要认识的类型 |
| `NotificationService` | 触发编排层。查模板 → 校验参数 → 渲染 → 路由到渠道 |
| `NotificationSender` (SPI) | 渠道接口。加 Push / 短信是新增一个 `@Component` |
| `InboxNotificationSender` | 站内信渠道：只落模板引用 + params，不落正文 |
| `NotificationTemplateService` | 模板查询。按版本的永久缓存 + 最新版的 TTL 缓存 |
| `NotificationInboxService` | 读侧：列表、未读数、详情（渲染）、标记已读 |
| `MemberNotificationCleanJob` | 阶段 2 的归档 |
