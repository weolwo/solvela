# 任务事件打点 —— 实现技术方案

> 任务中台今天在本平台内部是**空转**的：引擎、注册表、幂等键、丢弃流水全部就位，
> 但平台自己发生的事一件也没喂进去。这份方案解决的就是「把事件接上」这一件事，
> 以及一个更要紧的问题 —— **接上之后，任务系统不能长进每一个业务里**。

---

## 0. 现状：唯一的入口是给外部系统用的

`TaskEventService` 的类注释写着「**上游埋点唯一的进入口**」。全仓扫下来，它今天只有一个调用者：

| 调用者 | 位置 | 性质 |
|---|---|---|
| `TaskEventController.report` | `solvela-admin`，挂 `@RequiresPermission("taskEvent:report")` | 给**外部业务系统**用的 HTTP 端点 |

也就是说：会员注册、商城下单支付、充值、参与抽奖 —— 这些**本平台自己发生的事**，
一件都没有进任务引擎。`t_task_event` 注册表里 `MEMBER_REGISTER` / `ORDER_PAID` / `DAILY_SIGN`
三行种子数据 v3.47.0 就灌进去了，**至今没有任何生产者**。

C 端 `TaskController` 只有一个 GET「看我的进度」，连签到按钮都没有。

---

## 1. 🔴 核心约束：没有任何一个生产者可以认识任务引擎

这不是「要小心别写成耦合」，是**已经被编译器和架构测试否决了**的事。
本方案后面全部的形状都来自这一条，所以先摆清楚。

任务引擎住在 `solvela-marketing`（`<modules>` 第 19 位）的 `solvela/task/` 包下。
想打点的四个域分别在：

| 想打点的域 | 模块（顺序） | 能不能 `import solvela.task.*` | 谁在拦 |
|---|---|---|---|
| 会员注册 | `solvela-member`（14） | **不能** | 模块顺序 —— 在 marketing 之前，加依赖 Maven 直接报循环 |
| 资产 / 券 | `solvela-ledger`（18） | **不能** | 同上，且 `LedgerBoundaryTest` 反向守着 |
| 商城下单 | `solvela-mall`（20） | 物理上能，**但不许** | pom 刻意不含 marketing + `PlayBoundaryTest` 扫字节码常量池 |
| 外部充值 | `solvela-external`（21） | 物理上能，**且今天没人拦** | ⚠️ 见 §8 |

`PlayBoundaryTest` 读的是 class 常量池而不是源码，所以连「反射按字符串拿 `solvela.task.xxx`」
这种绕过编译期的写法也拦得住。

**这条约束是好消息。** 它意味着「任务系统长进每个业务里」这种最坏结局，
在 member / ledger 两个域已经不可能发生，在 mall 会当场变红。
方案要做的只是**别在剩下的那条缝里把它引回来**。

## 2. 两种形状，为什么选事件

### 2.1 方案 A：契约接口（对齐 `MemberProposalApi`）

在 `solvela-marketing-api` 里定义 `TaskEventApi.report(cmd)`，mall / member 直接调。
这是 `MallBoundaryTest` 失败信息里推荐的做法，而且 mall 的 pom 里**已经有** `solvela-marketing-api` 了。

- ✅ 类型安全、同步、IDE 能查引用
- ❌ 生产者必须知道「存在一个任务系统，我得记得告诉它」
- ❌ 加第二个消费者（数据统计、风控、将来的等级体系）时，**每个生产者都要再调一次**
- ❌ 漏调没有任何提示

### 2.2 方案 B：领域事件 + 适配层 ✅ 本方案采用

生产者只声明**一件既成事实**（「这笔订单付款了」），不知道谁在听。
任务侧写一个监听器，把领域事件翻译成 `TaskEventReportCommand` 喂给引擎。

```
  solvela-mall ──┐
solvela-member ──┼─ publish ─▶ solvela.event.BizActionEvent ◀─ listen ─ solvela-marketing / task
solvela-external ┘                （住在 solvela-model）                    （适配层 / 防腐层）

  依赖方向：mall → model ← marketing     两边都只认识 model，彼此不认识
```

- ✅ 加消费者，生产者**零改动**
- ✅ 生产者的词汇表里没有「任务」这个词
- ❌ 弱类型 —— 由 `t_task_event.payload_schema` 补（见 §3.1）

### 2.3 方案 B 的三条落地原则

选了事件之后，三个地方必须钉死，否则「解耦」只是名义上的。细节分别在 §5 / §3 / §4，这里先收口。

#### ① 事务解耦：AFTER_COMMIT，且 🔴 **不许加 `@Async`**

监听器必须挂 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`，这保证了两件事：

- 主业务事务**真正提交后**才打点 —— 不会出现「订单回滚了但进度涨了」
- 任务侧的成败**绝不回滚、也不阻塞**主业务 —— 任务库宕机，用户照样注册、照样下单

但**不要再叠 `@Async`**，尽管这是通用写法。这个项目里它会炸，有三条理由：

| | 理由 |
|---|---|
| 1 | `GlobalEventDispatcher` 的类注释记着：本类实现了 `SmartInitializingSingleton`，`@EnableAsync` 默认走 JDK 动态代理，而目标方法不在任何接口上 —— 监听器注册时直接报 `Need to invoke method ... but not found in any interface(s) of the exposed proxy type`。**已经踩过一次** |
| 2 | `TaskEventService` 的类注释：「🔴 异步边界在这里，且**刻意不用 `@Async` 注解**」，理由同上 |
| 3 | `@Async` 默认落在 `solvela-async-executor` 上 —— **队列无界**（OOM，不是降级）且正被派奖链路占用，撞 §3.2 论证过的两个问题 |

**正确形态**：AFTER_COMMIT 监听器跑在**提交线程**上，只做翻译 + 调 `report()`（微秒级），
由 `report()` 自己 submit 到有界的 `task-event-executor`。
**异步边界已经在引擎里了，外面不要再套一层。**

> ⚠️ **实现时改了一处**（2026-09-17）：监听器最终开了 `fallbackExecution = true`。
>
> 原计划照抄 `PrizeEventPublisher` 不开它，理由是"强制大家在事务内 publish"。
> 做到阶段 4 时发现这条走不通：**签到只写 Redis，一行库都不碰，它没有事务可言**。
> 不开的话，唯一的办法是给签到套一个什么都不做的 `@Transactional` 去骗出一次 commit ——
> 那是让事件机制反过来决定事务边界，本末倒置。
>
> 开了之后两种情况都对：有事务照常等 AFTER_COMMIT（回滚不投递，保证一点没变），
> 没事务则当场同步投递而不是静默消失。
>
> **"必须在事务内 publish"这条规矩仍然成立，但理由变了**：
> 从「不然收不到」变成「不然收得太早」—— 事务外发布会立刻投递，
> 业务随后回滚时进度却已经涨了。这个理由比原来那个更值得遵守，
> 因为它的后果是**错误的数据**，而不只是没数据。

#### ② 防腐翻译：适配层是唯一同时认识两边的地方

```java
// solvela-marketing 的 solvela/task/adapter 包
@Slf4j
@Component
@RequiredArgsConstructor
public class BizActionEventListener {

    private final TaskEventService taskEventService;
    private final MemberService memberService;   // §7：新老会员的判定归会员域

    /** 🔴 不加 @Async，见 §2.3①。本方法跑在提交线程上，只做翻译 + 提交 */
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
    public void onBizAction(BizActionEvent event) {
        try {
            TaskEventReportCommand cmd = new TaskEventReportCommand();
            cmd.setEventCode(event.actionCode());
            cmd.setMemberId(event.memberId());
            cmd.setEventBizId(event.bizId());                 // 幂等键穿透，见 ③
            cmd.setAmount(event.amount());
            cmd.setEventTime(event.occurredAt());             // 发生时间，不是处理时间
            cmd.setIsNewMember(memberService.isNewMember(event.memberId()));  // 新增方法
            cmd.setPayload(event.payload());
            taskEventService.report(cmd);
        } catch (RuntimeException e) {
            // 🔴 §5②：此刻业务事务已经提交，异常绝不能再往上抛
            log.error("[任务打点] 投递失败。action={}, member={}, bizId={}",
                    event.actionCode(), event.memberId(), event.bizId(), e);
        }
    }
}
```

🔴 **事件负载里只装领域既成事实，不许出现任务中台的术语。**
`BizActionEvent` 可以有 `memberId` / `bizId` / `amount`，
**不许**有 `taskCode` / `progress` / `taskRecordId` 这类字段 ——
一旦出现，商城就开始替任务系统记账了，而 §2.4 那条判据当场不成立。

> **`actionCode` 算不算任务术语？** 不算。`ORDER_PAID` 描述的是**商城自己发生的事**，
> 任务注册表只是恰好用同一个字符串订阅它。按 §2.4 的判据验一下：
> 把 marketing 摘掉，`ORDER_PAID` 在 mall 里依然有意义。
>
> 今天是 1:1 直传。真出现「一个业务动作要喂两个任务事件码」时，**映射写在适配层**，
> 商城依然一行不动 —— 那才是这个防腐层真正值钱的时候。

#### ③ 幂等键穿透，而且它**已经是强制的**，不是约定

领域事件必须带上可作幂等的天然单号，由适配层映射进 `eventBizId`：

| 业务动作 | 天然单号 → `eventBizId` |
|---|---|
| `ORDER_PAID` / `ORDER_AMOUNT` | 订单号 |
| 充值成功 | 外部单号 |
| `MEMBER_REGISTER` | `memberId`（一辈子一次） |
| `DAILY_SIGN` | 无 —— 服务端按事件自然日兜底 |

这条不用靠文档约束，运行时已经在守：`t_task_event.biz_id_required` 把它变成了**表里的强制契约**，
`TaskEventService.report()` 第 ② 步缺单号**当场拒绝并落丢弃流水**
（注释原话：「对订单类事件放过兜底 = 一天只算一笔，是资损级的错，不能只靠文档约定」）。

配合 `t_task_record_flow` 上的 `uk_t_tsk_flw_evt` 唯一键，重复投递会被数据库挡下 ——
这正是 §6.4 敢用「对账 job 重推」而不做 outbox 的前提。

### 2.4 判据：把 marketing 整个拿掉，下单还能不能跑

这是区分两个方案最干脆的一句话，也是将来评审新打点时的验收标准：

> **把 `solvela-marketing` 从 classpath 上摘掉，`solvela-mall` 还能不能编译通过、下单还能不能跑通？**
>
> 方案 B 可以（事件发出去没人接，仅此而已）。方案 A 不行。

`MemberProposalApi` 之所以是接口而不是事件，是因为**发奖要当场拿到「受理 / 拒绝 + 原因」**
—— 那是一次请求。而打点是广播一件已经发生的事，没有返回值可言，语义本来就不同。
别因为「项目里已经有 `MemberProposalApi` 这个成功案例」就把它套到这里。

## 3. 事件长什么样

### 3.1 一个通用事件，不是一个事件一个类

```java
public record BizActionEvent(
        String actionCode,          // ORDER_PAID / MEMBER_REGISTER / DAILY_SIGN ...
        Long memberId,              // 关联键
        String bizId,               // 天然单号，没有就传 null
        BigDecimal amount,          // 计量值，没有就传 null
        LocalDateTime occurredAt,   // 实际发生时间，不是被处理时间
        Map<String, Object> payload // 事件原文
) {}
```

**为什么不是 `OrderPaidEvent` / `MemberRegisteredEvent` 一个业务一个类**：

`t_task_event` 表里有一列 `payload_schema json COMMENT '该事件会带哪些字段，供模板设计器提示与校验'`
—— 这个项目**已经选择了「事件的 schema 是数据，不是类」**。`GOODS_SHARE` 那行种子数据的
`remark` 写得更直白：「本次新增，用来演示**加事件只加一行数据、前端零改动**」。

一个事件一个类的代价是：每加一个打点都要动 `solvela-model`，而那是**全仓所有模块的共同依赖**
—— 改它等于全量重编译，而且「加一个类」这个动作会让人误以为加打点是件大事。
通用事件下，加一个打点 = **生产者本地一行 publish + 后台加一行事件注册**，不动任何共享模块。

### 3.2 🔴 不许 `extends BaseBizEvent`

`solvela.event` 包下已经有 `BaseBizEvent` 和它的子类 `UserPrizeEvent`。
`BizActionEvent` 放同一个包，但**绝对不能继承它**。

理由是 `GlobalEventDispatcher.dispatch` 的签名：

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void dispatch(BaseBizEvent event) { ... }
```

它监听的是**父类**，所以进程里发布的任何 `BaseBizEvent` 子类都会被它接走。继承的后果有两个，都不好：

1. **没配路由时**：每一条业务事件都会打一行
   `【事件分发】未找到分类 [xxx] 的处理器` 的 warn。下单量有多大，日志就有多脏。
2. **配了路由时更糟**：它会把事件丢进 `solvela-async-executor`，而那个池
   **队列是无界的**（`AsyncConfig` 只设了 core / max，没调 `setQueueCapacity`，
   默认 `Integer.MAX_VALUE`）。这一点 `TaskEventExecutorConfig` 的类注释已经论证过：
   「后果不是『降级』而是『OOM』」。而且那个池正被**派奖链路**占用 ——
   一次下单洪峰会让派奖排在后面，表现是「抽奖中奖了但积分半天不到账」，
   两条链路看起来毫无关系，根因极难联想。

所以 `BizActionEvent` 是一个独立类型，有自己的监听器，只经过**一个有界队列**（`task-event-executor`）。

### 3.3 三个新文件放在哪

| 文件 | 模块 | 理由 |
|---|---|---|
| `solvela.event.BizActionEvent` | `solvela-model`（2） | 所有人都依赖它；`solvela.event` 包已经是事件的家 |
| `solvela.base.event.BizEventPublisher`（接口） | `solvela-base-core`（6） | 生产者都排在它之后；`AsyncConfig` 已经在这个模块里用 spring-context |
| `solvela.base.event.LocalBizEventPublisher`（实现） | 同上 | 一行 `applicationEventPublisher.publishEvent(event)` |

**为什么生产者调 `BizEventPublisher` 而不是直接注入 `ApplicationEventPublisher`**：
这是将来换传输层（outbox / MQ）唯一要改的地方。把它框在一个接口后面，改动面积就是可数的；
直接用 Spring 的发布器，那就是散落在 N 个 service 里的 N 个调用点。

> 🔴 **这个接口的注释不许写「将来换 MQ 加一个实现即可」。**
> `LocalPrizeEventPublisher` 的注释就是这么写的，而实际上 MQ 实现意味着
> outbox 表 + relay + 拓扑 + 死信 + 消费者，是一个迭代不是一个类。
> 更严重的是那个类曾挂着 `@ConditionalOnProperty(havingValue = "local")` 并注释说「配一下就切」，
> 但**另一个实现从来不存在** —— 谁真按注释配了 `mode=mq`，得到的是整个营销服务起不来。
>
> 照实写：「今天只有进程内实现；换 MQ 需要补 outbox + relay + 拓扑 + 消费者，调用点不受影响」。
> **不加 `@ConditionalOnProperty`**，等第二个实现真的存在了再加。

## 4. 打点清单：谁在什么时候发

| 事件码 | 生产者 | 触发点 | `bizId` | 档位 |
|---|---|---|---|---|
| `MEMBER_REGISTER` | `solvela-member` | `MemberRegisterService.register()` | `memberId` | 低 |
| `ORDER_PAID` | `solvela-mall` | **两处，见下** | 订单号 | **高** |
| `ORDER_AMOUNT` | `solvela-mall` | 同上 | 订单号 | **高** |
| `DAILY_SIGN` | C 端新接口 | 新增 `POST /task/sign` | 无（按自然日兜底） | 低 |
| 充值成功 | `solvela-external` | `ExternalRechargeService.payAndExecute()` | 外部单号 | **高** |
| `GOODS_SHARE` / `PAGE_VIEW` | C 端上报 | —— | —— | 本期不做，见 §10 |

### 🔴 `ORDER_PAID` 有两个产生点，只埋一处必然漏

商城的订单有**两条**走到「已付」的路：

| 路径 | 入口 | 说明 |
|---|---|---|
| 混合单（积分 + 现金） | `MallPayService.pay()` | 走假支付确认，`:147` 已经在发 `MallOrderPendingEvent` |
| **纯积分单** | `MallRedeemService.redeem()` | **不经过 pay**，落单那一刻资产就结清，`:442` 直接发 `MallOrderPendingEvent` |

两处都已经有「在业务事务内 publish 一个事件」的现成代码，把 `BizActionEvent` 加在同一个位置即可。

**只埋 `pay()` 的表现是：纯积分兑换不算任务进度。** 而纯积分单恰恰是这个平台最主要的兑换方式，
所以这个 bug 的实际效果是「订单类任务基本不动」—— 它不报错、不打日志，
只会变成「为什么我兑换了任务没进度」的客诉。和优惠券方案 §11.8 里那个
「纯积分单在落单那一刻资产就结清」是同一个根因，那次也是漏在同一个岔路口上。

## 5. 事务与线程边界

```
业务方法（@Transactional）
   │  bizEventPublisher.publish(event)      ← 必须在事务内
   │
   ├─ COMMIT
   │
   ▼
BizActionEventListener  @TransactionalEventListener(AFTER_COMMIT)
   │  跑在提交线程上，只做一件事：翻译 + 提交给线程池（微秒级）
   ▼
task-event-executor（有界 2000 + AbortPolicy）
   ▼
TaskEventService.handle
```

三条必须遵守的：

**① 有事务的业务，`publish` 必须在事务内调用。**
事务回滚时事件不会投递 —— 「单没落成但进度涨了」在这个形状下不可能发生。

⚠️ 监听器开了 `fallbackExecution`（理由见 §2.3① 那段方框），所以事务外 publish
**不会被丢弃**，而是**当场同步投递**。所以这条规矩守的不是"收得到"，
而是"别收得太早"：在一个有事务的业务里把 publish 写到事务外，
业务回滚后进度已经涨了 —— 那比收不到更糟。

**② 监听器必须把异常全吃掉。**
此刻业务事务**已经提交**：订单落了、积分扣了。异常再往上抛，用户收到 500 会以为兑换失败然后再兑一次。
形状对齐 `MallOrderFulfillListener`。

**③ 不复用 `solvela-async-executor`。**
理由见 §3.2 和 `TaskEventExecutorConfig` 的类注释（无界队列 + 舱壁隔离）。
`TaskEventService.report()` 已经注入了正确的池，本方案不碰它。

队列打满时 `report()` 会先 `saveRejectedFlow(ctx)` 落一条丢弃流水再抛 —— **丢事件不是静默的**，
`t_task_record_flow` 里查得到。这是 `AbortPolicy` 那个取舍的配套，已经实现好了。

## 6. 可靠性：分档处理，不引 MQ

### 6.1 为什么不引 MQ

- **生产者和消费者在同一个 JVM**。`solvela-app-biz` 的 pom 里 marketing / mall / member / external / ledger 全在，admin 也一样。今天走 MQ 是让消息从本机绕去 broker 再绕回来。
- 这件事这个仓库已经付过学费：`MqConfig` 的类注释记着，member 和 marketing 合并成 app-biz 之后，发奖专用的交换机 / 队列 / 死信 / 绑定共 6 个 bean 全部删除，理由是「**留一个没人消费的队列比没有队列更危险** —— 消息静默堆积，或者有人以为它在工作」。
- 另一次学费：`t_prize_dispatch_outbox` 表、实体、Dao 都建过，**零代码读写**，最后一并删除。

### 6.2 也不新搞「JVM 级 MQ」

已经有两套了，再写一个只会多一份语义：

| | 是什么 |
|---|---|
| `ApplicationEventPublisher` + `GlobalEventDispatcher` | pub / sub + 按 category 的路由表 + AFTER_COMMIT + 线程池 |
| `TaskEventService` + `task-event-executor` | 有界队列（削峰）+ 拒绝策略（背压）+ 丢弃流水（死信）+ 舱壁隔离 |

第二套就是一个 JVM 级 MQ，只是没叫这个名字 —— `TaskEventExecutorConfig` 的注释里，
一个进程内队列该做的设计决策一条不落地做过了。

而且关键在于：**纯内存的 JVM MQ，崩溃时丢的东西和现在的线程池一模一样**。
「进程挂了丢事件」恰恰是唯一让人想引 MQ 的理由，这条路买不到。

### 6.3 分档

| 档 | 事件 | 丢一条的后果 | 做法 |
|---|---|---|---|
| 低 | `DAILY_SIGN` / `MEMBER_REGISTER` / `PAGE_VIEW` | 用户再点一次就是了 | 进程内事件，不做投递保证 |
| 高 | `ORDER_PAID` / `ORDER_AMOUNT` / 充值 | 用户付了钱没进度 → 客诉 | **反查对账 job** |

### 6.4 高档位用反查对账，不用 outbox

**前提已经成立**：`t_task_record_flow` 上有唯一键
`uk_t_tsk_flw_evt (task_config_id, member_id, event_biz_id)`，
而 `TaskEventService` 已经在 catch `DuplicateKeyException`。
也就是说**任务事件今天就已经能安全承受重复投递** ——
这正是将来换任何异步传输最贵的那一关，已经过了。

既然重推是安全的，就不需要 outbox 那张表和那条写路径，只要一个 job：

> 扫最近 N 小时内已达「已付」的订单，和 `t_task_record_flow` 求差集，
> 把没有对应 `event_biz_id` 记录的补推一次。

形状对齐已经在跑的 `PrizeDispatchReconcileJob`，用同一套 `SolvelaJob` 框架。
⚠️ 同样只捞**足够旧**的行（建议 10 分钟前）：刚落库那条可能正在被线程池处理中，捞它等于和自己抢。
这个延迟不是保守，是并发正确性 —— 那个 job 的注释里原话。

#### 🔴 方向是「任务域来拉」，不是「业务域去推」

写的时候撞上一个 §1 那张表的直接后果：**这个 job 住哪儿都不对**。

- 放 `solvela-mall`：它要读 `t_task_record_flow` 才知道漏了谁 —— `PlayBoundaryTest` 当场红
- 放 `solvela-marketing`：它要读 `t_mall_order` —— `MallBoundaryTest` 当场红

解法是 `MallBoundaryTest` 失败信息里自己写着的那句：「请先定一个契约接口」。
于是加了一个 SPI，住在两边都依赖得到的 `solvela-marketing-api`：

```java
public interface BizActionAuditProvider {
    String supportActionCode();                  // 我负责哪个动作
    List<BizActionRecord> listSettled(from, to, limit);   // 窗口内哪些单结清了
}
```

**业务域只回答"有哪些"，任务域自己判"漏了谁"、自己补推。** 商城和外部场景各实现一个，
job 住在任务域、注入一个 `List<BizActionAuditProvider>`。

> 装配用 **List 注入 + 各实现自报 code**，不用 `Map<String, Provider>` ——
> 后者在本项目已经踩过三次（`GlobalEventDispatcher` / `PrizeStrategyFactory` /
> `AssetStrategyFactory`），三次都是编译通过、运行恒 null 的静默失效。
> 形状对齐 `ActivityRefProvider`。

⚠️ **实现时发现的一个坑，写在这里免得再踩**：job 里必须先判「有没有任务订阅这个动作」。
少了这一道，`t_task_record_flow` 里一条都没有，于是**窗口内每一单都会被判成"漏投"**，
每轮全量补推一遍 —— 日志天天报「补推 500 笔」，而实际什么都没发生。

### 6.5 什么时候才升级

把触发条件写死，免得将来靠感觉决定：

| 升级到 | 触发条件 |
|---|---|
| outbox + 轮询投递 | 对账 job 的分钟级延迟被产品判定为不可接受 |
| 真 MQ（RabbitMQ） | 同一批事件出现**多个独立消费方**（任务 + 统计 + 风控 + 等级），或资产域拆出去导致生产者与任务引擎不在一个进程 |

outbox 是 MQ 方案的**前置条件**，不是替代品 —— 先做 outbox，
将来把「job 轮询投递」换成「relay 投 broker」，业务侧和消费侧都不动。
`t_mq_message_log` 的 `consumer_key` 一列本来就是为多消费者留的。

## 7. `isNewMember` 由谁填 —— 两条入口的职责分界

`TaskEventContext.isNewMember` 的注释写着「**由上游告知**」，理由是
「营销域不拥有会员数据，而且『新会员』的定义本就属于会员域的业务概念」。
不传的后果是配了人群的任务会**丢弃该事件并写明原因**。

这条规则对**外部系统**是对的，但对**内部打点**会出问题：让 `solvela-mall` 去判断「这人算不算新会员」，
等于把会员域的业务概念搬进商城 —— 这正是本方案要消灭的那类耦合。

**决策：按入口分。**

| 入口 | `isNewMember` 谁填 | 理由 |
|---|---|---|
| HTTP `/taskEvent/report`（外部系统） | **上游必填**，维持现状 | 外部系统的会员模型我们不拥有 |
| `BizActionEventListener`（内部打点） | **适配层补** | marketing → member 是合法方向，`TaskEventService` 已经注入了 `MemberService` |

适配层补齐是合规的：模块顺序里 member（14）在 marketing（19）之前，
而 `TaskEventService.normalize()` 本来就已经「按 memberId 查一次会员表」拿 `memberName`。

🔴 但判定逻辑要放在**会员域**（`MemberService` 上加一个方法），适配层只是调用它 ——
定义仍然归会员域所有，没有搬家。写成「适配层自己判断注册时间差」就等于把定义偷渡过去了。

## 8. 要补的架构测试

§1 的表里有一个缺口：**`solvela-external`（21）排在 marketing（19）之后，
pom 里加一条 `solvela-marketing` 就能直连任务引擎，而今天没有任何测试拦它。**

它已经有 `ExternalLedgerBoundaryTest`（守 ledger 那条缝），照同一个形状再加一条：

```
solvela-external/src/test/java/solvela/arch/ExternalPlayBoundaryTest.java
  └─ 扫本模块 target/classes，常量池里不许出现
     solvela/task/  solvela/draw/  solvela/lottery/  solvela/activity/
```

🔴 **别忘了末尾那条 `scanned > N` 的断言。** `PlayBoundaryTest` 的注释解释了它为什么存在：
空扫是会通过的，而「空扫通过比没有测试更糟，因为它给人已经守住了的错觉」。

守 mall 的 `PlayBoundaryTest` 本方案不需要动 —— 因为 `BizActionEvent` 住在 `solvela/event/` 包下，
商城字节码常量池里出现的是 `solvela/event/`，不是 `solvela/task/`。
**这不是巧合，是 §2.2 那张依赖方向图的直接结果**：
哪天有人想把事件类挪进 `solvela/task/`，这条测试会当场变红，而那正是它该做的。

## 10. 明确不做

| 不做 | 理由 |
|---|---|
| MQ | §6.1 |
| 新写一个 JVM 级队列 | §6.2 —— 已经有两套 |
| outbox 表 | §6.4 —— 幂等键已在，对账 job 更省；触发条件见 §6.5 |
| `PAGE_VIEW` 打点 | 高频。`t_task_event` 里它的 `discard_log_flag` 已预置为 0（「否则不匹配的浏览会把流水表写爆」），说明设计时已经考虑过；但 C 端逐页上报会先把网关打满。等真有任务需要再单独评估 |
| 任务「领取」接口 | `TaskController` 的类注释已经定了：达标自动发奖，任务状态里没有 CLAIMED。加它需要先在运行态加一个状态，是产品决策 |
| 把打点做成注解（`@BizAction` + AOP） | 切出来的打点看不见触发条件，而「这一行在哪个事务里」恰恰是 §5 全部三条约束的前提。显式 publish 一行，代价小，可读性高得多 |
